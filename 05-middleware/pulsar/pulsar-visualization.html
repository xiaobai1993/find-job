⚡ 存算分离的核心价值

  • 计算层 Broker 无状态，加机器直接扩
  • 存储层 Bookie 独立扩容，不迁移数据
  • Broker 挂了不丢消息
  • 消息堆积再多不影响 Broker 性能

📊 与 Kafka 核心对比

  • Kafka：存算一体，扩容要迁分区数据
  • Pulsar：存算分离，独立扩容互不影响
  • Kafka Broker 有状态，挂了有丢失窗口
  • Pulsar Broker 无状态，故障转移秒级恢复

🏢 多租户支持

  • Tenant → Namespace → Topic 三层结构
  • 美餐支付/订单/对账各用独立 Namespace
  • 不同业务物理隔离，互不影响
  • 可按 Namespace 设置 TTL、限流、权限

消息完整流转过程

逐步演示一条支付回调消息从发送到消费的完整链路

① Producer 发送

  • 调用 producer.Send()
  • SDK 序列化后发给 Broker
  • 等待 Broker 写入 BookKeeper 后 ack
  • ack 收到才返回成功（同步模式）

② Broker 路由写入

  • 收到消息，分配 MessageID（Ledger:Entry）
  • 转发 BookKeeper，Quorum 写入
  • 至少 2/3 个 Bookie 确认后返回 ack
  • 同时更新 Subscription 分发队列

③ Consumer 推送与 ACK

  • Broker Dispatcher 按订阅模式分发
  • Shared 模式：Round-Robin 给可用 Consumer
  • Consumer 处理完调用 Ack
  • 未 Ack 超时后重新投递（At-Least-Once）

为什么 Broker 扩容不需要迁移数据？
消息存在 BookKeeper，不在 Broker 本地磁盘。Broker 只是路由+分发进程，挂了换一个新 Broker 接管 Topic，直接连接 BookKeeper 读已有 Ledger 数据，无需迁移任何东西。这是存算分离的本质。
Ledger 什么时候切换？
① Broker 重启 / Topic 换主 → 旧 Ledger 关闭，新建 Ledger 继续写入
② Ledger 超过 Size 上限 → 滚动到新 Ledger
③ 旧 Ledger 不可变（immutable），只读，保证数据完整性

💡 为什么美餐支付用 Shared 不用 Key_Shared？

  • 业务层已有幂等（状态机+Redis 锁）
  • 消费顺序不是强制需求，出错可重试
  • Shared 实现简单，消费者数量灵活扩缩
  • Key_Shared Key 分布不均时有热点问题

🔑 订阅模式是消费端配置的

  • 生产者完全不感知订阅模式
  • Consumer 首次 Subscribe 时 Broker 创建 Subscription 对象
  • 相同 AppName = 相同 Subscription Name = 同一消费组
  • K8s 每个 Pod 连接后加入同一 Subscription 的 Consumer 列表

ACK 确认机制 与 游标（Cursor）

Pulsar 是消息级 ACK，比 Kafka 的 offset 提交更灵活

消息状态模拟 — Subscription "payment-service"

待投递 已投递待ACK 已ACK NACK/重投
Pulsar ACK vs Kafka offset 提交

Kafka：提交 offset=10 意味着 0~9 全部消费完，无法单独确认某条消息。消息 5 处理失败，要么整体回退，要么跳过。

Pulsar：可以单独 ACK 任意一条。消息 5 NACK，只有消息 5 重新投递，其他消息不受影响。超过 maxRedeliverCount 后自动进死信队列。
Cursor（游标）是什么？

每个 Subscription 在 ZooKeeper/BookKeeper 里保存一个 Cursor，记录"哪些消息已经被 ACK 了"。
Cursor 不是简单的 offset 数字，而是一个 AckSet（位图），精确记录每条消息是否已 ACK，支持乱序确认。
Broker 重启后从 Cursor 恢复，继续从上次位置投递，不重复也不丢失。

🔄 美餐支付的 ACK 策略

  • 处理成功 → 调用 mqConsumer.Ack(msg)
  • 处理失败 → ReconsumeAfter(msg, 10s) 延迟重投
  • 重复消息（ErrMsgProcessed）→ 直接 Ack
  • 超过重试次数 → 自动进死信队列

⏱ AckTimeout 的影响

  • Consumer 收到消息后有 ackTimeout 时间窗口
  • 超时未 ACK → Broker 认为失败，重新投递
  • 这就是 At-Least-Once 的来源
  • 消费端必须做幂等处理

💀 死信队列（DLQ）

  • 消息 NACK 超过 maxRedeliverCount 次
  • Broker 自动投递到 Dead Letter Topic
  • 美餐：死信队列有监控告警
  • 人工排查，手动重发
