# Pulsar 面试题 - 基础篇 & 和 Kafka 核心对比

> 结合美餐支付实际使用场景，重点突出 Pulsar 和 Kafka 的差异，面试高频考点

---

## 一、基础概念

### 1. 什么是 Pulsar？和 Kafka 比有什么优势？（必问！你们用了 Pulsar 肯定会问为什么选）

**答：** 直接说你们选 Pulsar 的理由，结合业务讲

Pulsar 是下一代云原生分布式消息队列，采用存算分离架构，功能比 Kafka 强大很多，更适合复杂的业务消息场景。

| 维度 | Pulsar | Kafka |
|-----|--------|-------|
| **架构** | 存算分离，Broker 无状态，存储在 BookKeeper，弹性扩容方便 | 存算一体，Broker 有状态，扩容麻烦，要迁移数据 |
| **多租户** | 原生支持多租户、命名空间，租户隔离，不同业务互不影响 | 没有原生多租户，要自己实现 |
| **消息模型** | 同时支持队列模型（Queue，共享消费）和流模型（Stream，独占消费），兼容 Kafka 和 RabbitMQ 的模型 | 只支持流模型，不原生支持共享消费，消费只能按组消费，一个分区只能一个消费者 |
| **延迟消息** | 原生支持任意时间的延迟消息、定时消息，不用自己实现 | 不支持，要自己做 |
| **死信队列** | 原生内置，消费失败自动进死信，不用自己做 | 不原生支持，要自己实现 |
| **消息 TTL** | 原生支持按消息、按命名空间设置TTL | 只能按时间或者大小删，不能按消息单独设 |
| **分区数** | 一个Topic分区数可以很多，几十万也没问题 | 分区多了性能下降严重 |
| **扩容** | 计算层Broker无状态，加机器直接扩；存储层BookKeeper扩了自动均衡，不用迁移数据 | 扩容要手动迁移分区，麻烦，影响性能 |
| **消息堆积能力** | 存算分离，存储可以独立扩容，堆积几亿条消息也不影响性能 | 堆积多了性能下降明显 |
| **跨地域复制** | 原生内置跨地域复制，多机房同步很方便 | 要用外部工具MirrorMaker，麻烦 |
| **消费模型** | 支持4种订阅模式：独占、共享、灾备、Key_Shared，非常灵活 | 只有消费组的概念，模型单一 |
| **顺序消息** | 支持全局有序、分区有序、Key有序，Key_Shared模式下同一个Key还是顺序消费，还能多消费者并发 | 只能分区有序 |

> **我们支付为什么选 Pulsar？（你就这么答）**
> 主要是三点：1. 原生支持延迟消息、死信队列，不用自己造轮子，支付的超时检查、重试、失败兜底直接用；2. 多租户，支付、订单、对账不同业务隔离，互不影响；3. 存算分离，扩容方便，不用迁移数据，大促流量上来了直接加Broker就行，比Kafka运维简单太多。

### 2. Pulsar 的四种订阅模式？分别适用什么场景？

**答：** 这是 Pulsar 最核心的特性，必背

| 订阅模式 | 说明 | 适用场景 | 支付场景例子 |
|---------|------|---------|------------|
| **Exclusive 独占订阅** | 同一个订阅只能有一个消费者消费，消费者挂了就自动切到另一个，和 Kafka 消费组一样，分区有序 | 需要严格顺序的消费场景 | 支付状态变更消息，同一个订单要严格顺序处理 |
| **Shared 共享订阅** | 同一个订阅可以有多个消费者，每个消息发给一个消费者，轮询分发，和 RabbitMQ 的队列模式一样，消息不保证顺序，消费能力可以随便扩 | 不需要顺序的任务类消息，并发消费 | 支付成功通知下游、短信通知、生成账单，这些不要求顺序，多实例并发消费，性能高 |
| **Failover 灾备订阅** | 只有一个消费者在消费，其他的当备，主挂了备顶上，保证高可用 | 高可用要求高，顺序消费的场景 | 核心支付回调处理 |
| **Key_Shared 订阅** | 同一个Key的消息发给同一个消费者，不同Key可以并发消费，既保证了同一个Key的顺序，又能多消费者并发，兼顾顺序和性能 | **支付场景最常用！** 既要同一个订单有序，又要高并发 | 支付回调处理，同一个订单的消息顺序处理，不同订单并发处理，性能比独占模式高很多 |

> **支付场景我们主要用 Key_Shared 模式**，同一个 out_order_no 当 Key，保证同一个支付单的消息顺序处理，又可以多个消费者并发，性能非常好，Kafka 就做不到这一点，Kafka 同一个分区只能一个消费者，要并发就得多分区，Pulsar 不用。

### 3. Pulsar 的架构组件？分别什么作用？

**答：** Pulsar 是三层架构，存算分离：

1. **Client 层**：生产者、消费者，发消息收消息
2. **Broker 计算层**：无状态，负责接收和分发消息，和客户端交互，不存消息，无状态，直接扩机器就行
3. **BookKeeper 存储层**：有状态，负责实际存储消息，Ledger 为单位存储，分片存储，多副本高可用
4. **ZooKeeper**：存元数据，集群配置，选主，新版本也可以不用ZK了

**存算分离的好处：**
- 计算和存储可以独立扩容，计算不够加Broker，存储不够加Bookie，不用一起扩
- Broker 无状态，挂了不影响数据，恢复很快
- 消息存储在 BookKeeper，多副本，数据不丢
- 消息堆积再多也不影响 Broker 性能，存储可以无限扩

## 二、消息可靠性

### 4. Pulsar 怎么保证消息不丢？

**答：** 和 Kafka 类似，三层保证：

**1. 生产者端：**
- 同步发送，ack 收到才返回成功
- 发送失败自动重试
- 消息持久化配置，至少写入多少个Bookie副本才返回成功

**2. Broker + BookKeeper 层：**
- 消息写入 BookKeeper，多副本存储，默认3副本，过半写入成功才返回，数据不丢
- 多副本跨机架存储，单台机器挂了不丢数据

**3. 消费端：**
- 手动 ack，处理完了才 ack，没处理完不 ack，重启会重发
- 消费失败重试次数超过阈值自动进死信队列，不用自己实现
- 死信队列告警，人工兜底处理

> 支付场景我们开启了至少确认机制，3副本写入成功才返回，消费手动ack，死信告警，绝对不会丢消息。

### 5. Pulsar 的消息确认机制是什么？和 Kafka offset 有什么区别？

**答：**
Pulsar 是消息级别的确认，不是 offset 批量确认：
- 消费者处理完消息调用 acknowledge() 单独确认这条消息，消费端可以单独确认某条消息，不用按顺序批量提交
- 支持累积确认，确认了这条，之前的所有消息都自动确认了，和Kafka的offset提交差不多
- 支持单条确认，失败的消息不用重发全部，只重发没确认的

**和 Kafka 的区别：**
- Kafka 是按 offset 提交，提交到某个offset就认为之前的都消费完了
- Pulsar 更灵活，可以单条确认，处理失败的可以单独重试，不用影响其他消息
- 更适合业务消息处理，不同消息处理时间不一样，不会因为一条慢了影响其他的。

## 三、核心特性

### 6. Pulsar 延迟消息怎么用？支付场景怎么用的？

**答：**
Pulsar 原生支持延迟消息，发送的时候设置 deliverAfter 多少时间后再投递，或者 deliverAt 指定时间投递，非常简单。

**支付场景我们用的最多的就是支付超时自动关闭：**
- 创建支付单的时候，发一条延迟30分钟的消息，30分钟后消费者收到，检查支付单状态，如果还没支付就自动关闭，回滚子单
- 不用自己做延迟队列了，也不用扫数据库，非常方便，精度也高，比Redis ZSet做的延迟队列可靠多了，还不丢消息。

> Kafka 要自己实现延迟消息，Pulsar 直接内置，省了好多开发工作量，也更可靠。

---

### 7. Pulsar 的死信队列是什么？怎么用？

**答：**
消费失败的消息，重试指定次数还不成功，就自动进死信队列，不用自己写逻辑。

**配置很简单：**
```java
consumer.newBuilder()
    .deadLetterPolicy(DeadLetterPolicy.builder()
        .maxRedeliverCount(3) // 最多重试3次
        .deadLetterTopic("dlq-topic") // 死信队列topic
        .build())
    .subscribe();
```
- 消费失败3次就自动进死信，不用自己判断重试次数，不用自己转存
- 死信队列有监控告警，收到死信就告警，人工处理

**支付场景用的地方：**
- 支付回调处理失败，重试3次不行就进死信，人工排查
- 支付通知下游失败，重试失败进死信，兜底处理
