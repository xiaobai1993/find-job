存算分离的核心价值

Broker 无状态 → 挂了立即被其他 Broker 接管，扩 Broker 不迁数据；Bookie 独立扩容存储；对比 Kafka 存算耦合，扩容要迁移分区数据，耗时耗力。

消息确认机制 — 对比 Kafka

Pulsar 消息级别 ack
① 消费者处理消息
② 处理成功 → acknowledge(msgId)
③ 失败 → 不 ack → 自动重投
④ 超过重试次数 → 进死信队列
✓ 单条消息单独确认
✓ 失败只重发失败的，不影响其他
✓ 也支持累积确认（似 Kafka）
Kafka offset 批量提交
① 消费一批消息
② 全部处理完 → commitOffset(N)
③ N 之前全算已消费
④ 一条失败 → 这批都得重试
⚠ 不能跳过某条单独重试
⚠ 一条慢拖慢整批提交

支付场景最常用

Key_Shared：同一个 out_order_no 的消息始终路由到同一个消费者（保证顺序），不同订单并发消费（高吞吐）。Kafka 要做到这个需要大量分区+复杂分配，Pulsar 内置支持。

订阅模式对比表

模式消费者数消息分发顺序保证支付场景
Exclusive 1个（其他等待） 全部给唯一消费者 全局有序 支付状态变更顺序处理
Shared 多个并发 Round-Robin 轮询 无序 通知发送、账单生成（不要求顺序）
Failover 主备各1个 主消费者处理，主挂备顶 分区有序 核心回调高可用
Key_Shared ⭐ 多个并发 同key → 同消费者 同Key有序 支付回调（同订单顺序+高并发）

延迟消息 — 支付超时关闭场景

原理
// 发送延迟消息
producer.newMessage()
.deliverAfter(30, TimeUnit.MINUTES)
.value(payOrderId)
.send();
// 或者指定投递时间
.deliverAt(timestamp)
Broker 内部维护 时间轮（TimingWheel）
消息先写到延迟 Topic，到期后才投递到业务 Topic
精度：秒级（比 Redis ZSet 更可靠）
消息持久化，重启不丢
支付超时关单流程
① 创建支付单
② 发 30分钟 延迟消息
③ 用户支付成功 → ack 延迟消息
④ 30分钟后 → 消费者收到消息
⑤ 检查支付单状态
⑥ 未支付 → 自动关单 + 释放库存
⑦ 已支付 → 直接忽略

Pulsar vs 其他延迟方案

方案精度可靠性实现复杂度支付场景建议
Pulsar 原生 秒级 持久化，重启不丢 直接用 API 首选
Redis ZSet 秒级 内存，可能丢 中等 适合低重要性
Kafka自实现 级别固定 可靠 复杂，要维护 不推荐
数据库扫描 分钟级 一般 简单 性能差

死信队列(DLQ) — 消费失败兜底

配置
// Consumer 配置死信策略
consumer.newBuilder()
.deadLetterPolicy(
DeadLetterPolicy.builder()
.maxRedeliverCount(3)
.deadLetterTopic("dlq-pay")
.retryLetterTopic("retry-pay")
.build())
.subscribe();
消息重试 & 死信流程
① 消费失败 → 自动进重试 Topic
② 重试第1次 → 延迟10s后重投
③ 重试第2次 → 延迟30s后重投
④ 重试第3次 → 延迟60s后重投
⑤ 第3次仍失败 → 进 DLQ
⑥ DLQ 触发告警 → 人工处理
✓ 不影响其他消息的正常处理
消息处理状态模拟
msg-001: 支付回调处理 (out_order_no=P20240101001) 待处理
msg-002: 支付通知下游 (out_order_no=P20240101002) 待处理
msg-003: 账单生成任务 (order_date=2024-01-01) 待处理
支付场景DLQ策略

支付回调处理失败 → 重试3次（10s/30s/60s延迟）→ 仍失败进 DLQ → 监控告警 → 人工排查（是 DB 故障？下游超时？） → 修复后从 DLQ 重新消费。Kafka 需自己实现这套逻辑，Pulsar 内置。

Pulsar vs Kafka — 全面对比

维度KafkaPulsar
架构 存算耦合，Broker 有状态，扩容要迁数据 存算分离，Broker 无状态，计算/存储独立扩容
消费模型 只有 Consumer Group（流模型） 4种订阅模式（流+队列）兼容 Kafka/RabbitMQ
延迟消息 不原生支持，需自实现 原生支持，deliverAfter/deliverAt
死信队列 不原生支持，需自实现 内置，maxRedeliverCount 配置即可
多租户 无原生多租户 原生支持 Tenant/Namespace 层级隔离
消息堆积 堆积多影响性能（存算耦合） 存储独立，堆积不影响 Broker 性能
消息确认 批量 offset 提交 消息级别单条确认
跨地域复制 需 MirrorMaker 外部工具 原生内置 Geo-Replication
顺序保证 分区内有序 Key_Shared 同Key顺序 + 多消费者并发
适用场景 日志采集、大数据流、高吞吐简单消息 支付业务、多租户 SaaS、延迟消息、复杂消费
为什么支付选 Pulsar？（面试标准答案）

1. 原生延迟消息+死信队列：支付超时关单、重试兜底直接用，Kafka 需自造轮子；2. 多租户隔离：支付/订单/对账不同业务互不影响；3. 存算分离：大促加 Broker 即可，不用迁移数据，运维简单。
