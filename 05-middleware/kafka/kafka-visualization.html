元数据管理
Producer 生产者
  • 通过 message key 路由到指定分区 — key 相同的消息进同一分区（保证有序）
  • 支付场景：key = out_order_no，保证同一订单消息有序
  • acks=all：等所有 ISR 副本写入才返回成功（最高可靠性）
  • enable.idempotence=true：幂等生产者，防止重试重复写入
  • 批量发送：accumulate → batch → compress → send，减少网络 IO
Broker 节点
  • 每个 Broker 存储部分分区数据，分区分散在不同 Broker 实现负载均衡
  • 每个分区有一个 Leader（负责读写）和多个 Follower（只负责同步）
  • Controller 节点：管理整个集群的元数据，负责 Leader 选举
  • 消息存储格式：segment 文件（.log 消息体 + .index 偏移索引 + .timeindex 时间索引）
  • 默认保留 7 天，到期无论是否消费都删除
Consumer Group 消费者组
  • 同一个 Group 中，每个分区只能被一个消费者消费
  • 消费者数 ≤ 分区数（多出来的消费者空转，浪费）
  • offset 存储在 __consumer_offsets 内部 Topic
  • 手动提交 offset：业务处理完再提交，防止丢消息
  • 死信队列：失败重试 N 次后进 DLQ，人工处理
ZooKeeper / KRaft
  • 存储集群元数据：Broker 列表、Topic 配置、分区分配、消费者组 offset
  • 负责 Controller 选举：第一个在 ZK 上写 /controller 节点的 Broker 成为 Controller
  • Kafka 2.8+ 支持 KRaft 模式，不再依赖 ZK，自己用 Raft 管理元数据
  • KRaft 支持 几十万分区（ZK 模式最多几万）

面试口诀

Producer → 按 key 哈希选 Partition → 发给 Leader → Leader 写本地 → Follower 拉取同步 → 等 ISR 全部 ACK → 返回成功 → 消费者按 offset 拉取

为什么 Kafka 吞吐量极高？

① 顺序写磁盘

消息追加到 Partition 文件末尾，顺序写速度与内存相当，比随机写快 100x+

600MB/s
~0.1%

HDD 顺序写 vs 随机写 — 相差 6000 倍

② 零拷贝 (sendfile/mmap)

数据不经用户态，直接内核 → 网卡，减少 2 次 CPU 拷贝和 2 次系统调用

传统方式 (4次拷贝)

↓

↓
内核 → 用户态 ❌
↓
用户态 → socket ❌
↓
内核 → 网卡 (DMA)

③ 批量处理

Producer 攒一批再发（batch.size），Consumer 一次拉一批（max.poll.records），大幅减少网络 IO 次数

一条条发：10万条 = 10万次网络请求
批量发：10万条 / 500 = 200次请求

④ PageCache 页缓存

写消息先写到 OS 页缓存，后台异步刷盘；读消息也先读 PageCache，大概率命中，不用实际 IO

Write: 内存速度写 PageCache → 返回
Flush: OS 后台异步将脏页刷盘
Read: 先查 PageCache → miss才读盘
面试总结

Kafka 快的四个核心：顺序写磁盘 + 零拷贝 + 批量处理 + 页缓存。单机轻松扛 10w+ QPS。

ISR / HW / LEO — 副本同步机制

核心概念
LEO (Log End Offset)：各副本已写入的最新 offset
HW (High Watermark)：所有 ISR 都同步了的最大 offset
ISR：与 Leader 同步差距在阈值内的副本集合
Consumer 只能消费 HW 以内的消息
ISR 踢出条件
超过 replica.lag.time.max.ms（默认10秒）

Rebalance 过程 & 影响

触发时机
  • 消费者实例 加入/离开 消费者组
  • 消费者心跳超时（session.timeout.ms 默认45s）
  • 消费处理时间超过 max.poll.interval.ms
  • Topic 分区数变更
影响 & 优化
  • Rebalance 期间 全组停止消费（STW）
  • 分区重分配可能导致重复消费
  • 优化：调大 session 超时时间
  • 优化：消费逻辑不要太慢，异步处理
  • 优化：批量优雅上下线，不要频繁重启

支付场景

大促时支付量突增，消费者消费慢积压几十万条 → 临时加消费者实例 → 很快消费完 → 后续优化消费逻辑改为批量处理 → 彻底解决。

KRaft 模式 vs ZooKeeper 模式

维度ZooKeeper 模式KRaft 模式 (2.8+)
依赖 依赖 ZK，需单独部署运维 无外部依赖，Kafka 自己管理元数据
最大分区数 几万分区（ZK 存储瓶颈） 几十万分区
运维复杂度 要维护 ZK + Kafka 两套 只维护 Kafka
可用性 ZK 挂了元数据不可用 自己 Raft 选主，可用性更高
启动速度 ZK 同步元数据慢 启动更快
选举机制 ZK 临时节点竞争 Raft 协议选 Active Controller
生产建议 老版本，存量系统 新项目推荐 KRaft（3.3+正式可用）
架构演进

Kafka 新版本用 KRaft 替代 ZK：不用外部依赖，支持更多分区，运维更简单。Controller 用 Raft 协议选主，元数据存在 Kafka 自己的 log 里，不用 ZK 了。
