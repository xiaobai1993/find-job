# SQS 支付场景专项

> 结合支付业务的AWS云原生落地实践，SQS + SNS 经典架构

---

## 一、支付服务 SQS + SNS 经典架构

### 1. 你们支付在AWS上的消息架构是怎么设计的？

**答：** 直接说你们的架构，面试官一听就知道你有云原生落地经验

我们核心的支付事件用的是 **SNS + SQS 扇出架构**，非常稳定好用：

```
支付服务 → 支付成功SNS Topic
                ├── 订单服务SQS队列(FIFO) → 订单服务消费，更新订单状态
                ├── 对账服务SQS队列(标准) → 对账服务消费，生成账单明细
                ├── 用户通知SQS队列(标准) → 通知服务消费，发支付成功短信、公众号消息
                ├── 风控服务SQS队列(标准) → 风控服务消费，分析支付行为
                ├── 财务系统SQS队列(标准) → 财务系统消费，记账
                └── 数据中心SQS队列(标准) → 数仓消费，做数据统计分析
```

**为什么这么设计？**
1. **完全解耦**：支付服务只需要发一条消息到SNS，不用管有多少下游，新增下游直接加个SQS队列订阅就行，不用改支付服务代码，加新下游零成本
2. **故障隔离**：比如对账服务挂了，只是它自己的SQS队列积压，完全不影响支付主流程，也不影响其他下游服务，不会一个下游挂了全链路都挂
3. **削峰填谷**：大促的时候支付量突增，各个下游可以自己控制消费速度，自己扩消费者实例，不会被打垮
4. **不用自己运维MQ**：全托管，SNS和SQS都是AWS管的，99.99%SLA，不用自己搭集群、扩容、处理故障，省了好多运维成本
5. **成本极低**：按调用次数付费，我们一个月几百万条消息，才几十块钱，比自己搭Pulsar集群省多了

### 2. 核心支付流程哪些地方用了 SQS？

**答：**
1. **第三方支付回调处理**：微信、支付宝的回调过来，直接发FIFO SQS队列，异步处理，接口立刻返回success，避免回调超时重复发送
   - 用FIFO队列，同一个out_order_no的消息保证顺序，不会乱序
2. **支付超时检查**：创建支付单发15分钟延迟消息，15分钟后检查状态，还没支付就关闭，更长时间的超时就用Step Functions做
3. **支付失败回滚任务**：支付失败了发SQS异步回滚余额、补贴，不用同步处理
4. **死信兜底**：所有核心队列都配了死信队列，消费失败3次就进死信，告警人工处理
5. **补单任务**：对账发现不一致的补单任务，丢到SQS异步慢慢处理，不影响主流程

## 二、踩过的坑（必讲，加分项）

### 3. 用SQS + SNS 做支付踩过哪些坑？怎么解决的？

**答：** 说几个真实的，显得你有生产经验

**坑1：SNS 转发消息给SQS，重复投递**
最开始没注意，SNS是至少一次投递，有时候同一条消息会给SQS发两次，导致重复消费
- 解决：消费端三层幂等，本来就有，所以没出问题，就是多了点日志，后来又加了消息ID在Redis去重，就完全没重复了

**坑2：FIFO队列的消息组ID设错了，导致消息乱序**
最开始FIFO队列的MessageGroupId随便设的一个固定值，导致所有消息都在同一个组里，只能一个消费者消费，并发上不去，后来改成用out_order_no当MessageGroupId，同一个订单的消息有序，不同订单并发消费，性能就上去了
> 这个是FIFO队列最容易踩的坑，一定要说，面试官一听就知道你真用过FIFO

**坑3：死信队列没告警，死信了一周才发现**
最开始只做了积压告警，没做死信队列的告警，有几条回调处理失败进死信了，没人知道，对账的时候才发现
- 解决：给所有核心队列的死信都加了CloudWatch告警，只要有1条死信就立刻发邮件、短信告警，收到马上处理，后来就再也没出过问题

**坑4：可见性超时设置太短，回调处理慢导致重复消费**
最开始可见性超时用的默认30秒，但是回调处理要查单、更状态、发通知，有时候要40多秒，还没处理完就超时了，消息又被其他消费者拿了，重复处理
- 解决：把核心回调队列的可见性超时改成5分钟，处理到一半还可以动态延长，就没再出现过超时重复的问题了

### 4. FIFO 队列的 MessageGroupId 和 MessageDeduplicationId 分别是什么作用？

**答：** 这个是FIFO队列必考的，一定要说清楚

- **MessageGroupId**：消息分组ID，同一个组的消息保证严格有序，同一个组的消息只会发给同一个消费者，不同组的可以并发消费
  - 我们支付场景就用out_order_no当MessageGroupId，同一个订单的消息都在一个组，保证顺序，不同订单的可以并发处理，兼顾顺序和性能
- **MessageDeduplicationId**：去重ID，FIFO队列5分钟内相同的MessageDeduplicationId的消息只会投递一次，不会重复
  - 我们用消息的唯一ID或者out_order_no + 消息类型当去重ID，防止重复发消息，生产者端就去重了

> 这两个是FIFO的核心，搞清楚这两个才算是真的会用FIFO队列，不是只会开开关。

## 三、最佳实践

### 4. 支付场景用 SQS 的最佳实践有哪些？

**答：**
1. **核心流程用FIFO，非核心用标准队列**：支付状态变更、回调这些要顺序不能重复的用FIFO，通知、统计、日志这些用标准队列，便宜性能高
2. **永远开长轮询**：WaitTimeSeconds设20秒，省90%的成本，还减少空请求
3. **所有核心队列必须配死信+告警**：不要嫌麻烦，不然死信了没人知道就出大事了
4. **可见性超时要根据业务合理设置**：不要用默认30秒，要比业务最长处理时间多一点，避免超时重复消费
5. **批量拉取批量删除**：一次拉10条，处理完批量删，省成本还快
6. **消费端幂等永远是底线**：不管FIFO说的多么不重复，业务层一定要做幂等，永远不要相信MQ的 Exactly-Once
7. **大消息不要直接发SQS**：超过256KB的存在S3，SQS里传地址，不然发不出去
8. **消息不要存超过7天**，超过7天的业务自己存数据库，SQS最多存14天，久了容易丢。

## 面试答题技巧

SQS这块面试的时候，重点突出两点：
1. **SNS + SQS 扇出架构**，这个是AWS最经典的消息架构，把你们支付的实际架构画出来讲，说清楚为什么这么设计，带来了什么好处，面试官就知道你真的有云原生架构经验，不是只会用开源MQ
2. **FIFO的两个ID的用法**，MessageGroupId和MessageDeduplicationId分别怎么用的，踩过什么坑，这个是区分有没有真用过FIFO的关键，说对了印象分直接拉满。
