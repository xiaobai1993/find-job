# SQS 进阶 & 与 SNS 联动场景

> AWS 消息全家桶进阶用法，云原生场景必备

---

## 一、SQS 进阶知识点

### 1. SQS 延迟消息支持多久？怎么实现更久的延迟？

**答：**
SQS 原生支持的延迟消息最长是 **15分钟**，超过15分钟的延迟就不能直接用SQS原生的了。

**超过15分钟的长延迟怎么实现？**
1. **Step Functions 状态机**：AWS原生的工作流服务，支持任意时间的等待，到时间了再调用Lambda或者发SQS消息，最官方的方案，不用自己写逻辑
2. **自己做分级延迟队列**：设置多个不同延迟时间的队列，比如15分钟、1小时、1天，到期了检查是不是到时间了，没到就发到下一级队列，循环直到到时间
3. **DynamoDB + 定时任务扫描**：把延迟消息存在DynamoDB，定时任务扫到时间的，发去SQS处理
4. **EventBridge 定时事件**：固定时间触发的延迟消息，直接用EventBridge定时规则，到时间发消息给SQS

> 支付场景的支付超时关闭一般是30分钟、1小时，超过了SQS原生的15分钟，就用Step Functions或者分级队列实现就好。

---

### 2. SQS 大批量处理消息怎么优化？

**答：**
1. **批量拉取**：`ReceiveMessage` 一次最多拉10条消息，批量处理，减少请求次数，省钱还快
2. **批量删除**：处理完10条一起调用 `DeleteMessageBatch` 批量删除，比一条条删省90%的请求数
3. **长轮询开启**：WaitTimeSeconds设成20秒，减少空请求，降低成本
4. **异步并发处理**：拉到一批消息，丢到线程池里并发处理，提高消费速度
5. **动态调整可见性超时**：处理慢的消息手动调用 `ChangeMessageVisibility` 延长超时时间，不要全局设太大，避免消费者挂了消息很久不能重新投递

---

### 3. SQS 死信队列怎么配置？最佳实践？

**答：**
**配置很简单：**
1. 新建一个死信队列（标准或者FIFO对应就行）
2. 给原队列配置死信规则：`maxReceiveCount` 最大接收次数，比如3次，消费超过3次还没删的就自动转到死信队列

**最佳实践：**
1. **死信队列一定要加监控告警**：有消息立刻告警，人工处理，不然死信了没人知道就丢了
2. **不要用同一个死信队列给多个原队列用**：每个核心队列单独配自己的死信，方便排查问题
3. **定期清理死信队列**：处理完的消息及时清，别占着，最多存14天
4. **死信队列里的消息要保留上下文**：原队列名、接收次数、第一次接收时间，方便排查为什么进死信了

---

### 4. SQS 能做到 Exactly-Once 吗？

**答：**
- FIFO队列提供的是 **Exactly-Once 处理**，是指不会重复投递，但是极端情况下比如消费者处理完了删消息的时候网络断了，还是会重复，所以业务层还是要做幂等
- 严格来说，没有任何MQ能做到100% Exactly-Once，都是至少一次投递，幂等永远是业务层要做的，不要依赖MQ。

## 二、SQS + SNS 联动（AWS最常用的架构！必问）

### 5. SNS 是什么？和 SQS 有什么区别？

**答：**
SNS 是 AWS 的发布订阅消息服务，也就是 Pub/Sub 模式，和 SQS 队列模式不一样：

| 维度 | SNS (发布订阅) | SQS (消息队列) |
|-----|---------------|---------------|
| 模型 | 一对多，发布一条消息，所有订阅者都能收到 | 一对一，一条消息只能被一个消费者消费 |
| 消费方式 | 推模式，SNS主动推给订阅者（HTTP、邮件、短信、SQS、Lambda等） | 拉模式，消费者主动拉消息 |
| 适用场景 | 广播通知，一个事件多个下游处理 | 异步任务，削峰填谷，点对点消费 |

> 最简单的区分：一个事件要给多个系统处理就用 SNS，只要一个系统处理就用 SQS。

---

### 6. SNS + SQS 扇出架构是什么？有什么好处？

**答：** 这是AWS最经典的消息架构，面试必问！

**架构：**
生产者只发消息给 SNS Topic，然后把多个SQS队列订阅这个SNS Topic，SNS收到一条消息就会自动转发给所有订阅的SQS队列，每个队列各拿一份消息，各自处理。

```
生产者 → SNS Topic
            ├── 订阅 → 订单服务SQS队列 → 订单服务消费
            ├── 订阅 → 对账服务SQS队列 → 对账服务消费
            ├── 订阅 → 通知服务SQS队列 → 通知服务消费
            └── 订阅 → 风控服务SQS队列 → 风控服务消费
```

**好处：**
1. **完全解耦**：生产者不用知道有多少个下游，新增下游不用改生产者代码，直接加个SQS队列订阅SNS就行，非常方便
2. **故障隔离**：下游服务挂了不影响生产者，也不影响其他下游，每个队列自己处理自己的，积压了也不影响别人
3. **扩展性极强**：加下游零成本，不用改上游代码
4. **可靠性高**：SNS和SQS都是多副本高可用，不丢消息

> **支付场景我们就是这么用的！**
> 支付成功只发一条消息到支付成功的SNS Topic，然后订单、对账、通知、风控、用户消息这些下游各自订阅自己的SQS队列，自己消费，完全解耦，加新下游不用改支付服务，太方便了。

---

### 7. 为什么不直接让 SNS 推给下游服务，要中间加一层 SQS？

**答：** 这个问题很常见，面试经常问
1. **削峰填谷**：SNS直接推HTTP的话，下游扛不住大流量就挂了，加一层SQS可以缓存消息，下游慢慢消费，不会被打垮
2. **保证消息不丢**：SNS推HTTP如果下游挂了推送失败，虽然会重试，但是重试次数有限，重试完了就丢了，加SQS的话消息存在队列里，多久都不丢，等下游恢复了再消费
3. **消费速度自己控制**：下游可以自己控制消费速度，并发数自己调，不用被动接SNS的推送
4. **错误处理方便**：消费失败进死信队列，告警人工处理，SNS推送失败处理起来麻烦
5. **解耦更彻底**：SNS只负责分发，下游怎么处理完全自己控制，和SNS没关系

---

### 8. SNS + SQS 架构怎么保证消息不丢？

**答：** 多层保证：
1. SNS 收到消息后多AZ存储，不丢
2. SNS 转发到SQS是至少一次投递，一定会转过去，失败会重试
3. SQS 多AZ存储，消费前一直存在
4. 消费失败进死信，告警人工处理
5. 最终对账兜底，每天核对，不一致补单

## 三、其他AWS消息服务对比

### 9. SQS、SNS、EventBridge 怎么选？分别适用什么场景？

**答：**
| 服务 | 模式 | 适用场景 | 支付场景例子 |
|-----|------|---------|------------|
| **SQS** | 点对点队列 | 异步任务、削峰填谷、一个消息只给一个系统处理 | 支付回调处理、自动支付扣款、回滚任务 |
| **SNS** | 发布订阅广播 | 一个事件多个下游处理，扇出架构 | 支付成功事件广播给所有下游系统 |
| **EventBridge** | 事件总线、路由 | 跨服务、跨账号的事件路由，集成AWS服务和第三方SaaS |  AWS资源事件、定时任务、跨业务域的事件分发 |

> 简单记：内部业务同一个域的事件分发用SNS，跨域跨账号、集成AWS服务用EventBridge，点对点异步处理用SQS。

---

### 10. SQS 有什么限制？

**答：**
1. 消息最大体积：256KB，超过了要用S3存，SQS里存地址
2. 消息最长保留时间：14天，默认4天
3. 可见性超时：最长12小时
4. 延迟消息最长：15分钟
5. FIFO队列吞吐量：单队列最高3000条/秒（批量），300条/秒（单条），超过了要拆多个队列
6. 一次最多拉10条消息
