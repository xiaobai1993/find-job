# PostgreSQL 面试题 - 基础篇 & 和 MySQL 核心对比

> 结合美餐支付实际使用场景，重点突出 PG 与 MySQL 的差异点，面试高频考点

---

## 一、核心基础对比（必问！为什么你们支付用 PG 不用 MySQL？）

### 1. PostgreSQL 和 MySQL 核心区别？

**答：** 直接说你们选 PG 的理由，结合业务讲，加分项！

| 维度 | PostgreSQL | MySQL (InnoDB) |
|-----|-----------|---------------|
| **定位** | 功能最强大的开源关系型数据库，对标商业 Oracle | 最流行的轻量关系型数据库，互联网场景用的多 |
| **MVCC 实现** | 多版本数据直接存在数据页里，没有 undo log，旧版本通过 vacuum 清理 | undo log + redo log，版本链存在 undo log 里 |
| **索引支持** | 极其丰富：B树、Hash、GIN(倒排)、GiST、BRIN(块范围)、部分索引、表达式索引、覆盖索引 | 主要是 B+Tree，支持的索引类型少 |
| **数据类型** | 极其丰富：jsonb、数组、枚举、hstore(kv)、几何类型、UUID、自定义类型 | 类型少，只有基础类型，JSON 支持弱 |
| **分区功能** | 原生支持非常完善，支持范围、列表、哈希、多级子分区，分区裁剪优秀 | 分区功能弱，只有 range 和 list，不支持原生 hash 分区（8.0才勉强支持），不支持多级分区 |
| **SQL 标准兼容** | 非常严格，支持大部分 SQL 标准，窗口函数、CTE、递归查询都很强 | 兼容性差，有很多自己的方言，功能不全 |
| **存储引擎** | 只有一个原生存储引擎，插件化程度低 | 多存储引擎，默认 InnoDB |
| **扩展性** | 极强，支持自定义函数、触发器、自定义类型、扩展插件（如PostGIS、timescaledb） | 扩展性弱，插件少 |
| **并发写性能** | 高并发下性能更稳定，不会像 MySQL 有很多锁等待 | 简单写场景快，高并发复杂场景容易性能抖动 |
| **优化器** | 优化器非常强大，复杂 SQL、多表 join 执行计划更准 | 优化器相对简单，复杂 join 容易选到烂的执行计划 |
| **无主键表** | 不要求必须有主键，也可以正常用 | 没有主键的话性能很差，隐式 rowid |

> **我们支付为什么选 PG？（你就这么答）**
> 主要就是两点：一是分区功能强，我们的支付单表、流水表数据量大，需要按时间范围分区 + 按账号ID哈希分区的多级分区，MySQL 的分区功能满足不了；二是 jsonb 类型非常好用，支付的扩展信息、渠道返回的原始报文都直接存在 jsonb 里，还可以建索引查询，不用单独建扩展表，方便很多。

## 二、核心原理基础

### 2. PG 的 MVCC 实现原理？和 MySQL 有什么区别？

**答：** 这是 PG 面试必问，也是和 MySQL 最大的区别之一

**PG 的 MVCC 实现：**
1. **没有 undo log**：每行数据都有两个隐藏字段 `xmin` 和 `xmax`
   - `xmin`：插入这行数据的事务 ID
   - `xmax`：删除或更新这行数据的事务 ID，没删除就是 0
2. **更新不是原地修改**：更新一行的时候，不是修改原数据，而是新插入一行版本，原行的 xmax 设置为当前事务ID
3. **版本都存在数据页里**：所有历史版本都和当前版本存在同一个数据文件里，不会单独存 undo log
4. **可见性判断**：查询的时候根据事务的快照，判断 xmin 和 xmax 是否在可见的事务范围内，返回对应的版本
5. **垃圾回收**：旧的版本不会自动删除，需要后台的 `vacuum` 进程定期清理死元组，释放空间，可以被新数据复用

**和 MySQL InnoDB 的区别：**

| 维度 | PG MVCC | MySQL InnoDB MVCC |
|-----|---------|-----------------|
| **版本存储位置** | 和当前数据存在同一个数据页里 | undo log 里单独存 |
| **清理机制** | vacuum 后台进程定期清理死元组 | purge 线程清理不需要的 undo log |
| **长事务影响** | 长事务会导致 vacuum 无法清理旧版本，表越来越膨胀，性能下降 | 长事务会导致 undo log 越来越大 |
| **回滚速度** | 极快，回滚只需要改事务状态，不需要删数据 | 大事务回滚慢，要 undo 回滚所有操作 |
| **数据膨胀** | vacuum 不及时会严重膨胀，表空间占用变大 | 不会膨胀，undo log 单独清理 |
| **读性能** | 读不需要加任何锁，也不会阻塞写，完全非阻塞 | 读也不加锁，差不多 |

> **支付场景踩过的坑**：之前有个慢查询事务跑了几个小时没提交，导致 vacuum 没法清理旧版本，支付单表几天就从 100G 膨胀到了 300G，后来强制kill掉长事务，vacuum full 才收缩回去，所以 PG 一定要监控长事务，不能有长时间不提交的事务。

### 3. VACUUM 是什么作用？VACUUM 和 VACUUM FULL 区别？

**答：**
**VACUUM 的作用：**
1. 清理死元组（已经被删除或更新的旧版本数据），释放空间给新数据复用
2. 更新统计信息，给优化器用
3. 冻结旧的事务ID，防止事务ID回卷（PG 事务ID是32位的，循环使用，需要冻结）

**两者区别：**

| 维度 | VACUUM | VACUUM FULL |
|-----|--------|------------|
| **是否释放空间给OS** | 不释放，只是标记为可复用，文件大小不变 | 会把空间还给操作系统，文件会变小 |
| **是否锁表** | 不锁表，在线执行，不影响业务读写 | 会锁表！执行期间表不能写，大表会堵很久 |
| **执行速度** | 快，边扫边清理 | 很慢，相当于整表重建 |
| **使用场景** | 日常定期跑，自动跑就行 | 表膨胀很严重，需要收缩空间的时候才用，而且要业务低峰期用 |
| **对性能影响** | 很小，几乎没影响 | 影响很大，生产环境不要随便跑 |

### 4. PG 支持哪些索引类型？分别适用什么场景？

**答：** PG 最大的优势之一就是索引类型丰富，面试常考

| 索引类型 | 适用场景 | 支付场景例子 |
|---------|---------|------------|
| **B-Tree 索引** | 默认索引，等值查询、范围查询，最常用，适合大多数场景 | 支付单ID、out_order_no 建唯一索引，和 MySQL 一样 |
| **Hash 索引** | 只支持等值查询，不支持范围，查询比B树快一点，占用空间小 | 只需要等值查询的字段，比如 account_type 渠道类型 |
| **GIN 索引** | 倒排索引，适合数组、jsonb 类型的多值查询，包含查询 | 扩展信息存在 jsonb 里，需要查里面某个字段的值，就给 jsonb 建 GIN 索引 |
| **GiST 索引** | 通用搜索树，适合几何类型、全文检索、范围类型查询 | 地理位置查询，附近的门店，用 PostGIS 就靠这个 |
| **BRIN 索引** | 块范围索引，适合大表的有序字段，比如自增ID、时间，占用空间极小，比B树省100倍空间 | **支付单的 created_at 时间字段**，数据是按时间顺序写入的，建 BRIN 索引只有几十KB，查询某段时间的记录和B树差不多，省太多空间了 |
| **部分索引** | 只给满足条件的行建索引，不是全表，省空间 | 只给未完成的支付单建索引：`CREATE INDEX idx_status ON payment_slip(status) WHERE status < 6;` 终态的支付单不用查，索引很小 |
| **表达式索引** | 给函数表达式的结果建索引 | `CREATE INDEX idx_date ON payment_slip( DATE(created_at) );` 按天查询的时候就能走到索引，MySQL 不支持，MySQL用函数就会索引失效 |
| **覆盖索引** | 和 MySQL 一样，INCLUDE 子句把需要的字段加进去，避免回表 | `CREATE INDEX idx_user_id ON payment_slip(user_id) INCLUDE (amount, created_at);` |

> **支付场景巨好用的两个索引**：
> 1. **BRIN 索引**：时间字段用这个，几亿行的表索引才几百KB，太香了，MySQL没有
> 2. **表达式索引**：比如你想按支付单创建时间的日期查，直接给 DATE(created_at) 建索引，不用额外存一个日期字段，MySQL 做不到，MySQL里用函数索引就失效了。

### 5. PG 的事务隔离级别？和 MySQL 有什么不一样？

**答：**
PG 支持 4 种隔离级别，但是实际实现上和标准有区别：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---------|-----|----------|-----|------|
| 读未提交 Read Uncommitted | ❌ 实际上不会，PG 实现上和读已提交一样 | - | - | PG 里这个级别和 RC 没区别 |
| 读已提交 Read Committed | ❌ 不会 | ✅ 会 | ✅ 会 | 大部分系统默认用这个，PG默认也是这个 |
| 可重复读 Repeatable Read | ❌ 不会 | ❌ 不会 | ✅ 还是会有幻读！ | 注意！PG 的 RR 级别不能完全避免幻读，和 MySQL InnoDB 不一样，MySQL 用 Next-Key Lock 解决了，PG 没有间隙锁，所以还是会幻读 |
| 可序列化 Serializable SSI | ❌ 不会 | ❌ 不会 | ❌ 完全不会 | PG 的 SSI 是真正的可串行化，用序列化快照隔离，性能损失不大，强一致性场景用 |

> **和 MySQL 最大的区别**：MySQL 的 RR 级别已经基本解决了幻读，PG 的 RR 级别还是会有幻读，因为 PG 没有间隙锁，如果你要完全避免幻读，就要用 SSI 隔离级别。
> 支付场景我们一般用默认的 RC 级别就行，幂等靠唯一索引和状态机保证，不用 SSI，性能更好。

### 6. PG 锁机制和 MySQL 有什么区别？

**答：**
1. **没有间隙锁！** 这是最大的区别，PG 只有行锁和表锁，没有 MySQL 的间隙锁、Next-Key Lock，所以 RR 级别下还是会有幻读
2. **锁粒度更丰富**：PG 支持多种不同强度的表锁，比如 ACCESS SHARE、ROW SHARE、ROW EXCLUSIVE、SHARE、EXCLUSIVE 等等，不同操作加不同强度的锁，冲突矩阵更细，并发更高
3. **行锁都是一样的**：都是在索引上加行锁，没索引就锁表，和 MySQL 一样
4. **死锁检测**：PG 自带死锁检测，发现死锁会自动回滚其中一个事务，和 MySQL 差不多

> **支付场景注意点**：因为没有间隙锁，所以不要依赖 RR 隔离级别防幻读，幂等还是要靠唯一索引，比如 out_order_no 建唯一索引，重复插入直接报错，比靠锁靠谱多了。
