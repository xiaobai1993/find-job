## 一、支付场景 PG 核心特性应用

### 1. 支付场景哪些地方用到了 PG 的特色功能？

**答：** 直接说你们的实际用法，显得你真的用过 PG，不是只会用 MySQL

我们支付服务主要用了 PG 这几个非常好用的特性：

1. **jsonb 类型存扩展信息**
   - 支付单的扩展属性、第三方渠道返回的原始报文、不同支付产品的特殊字段，都存在 jsonb 字段里，不用单独建一堆扩展表，也不用改表结构加字段，非常灵活
   - 而且 jsonb 可以建 GIN 索引，需要查询里面某个字段的时候也能走索引，不用全表扫
   ```sql
   -- 建表的时候加jsonb字段
   extra jsonb NOT NULL DEFAULT '{}'::jsonb;
   -- 给jsonb里的mch_extra字段建GIN索引
   CREATE INDEX idx_extra_mch ON payment_slip USING GIN ((extra->'mch_extra'));
   -- 查询的时候直接用
   SELECT * FROM payment_slip WHERE extra->'mch_extra'->>'mch_name' = '某某商户';
   ```
   > 比 MySQL 的 JSON 类型好用太多了，MySQL的JSON建索引很麻烦，而且功能弱。

2. **多级分区表**
   - 刚才讲过的，支付单表按时间范围+用户ID哈希的两级分区，性能提升非常明显，归档也方便

3. **表达式索引 & 部分索引**
   - 表达式索引：按支付创建日期统计的时候，直接给 `DATE(created_at)` 建索引，不用额外存一个冗余的日期字段，查询也能走索引，MySQL 做不到，MySQL用函数就会索引失效
   - 部分索引：只给未完成的支付单建状态索引，终态的支付单占了90%以上，都不用建，索引大小只有原来的十分之一，查询更快
   ```sql
   -- 表达式索引
   CREATE INDEX idx_created_date ON payment_slip (DATE(created_at));
   -- 部分索引：只给未终态的支付单建状态索引
   CREATE INDEX idx_status_not_end ON payment_slip (status) WHERE status < 6;
   ```

4. **UPSERT 做幂等**
   - PG 原生支持 `INSERT ... ON CONFLICT (唯一键) DO UPDATE ...` 语法，就是 MySQL 的 INSERT ON DUPLICATE KEY UPDATE，但是功能更强，做幂等非常方便
   - 比如支付回调处理，来了回调直接插入，存在就更新，不用先查再判断，原子操作，性能好
   ```sql
   INSERT INTO callback_log (out_order_no, callback_data)
   VALUES ('xxx', '{}')
   ON CONFLICT (out_order_no) DO UPDATE SET callback_data = EXCLUDED.callback_data, updated_at = now();
   ```
   一条SQL就搞定幂等，不用加锁，非常好用。

5. **CTE 递归查询 & 窗口函数**
   - 对账、统计的时候用窗口函数算累计金额、排名，非常方便，SQL 写出来很简洁，性能也比自己写子查询快很多
   - 比如统计每个商户每天的支付金额环比，用窗口函数几行就写完了

### 2. 用 PG 做支付业务，比 MySQL 好在哪里？

**答：**（结合你们实际说，不要说空话）
1. **分区功能强**：多级分区我们刚需，MySQL 做不了范围+哈希的多级分区，分区裁剪也不准，PG 用了之后支付单查询性能提升了好几倍，归档历史数据秒级完成
2. **jsonb 太好用了**：支付的扩展信息太多了，不同渠道不同产品的字段都不一样，用 jsonb 不用频繁改表加字段，还能建索引查询，省了很多扩展表，开发效率高很多
3. **优化器更强**：复杂的多表关联查询、统计查询，PG 的执行计划比 MySQL 准很多，不容易出慢SQL，我们对账的一些复杂SQL在MySQL里跑几分钟，在PG里几秒就出来了
4. **BRIN 索引太香了**：支付单的时间字段建BRIN索引，几亿行的表，索引才几百KB，和B树索引查询性能差不多，省了大量的存储空间，内存也能缓存更多数据
5. **数据一致性更好**：PG 的事务、数据校验都更严格，不会出现MySQL那种数据丢失、静默损坏的情况，资金业务更放心

## 二、支付场景 PG 踩过的坑

### 3. 支付业务用 PG 踩过哪些印象深刻的坑？

**答：** 说几个真实的，面试官爱听

**坑1：长事务导致表严重膨胀**
- 有一次对账的一个慢查询，事务跑了3个小时没提交，导致 vacuum 没法清理这段时间产生的死元组，支付单表两天就从100G膨胀到了300G，查询越来越慢
- 解决：
  - 监控所有运行超过5分钟的长事务，自动告警，必要的话kill掉
  - 调整 autovacuum 参数，让vacuum跑的更频繁一点
  - 对账统计都跑从库，不要跑主库，避免长事务影响主库
- 经验：PG 对长事务的容忍度比MySQL低很多，一定要严格控制长事务，不然表膨胀很恐怖

**坑2：vacuum 不及时导致性能下降**
- 支付单更新很频繁，每天产生大量死元组，最开始vacuum参数配的太保守，清理速度赶不上产生的速度，表越来越大，查询越来越慢
- 解决：
  - 调大 autovacuum_work_mem，让vacuum跑的更快
  - 对更新频繁的表单独设置更激进的vacuum参数，比如：
    ```sql
    ALTER TABLE payment_slip SET (autovacuum_vacuum_scale_factor = 0.05);
    ```
    死元组占比到5%就触发vacuum，不用等到默认的20%
  - 业务低峰期手动跑vacuum analyze，更新统计信息

**坑3：分区表的全局唯一问题**
- 最开始没注意，分区表没法建全局唯一索引，out_order_no 只能建联合唯一索引，带分区键，理论上可能出现不同分区有相同的 out_order_no
- 解决：业务层做幂等校验，插入前先查（或者用分布式锁），加上数据库唯一索引兜底，因为我们查询out_order_no的时候都会带上user_id分区键，所以联合唯一索引还是能用的，不会出问题

**坑4：大量死元组导致索引膨胀**
- 索引也会膨胀，死元组的索引条目也占空间，最开始只清理了表没管索引，索引越来越大
- 解决：用 pg_repack 工具在线重建膨胀的索引和表，不用锁表，业务无感知，定期做就行

## 三、PG 性能优化（支付场景）

### 4. 支付业务的 PG 做了哪些性能优化？

**答：**

**参数优化：**
1. **shared_buffers**：配成物理内存的 25%，比如64G内存就配16G，让更多数据缓存在内存里
2. **work_mem**：调大一点，排序、hash join的时候用，避免用临时文件，复杂查询快很多
3. **maintenance_work_mem**：调大，vacuum和建索引的时候更快
4. **autovacuum 相关参数**：调的更激进，更新频繁的支付表提前触发vacuum，避免膨胀
5. **effective_cache_size**：配成内存的50%-75%，给优化器参考，知道系统有多少缓存可用，执行计划更准

**业务优化：**
1. **所有查询尽量带分区键**，保证分区裁剪生效，不要跨全分区扫
2. **热表的更新尽量走主键**，行锁粒度小，并发高
3. **jsonb 不要存太多太大的数据**，超过10KB的还是存对象存储或者单独的表，不然太占空间，查询慢
4. **用 BRIN 索引代替时间字段的 B 树索引**，省99%的空间，性能差不多
5. **部分索引用起来**，区分度低的字段，只给需要的部分建索引，小索引查询更快
6. **定期做 pg_repack**，清理膨胀的表和索引，回收空间，提升性能
7. **读写分离**：统计、对账、后台查询都走从库，主库只处理核心支付写入和查询，保证主库性能

### 5. 怎么排查 PG 的慢SQL？和 MySQL 有什么不一样？

**答：**
**排查流程：**
1. **开启慢查询日志**，设置 log_min_duration_statement = 1000（超过1秒的都记录）
2. **用 pg_stat_statements 扩展**，这个是PG最常用的慢查询分析工具，可以统计所有SQL的执行次数、平均耗时、总耗时，比慢查询日志好用，直接找TOP N的慢SQL
3. **EXPLAIN ANALYZE 看实际执行计划**，比MySQL的EXPLAIN信息详细很多，能看到每一步实际扫描了多少行，耗时多久，是不是走了分区裁剪，是不是走了索引
4. **看 pg_stat_activity 视图**，查当前正在运行的SQL，有没有长事务，有没有锁等待
5. **锁等待排查**：查询 pg_locks 视图，看哪些事务在等锁，谁持有锁

**和 MySQL 的区别：**
- PG 的 EXPLAIN ANALYZE 会实际执行SQL，给出真实的执行数据，比 MySQL 的预估准确很多
- pg_stat_statements 功能比 MySQL 的慢查询日志强大很多，可以聚合统计所有SQL的性能数据
- PG 没有 MySQL 的 show profile，但是有更强大的扩展工具

## 面试答题技巧

PG 这块面试的时候，你就重点突出两点：
1. **分区的实际经验**：你们做了范围+哈希的两级分区，怎么设计的，踩了什么坑，带来了什么收益，这个是大部分人没有的实际项目经验，一说出来面试官就知道你是真用过PG，不是只会基础
2. **和 MySQL 的对比**：结合你们的实际选型，说清楚为什么选PG不选MySQL，PG的哪些特性解决了你们的什么业务痛点，不要只背官方文档的区别，要结合业务说

不用太深入底层原理，重点讲你实际做过的，分区、jsonb、这些都是你们实际在用的，讲出来就没问题。
