> 结合美餐支付业务：按账号ID哈希分区 + 按雪花ID时间范围分区的多级分区，深度讲解原理、实战、踩坑、和MySQL分区的对比

## 一、PG 分区基础

### 1. PG 分区是什么？有什么优势？

**答：**
分区就是把一张逻辑上的大表，物理上分成多个小的分区表，但是对应用层完全透明，还是和操作一张表一样。

**核心优势（为什么我们支付用分区？）：**
1. **查询性能大幅提升**：查询条件带上分区键的话，只需要扫对应的分区，不用扫全表，比如查某个用户的支付记录，只扫那个哈希分区就行，数据量小了几个量级
2. **历史数据清理极快**：按时间分区的话，过期的历史数据直接 DROP 分区就行，秒级完成，不用 DELETE 删几亿行，不会产生大量死元组
3. **冷热数据分离**：热数据存在快的SSD，冷的历史分区可以移到慢的存储，节省成本
4. **备份恢复快**：单分区出问题只恢复单个分区就行，不用整表恢复
5. **写入性能更好**：写入分散到多个分区，减少IO竞争，高并发下比单表好很多

---

### 2. PG 支持哪几种分区类型？分别适用什么场景？

**答：** 原生支持4种，比MySQL多很多，功能更完善

| 分区类型 | 原理 | 适用场景 | 支付场景例子 |
|---------|------|---------|------------|
| **范围分区 (RANGE)** | 按分区键的范围分，比如时间、ID | 时间序列数据，按时间归档，连续值查询 | **支付单按创建时间范围分区**，每个月一个分区，过期的直接删 |
| **列表分区 (LIST)** | 按分区键的枚举值分，每个分区对应几个固定值 | 分区键是枚举值，区分度不高的 | 支付子单按渠道类型分：微信、支付宝、余额，每个渠道一个分区 |
| **哈希分区 (HASH)** | 按分区键取模，均匀分到各个分区 | 分区键是离散值，查询都是按分区键查，均匀分散读写压力 | **支付单按 user_id / account_id 哈希分区**，均匀分散到N个分区，避免热点分区 |
| **多级分区** | 分区下面再建子分区，支持任意组合 | 超大数据量，需要两个维度分区 | **我们支付实际用的：一级按时间范围分区（月），二级按账号ID哈希分区（64个）**，既方便历史归档，又能分散单分区的压力 |

> **MySQL 对比：** MySQL 8.0 才勉强支持哈希分区，而且不支持多级分区，分区裁剪也经常失效，功能比 PG 差远了，这就是我们选 PG 做分区的核心原因。

## 二、我们支付的分区实战（重点，面试就说你做的）

### 3. 你们支付表是怎么做分区的？为什么这么设计？

**答：** 直接说你们的方案，面试官最喜欢听实际项目经验

我们的支付单表数据量很大，一年就有好几亿行，所以用了**两级分区**的设计：

**一级分区：RANGE 范围分区，按支付单 ID（雪花ID）的时间范围分区，每个月一个分区**
- 为什么用雪花ID而不是 created_at？
  - 雪花ID本身就包含了时间信息，和创建时间是一致的，而且雪花ID是主键，查询的时候经常带ID条件，分区裁剪效率更高
  - created_at 如果建了BRIN索引也可以，但是主键ID自带顺序，不用额外建索引
- 好处：历史数据归档非常方便，超过1年的旧分区直接DROP，秒级删除，不用DELETE删几亿行，不会产生大量死元组，也不会导致表膨胀

**二级分区：HASH 哈希分区，按 user_id / mch_id 哈希，分 64 个哈希子分区**
- 为什么还要哈希分区？
  - 单月的一个分区还是有几千万行，还是太大，查询慢
  - 大部分支付查询都是按用户ID或者商户ID查的，带上这个条件就能命中对应的哈希子分区，只扫几十分之一的数据，查询性能提升几十倍
  - 写入也分散到64个分区，IO压力分散，高并发写入性能更好

**分区数量怎么定的？**
- 哈希分区64个，是因为我们预估5年的数据，每个分区的数据量在200万行左右，是PG比较合适的大小，分区太多元数据会大，太少的话每个分区还是太大
- 范围分区按月，刚好和我们的对账、统计周期一致，归档也方便

### 4. 分区的SQL怎么写？给个你们的例子

**答：** 给个简化版的支付单表分区建表SQL，面试可以说个大概

```sql
-- 1. 创建父表，声明是分区表，分区键是id（雪花ID）范围分区
CREATE TABLE payment_slip (
    id bigint NOT NULL,
    out_order_no varchar(64) NOT NULL,
    user_id bigint NOT NULL,
    mch_id bigint NOT NULL,
    amount bigint NOT NULL,
    status tinyint NOT NULL,
    created_at datetime NOT NULL,
    updated_at datetime NOT NULL,
    PRIMARY KEY (id, user_id) -- 注意！分区键必须包含在主键里，不然建不了
) PARTITION BY RANGE (id);

-- 2. 创建每个月的一级分区，2024年5月的分区，再按user_id哈希分64个二级分区
CREATE TABLE payment_slip_202405 PARTITION OF payment_slip
FOR VALUES FROM (7238255882288988160) TO (7265485676840509440) -- 对应2024-05-01到2024-06-01的雪花ID范围
PARTITION BY HASH (user_id);

-- 3. 给202405这个分区创建64个哈希子分区
CREATE TABLE payment_slip_202405_00 PARTITION OF payment_slip_202405 FOR VALUES WITH (MODULUS 64, REMAINDER 0);
CREATE TABLE payment_slip_202405_01 PARTITION OF payment_slip_202405 FOR VALUES WITH (MODULUS 64, REMAINDER 1);
-- ... 一直建到 63
```

> **注意点：** 分区键必须包含在主键和所有唯一索引里！比如 out_order_no 要建唯一索引的话，必须带上 id 和 user_id 两个分区键，不然建不了，这是PG分区的限制，也是我们踩过的坑。

### 5. 什么是分区裁剪？怎么确认分区裁剪生效了？

**答：**
**分区裁剪（Partition Pruning）**：查询的时候，优化器根据WHERE条件，自动跳过不需要的分区，只扫描需要的分区，这是分区性能提升的核心。

**怎么验证生效了？** 用 EXPLAIN 看执行计划：
```sql
EXPLAIN SELECT * FROM payment_slip
WHERE id = 7238255882288988160 AND user_id = 12345;
```
看执行计划里扫描的分区，如果只扫了 `payment_slip_202405_12` 这一个分区，说明裁剪生效了。如果显示扫描所有分区，就是没生效，要优化查询条件，必须带上分区键。

**分区裁剪失效的常见场景（坑！）：**
1. **查询条件没带分区键**：比如只按 amount 查，没带 id 和 user_id，就会扫所有分区，比单表还慢
2. **分区键上用了函数**：比如 `WHERE DATE(created_at) = '2024-05-01'`，函数用在分区键上，裁剪失效，和索引失效一个道理
3. **分区键类型不匹配**：分区键是int，传了字符串，隐式转换，裁剪失效
4. **关联查询没带分区键**：join 的时候两个表都没带分区键，都会全部分区扫

## 三、分区踩过的坑（必讲！显得你有实际经验）

### 6. 用 PG 分区踩过哪些坑？怎么解决的？

**答：** 说3-4个你们实际踩过的，面试官最吃这个

**坑1：唯一索引必须包含所有分区键，否则建不了**
- 最开始我们想给 out_order_no 建全局唯一索引，但是建不了，因为分区表的所有唯一索引都必须包含所有的分区键（id + user_id），PG不支持跨分区的全局唯一索引
- 解决：要么就把 out_order_no 加上分区键建联合唯一索引，要么就业务层面自己保证全局唯一，我们是用业务层+数据库联合保证，查询的时候带上分区键，唯一索引还是能用的
- **和 MySQL 对比：** MySQL 分区也有这个问题，都不支持全局唯一索引，所以分区表的唯一性都要业务自己兜底

**坑2：分区数量不是越多越好**
- 最开始我们想分256个哈希分区，结果发现元数据太多，表连接的时候优化器很慢，DDL也很慢，查询反而性能下降
- 解决：控制分区数量，单表分区总数不要超过几百个，我们现在64个哈希分区，每个月一级分区，一年也就 12*64=768 个，比较合适
- 经验值：每个分区的数据量不要太大（单表千万级以内），也不要太小（几十万以上），不然分区 overhead 反而大于收益

**坑3：跨分区查询性能差**
- 后台对账的时候，统计整个月的所有数据，不带user_id条件，就需要扫64个分区，性能反而不如单表
- 解决：统计类的查询不要跑主库，跑从库或者数仓，或者做预聚合，正常的用户查询都是带user_id的，都会走分区裁剪，没问题

**坑4：新增分区要提前做**
- 最开始忘了提前建下个月的分区，到了6月1号，新的支付单插入不进去，报错没有对应分区，线上告警
- 解决：写了个定时任务，每个月25号就提前把下下个月的分区都建好，永远留至少一个月的缓冲，不会断

**坑5：分区键不能更新**
- 想修改某个支付单的user_id，改了之后这个行就不属于原来的分区了，PG会报错，分区键的值是不能改的
- 解决：设计的时候分区键选永远不会更新的字段，比如ID、user_id这些，创建了就不会变，不要选会修改的字段当分区键

## 四、PG 分区和 MySQL 分区的对比（面试必问）

### 7. PG 的分区比 MySQL 强在哪里？

**答：**

| 维度 | PostgreSQL 分区 | MySQL 分区 |
|-----|----------------|-----------|
| **分区类型** | 支持RANGE、LIST、HASH、多级任意组合，非常灵活 | 8.0才支持HASH分区，不支持多级分区，类型少 |
| **分区裁剪** | 优化器非常强大，裁剪很准，大部分场景都能正确裁剪 | 裁剪经常失效，优化器弱，复杂查询经常扫全部分区 |
| **分区数量** | 支持几千个分区都没问题 | 分区数量多了性能下降严重，一般不建议超过100个 |
| **分区维护** | ADD/DROP 分区都是秒级，支持拆分、合并分区 | DROP分区快，但是ADD分区经常要锁表，慢 |
| **子分区** | 支持任意多级子分区，组合非常灵活 | 不支持子分区，只能一级 |
| **性能** | 高并发下分区查询写入都更稳定 | 分区性能提升不明显，甚至有时候比单表还慢 |
| **全局索引** | 都不支持，差不多 | 都不支持 |

> **总结：** 如果只是简单的按时间范围分区，MySQL 其实也能用，但是像我们需要范围+哈希的多级分区，或者查询比较复杂的，MySQL 分区完全满足不了，PG 的分区功能才是生产级别的。

## 五、分区最佳实践（面试可以说你总结的经验）

### 8. 分区表设计的最佳实践？

**答：**
1. **分区键选查询最常用的、不会更新的、区分度合适的字段**：比如我们选的ID（时间）和user_id，都是查询必带的，而且不会更新
2. **控制分区数量**：不要太多也不要太少，每个分区的数据量控制在百万到千万级别，总数不要超过几千
3. **一定要带上分区键查询**：所有业务查询尽量都带上分区键，不然分区裁剪失效，还不如单表
4. **提前创建分区**：范围分区一定要提前建好，不要等数据插入报错了才想起建，用定时任务自动建
5. **唯一索引必须包含分区键**：设计表的时候就要考虑到，不然建不了唯一约束
6. **统计类查询不要用分区主库**：跑从库或者数仓，避免全分区扫影响线上业务
7. **定期归档旧分区**：冷数据可以move到慢存储，或者直接备份后删除，降低主库压力
8. **大表改分区怎么平滑做？** 用 pg_repack 或者逻辑复制，不停机迁移，不要直接ALTER TABLE改分区，会锁表很久
