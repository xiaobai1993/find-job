哨兵选举流程 & 从库选主优先级

故障检测流程
① Sentinel 每秒 PING 所有节点
② Master 无响应 → 主观下线 (SDOWN)
③ 通知其他 Sentinel 确认
④ 超过半数 Sentinel 确认下线
⑤ → 客观下线 (ODOWN)
⑥ 开始从 Slave 中选新 Master
新 Master 选举优先级
1. replica-priority 越低越优先（默认100）
2. 复制偏移量最大的优先（数据最新）
3. Run ID 字典序最小的优先
✅ 选出来的新 Master 数据最全
✅ 其他 Slave 改为复制新 Master
✅ 通知客户端新 Master 地址
面试要点

哨兵 = 监控 + 自动故障转移 + 通知客户端。过半 Sentinel 认为 Master 挂 → 客观下线 → 按优先级选 Slave 升级 → 通知客户端新地址。部署奇数个哨兵（3或5）防止脑裂。

为什么是 16384 个槽？

• 心跳包要携带槽信息
• 16384 槽 = 2KB 位图（2048字节）
• 65536 槽 = 8KB，心跳包太大占带宽
• 一般集群节点不超过 1000 个
• 16384 / 1000 = 每个节点约16槽，足够了
// key 路由计算
slot = CRC16(key) % 16384
// hash tag: {xxx}
key = "order_{123}_status"
→ 只对 {123} 计算 CRC16
→ 强制同一 tag 到同一节点
→ 支持多 key 原子操作
面试要点

Cluster = 数据分片 + 去中心化 + 自动故障转移。每个 key 通过 CRC16 % 16384 路由到对应节点，每个节点负责部分槽。客户端连任意节点，路由错了会返回 MOVED 重定向。

一致性哈希 — 为什么用它？和取模哈希区别

普通取模哈希的问题
节点数 = N，key % N 路由
新增/删除节点 → N 变化
→ 几乎所有 key 都要重新映射
→ 缓存大量失效 → 缓存雪崩！
一致性哈希的解决
哈希环（0 ~ 2³²）
节点映射到环上某个位置
key 顺时针找最近节点
新增节点：只影响相邻节点的 key
删除节点：只影响该节点的 key
其他节点不受影响！
3个节点的哈希环

虚拟节点 — 解决数据倾斜

问题：数据倾斜
节点少 → 分布可能不均匀
某节点可能承担 50%+ 的 key
热点问题、负载不均
解决：虚拟节点
每个真实节点映射 N 个虚拟节点
虚拟节点分布更均匀
key 路由到虚拟节点 → 映射真实节点
一般 100~200 个虚拟节点/真实节点
// 虚拟节点命名规则
Node1#VN0, Node1#VN1 ... Node1#VN99
Node2#VN0, Node2#VN1 ... Node2#VN99
// 路由
slot = CRC32("out_order_123")
→ 顺时针找最近虚拟节点
→ 虚拟节点对应 → 真实节点
// Redis Cluster 不用一致性哈希
// Cluster 用固定16384槽
// 一致性哈希用于自建代理层
// 如 Twemproxy / Codis

Redis 分布式锁 — SET NX EX + Redisson

基础实现
# 加锁（原子操作）
SET lock:pay_{orderId}
{unique_uuid} NX EX 30
# 解锁（Lua脚本保证原子）
if GET(key) == my_uuid then
DEL(key)
end
四大坑 & 解决方案
❶ 锁过期业务未完 → Redisson 看门狗续期
❷ 不可重入 → Hash 结构记次数
❸ 主从切换锁丢失 → RedLock(多节点)
❹ 非原子加锁+过期 → SET NX EX 一条命令

Redisson 看门狗原理

加锁成功 → 后台启动 TimerTask，每隔 10s（锁30s的1/3）检查 → 还持有锁就续期到 30s → 业务执行多久就续多久。解锁时取消 TimerTask。

维度主从复制哨兵模式Cluster 集群
故障转移 手动切换 自动故障转移 自动故障转移
水平扩展 不支持 不支持（单主写） 支持，数据分片
数据量 单机限制 单机限制 理论无上限
写能力 单主 单主 多主并行写
运维复杂度 简单 中等 复杂
多 key 操作 支持 支持 需在同一槽（hash tag）

选型建议

数据量小 → 哨兵；数据量大/写压力大 → Cluster。Cluster 注意 mget/pipeline 只能在同一个槽（用 hash tag {} 解决）。支付场景一般用哨兵，数据量不大，强一致优先，或者直接上 Cluster。

大 Key / 热 Key 问题

大 Key 危害 & 解决
读写耗时长，阻塞主线程
集群节点内存倾斜
删除时阻塞（需用 UNLINK 异步删）
✓ 拆分大 Hash/List 为多个小的
✓ 大 value 存对象存储，Redis 存引用
✓ redis-cli --bigkeys 扫描
热 Key 危害 & 解决
流量集中打到同一节点
节点 CPU/带宽打满
✓ 本地缓存 (Caffeine) 分担
✓ 热 key 复制：key_0~key_9 随机读
✓ Redis 4.0+ hotkeys 自动发现
