面试要点

Push 模式每轮每个感染节点随机选择 Fanout 个未感染节点传播，收敛速度 O(log N)。Fanout 越大收敛越快但网络开销越大。Push-Pull 模式收敛最快，因为双向交换信息减少了冗余传播。

Gossip Section（随机 1/3 节点信息）
node_id: e5f6..., ip:port: 10.0.0.2:6379, flags: master, last_in: 1234ms
node_id: g7h8..., ip:port: 10.0.0.3:6379, flags: slave, last_in: 567ms
... (约 N/3 条)
面试要点

PING 消息不只是心跳！还顺带传播了其他节点的状态信息，这是 Gossip 的精髓。每次通信都是"一拖多"——发送者和 1/3 集群节点的状态在一次 PING 中全部传递。这使得信息传播速度远超单纯的 1 对 1 通信。

面试要点

Redis 用最简单的 Push + Fanout=1，够用就好。Cassandra 更"重"——Fanout=3 + Push-Pull + Merkle Tree 反熵，因为要保证数据副本的一致性。Consul 基于 SWIM 协议改进，间接探测减少了网络分区导致的误判。选协议要看场景——不需要强一致就用 Gossip，需要就用 Raft。

使用场景总结

适合 Gossip 的场景
1. 节点成员管理与故障检测
2. 元数据/配置信息传播
3. 服务发现与注册
4. 缓存失效通知
5. 区块链交易传播
→ 特点：允许短时间不一致
不适合 Gossip 的场景
1. 分布式锁的互斥判断
2. 银行转账的余额一致性
3. 配置的强一致读取
4. 需要线性一致性的场景
5. 领导者选举
→ 特点：需要强一致/线性一致

Gossip 收敛曲线 — 不同 Fanout 和模式对比

面试要点

Fanout=1 时 Push 模式需要约 log₂(N) 轮感染所有节点。Fanout=2 收敛速度提升约 40%。Push-Pull 模式比纯 Push 快约 30%，因为它双向交换信息减少了"盲区"。但 Fanout 越大网络开销越大，Redis 选择 Fanout=1 是在收敛速度和网络开销间的平衡。
