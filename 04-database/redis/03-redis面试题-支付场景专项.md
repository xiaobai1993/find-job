## 一、分布式锁在支付中的应用（必问！你们支付肯定用了）

### 1. 支付场景哪些地方用到了分布式锁？

**答：** （直接说你们项目里的实际场景）
我们支付服务主要在这几个地方用了 Redis 分布式锁：

1. **防重复支付**：同一个用户对同一个订单发起支付，加锁防止重复创建支付单
   ```go
   // 锁的key：pay:lock:out_order_no:{订单号}
   // 同一个订单号同时只能有一个支付请求在处理
   lock := redisson.GetLock("pay:lock:order:" + outOrderNo)
   lock.Lock(10, time.Second)
   defer lock.Unlock()
   ```

2. **餐点库存扣减**：餐点是有限的，多个用户同时抢同一个餐别的餐点，要加锁防止超卖
   - 先加分布式锁，扣减库存成功了再继续支付流程，不然直接返回库存不足

3. **换单操作**：旧单退款+新单支付这个原子操作，加锁防止旧单同时被其他操作修改

4. **回调并发处理**：微信/支付宝可能同时发多次回调过来，加锁保证同一个支付单同时只处理一次回调

---

### 2. 分布式锁失效了怎么办？会不会有问题？

**答：** 这个问题面试官常问，考察你有没有兜底思维

分布式锁只是第一层防护，不是100%可靠的，我们有多层兜底：

1. **第一层：Redis 分布式锁**：挡住大部分并发请求
2. **第二层：数据库唯一索引**：`out_order_no` 唯一索引，就算锁失效了，重复插入支付单数据库会报错，从底层拦住
3. **第三层：状态机判断**：处理回调或者更新支付单状态的时候，带上原状态条件，比如 `UPDATE payment_slip SET status = 6 WHERE id = 123 AND status = 3`，就算锁失效了，也不会重复更新，不会丢更新

> **面试加分项**：分布式锁只是优化性能，减少并发冲突，不是正确性的保证，正确性最终还是靠数据库的约束和乐观锁来保证，Redis挂了或者锁失效了也不会出资金问题。

### 3. 支付业务用分布式锁踩过什么坑？

**答：** 说一两个踩过的坑，显得你有实际经验

**坑1：锁过期时间设置短了，业务没执行完锁就释放了**
- 最开始我们把超时时间设成10秒，但是有时候支付渠道调用慢，超过10秒才返回，锁自动释放了，别的请求进来就有并发问题
- 解决：用 Redisson 的看门狗，自动续期，只要业务还在执行，锁就不会过期

**坑2：加锁粒度太大，影响性能**
- 最图省事直接锁了整个支付入口，所有支付请求都串行，性能上不去
- 解决：缩小锁粒度，按 `out_order_no` 维度加锁，不同订单的支付互不影响，并发就上去了

**坑3：Redis 主从切换锁丢失**
- 有一次主库挂了，锁还没同步到从库，从库切为主库，锁就没了，刚好那时候有并发请求，导致重复回调处理了
- 解决：其实最终也没出问题，因为数据库层有状态机判断兜底，只是多打了点日志，我们也没上红锁，没必要，性能损耗大，有数据库兜底就够了

## 二、延迟队列做支付超时关闭（你们项目里就用了！）

### 4. 支付单超时自动关闭怎么实现的？用 Redis 怎么做？

**答：** 我们用的是双重保证，Redis 延迟队列 + 定时轮询兜底

**Redis ZSet 实现延迟队列：**
1. 创建支付单的时候，把支付单ID作为member，超时时间戳作为score，放到ZSet里
   ```redis
   ZADD pay:timeout:queue 1716624000 支付单ID12345
   ```
2. 后台开个定时任务，每隔1秒扫一次ZSet，拿score小于当前时间的元素，就是已经超时的支付单
   ```redis
   ZRANGEBYSCORE pay:timeout:queue 0 当前时间戳 0 10
   ```
3. 拿到超时的支付单，先删除这个元素（ZREM），删除成功了才去处理关闭逻辑，不然就是别的worker已经拿了
4. 处理逻辑：把支付单状态改成超时关闭，回滚已经支付的子单，发送MQ通知下游

**为什么还要定时轮询兜底？**
- 怕 Redis 挂了或者延迟队列任务丢了，每分钟还有个定时任务直接扫数据库里超时未支付的订单，做兜底处理，保证不会有遗漏

> **你们支付文档里就写了「定时轮询+延迟消息双重保证」，面试的时候直接说这个，说你做过，印象分很高。**

---

### 5. 延迟队列用 Redis 做有什么优缺点？为什么不用 MQ 的延迟消息？

**答：**

| 方案 | 优点 | 缺点 |
|-----|------|------|
| **Redis ZSet 做** | 简单，不用引入额外组件，轻量，可控性高，随时可以查看有多少待处理的 | 高并发下需要自己做幂等、去重，可靠性不如MQ，Redis挂了可能丢消息 |
| **MQ 延迟消息** | 可靠性高，有ACK机制，失败重试，幂等保证 | 依赖MQ的功能，比如RocketMQ有，Kafka就没有，监控排查麻烦 |

**我们为什么用Redis？**
1. 支付超时这个场景对可靠性要求不是100%，我们有数据库轮询兜底，就算丢了也没关系，兜底任务会补上
2. 简单好用，运维成本低，不用专门改MQ配置
3. 支付单量不大，Redis完全扛得住，性能好

## 三、幂等性保证

### 6. 支付回调怎么保证幂等？Redis 怎么配合做？

**答：** 支付回调是最容易有重复的，微信支付宝都可能发好几次，我们有三层幂等：

1. **第一层：Redis 去重**
   - 回调过来先拿回调的唯一流水号去Redis里查有没有处理过
   - `SET pay:callback:processed:{流水号} 1 NX EX 24h`，设置成功就是没处理过，继续处理；设置失败就是已经处理过了，直接返回成功
   - 这一步就能挡住99%的重复回调，不用到数据库查

2. **第二层：状态机判断**
   - 处理的时候先查支付单状态，如果已经是终态（成功/失败/关闭），直接返回成功，不重复处理

3. **第三层：数据库唯一索引**
   - 回调流水号建唯一索引，重复插入直接报错，兜底

> **为什么Redis要设置24小时过期？** 因为回调一般都是短时间重复发，超过24小时的重复回调基本没有，留着也占内存，过期了就算重复来了还有状态机兜底，没问题。

### 7. 同一个用户短时间重复提交支付怎么防？

**答：**
1. **前端防**：用户点击支付按钮后置灰，防止重复点击（但是防不住刷接口的）
2. **接口幂等token**：进入收银台的时候后端生成一个唯一的支付token存在Redis里，提交支付的时候必须带这个token，用了就删掉，同一个token只能用一次
3. **Redis 加锁**：同一个用户+同一个订单号加分布式锁，防止并发请求
4. **数据库唯一索引**：同一个业务单号只能有一个支付单

## 四、缓存的使用

### 8. 支付场景哪些数据适合放 Redis 缓存？哪些不能放？

**答：**

**适合缓存的（读多写少，允许短时间不一致）：**
1. **用户基础信息**：用户ID、名称、身份等级这些，基本不变，缓存起来不用每次查数据库
2. **商户配置信息**：商户支持的支付方式、费率、开关配置这些，读多写少，缓存起来
3. **支付产品配置**：各个支付渠道的开关、参数配置
4. **风控规则**：风控的限流、拦截规则
5. **支付结果的短时间缓存**：支付成功的结果，缓存5分钟，用户重复查询直接返回

**绝对不能缓存的（强一致性要求）：**
1. **支付单的当前状态**：这个绝对不能以缓存为准，必须查数据库，不然支付成功了缓存还是支付中，就出问题了
2. **用户余额、账户金额**：强一致，必须查数据库，或者缓存只做降级用，更新的时候严格删缓存
3. **库存数据**：餐点库存这些，不能以缓存为准，会超卖

---

### 9. 支付场景怎么保证缓存和数据库的一致性？

**答：**
我们用的是 **更新数据库 + 删除缓存 + Canal 监听binlog 兜底删除** 的方案

1. 更新数据的时候，先更数据库，再删缓存
2. 删缓存失败了怎么办？丢到MQ里异步重试，直到删成功
3. 最后兜底：用Canal监听MySQL的binlog，有数据变更就去删除对应的缓存，保证最终一定删掉
4. 强一致的场景（比如余额、支付状态）：直接查数据库，不走缓存，或者缓存只做降级，异常情况下才用

> **核心原则**：支付核心的资金相关数据，永远以数据库为准，缓存只是用来加速查询和降级的，不会用来做判断依据。

## 五、限流

### 10. 支付接口怎么做限流？Redis 怎么实现？

**答：** 支付接口很容易被恶意刷，我们用了多级限流：

**Redis 实现的限流：**
1. **用户维度限流**：同一个用户ID，一分钟内只能发起10次支付请求，多了直接返回请求频繁
   - 用ZSet或者滑动窗口限流算法，Lua脚本保证原子性
2. **IP维度限流**：同一个IP，一分钟只能请求50次，防止脚本刷
3. **商户维度限流**：同一个商户，总QPS限制在200，防止单个商户把系统打挂
4. **接口总限流**：整个支付接口总QPS限制在1000，超过了就返回系统繁忙，保护数据库

**限流算法我们用的是令牌桶算法**，Redisson里自带的RRateLimiter，直接用就行，简单方便。

> **为什么要限流？** 之前遇到过测试环境有人压测没加限压，把数据库打满了，线上就全加上了，尤其是支付回调接口，微信支付宝的回调可能会有流量突刺，限流保证系统不挂。

## 六、其他场景

### 11. 支付对账的时候用 Redis 做过什么优化？

**答：**
对账需要比对第三方流水和我们系统的流水，用集合对比很快：
1. 把第三方的流水号都放一个Set里，我们系统的流水号放另一个Set
2. 用 `SDIFF` 求差集，直接就能找出哪些是对不上的，比循环比对快很多
3. 对账的日活、支付用户数统计，用 HyperLogLog 做，不用存所有用户ID，省内存又快

### 12. Redis 挂了支付服务会不会挂？怎么降级？

**答：** 不会挂，我们有降级方案：
1. 分布式锁降级：Redis挂了，就用数据库行锁（`SELECT ... FOR UPDATE`）代替，虽然性能差一点，但是功能正常
2. 缓存降级：缓存查不到就直接查数据库，慢点而已，不影响业务
3. 延迟队列降级：Redis延迟队列不用了，全靠数据库定时轮询兜底，功能正常
4. 限流降级：Redis挂了就先关闭限流，或者用本地限流，保证业务可用

> **核心思想**：Redis 是辅助组件，不是核心依赖，挂了也不能影响支付主流程，最多性能差一点，资金不能出问题。
