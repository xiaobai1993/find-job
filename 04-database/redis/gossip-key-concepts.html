Gossip 协议关键概念 — 面试必知

1. Gossip 到底在干什么？

公司 100 个人，怎么让所有人都知道"张三离职了"？

方案 A — 中心化广播

  • 找个人站中间喊一嗓子
  • 这个人请假了 → 没人喊了
  • 单点故障

方案 B — Gossip 模式

  • 每人每秒随机找一个同事聊一句
  • "嘿，张三离职了，李四说王五也调岗了"
  • 收到的人继续跟别人聊
  • 没有中心，每个人都是传播者
核心思想

每个节点像"传闲话"一样，定期随机找邻居交换情报。一次聊天不只确认对方活着，还顺带传播其他人的消息。经过 O(log N) 轮传播，所有节点都知道了集群的完整状态。

2. PING 为什么要携带其他节点信息？

如果 PING 只是心跳（只确认对方活着），那每个节点只知道直接通信的邻居状态：

没有 Gossip 段： M1 只知道 M2 还活着 M1 只知道 M3 还活着 但 M1 不知道 M2 知不知道 M3 的情况

有了 Gossip 段之后：

有 Gossip 段： M1 → M2: PING 顺带说: "M3 5秒前还活着" 顺带说: "M4 我15秒没收到回复，怀疑挂了" 一次 PING，"一拖多"，交换了整个集群的情报
传播的信息为什么每个节点需要知道
集群里有哪些节点客户端请求过来，我需要知道该路由给谁
每个节点负责哪些 slotkey 属于哪个 slot，该找哪个节点
哪个节点挂了目标节点挂了，我需要返回重定向或报错
哪个 slave 提升成了 master故障转移后，路由表要更新
最终实现

每个节点都拥有一份完整的集群状态表，能独立做出正确的路由决策。这就是为什么 Redis Cluster 不需要 ZooKeeper 那样的中心协调器——每个节点都是"信息中心"。

3. 哈希槽路由 vs Gossip — 数据层 vs 控制层

这两个是不同层面的东西，不要搞混：

数据层（客户端请求）控制层（集群内部）
干什么处理 SET/GET 这些命令维护集群该由哪些节点组成
协议哈希槽路由 — CRC16(key) % 16384Gossip 协议 — 节点间交换状态
谁参与客户端 → Redis 节点Redis 节点 → Redis 节点
数据层： 客户端发 SET user:123 "hello" → CRC16("user:123") % 16384 = 6918 → 路由到负责 slot 6918 的 M2 → M2 不归它管？返回 MOVED 10.0.0.2:6379 控制层： M1 → M3: PING（我活着，M2 我15秒没收到回复了） → 维护集群状态，故障检测
一句话区分

哈希槽管的是"这个 key 该找谁"，Gossip 管的是"集群里都有谁、谁还活着"。

4. 哨兵模式 vs Cluster 模式

维度哨兵模式（Sentinel）Cluster 模式
架构1主N从 + 独立的哨兵进程多主多从，无哨兵
谁来监控哨兵（独立的第三方）节点自己（通过 Gossip）
谁来故障转移哨兵投票决定节点通过 Gossip PFAIL→FAIL 投票
数据分片不分片，所有数据在 master 上分 16384 个 slot，分布在不同 master
适用规模数据量不大，主要求高可用数据量大，需要水平扩展
核心区别

哨兵模式：多雇了一群"保安"（Sentinel 进程）专门盯着 Redis 主从，谁挂了保安来处理。数据不分片。
Cluster 模式：不要保安了，节点自己通过 Gossip 互相盯着。数据分片到多个 master 上。
Gossip 就是 Cluster 模式下的"哨兵替代品"——不需要额外进程，节点自己搞定监控和故障转移。

5. Gossip 谁和谁通信？

每个节点都参与 Gossip，不区分主从。

注意

从节点参与 Gossip 通信，但投票权只有 master 有。PFAIL→FAIL 的判断只算 master 的票。可以理解为：slave 能"传闲话"，但不能"投票定罪"。

6. 主节点挂了，从节点如何提升为主节点？

找从节点——不用"找"，从节点自己知道

每个从节点通过 Gossip 已经知道自己的 master 是谁、状态如何。master 被 FAIL 后，从节点自己发起选举。

选举流程（4 步）

步骤1：从节点发现 master 被 FAIL │ ▼ 步骤2：从节点等一小会儿（延迟 = 基础延迟 + 排名偏移） 排名越靠前（复制数据越新），等得越短，越先发起选举 │ ▼ 步骤3：从节点向所有 master 发起选举请求 携带自己的 last_epoch 和复制偏移量 │ ▼ 步骤4：每个 master 投票 规则：每个 epoch 每个 master 只能投一票 获得多数 master 同意 → 当选新 master

选举规则（面试重点）

规则说明
谁先发起复制偏移量最大的从节点（数据最新），排名最靠前，延迟最短，最先发起
谁有投票权只有 master 能投票，slave 不参与投票
多数派需要获得超过半数 master 的同意票
一票制每个 config_epoch 每个 master 只能投一票，防止脑裂
config_epoch递增的全局版本号，谁的 epoch 更大谁说了算，解决冲突

为什么复制偏移量最大的优先？

M2 有两个从节点 S2a 和 S2b S2a 复制偏移量 = 1000（收到了 1000 条写命令） S2b 复制偏移量 = 800（落后了 200 条） → S2a 排名靠前，延迟更短，先发起选举 → 因为 S2a 数据更全，丢数据最少

两个从节点同时发起怎么办？

config_epoch 保证不会冲突：从节点发起选举时自增 epoch，master 如果已给相同或更高 epoch 投过票就拒绝。先到先得。

完整时间线

T+15s

7. 为什么有 Gossip 还需要 Raft？

Gossip 有一个根本代价——它只能做到最终一致。

同样的故障，两种协议的反应速度

Gossip 反应（15 秒级）

M2 在 T+0s 宕机 T+0s ~ T+15s 窗口期： M1 还认为 M2 活着 → 继续路由给 M2 → 超时/失败 M3 还认为 M2 活着 → 继续路由给 M2 → 超时/失败

集群状态不一致，有人觉得活着有人觉得死了

Raft 反应（毫秒级）

Leader M2 宕机 T+0.1s M1、M3 心跳超时（几百毫秒） T+0.2s M1、M3 立刻发起选举 T+0.3s 获得多数票，新 Leader 产生 T+0.3s 全集群立刻达成一致

不存在"有人觉得活着有人觉得死了"的窗口期

核心区别就一个：一致性强度

GossipRaft
一致性最终一致（有窗口期不一致）强一致（任何时候都是最新值）
故障检测15 秒级毫秒级
脑裂风险靠 config_epoch 事后解决多数派机制事前防止
网络开销每秒 N 次 PING，很轻每次写要多数派确认日志，较重

选择标准：集群状态不一致的那几秒，能不能接受？

场景选择原因
Redis ClusterGossip缓存而已，15 秒窗口期可以接受，轻量更重要
etcd / ZooKeeperRaft存的是配置、锁、选主，差一秒都不行
TiKVRaft数据库，写进去的数据不能丢不能不一致
ConsulGossip + Raft成员管理用 Gossip（可以等），共识用 Raft（不能等）

最精辟的理解

Gossip 管的是"谁在集群里"——晚几秒知道无所谓

Raft 管的是"数据写没写成功"——少一秒都不行

Redis Cluster 用 Gossip 是因为缓存场景用轻量级协议够了，不值得背上 Raft 的开销。如果你存的是银行余额，那 15 秒内两个节点对同一笔交易做出不同判断，钱就错了。

8. 面试一句话总结

三句话记住 Gossip

1. Gossip 是所有节点参与的"传闲话"协议，一次 PING 不只心跳，还顺带传播 1/3 节点状态。

2. 主节点挂了，数据最新的从节点最先发起选举，获得多数 master 同意就提升为新 master，config_epoch 防脑裂。

3. Gossip 只能最终一致，适合缓存/成员管理等可以等几秒的场景；需要强一致就用 Raft。
