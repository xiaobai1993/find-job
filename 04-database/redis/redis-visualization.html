底层切换规律

Redis 的数据结构会根据元素数量和大小自动切换底层实现：
小数据量用紧凑结构（ziplist/intset），省内存；元素多了自动升级到哈希表/跳表，保证性能。

② RDB vs AOF 持久化

两种持久化各有优缺点，生产推荐混合使用

📸 RDB — 快照

⏰定时触发（bgsave / 满足条件自动触发）
🍴fork子进程生成快照（CoW，不阻塞主进程）
💾生成 dump.rdb 二进制文件
🚀恢复：直接加载二进制，快！
文件小（压缩） 恢复快 最多丢分钟级数据 fork时有短暂停顿

📝 AOF — 日志

✍️每条写命令执行后追加到文件
💽刷盘策略：always/everysec/no
♻️BGREWRITEAOF 定期重写压缩文件
🔄恢复：重放所有命令，慢
最多丢1秒数据 可读性好 文件大 恢复慢

点击演示按钮查看过程

混合持久化（Redis 4.0+，推荐）

AOF重写时，文件开头写入RDB内容（快照），后面追加增量的AOF命令。
恢复时：先加载RDB部分（快），再重放AOF增量（少），两全其美！

[RDB二进制内容] ← 快照，快速恢复到某个时间点
SET key1 val1 ← 快照之后的增量AOF命令
INCR counter
HSET order status paid
配置：aof-use-rdb-preamble yes
刷盘策略（AOF）丢数据风险性能推荐场景
always（每次写都刷）几乎不丢最慢极重要数据，极少用
everysec（每秒刷）最多丢1秒好推荐，平衡安全和性能
no（交给OS）可能丢数秒最快不关心数据安全

③ 缓存三大问题

穿透 / 击穿 / 雪崩 — 面试必考，一定要能区分并说出解决方案

🔍 缓存穿透
💥 缓存击穿
❄️ 缓存雪崩
三者区别一句话

穿透 = 查询不存在的key → 每次都打DB（恶意攻击）
击穿 = 一个热点key过期 → 瞬间大量请求打DB（突然热点）
雪崩 = 大量key同时过期 / Redis宕机 → DB被全打崩（规模更大）

哨兵模式 vs Cluster 集群

🛡️ 哨兵（Sentinel）

3个哨兵节点 + 1主N从。哨兵监控主库，主库故障自动选新主（raft投票），通知客户端新地址。
适合：数据量不大但需要高可用。不解决数据分片问题。

🌐 Cluster 集群

16384个哈希槽分配给N个主节点，key通过CRC16取模找槽。每个主节点有若干从节点。
适合：数据量大需要水平扩容，同时具备高可用。

单线程为什么快？

⚡
纯内存访问
内存读写 ~100ns，磁盘随机IO ~10ms，差10万倍
🚫
无锁竞争
单线程不需要加锁，省去锁竞争、上下文切换开销
📡
epoll IO复用
一个线程处理万级连接，不需要线程池
🏎️
高效数据结构
SDS、跳表、压缩列表专门优化，O(1)~O(logN)
单线程的缺点

慢命令会阻塞所有其他命令！比如 KEYS *（全量扫描）、大key的DEL、SORT复杂排序。
线上 禁止用 KEYS *，改用 SCAN 游标分批扫描。大key删除用 UNLINK（异步删除）。
