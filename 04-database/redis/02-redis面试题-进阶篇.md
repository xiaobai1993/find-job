# Redis 面试题 - 进阶篇

> 重点：缓存三大问题、分布式锁、集群、高可用、性能优化

---

## 一、缓存三大问题（必考！）

### 1. 什么是缓存穿透？怎么解决？

**答：**
**问题描述**：查询一个数据库里根本不存在的数据，缓存里也没有，每次请求都穿透到数据库，恶意攻击的话数据库压力大就挂了。
比如攻击的人用大量不存在的订单号查支付单，缓存查不到就每次都查数据库。

**解决方案：**

1. **缓存空值**：查数据库不存在的话，也在缓存里存个空值，设置个短的过期时间（比如5分钟），下次再查就直接返回空，不用查数据库
   - 优点：简单
   - 缺点：占内存，可能缓存和数据库短时间不一致

2. **布隆过滤器 (Bloom Filter)**：把所有存在的key都提前放到布隆过滤器里，查询的时候先过布隆过滤器，说不存在就直接返回，不用查缓存和数据库
   - 优点：省内存，适合大数据量
   - 缺点：有误判率，布隆过滤器说存在的可能不存在，说不存在的一定不存在；删除困难
   - 适合：数据基本不怎么变的场景，比如用户ID、订单号集合

3. **接口层加校验**：参数合法性校验，比如订单号格式不对直接拦截，不用到后面查库

> **支付场景用什么？** 支付单查询的话，布隆过滤器 + 参数校验就够了，订单号格式是固定的，先校验格式，再过布隆过滤器，基本上能挡住大部分恶意请求。

---

### 2. 什么是缓存击穿？怎么解决？

**答：**
**问题描述**：某一个热点key，刚好在某一瞬间过期了，这时候大量并发请求同时过来，都没命中缓存，一起去查数据库，数据库压力瞬间打爆。
比如微信支付回调的接口，某个热门商户的支付结果刚好缓存过期了，瞬间几千个请求都去查数据库。

**解决方案：**

1. **加互斥锁（分布式锁）**：缓存失效的时候，不是所有人都去查数据库，先拿分布式锁，拿到锁的人去查数据库并回写缓存，其他人等一会再查
   ```java
   // 伪代码
   public Object get(String key) {
       Object value = redis.get(key);
       if (value != null) return value;

       // 缓存失效，加锁
       String lockKey = "lock:" + key;
       if (redis.set(lockKey, "1", "NX", "EX", 10)) {
           try {
               value = db.query(key);
               redis.set(key, value, 3600);
               return value;
           } finally {
               redis.del(lockKey);
           }
       } else {
           // 没拿到锁，休眠100ms再查
           Thread.sleep(100);
           return get(key);
       }
   }
   ```
   - 优点：简单，一致性好
   - 缺点：有性能损耗，线程等待

2. **热点key永不过期**：特别热点的key不设置过期时间，后台异步更新缓存，适合对一致性要求不是特别高的场景
3. **提前预热**：热点数据提前加载到缓存里，过期时间加个随机值，避免同一时间大量key同时过期

---

### 3. 什么是缓存雪崩？怎么解决？

**答：**
**问题描述**：大面积的缓存key在同一时间全部过期，或者Redis直接挂了，所有请求都打到数据库，数据库直接崩了。
比击穿更严重，击穿是一个热点key，雪崩是大量key或者整个缓存都不可用。

**解决方案：**

1. **过期时间加随机值**：设置key的过期时间的时候，不要都设成一样的，比如都设成1小时+随机的几分钟，避免同一时间大量过期
   ```java
   // 不要这么写：都设置3600秒
   redis.set(key, value, 3600);
   // 改成这样：基础时间 + 随机几分钟
   redis.set(key, value, 3600 + RandomUtils.nextInt(0, 300));
   ```

2. **Redis 集群部署**：做高可用，主从 + 哨兵 + 集群，避免单点故障，Redis 挂了还有其他节点顶上去

3. **服务降级 & 熔断**：缓存不可用的时候，接口直接降级返回默认值或者错误，不要所有请求都去查数据库，用Hystrix或者Sentinel做熔断，保护数据库

4. **多级缓存**：本地缓存（Caffeine、Guava Cache） + Redis 缓存，本地缓存扛一部分，Redis 挂了还有本地缓存顶着

## 二、缓存一致性问题

### 4. 缓存和数据库双写一致性怎么保证？先更数据库还是先删缓存？

**答：** 这是高频面试题！没有完美的方案，都是权衡，要结合业务说。

**四种方案对比：**

| 方案 | 一致性 | 性能 | 问题 |
|-----|-------|------|------|
| 先更数据库，再更缓存 | 差 | 好 | 并发下A更数据库，B更数据库，B更缓存，A再更缓存 → 缓存是旧的脏数据 |
| 先更缓存，再更数据库 | 最差 | 好 | 数据库更失败，数据完全不一致 |
| **先删缓存，再更数据库** | 一般 | 好 | 删完缓存，还没更数据库，另一个线程读，把旧值写回缓存 → 脏数据 |
| **先更数据库，再删缓存**（推荐） | 好 | 好 | 概率极低的脏数据：缓存刚好过期，A读的时候缓存没了，去读数据库拿到旧值，这时候B更完数据库删了缓存，A再把旧值写回缓存 → 这个概率非常非常低，因为写数据库比读慢多了 |

**通用最佳实践：先更数据库，再删缓存**

**那删缓存失败了怎么办？**
- **方案1：重试机制**：删缓存失败了，重试几次，或者丢到MQ里异步重试
- **方案2：订阅MySQL binlog**：用Canal监听MySQL的binlog，有变更就去删对应的缓存，保证最终一致性
  > 这个方案最靠谱，不管业务代码里删没删成功，binlog一定会来，最终缓存一定是对的

> **支付场景怎么选？**
> 支付对一致性要求高，就用更数据库 + 删缓存 + binlog 异步兜底的方案，最终一致。支付状态这种强一致的，就直接查数据库，或者缓存只做降级用，不以缓存为准。

## 三、分布式锁（必考！你们支付肯定用了）

### 5. Redis 分布式锁怎么实现？有什么坑？

**答：**

**最基础的实现：**
```redis
SET lock_key unique_value NX EX 30
```
- `NX`：只有key不存在的时候才设置成功，就是加锁成功
- `EX 30`：自动过期30秒，防止锁释放失败死锁
- `unique_value`：每个客户端加锁的时候生成唯一值，解锁的时候要判断是不是自己加的锁，不能删别人的锁

**解锁的时候必须用 Lua 脚本保证原子性：**
```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```
不能先get判断再del，不是原子操作，中间可能锁过期了别人加上了，你给人删了。

---

**常见的坑（一定要说出来，加分！）：**

1. **锁过期了，业务还没执行完**
   - 问题：业务执行时间超过了锁的过期时间，锁自动释放了，别的线程拿到锁，并发问题就来了
   - 解决：**看门狗（Watch Dog）**，加锁成功后，后台开个定时线程，每隔一段时间（比如过期时间的1/3）就去给锁续期，Redisson 就是这么实现的

2. **锁不可重入**
   - 问题：同一个线程想重复加同一把锁，加不上
   - 解决：用 Hash 结构存，key 是锁名，field 是客户端唯一ID + 线程ID，value 是加锁次数，加锁的时候次数+1，解锁的时候次数-1，到0才释放锁，Redisson 的可重入锁就是这么做的

3. **主从切换锁丢失**
   - 问题：Redis 主从架构，加锁成功后主库挂了，锁还没同步到从库，从库升级成主库，别人就可以再加锁
   - 解决：**红锁（RedLock）**，向 N/2 + 1 个独立的 Redis 节点都加锁，都成功才算加锁成功，过半就不会丢，但是性能差，一般业务其实不用，用数据库兜底就行
   - **面试加分项**：其实大部分业务不需要红锁，锁丢了还有数据库唯一索引兜底，支付场景最终还是靠数据库保证一致性，分布式锁只是减少并发，不是100%可靠的。

4. **加锁和设置过期时间不是原子操作**
   - 问题：先SETNX加锁成功了，还没设过期时间进程挂了，锁就永远不会释放，死锁
   - 解决：用 `SET key value NX EX 过期时间` 一条命令原子执行，别分开写

---

### 6. Redisson 原理知道吗？

**答：** 加分项，实际开发都用 Redisson，很少自己手写

**核心特性：**
1. **可重入锁**：Hash结构存加锁次数，支持同一个线程多次加锁
2. **看门狗自动续期**：加锁成功后台启动定时任务，每隔10秒（默认锁30秒，1/3时间）检查一下，还持有锁就续期到30秒，业务执行多久续多久
3. **Lua 脚本保证原子性**：加锁、解锁、续期都是用Lua脚本执行的，保证原子
4. **支持多种锁**：公平锁、读写锁、红锁、联锁、信号量、闭锁等等

> **支付场景关联**：你们餐点库存校验、重复支付检查用的分布式锁应该就是 Redisson 对吧？实际项目里不要自己手写分布式锁，坑太多，直接用 Redisson 就好。

## 四、高可用 & 集群

### 7. Redis 主从复制原理？

**答：**
和 MySQL 主从复制类似，也是异步复制：

1. **全量同步**：从库第一次连接主库，或者断开重连跟不上了，主库生成RDB快照发给从库，从库加载进去，同步完成
2. **增量同步**：全量同步完成后，主库后续的写命令都异步发给从库，从库执行，保持和主库一致

**特点：**
- 主库负责写，从库负责读，读写分离，提高并发
- 异步复制，主从有延迟，主库挂了可能丢数据
- 一个主库可以有多个从库，从库也可以有从库，级联复制

---

### 8. 哨兵模式 (Sentinel) 是什么作用？

**答：**
哨兵是用来做 Redis 主从自动故障转移的，解决主库挂了需要手动切的问题。

**核心功能：**
1. **监控**：哨兵不断检查主从节点是不是正常活着
2. **自动故障转移**：主库挂了，哨兵会选举出一个从库升级成新的主库，其他从库指向新主库
3. **通知**：故障转移完成了通知客户端新的主库地址
4. **配置中心**：客户端连接哨兵，从哨兵拿主库地址，不用写死IP

**选举机制：**
- 哨兵集群一般部署3个或5个节点（奇数，方便选主）
- 超过半数的哨兵认为主库挂了（客观下线），才会开始故障转移
- 从库选举优先级：优先级高的 → 复制偏移量大的（数据最新） → run_id小的

---

### 9. Redis Cluster 集群原理？

**答：**
哨兵模式还是一主多从，写能力还是只有一个主库，数据量太大单实例放不下，就用 Cluster 集群。

**核心原理：**
- **哈希槽 (Hash Slot)**：一共 16384 个槽，每个key通过 `CRC16(key) mod 16384` 计算属于哪个槽，每个节点负责一部分槽
- 比如3主3从集群，节点1负责0-5460，节点2负责5461-10922，节点3负责10923-16383
- **去中心化**：每个节点都知道其他节点负责哪些槽，客户端连任意一个节点都可以查询
- **故障转移**：每个主节点都有从节点，主库挂了从节点自动顶上去，和哨兵类似

**为什么是16384个槽？**
- 作者回答的：心跳包要带槽信息，16384个刚好2KB，太大了心跳包占带宽，太小了不够分，一般集群节点不会超过1000个，16384足够了。

## 五、性能优化

### 10. 大key问题怎么发现？怎么解决？

**答：**
**大key的危害：**
- 读写大key耗时久，阻塞Redis
- 内存不均匀，集群环境下节点内存倾斜
- 大key删除的时候会阻塞Redis很久
- 网络传输慢，超时多

**怎么发现：**
1. `redis-cli --bigkeys` 命令扫描，但是会扫整个库，生产环境小心用，可能会卡
2. 用`SCAN`命令分批扫描，自己判断大小
3. 第三方工具：Redis 4.0+ 的 `MEMORY USAGE key` 命令看key占多大内存
4. 运维监控告警

**怎么解决：**
1. **拆分大key**：大hash拆成多个小hash，大list拆成多个小list，存的时候加个后缀
2. **大value不要放Redis**：太大的value比如超过10KB，考虑存MongoDB或者对象存储，Redis只存key和地址
3. **异步删除**：4.0+ 有 `UNLINK` 命令，异步删除大key，不阻塞主线程

---

### 11. 热key问题怎么发现？怎么解决？

**答：**
**热key的危害：** 某一个key访问量特别大，都打到同一个Redis节点，节点压力大，甚至打挂。
比如大促的时候某个爆款商品的库存，或者某个热点商户的配置。

**怎么发现：**
1. 客户端统计：SDK层面统计访问频率高的key
2. Redis 4.0+ 有 `hotkeys` 特性，开启后可以自动发现热key
3. 代理层或者监控统计

**怎么解决：**
1. **本地缓存**：热key在应用层用本地缓存（Caffeine、Guava）存一份，不用每次都查Redis，减轻Redis压力
2. **热key拆分复制**：把一个热key复制成多个副本，比如`key_0、key_1、key_2...key_9`，都存一样的值，查询的时候随机选一个，把流量分散到不同节点上
3. **集群节点扩容，分散热点**

---

### 12. Redis 为什么单线程还能扛那么高并发？

**答：** 这个可以展开说
1. 纯内存操作，本来就快
2. IO多路复用epoll模型，非阻塞IO，一个线程就能处理几万并发连接
3. 单线程避免了多线程上下文切换和锁竞争的开销，很多人以为多线程一定快，其实在纯内存操作、没有阻塞的场景下，单线程反而更快，没有切换开销
4. 高效的数据结构，底层都是优化过的，跳表、压缩列表这些，操作复杂度低
