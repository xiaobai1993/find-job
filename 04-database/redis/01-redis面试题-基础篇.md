# Redis 面试题 - 基础篇

> 结合支付场景，覆盖面试高频考点

---

## 一、基础概念

### 1. Redis 为什么快？单线程为什么性能还这么高？

**答：** 面试必问第一题

**快的四个核心原因：**
1. **纯内存操作**：所有数据都存在内存里，读写都是纳秒级的
2. **单线程模型**：避免了多线程的上下文切换和锁竞争的开销，反而更快
3. **IO 多路复用**：epoll 模型，非阻塞 IO，一个线程处理大量并发连接
4. **高效的数据结构**：底层是简单动态字符串、跳表、压缩列表这些，性能很高

> **注意**：Redis 6.0 以后有多线程了，但是多线程只是用来处理网络 IO 和数据解析，命令执行还是单线程的，核心逻辑还是单线程。

---

### 2. Redis 支持哪些数据结构？分别适用什么场景？

**答：** 基础 5 种 + 高级 3 种，每个都要能说出来对应的场景

| 数据类型 | 底层结构 | 适用场景 | 支付场景例子 |
|---------|---------|---------|------------|
| **String** | 简单动态字符串 SDS | 最常用，存字符串、数字、二进制 | 存用户余额缓存、分布式锁的value、支付结果缓存、token |
| **Hash** | 压缩列表 / 哈希表 | 存对象类型的字段，比string省空间 | 存支付单的基本信息（金额、状态、用户ID），不用序列化整个对象 |
| **List** | 压缩列表 / 双向链表 | 消息队列、列表、栈 | 简单的任务队列，支付回调失败重试队列 |
| **Set** | 哈希表 | 去重、交集并集差集、抽奖 | 去重：同一个订单的重复回调直接丢弃；统计今天支付的用户ID去重 |
| **ZSet (Sorted Set)** | 跳表 + 哈希表 | 有序列表、排行榜、延迟队列 | **支付超时检查**：score存支付超时时间戳，定时扫描超时的订单关闭；排行榜 |
| **Bitmap** | 基于string实现 | 位运算，大量布尔值统计 | 统计用户连续签到、日活统计，省空间 |
| **HyperLogLog** | 基数统计 | 大数据量去重统计，有误差(0.81%) | 统计支付页UV，不用存所有用户ID，省内存 |
| **Geo** | 基于zset实现 | 地理位置查询 | 附近的食堂、门店距离计算（美餐业务刚好能用） |
| **Stream** | 5.0+新增 | 专业的消息队列，支持消费组、ACK | 比list更可靠的消息队列，支付异步任务处理 |

### 3. Redis 和 Memcached 区别？为什么选 Redis 不选 Memcached？

**答：**

| 维度 | Redis | Memcached |
|-----|-------|-----------|
| **数据类型** | 支持多种丰富的数据结构 | 只支持简单的 key-value 字符串 |
| **持久化** | 支持 RDB 和 AOF 持久化，宕机不丢数据 | 纯内存，不支持持久化，重启就没了 |
| **内存利用率** | 有压缩列表等优化，更高 | 简单，相对低 |
| **集群** | 原生支持集群模式 | 只能客户端分片 |
| **功能** | 支持发布订阅、Lua脚本、事务、过期策略 | 功能简单 |
| **多线程** | 6.0+支持多线程IO | 原生多线程 |

> **支付场景选Redis的原因很简单**：需要持久化，不能重启缓存就全没了；需要zset做延迟队列、hash存对象，这些Memcached都做不了。

## 二、持久化

### 4. Redis 持久化 RDB 和 AOF 的区别？优缺点？

**答：** 必考！

| 维度 | RDB | AOF |
|-----|-----|-----|
| **是什么** | 某一时刻的内存数据快照，二进制文件 | 记录所有写命令的日志，文本格式 |
| **触发方式** | 手动 save/bgsave，自动按配置的时间间隔 | 每次写命令都追加，或者每秒刷盘 |
| **恢复速度** | 快，直接加载二进制文件 | 慢，要重放所有命令 |
| **文件大小** | 小，压缩过 | 大，时间长了会很大 |
| **数据安全性** | 差，最后一次快照后的数据会丢 | 好，最多丢1秒数据 |
| **对性能影响** | fork子进程生成快照，fork的时候会卡一下 | 小，只是追加写日志 |
| **重写机制** | 没有 | 有 BGREWRITEAOF 重写，压缩AOF文件大小 |

---

### 5. 生产环境怎么选持久化策略？支付场景用什么？

**答：**
- **数据不敏感、丢了没关系的**：可以只用RDB，恢复快
- **核心数据、不能丢的**：RDB + AOF 混合开启，既保证数据安全，恢复也快
- **Redis 4.0+ 有混合持久化**：AOF重写的时候把RDB内容放在AOF开头，既有AOF的安全性，恢复又快，推荐开启

> **支付场景用什么？** 缓存的话可以只开AOF每秒刷盘就行，就算丢了也可以从数据库查回来。如果是存重要数据（比如分布式锁、延迟队列），就开混合持久化，保证重启后数据不丢，不影响业务。

## 三、过期删除 & 内存淘汰

### 6. Redis 过期键的删除策略？

**答：** 三种策略结合使用

1. **定时删除**：设置键过期的时候就创建个定时器，到时间立刻删
   - 优点：内存释放及时
   - 缺点：占用CPU，太多过期键的时候CPU压力大，Redis没怎么用这个

2. **惰性删除**：键过期了不主动删，等你去访问的时候才判断过期了就删掉
   - 优点：不占CPU
   - 缺点：大量过期键没人访问的话一直占内存，内存泄漏

3. **定期删除**：每隔一段时间（默认100ms）随机抽一些设置了过期的键检查，过期了就删
   - 平衡了CPU和内存，是Redis的主要策略

> **Redis 实际用的是：惰性删除 + 定期删除 结合**

---

### 7. 内存满了怎么办？内存淘汰策略有哪些？

**答：** 内存超过 `maxmemory` 设置的阈值就会触发淘汰策略

**8 种淘汰策略（Redis 4.0+）：**

| 策略 | 说明 |
|-----|------|
| **noeviction** | 默认策略，不淘汰，新写入直接报错 |
| **allkeys-lru** | 所有键中，淘汰最近最少使用的（最常用） |
| **allkeys-lfu** | 所有键中，淘汰使用频率最低的（4.0+新增） |
| **allkeys-random** | 所有键中随机淘汰 |
| **volatile-lru** | 只在设置了过期时间的键里，淘汰最近最少使用的 |
| **volatile-lfu** | 只在设置了过期时间的键里，淘汰使用频率最低的 |
| **volatile-random** | 只在设置了过期时间的键里随机淘汰 |
| **volatile-ttl** | 只在设置了过期时间的键里，淘汰最早要过期的 |

> **支付场景选什么？** 一般缓存都选 `allkeys-lru`，把不常用的缓存淘汰掉，留热点数据在内存里。如果是做分布式锁、延迟队列这些不能被淘汰的，就用 `noeviction`，或者把重要的key不设置过期时间，用volatile系列策略。

## 四、其他基础

### 8. Redis 事务是什么？和 MySQL 事务有什么区别？

**答：**
Redis 事务是把一组命令打包，按顺序一次性执行，中间不会被其他命令打断。

**三个命令：**
- `MULTI`：开启事务
- 命令入队
- `EXEC`：执行事务
- `DISCARD`：取消事务

**和 MySQL 事务的区别：**
1. **没有原子性保证**：Redis 事务只是按顺序执行，中间有命令失败了前面的也不会回滚，后面的还继续执行，不支持回滚
2. **没有隔离级别**：就是个命令队列，执行的时候一起执行，不存在脏读不可重复读这些问题
3. **本质是个批处理**：主要是减少网络RTT，把多个命令一次发过去执行，不是为了原子性

> **要原子性用什么？** 用 Lua 脚本，Lua 脚本是原子执行的，比事务好用。
