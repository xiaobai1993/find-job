面试关键点

Server 层的组件是所有存储引擎共享的，执行器通过统一的 handler API 调用引擎。所以 一条 SQL 的解析、优化在 Server 层，而数据的读写、事务、锁在引擎层。binlog 在 Server 层，redo/undo log 在引擎层。

以 UPDATE accounts SET balance = balance - 100 WHERE id = 1 为例，逐步演示

步骤 0/12

客户端 TCP 连接到 MySQL，连接器验证用户名密码，从权限表加载权限。连接建立后保持，show processlist 可见。

词法分析识别 UPDATE/accounts/SET/balance/WHERE/id 等关键字和标识符；语法分析构建 AST 语法树。SQL 有语法错误在此报 1064。
Server 层
3
预处理器 — 语义检查
检查表 accounts 是否存在、列 balance 是否存在、用户是否有 UPDATE 权限。解析阶段会同时展开 * 和视图。
Server 层
4
优化器 — 选择执行计划
决定走 id 主键索引还是全表扫描。此处 id=1 有主键索引，选择 index_read 精确匹配。生成执行计划。
Server 层CBO 优化
5
执行器 — 调用引擎读取数据页
执行器调用 InnoDB handler 的 index_read() 接口。InnoDB 先查 Buffer Pool，命中直接返回；未命中则从磁盘 .ibd 文件加载 16KB 数据页到 Buffer Pool。
Server→引擎Buffer Pool
6
InnoDB — 记录 Undo Log (旧值)
将 id=1 的旧行 (balance=500) 写入 Undo Log。用于回滚和 MVCC 版本链。Undo Log 写入 Buffer Pool 中的 undo 页，同时产生 redo。
引擎层Undo Log
7
InnoDB — 更新 Buffer Pool 中的数据页
在内存中修改 balance = 400。此时数据页变为脏页（内存与磁盘不一致）。数据页标记为 dirty，加入 Flush List。
引擎层脏页内存操作
8
InnoDB — 写 Redo Log (WAL)
将修改记录写入 Log Buffer，再根据 innodb_flush_log_at_trx_commit 策略刷盘：
• =1(默认)：每次提交 fsync 到 redo file → 不丢数据
• =2：每次提交 write 到 OS cache → OS 崩溃丢 1s
• =0：每秒刷 → 丢 1s 数据
引擎层Redo LogWAL
9
Server 层 — 写 Binlog
执行器写入 binlog。记录逻辑变更(行变更或语句)。用于主从复制和 PITR 点恢复。binlog 写入 OS cache 后 fsync（sync_binlog 控制）。
两阶段提交：先 prepare(redo)，再写 binlog，最后 commit(redo)。
Server 层Binlog2PC
10
InnoDB — Commit (Redo 记录 commit 状态)
Redo log 写入 commit 标记，事务正式提交。两阶段提交完成。客户端收到 "OK" 响应。此时数据仍在 Buffer Pool 脏页中，尚未落盘。
引擎层Redo Log2PC完成
11
后台线程 — 脏页刷盘 (随机写)
Page Cleaner Thread 或 LRU 淘汰时，将 Buffer Pool 中的脏页 pwrite() 写回磁盘 .ibd 文件。脏页落盘是随机写，因为不同脏页属于不同的表空间位置，无法顺序。
刷盘前先写 Doublewrite Buffer 防页撕裂。
后台线程随机写磁盘
12
Checkpoint — 推进 Redo Log
脏页落盘后，InnoDB 推进 checkpoint，标记这部分 redo log 可以被覆盖。write pos 和 checkpoint 之间的距离就是可用的 redo 空间。

SELECT vs UPDATE 关键区别

SELECT 不涉及 Undo/Redo/Binlog 写入。SELECT 最大的性能变量是是否命中 Buffer Pool。未命中则产生磁盘随机读(IO 瓶颈)。

面试必答

Buffer Pool 的大小直接决定数据库性能。缓存命中率是关键指标 (SHOW STATUS LIKE 'Innodb_buffer_pool_read%')。命中率 < 99% 说明内存不够，需要扩容或优化 SQL。

⑥ 顺序写 vs 随机写 — 核心问题解答

为什么 Redo Log 是顺序写？脏页落盘是随机写？这到底是怎么回事？

写入位置永远在文件末尾追加，不需要寻址。磁盘磁头(或 SSD 控制器)不用来回移动。1→2→3→4... 连续写入。

为什么是顺序写？

Redo Log 是固定大小的两个文件循环使用。写入指针(write pos)永远往后走，写满了就跳到另一个文件开头。不需要找特定位置，只在 write pos 处追加。这就是"顺序写"。

脏页分布在不同表空间的不同位置，写入时需要 seek 到指定位置。2→5→7→10... 跳跃式写入。

为什么是随机写？

每个脏页属于不同的表(.ibd 文件)的不同 B+ 树位置。页A在偏移量 0x1000，页B在 0xF0000，页C在另一个文件。Flush List 中的脏页物理位置毫无规律，必须 seek 到各自位置写入。

到底怎么回事？深入理解

核心问题：WAL (Write-Ahead Logging) 的精髓

MySQL 的设计目标是：尽量减少事务提交时的磁盘 IO 开销。

如果没有 Redo Log，事务提交时必须把修改过的所有数据页刷盘才能保证持久性。由于数据页散落在磁盘各处，这就是多次随机写，非常慢。

有了 Redo Log，事务提交只需：追加写 redo log = 1次顺序写。数据页留在 Buffer Pool 中，之后慢慢刷盘（后台线程异步随机写）。

性能对比
操作写入方式机械硬盘SSD原因
Redo Log 写入顺序写~100 MB/s~500 MB/s追加，无需寻址
数据页落盘随机写~200 IOPS~50k IOPS每个页位置不同，需 seek
事务提交(无redo)多次随机写极慢较慢每个修改页都要 fsync
事务提交(有redo)1次顺序写快很快只需 fsync redo block
一句话总结

WAL 的本质：用一次顺序写替代多次随机写。事务提交只写 redo log (顺序)，数据页延迟异步落盘 (随机)。crash 后用 redo 重放恢复。

为什么顺序写比随机写快？

机械硬盘 (HDD)：

顺序写只需磁头移动一次，后续数据连续写入。随机写每次都要寻道(seek ~5-10ms) + 旋转延迟(~4ms @7200RPM)。一次 seek 就够顺序写好几 MB 了。

固态硬盘 (SSD)：

SSD 没有机械部件，但顺序写仍然更快：① SSD 以页(4KB)为单位写，必须先擦除块(256KB)；② 顺序写减少写放大(FTL 映射更高效)；③ 随机写触发更多的垃圾回收(GC)。顺序写可利用更大的内部并行度。

面试高频追问

Q: 如果 redo log 写满了怎么办？
A: write pos 追上 checkpoint 时，必须停下来将部分脏页刷盘，推进 checkpoint 腾出空间。这时用户线程会被阻塞，性能下降。所以 innodb_log_file_size 要设合理(通常 1-4GB)。

补充：Doublewrite Buffer — 为什么脏页刷盘还需要双写？

InnoDB 的页大小是 16KB，而操作系统/fs 的原子写入单位通常是 4KB(或更小)。如果写 16KB 到一半断电，就会出现页撕裂(partial write)——数据页损坏，无法通过 redo log 恢复（因为 redo 记录的是"对某个页的修改"，页本身坏了就无法重放）。

先顺序写一份到 Doublewrite Buffer(连续 2MB，顺序写快)，再随机写到各自的 .ibd 位置。如果第②步写到一半断电，crash 后从 Doublewrite 恢复完整页。

注意

Doublewrite 增加了约 5-10% 的写开销，但对数据安全至关重要。某些场景(如 ZFS 文件系统保证原子写)可以关闭 innodb_doublewrite=0。

完整 IO 流程总结

① 事务修改数据 → 写入 Buffer Pool (内存，微秒级)
② 记录 Undo Log → 写入 Buffer Pool 中的 undo 页 (内存)
③ 写 Redo Log → Log Buffer → fsync 到 redo log file (顺序写，毫秒级) ← 事务提交的关键路径
④ 写 Binlog → fsync 到 binlog file (追加写，Server 层)
⑤ 后台线程异步刷脏页 → Doublewrite Buffer → .ibd 文件 (随机写，后台异步)
⑥ Checkpoint 推进 → 释放 redo log 空间
面试一句话

事务提交只做一次顺序写 redo log，数据页留在内存延迟刷盘。这把事务延迟从"多次随机写"降到"一次顺序写"。这就是 WAL 的价值。脏页落盘是随机写，但不影响事务响应时间——它是后台异步做的。
