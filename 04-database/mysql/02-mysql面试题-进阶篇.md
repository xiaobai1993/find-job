## 一、MVCC 原理（必考！）

### 1. 什么是 MVCC？底层原理？

**答：**
MVCC (Multi-Version Concurrency Control) 多版本并发控制，是 InnoDB 实现隔离级别的核心机制，让读写不冲突，提高并发性能。

**底层依赖三个东西：**
1. **隐藏列**：每行数据都有
   - `DB_TRX_ID`：最后修改这行的事务 ID
   - `DB_ROLL_PTR`：回滚指针，指向上一个版本的 undo log
   - `DB_ROW_ID`：隐式主键（没定义主键的时候用）

2. **undo log 版本链**：每次修改都把旧版本写入 undo log，通过回滚指针串成一条链

3. **Read View（读视图）**：事务开始查询时生成，用来判断哪个版本对当前事务可见

---

### 2. Read View 的四个核心属性？可见性判断规则？

**答：**

**Read View 四个属性：**
- `m_ids`：生成 Read View 时，当前所有活跃（未提交）的事务 ID 列表
- `min_trx_id`：活跃事务里最小的 ID
- `max_trx_id`：下一个要分配的事务 ID（= 最大活跃 ID + 1）
- `creator_trx_id`：当前创建 Read View 的事务 ID

**可见性判断规则（按顺序判断）：**
1. 如果行的 `trx_id < min_trx_id` → 可见（这个事务在我生成视图前就提交了）
2. 如果行的 `trx_id >= max_trx_id` → 不可见（这个事务是我生成视图后才开启的）
3. 如果行的 `trx_id` 在 `m_ids` 里 → 不可见（这个事务还没提交）
4. 不在 `m_ids` 里 → 可见（已经提交了）

> **不满足可见就顺着 undo 版本链往前找，直到找到第一个可见的版本，或者找不到就返回空。**

---

### 3. RC 和 RR 隔离级别下 MVCC 的区别？

**答：** 核心就是 **生成 Read View 的时机不一样**

| 隔离级别 | Read View 生成时机 | 效果 |
|---------|------------------|------|
| **RC (读已提交)** | **每次 SELECT 都生成新的** | 所以能读到其他事务刚提交的修改 → 不可重复读 |
| **RR (可重复读)** | **只有事务中第一次 SELECT 时生成，后面复用同一个** | 所以同一个事务里多次读结果都一样 → 可重复读 |

## 二、锁机制深度题

### 4. InnoDB 的行锁有哪几种？什么是间隙锁？Next-Key Lock？

**答：**

**行锁的三种算法（都是 RR 隔离级别下的）：**

1. **Record Lock（记录锁）**：锁住具体的索引行
   - 比如 `WHERE id = 1`，id 是主键，就只锁住 id=1 这一行

2. **Gap Lock（间隙锁）**：锁住索引之间的间隙，不锁记录本身，防止幻读
   - 比如 id 有 1,4,7 三个值，间隙就是 `(负无穷,1)、(1,4)、(4,7)、(7,正无穷)`
   - 间隙锁是共享的，多个事务可以同时加同一个间隙的锁，不冲突
   - **唯一索引等值查询，命中记录的话，间隙锁会退化成记录锁**

3. **Next-Key Lock（临键锁）** = Record Lock + Gap Lock，左开右闭区间
   - 默认的行锁算法
   - 比如 `WHERE id > 4`，就会锁 `(4,7]、(7, 正无穷)` 这两个区间
   - **目的：解决幻读问题**

> **支付场景关联**：用 `WHERE out_order_no = 'xxx' FOR UPDATE`，如果 out_order_no 是唯一索引，命中了就只锁这一行（记录锁）；如果没命中，就锁间隙，防止其他事务插入相同的 out_order_no，保证幂等。

---

### 5. 什么情况下行锁会升级为表锁？

**答：**
**最主要的原因：没走索引！**
InnoDB 的行锁是针对索引加的，不是针对行的，如果你的查询条件没用到索引，就会升级为表锁。

**其他场景：**
1. 隔离级别是 RC，并且优化器觉得走索引还不如全表扫快（比如更新大部分行）
2. 数据量太小，优化器直接选全表扫

> **支付场景大坑警告**：更新支付单的时候如果用 `WHERE mch_id = 123`，mch_id 没建索引，那就锁整张表！所有支付请求都卡住，线上 P0 事故。

---

### 6. 乐观锁和悲观锁的区别？支付场景怎么用？

**答：**

| 维度 | 悲观锁 | 乐观锁 |
|-----|--------|--------|
| **思想** | 假设一定会并发冲突，操作前先加锁 | 假设不会冲突，提交的时候才检查 |
| **实现** | `SELECT ... FOR UPDATE` 行锁 | 版本号 version 或 CAS |
| **适用场景** | 写多读少，冲突概率高 | 读多写少，冲突概率低 |
| **性能** | 冲突少的时候高，冲突多的时候线程等待 | 冲突少的时候好，冲突多的时候重试浪费 CPU |

**支付场景应用：**
```sql
-- 悲观锁：扣款前先锁余额行
SELECT balance FROM user_balance WHERE user_id = 123 FOR UPDATE;
UPDATE user_balance SET balance = balance - 100 WHERE user_id = 123;

-- 乐观锁：用版本号
UPDATE user_balance
SET balance = balance - 100, version = version + 1
WHERE user_id = 123 AND version = 旧版本号;
-- 影响行数为0说明被别人改了，重试
```

> **面试加分项**：余额扣款这种冲突概率高的场景，其实用悲观锁更合适，乐观锁重试太多反而性能差。你们支付里余额扣款应该就是用 FOR UPDATE 悲观锁吧？

## 三、SQL 优化

### 7. EXPLAIN 输出各个字段的含义？重点关注哪些？

**答：** 面试必背，至少说 5 个核心字段

| 字段 | 含义 | 什么值比较好 |
|-----|------|------------|
| **type** | 访问类型 | system > const > eq_ref > ref > range > index > ALL <br> ✅ 至少要到 range 级别，ALL 是全表扫描，要优化 |
| **key** | 实际用的索引 | 不是 NULL 就行，要和你预期的一致 |
| **key_len** | 索引使用的字节数 | 尽量小，说明索引用的充分 |
| **rows** | 预估扫描的行数 | 越小越好 |
| **Extra** | 额外信息 | ✅ 好的：Using index（覆盖索引）、Using where <br> ❌ 坏的：Using filesort（文件排序）、Using temporary（临时表）、Using join buffer（关联走了缓冲区） |
| **possible_keys** | 可能用到的索引 | - |
| **ref** | 索引列的比较条件 | - |

### 8. 分页查询优化：深分页问题怎么解决？

**答：**
深分页比如 `LIMIT 1000000, 10`，MySQL 要先扫 1000010 行，再扔掉前面 100 万，性能极差。

**优化方案：**
1. **主键回表优化**：先在索引上定位到起始 ID，再回表查
   ```sql
   -- 慢写法
   SELECT * FROM payment_slip WHERE mch_id = 123 LIMIT 1000000, 10;

   -- 优化写法
   SELECT * FROM payment_slip
   WHERE id >= (SELECT id FROM payment_slip WHERE mch_id = 123 LIMIT 1000000, 1)
   LIMIT 10;
   ```

2. **游标分页（推荐）**：不让用户随便跳页，用上一页最后一条的 ID 当游标
   ```sql
   -- 第一页
   SELECT * FROM payment_slip WHERE mch_id = 123 ORDER BY id LIMIT 10;
   -- 第二页，传上一页最后一个 id=99
   SELECT * FROM payment_slip WHERE mch_id = 123 AND id > 99 ORDER BY id LIMIT 10;
   ```

> **支付场景关联**：对账系统、后台管理系统的列表查询一定要用游标分页，不然数据量大了查询超时。

### 9. count(*)、count(1)、count(列名)、count(主键) 区别？

**答：**

| 写法 | 含义 | 效率 |
|-----|------|------|
| **count(*)** | 统计总行数，不会忽略 NULL | 最快，InnoDB 专门优化过 |
| **count(1)** | 和 count(*) 基本一样，也是统计总行数 | 和 count(*) 差不多，现代版本没区别 |
| **count(主键 id)** | 统计主键不为 NULL 的行数 | 稍慢，需要判断主键非空 |
| **count(普通列)** | 统计该列不为 NULL 的行数 | 最慢，还要判断列值是否 NULL |
| **count(distinct 列)** | 统计该列去重后的非空行数 | 最慢 |

> **结论**：统计行数直接用 `count(*)` 就对了，别写 `count(id)` 或者 `count(1)`，没必要。

### 10. 大表添加字段怎么加？为什么？

**答：**
MySQL 5.6+ 有 Online DDL，加普通字段（没有默认值或者默认值是固定的）不会锁表，但是有坑：

**不同版本的情况：**
- **5.6 以前**：加字段全表锁，锁表期间不能写，大表直接挂
- **5.6+ Online DDL**：加字段的时候用 `ALGORITHM=INPLACE, LOCK=NONE`，不需要拷表，不锁写
- **8.0 秒加列**：新增带默认值的列，只改元数据，秒级完成，不需要修改每一行数据

**大表加字段的最佳实践：**
1. 先在从库加，再切主库，或者用 pt-online-schema-change、gh-ost 工具
2. 字段允许为 NULL，不要设置默认值（老版本）
3. 业务低峰期执行
4. 8.0 直接加就行，秒级

## 四、主从复制 & 高可用

### 11. MySQL 主从复制原理？

**答：**

**三个线程 + 两个日志：**
1. **主库的 binlog dump 线程**：从库连接过来后，主库把 binlog 发给从库
2. **从库的 IO 线程**：拉取主库的 binlog 写到 relay log（中继日志）
3. **从库的 SQL 线程**：重放 relay log 里的事件，把数据写到从库

```
主库执行事务 → 写 binlog → binlog dump线程发出去
                              ↓
                     从库 IO线程收 → 写 relay log
                                        ↓
                               从库 SQL线程重放 → 数据写入
```

---

### 12. 主从延迟的原因？怎么解决？

**答：**

**常见原因：**
1. **从库单线程重放**：5.7 以前 SQL 线程是单线程，主库并发写，从库单线程追，肯定慢
2. **没有主键或唯一索引**：binlog 是 ROW 模式，更新没主键的表，从库要全表扫
3. **大事务**：主库执行了一个 1 分钟的大事务，提交后从库也要重放 1 分钟
4. **从库硬件差**：CPU、磁盘比主库差
5. **从库跑查询**：从库跑了大查询，占用资源，影响 SQL 线程

**解决方案：**
1. 升级到 5.7+，开启并行复制（基于 group commit 的逻辑时钟）
2. 所有表必须有主键
3. 大事务拆成小事务
4. 从库硬件和主库一致
5. 读写分离的从库不要跑太重的查询

> **支付场景关联**：支付单刚创建，马上去从库查不到，就是主从延迟了。这种场景要查主库，或者用半同步复制保证一致性。

---

### 13. 半同步复制和异步复制区别？

**答：**

| 模式 | 过程 | 数据一致性 | 性能 |
|-----|------|----------|------|
| **异步复制** | 主库 commit 就返回客户端成功，不管从库有没有收到 | 主库挂了可能丢数据 | 最好 |
| **半同步复制** | 主库 commit 后，等至少一个从库收到 binlog 并写入 relay log，再返回成功 | 一致性高，最多丢一个事务的日志 | 稍差，多了一次网络 RTT |

> **支付场景**：核心交易库建议用半同步，保证主从数据一致，不要丢支付记录。

## 五、存储引擎

### 14. InnoDB 和 MyISAM 区别？（背就行，虽然现在都用 InnoDB）

**答：**

| 维度 | InnoDB | MyISAM |
|-----|--------|--------|
| **事务** | ✅ 支持 | ❌ 不支持 |
| **行锁** | ✅ 支持 | ❌ 只有表锁 |
| **崩溃恢复** | ✅ 有 redo log | ❌ 崩溃容易损坏 |
| **外键** | ✅ 支持 | ❌ 不支持 |
| **MVCC** | ✅ 支持 | ❌ 不支持 |
| **聚簇索引** | ✅ 是 | ❌ 非聚簇 |
| **count(*)** | 需要扫表 | 有计数器，极快 |
| **存储文件** | .ibd（数据索引一体） | .MYD + .MYI 分开 |
| **版本默认** | MySQL 5.5+ 默认 | 老版本默认 |

> **一句话总结**：除了读极多完全不写的场景，都用 InnoDB，支付这种核心业务根本不用考虑 MyISAM。
