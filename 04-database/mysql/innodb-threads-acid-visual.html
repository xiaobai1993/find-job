InnoDB 四大后台线程（点击展开详情）
🎛
Master Thread
调度员 · 最核心的后台线程
1s
每 1 秒循环
① 刷新 redo log buffer 到磁盘（即使事务未提交）
② 合并 Insert Buffer（根据 IO 繁忙程度决定）
③ 刷脏页到磁盘（根据脏页比例决定数量）
④ 空闲时切换到 background loop
10s
每 10 秒循环
① 刷新 100 个脏页到磁盘
② 合并 Insert Buffer
③ 强制刷新 redo log buffer
④ full purge，清理无用 undo 页
bg
background loop（空闲/关闭时）
① 删除无用 undo 页
② 合并 Insert Buffer
③ 跳回主循环
历史演进：5.5 前所有工作全在 Master Thread，后逐步拆出 Purge Thread（5.5）和 Page Cleaner（5.6），Master Thread 持续瘦身。
📦
IO Thread
搬运工 · 处理 AIO 异步 IO 回调
InnoDB 大量使用 AIO（异步 IO）提高磁盘吞吐。IO Thread 负责 AIO 请求完成后的回调处理，分 4 种子线程：
read thread × 4
处理数据页读请求
innodb_read_io_threads
write thread × 4
处理数据页写请求
innodb_write_io_threads
insert buffer thread × 1
Insert Buffer 写 IO
—
log thread × 1
redo log 写 IO
—
读写分离：读请求和写请求由独立线程池处理，高并发 IO 时互不阻塞，是 InnoDB 高吞吐的基础。
🧹
Purge Thread
清洁工 · 回收无用 undo log
事务提交后，其写的 undo log 不能立刻删除——可能还有其他事务的 Read View 在引用历史版本。Purge Thread 判断何时可以安全回收：
事务提交
→
undo log 保留
→
等待所有 Read View 不再引用
无活跃事务引用
→
Purge Thread 回收页面
innodb_purge_threads = 4（默认，MySQL 8.0）
长事务的危害：若某事务一直持有老 Read View，Purge Thread 无法推进，undo log 持续堆积，磁盘暴涨。这是长事务最大的隐患之一。
💾
Page Cleaner Thread
落盘工 · 刷脏页到磁盘（5.6+）
MySQL 5.6 从 Master Thread 独立拆出，专门负责将 Buffer Pool 中的脏页刷新到磁盘，避免阻塞主线程。
触发刷脏的时机：
①
脏页比例过高
超过 innodb_max_dirty_pages_pct（默认 90%）时主动刷脏
②
redo log 空间不足
redo log 是环形结构，快写满时必须先把对应脏页落盘，才能覆盖老的 log
③
正常关闭
数据库 shutdown 时强制刷所有脏页
innodb_page_cleaners = 4（默认） 建议与 Buffer Pool 实例数一致

D 持久性 — redo log（WAL）
核心思路 WAL：Write-Ahead Logging
直接写数据页是随机 IO，代价高。InnoDB 改成先写 redo log（顺序 IO），再异步刷数据页：
① 修改数据
→
先写 redo log（顺序IO）
→
修改 Buffer Pool 脏页
→
COMMIT 返回成功
脏页由 Page Cleaner 异步落盘
·
崩溃后用 redo log 重放恢复
redo log 是物理日志，记录：第 X 页偏移 Y 处，值从 A 变为 B
关键参数 innodb_flush_log_at_trx_commit
值行为安全性性能
1（默认）每次 COMMIT 强制 fsync 到磁盘最安全略低
2COMMIT 写 OS buffer，每秒 fsync宕机丢 1 秒中
0每秒写 buffer + fsync 一次宕机丢 1 秒最高
防止部分写 doublewrite buffer
InnoDB 页 16KB，OS 每次 IO 4KB，写到一半宕机会产生坏页。redo log 修复不了坏页（需要先有完整页才能 apply）。
脏页
→
先写 doublewrite buffer（连续磁盘区域，顺序IO）
→
再写到真正的磁盘位置
崩溃 →
从 doublewrite buffer 恢复完整页
→
再 apply redo log
A 原子性 — undo log
核心机制 修改数据前先记录"如何撤销"
操作undo log 记录的内容
INSERT id=5DELETE id=5
DELETE id=5INSERT id=5（原来所有字段值）
UPDATE amount 100→200UPDATE amount 200→100
需要回滚时，按 undo log 链从后往前依次执行逆操作，所有修改被撤销。
版本链 undo log 同时支撑 MVCC
每行有隐藏字段 DB_ROLL_PTR，指向最近的 undo log。多个版本串成链，MVCC 沿链找历史版本：
当前版本
amount=200
trx_id=100
→
版本 V2
amount=150
trx_id=80
→
版本 V1
amount=100
trx_id=50
→
原始版本
amount=50
trx_id=10
MVCC 快照读沿版本链找到对当前事务可见的版本，无需加锁
I 隔离性 — MVCC + Lock
快照读 普通 SELECT → MVCC，不加锁
事务做快照读时创建 Read View，包含 4 个字段：
字段含义
m_ids当前所有活跃（未提交）事务的 ID 列表
min_trx_idm_ids 中最小值
max_trx_id下一个将分配的事务 ID
creator_trx_id创建此 Read View 的事务 ID
可见性判断（行的 DB_TRX_ID）：
trx_id < min_trx_id
→ 快照前已提交 → 可见 ✓
trx_id >= max_trx_id
→ 快照后才开始 → 不可见 ✗
在 m_ids 里
→ 还未提交 → 不可见 ✗，沿版本链找上一个
不在 m_ids 里
→ 已提交 → 可见 ✓
隔离级别Read View 创建时机效果
RC每条 SELECT 重新创建能看到最新提交 → 不可重复读
RR整个事务只创建一次，之后复用永远看同一快照 → 可重复读
当前读 FOR UPDATE / 写操作 → 加锁
隔离级别加的锁能防幻读？
RCRecord Lock（行锁），无间隙锁不能
RRNext-Key Lock（行锁 + 间隙锁）能
SERIALIZABLE普通 SELECT 也加 S Next-Key Lock完全隔离
C 一致性 — 目标，由 A + I + D 共同保证
定位 一致性是目标，AID 是手段
A 原子性
→ 事务要么全做要么全不做，不出现半截状态
I 隔离性
→ 并发事务互不干扰，不读到中间状态
D 持久性
→ 提交的数据不因崩溃丢失
↓
数据库从一个一致状态 → 转移到另一个一致状态
约束 数据库层面的额外保障
约束类型保证的一致性
PRIMARY KEY主键唯一且非空
UNIQUE唯一约束，防止重复值
FOREIGN KEY引用完整性，防止悬空引用
NOT NULL非空约束
CHECK值范围约束（MySQL 8.0.16+ 真正生效）
协作关系 undo log 和 redo log 的分工
undo log 本身也是对数据页的修改，它的持久性同样靠 redo log 保护：
修改 undo 段
→
产生 redo log
→
undo log 也得到持久化保护
崩溃恢复完整流程：
①
用 redo log 重放所有已提交事务的变更（含 undo 段的恢复）
②
用 undo log 回滚所有崩溃时未提交的事务
③
数据库恢复到一致状态 ✓
