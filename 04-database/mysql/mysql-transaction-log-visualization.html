② 三大日志对比

undo log / redo log / binlog 各司其职，缺一不可

维度undo logredo logbinlog
所属层InnoDB 引擎层InnoDB 引擎层MySQL Server 层（所有引擎通用）
主要作用事务回滚 + MVCC版本链崩溃恢复（保证持久性）主从复制 + 数据恢复
写入时机事务执行 DML 之前数据页修改后（prepare阶段）事务提交时一次性写入

为什么需要两阶段提交？

如果不做两阶段提交，redo log 和 binlog 可能不一致：

❌ 先写redo，崩溃，没写binlog
重启后：InnoDB按redo恢复，数据有修改。但binlog没有这条记录，从库同步后数据不一致。
❌ 先写binlog，崩溃，没写redo
重启后：InnoDB回滚事务（没redo），数据回到旧值。但binlog有记录，从库同步后多了这条，主从不一致。
✅ 两阶段提交解决方案
redo log(prepare) → binlog → redo log(commit)
崩溃恢复时：redo有prepare但没commit → 检查binlog是否有记录 → 有就提交，没有就回滚。主从永远一致。

WAL（Write-Ahead Log）原则

先写日志（redo log），再改数据页。这样崩溃了可以用日志恢复，不用每次都同步刷数据页到磁盘（顺序写比随机写快很多）。

③ MVCC 版本链

每次修改都保留旧版本，形成链表，读历史版本不加锁

每行数据有两个隐藏字段：DB_TRX_ID（最后修改它的事务ID）和 DB_ROLL_PTR（回滚指针，指向undo log里的上一个版本）。

每次修改时，新版本放在数据页，旧版本写入 undo log，通过回滚指针串成一条链。

← 最新版本（数据页）         旧版本（undo log）→

版本可见性判断（MVCC核心）

读取某一行时，按以下规则判断哪个版本对当前事务可见：

如果 trx_id < min_trx_id  → 可见（创建ReadView前就提交了）
如果 trx_id >= max_trx_id → 不可见（创建ReadView后才开启）
如果在 m_ids 里          → 不可见（还没提交的活跃事务）
不在 m_ids 里            → 可见（已提交）

④ Read View — RC 和 RR 的本质区别

同样的MVCC机制，只因Read View创建时机不同，产生了完全不同的行为

RC（读已提交）：每次 SELECT 都重新创建一个 Read View → 每次都能看到别人最新提交的数据 → 不可重复读
RR（可重复读）：整个事务只在第一次 SELECT 时创建 Read View，之后复用 → 永远看同一个快照 → 可重复读

Read View 的四个关键属性

属性含义用于判断
m_ids生成ReadView时所有活跃（未提交）的事务ID列表在列表里 = 还未提交 = 不可见
min_trx_idm_ids 中最小的事务IDtrx_id < 此值 = 肯定已提交 = 可见
max_trx_id下一个将分配的事务ID（当前最大+1）trx_id >= 此值 = 还没开启 = 不可见
creator_trx_id创建此ReadView的事务ID= 自己修改的，永远可见
长事务危害（RR下）

RR隔离级别下，Read View 活到事务结束。
如果有个事务开启后一直不提交（比如忘了COMMIT），它的 min_trx_id 会阻止 purge 线程清理 undo log。
期间产生的所有版本都无法删除 → undo log 膨胀 → 磁盘爆满！
这就是为什么要避免长事务，线上一定要设置 innodb_lock_wait_timeout。

⑤ 崩溃恢复流程

MySQL 崩溃重启后，靠 redo log + undo log 保证数据一致性。点击各崩溃点查看恢复策略

正常提交流程：undo写入 → 改Buffer Pool → redo(prepare) → binlog写入 → redo(commit)

MySQL 重启后，会扫描 redo log，根据 redo 和 binlog 的状态决定每个事务的命运。

步骤1：写 undo log
记录旧值，保证可以回滚
步骤2：修改 Buffer Pool 脏页
内存里的数据页被修改，还未刷盘
步骤3：写 redo log（prepare状态）
持久化修改意图到磁盘，还未提交
步骤4：写 binlog
主从复制的日志，一次性写入
步骤5：redo log 标记 commit ✅
事务正式提交，一切完成
👆 点击任意步骤，看在此处崩溃后如何恢复
一句话总结崩溃恢复规则

redo有commit标记 → 直接提交（重放redo）
redo有prepare但binlog也有 → 提交（两阶段提交达成一致）
redo有prepare但binlog没有 → 回滚（用undo log撤销）
redo都没有 → 回滚（事务从未开始）
