# MySQL 分库分表从零理解 + 支付场景

> 分库分表不是为了炫技，而是单库单表在容量、性能、连接数、IO、DDL、归档等方面真的遇到瓶颈后，才用来做水平扩展的方案。

---

## 一、先理解：为什么要分库分表？

分库分表要解决的核心问题是：

```text
单表太大，查询和维护变慢；
单库压力太高，CPU、IO、连接数、存储容量扛不住；
业务数据增长确定，单机 MySQL 已经不够用了。
```

比如支付单表 `payment_order` 持续增长到几千万、上亿行后，可能出现：

```text
索引越来越大
B+ 树层级变高
查询扫描范围变大
DDL 变慢
归档和备份恢复困难
单库 IO、CPU、连接数接近瓶颈
```

这时才需要考虑分库分表。

---

## 二、什么是分库？什么是分表？

### 1. 分表

分表是把一张大表拆成多张小表。

原来：

```text
payment_order
```

拆成：

```text
payment_order_0000
payment_order_0001
payment_order_0002
...
payment_order_1023
```

分表主要解决：

```text
单表数据量太大
索引太大
查询、DDL、归档变慢
```

---

### 2. 分库

分库是把数据拆到多个 MySQL 实例。

例如：

```text
payment_db_00
payment_db_01
payment_db_02
payment_db_03
```

分库主要解决：

```text
单个 MySQL 实例 CPU、IO、连接数、存储容量瓶颈
```

注意：

```text
只分表不分库，压力仍然在同一个 MySQL 实例上。
分库才能真正扩展数据库实例能力。
```

---

## 三、垂直拆分和水平拆分

### 1. 垂直拆分

垂直拆分是按业务边界拆。

原来一个库里有：

```text
用户表
订单表
支付表
退款表
账务表
对账表
```

拆成：

```text
user_db
order_db
payment_db
accounting_db
reconciliation_db
```

好处：

```text
业务边界清晰
不同业务独立扩展
降低单库复杂度
故障影响范围变小
```

支付系统里，一般不会把订单、支付、财务、对账全部长期放在同一个库里。

---

### 2. 水平拆分

水平拆分是把同一类业务数据按规则拆到多个库表。

例如支付单按 `payment_id` hash 拆：

```text
payment_order_0000
payment_order_0001
...
payment_order_1023
```

水平拆分解决的是：

```text
同一类业务数据量太大
单表或单库扛不住增长
```

---

## 四、分片键怎么选？

分库分表最关键的是分片键，也叫 sharding key。

常见分片键：

```text
user_id
merchant_id
order_id
payment_id
tenant_id
```

选择原则：

```text
1. 查询最常用
2. 分布要均匀
3. 尽量避免跨分片查询
4. 业务上稳定，不会频繁变化
5. 能让核心事务尽量落在一个分片内
```

---

## 五、支付系统里分片键怎么选？

分片键没有绝对正确，只有业务取舍。

### 1. 按 `user_id` 分片

适合用户维度查询：

```sql
SELECT * FROM payment_order
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT 20;
```

优点：

```text
用户查自己的支付记录很快
```

缺点：

```text
商户查交易流水可能跨很多分片
```

---

### 2. 按 `merchant_id` 分片

适合商户维度查询和对账：

```sql
SELECT * FROM payment_order
WHERE merchant_id = ?
  AND created_at BETWEEN ? AND ?;
```

优点：

```text
商户交易查询、商户对账方便
```

缺点：

```text
用户维度查询可能跨分片
大商户可能形成热点
```

---

### 3. 按 `payment_id` 分片

适合支付主链路点查：

```sql
SELECT * FROM payment_order
WHERE payment_id = ?;
```

优点：

```text
支付单点查快
分布通常更均匀
主链路路由简单
```

缺点：

```text
按用户、商户、时间范围查都可能跨分片
```

---

### 4. 面试时不要说死

更合理的说法：

> 分片键要根据核心访问路径决定。如果支付主链路主要按支付单号查询，可以按 `payment_id` 分片；如果商户交易查询和对账是高频场景，就要考虑 `merchant_id`，或者通过索引表、ES、ClickHouse、数仓来解决非分片键查询。

---

## 六、常见分片算法

### 1. 取模分片

```text
shard = user_id % N
```

例如：

```text
user_id % 4 = 0 → db_00
user_id % 4 = 1 → db_01
user_id % 4 = 2 → db_02
user_id % 4 = 3 → db_03
```

优点：

```text
简单
分布均匀
路由快
```

缺点：

```text
扩容麻烦。
如果 N 从 4 变成 8，大量数据要重新迁移。
```

---

### 2. 范围分片

比如按时间拆：

```text
payment_order_202601
payment_order_202602
payment_order_202603
```

优点：

```text
按时间查询、归档、清理方便
```

缺点：

```text
热点明显，最新时间段压力最大
```

对账明细、历史流水、日志类数据经常按时间分区或分表。

---

### 3. 预分片

一开始就创建较多逻辑分片：

```text
payment_order_0000 ~ payment_order_1023
```

即使物理库只有 4 个，也可以这样映射：

```text
db_00：0000 ~ 0255
db_01：0256 ~ 0511
db_02：0512 ~ 0767
db_03：0768 ~ 1023
```

以后从 4 个库扩到 8 个库，只迁移部分逻辑表即可。

实际工程里，预分片比简单取模更容易扩容。

---

## 七、分库分表带来的问题

分库分表提升扩展性，但会牺牲简单性。

### 1. 跨分片查询困难

比如按 `payment_id` 分片，但现在要按商户查：

```sql
SELECT * FROM payment_order
WHERE merchant_id = ?
  AND created_at BETWEEN ? AND ?;
```

如果没有路由信息，就可能要扫所有分片。

解决方式：

```text
尽量让查询带分片键
建立索引映射表
同步到 ES / ClickHouse / 数仓
按业务维度做冗余表
```

---

### 2. 跨库 Join 困难

原来可以：

```sql
SELECT *
FROM payment_order p
JOIN refund_order r ON p.id = r.payment_id;
```

分库分表后，两个表可能不在同一个库，Join 成本很高。

解决方式：

```text
避免跨库 Join
在应用层组装
冗余必要字段
相关表使用同一个分片键
```

例如支付单和支付子单都按 `payment_id` 分片，尽量让一次支付相关数据落到同一个分片。

---

### 3. 分布式事务问题

跨多个库更新，就可能需要分布式事务。

所以设计时要尽量避免：

```text
一个业务事务同时写多个分片
```

支付系统里更常见做法：

```text
单个支付单的核心状态落在一个分片内
跨服务、跨库动作通过 MQ 最终一致
最终由对账系统兜底
```

---

### 4. 全局唯一 ID

分库分表后，不能简单依赖单库自增 ID。

否则可能出现：

```text
db_00 生成 id = 1
db_01 也生成 id = 1
```

常见全局 ID 方案：

```text
雪花算法
号段模式
数据库发号器
Redis INCR
UUID / ULID
```

支付系统通常更适合：

```text
雪花 ID / 号段模式 / 自研订单号生成器
```

因为需要可控、趋势递增、易排查。

---

### 5. 分页排序困难

例如查全局最近 20 条支付单：

```sql
SELECT * FROM payment_order
ORDER BY created_at DESC
LIMIT 20;
```

如果数据分布在 16 个分片，需要：

```text
每个分片查 top 20
应用层 merge sort
再取全局 top 20
```

成本很高。

这类复杂检索通常不建议走交易主库，而是走：

```text
ES
ClickHouse
数仓
宽表
搜索索引
```

---

### 6. 扩容迁移复杂

如果直接按 `% 4` 分片，后来变成 `% 8`，大量数据都要重新分布。

更稳妥的方式：

```text
预分片
逻辑分片和物理库解耦
灰度迁移
双写校验
数据对账
```

---

## 八、支付系统表怎么拆？

假设有这些表：

```text
payment_order
payment_sub_order
refund_order
refund_sub_order
payment_flow
accounting_entry
reconciliation_detail
```

### 1. 支付主链路表

```text
payment_order
payment_sub_order
refund_order
refund_sub_order
```

可以按：

```text
payment_id / order_id
```

做水平拆分。

目标：

```text
一次支付相关的数据尽量落在同一个分片
主链路按支付单号点查性能稳定
```

---

### 2. 账户流水 / 会计流水

流水数据量很大，可以按：

```text
account_id + 时间
```

或者：

```text
流水 ID hash + 时间归档
```

核心考虑：

```text
账户维度查询
账期维度归档
批量对账和审计
```

---

### 3. 对账明细

对账天然和日期强相关，适合：

```text
按日期分区 / 分表
```

例如：

```text
recon_detail_20260518
recon_detail_20260519
```

因为对账通常是 T+1 批处理：

```text
按账期扫描
按渠道扫描
按业务类型扫描
```

时间维度很重要。

---

## 九、非分片键查询怎么办？

### 1. 映射表

如果按 `payment_id` 分片，但要用 `merchant_order_no` 查，可以建路由映射表：

```text
merchant_order_no → payment_id → shard_no
```

查询流程：

```text
先查映射表拿到 payment_id / shard_no
再路由到对应分片查主表
```

---

### 2. 冗余索引表

例如：

```text
payment_order_index_by_merchant_order
```

字段：

```text
merchant_order_no
payment_id
merchant_id
created_at
shard_no
```

适合高频的非分片键查询。

---

### 3. 同步到 ES / ClickHouse

如果是复杂查询：

```text
多条件筛选
模糊搜索
分页排序
运营后台查询
大范围统计
```

一般同步到：

```text
ES
ClickHouse
数仓
```

交易主库只负责主链路，不承担复杂检索和报表分析。

---

## 十、分库分表后的事务怎么处理？

核心原则：

```text
尽量让同一个业务事务只落到一个分片，避免跨分片事务。
```

例如：

```text
支付单和支付子单使用同一个 payment_id 分片
退款单也携带 payment_id 或能路由到同一分片
```

如果确实跨服务、跨库：

```text
不要轻易用 2PC 硬包
优先使用本地事务 + MQ + 幂等 + 补偿 + 对账
```

支付系统里可以这样设计：

```text
Payment 本地事务更新支付单状态
写本地消息或发送可靠消息
订单/财务/对账消费消息
失败重试，重复消费靠幂等
T+1 对账兜底
```

---

## 十一、什么时候才需要分库分表？

不要简单说“数据量大就分”。

更准确是看这些信号：

```text
单表数据量持续增长到几千万以上
索引明显膨胀
慢查询明显增多
单库 CPU / IO / 连接数接近瓶颈
DDL、归档、备份恢复变得困难
业务未来增长确定，单机扩容空间不足
```

也不要过早分库分表。

优先级通常是：

```text
优化 SQL 和索引
冷热数据归档
读写分离
分区表
垂直拆库
水平分库分表
```

分库分表是复杂度很高的方案，不能作为第一选择。

---

## 十二、线上单表迁移到分表怎么做？

这是非常真实的生产问题：

```text
原来线上只有一张大订单表 orders
已经跑了很多年，数据量很大
现在要改成按 order_id hash 取模分表
```

这时最难的不是取模规则，而是：

```text
已有历史数据怎么迁？
迁移期间新数据怎么写？
读请求怎么切？
怎么不停机？
怎么保证数据不丢、不重、不乱？
出问题怎么回滚？
```

不能简单停机导数据，因为订单表通常是核心表，停机时间不可控，数据迁错后回滚也很困难。

---

### 1. 总体迁移思路

比较稳的方式是**不停机平滑迁移**：

```text
建新表 → 双写 → 全量迁移 → 增量同步 → 数据校验 → 灰度切读 → 切写 → 老表归档
```

也可以理解成：

```text
先让新老结构并行，再逐步把读写流量切过去。
```

---

### 2. 第一步：建新分表

比如原来是：

```text
orders
```

现在拆成 64 张表：

```text
orders_00
orders_01
...
orders_63
```

路由规则：

```text
shard = order_id % 64
```

建表时要保证：

```text
字段一致
索引一致
字符集一致
默认值一致
唯一约束重新评估
```

特别注意唯一索引。

原来老表里可能有：

```sql
UNIQUE KEY uk_order_no(order_no)
```

分表后每张表内唯一，不等于全局唯一。

所以要确认：

```text
order_no 是否由发号器保证全局唯一
是否需要全局唯一索引表
是否需要调整业务号生成规则
```

---

### 3. 第二步：上线双写

新增或更新订单时，同时写：

```text
老表 orders
新分表 orders_xx
```

迁移早期通常是：

```text
老表为主数据源
新表作为影子表
```

也就是：

```text
老表写成功，主流程成功
新表写失败，记录失败日志或本地消息，异步补偿
```

不要一开始就让新表成为主链路，否则风险太高。

---

### 4. 第三步：全量迁移历史数据

双写上线后，开始迁移历史数据。

通常按主键范围小批量扫描：

```sql
SELECT * FROM orders
WHERE id > ?
ORDER BY id
LIMIT 1000;
```

然后根据：

```text
order_id % 64
```

写入对应分表。

迁移时要注意：

```text
小批量迁移
控制 QPS
避开业务高峰
失败可重试
避免大事务
避免主从延迟和 binlog 暴涨
```

不要一次性大事务全量导入，否则容易打满 IO、拖垮线上库。

---

### 5. 第四步：处理增量数据

迁移期间，订单仍然在新增和更新。

常见有两种方式。

#### 方案一：业务双写覆盖增量

因为双写已经上线，新产生的数据会同时写老表和新表。

但要注意历史数据迁移过程中，老订单可能被更新。

比如迁移任务读到：

```text
订单状态 = 待支付
```

但业务随后把订单更新成：

```text
订单状态 = 已支付
```

如果迁移任务用旧数据覆盖新表，就会把新状态覆盖成旧状态。

解决方式：

```text
使用 update_time / version 做条件更新
迁移任务只更新版本更老的数据
或者全量迁移 insert ignore，后续靠增量同步修正
```

#### 方案二：Binlog 增量同步

使用 Canal、Debezium、Flink CDC 等订阅老表 binlog：

```text
老表变更 → 捕获 binlog → 路由写入新分表
```

优点：

```text
业务侵入较小
适合迁移周期长、数据量大的场景
```

缺点：

```text
链路更复杂
要保证顺序、幂等、延迟可监控
```

---

### 6. 第五步：数据校验

迁移完成后，不能直接切读，必须做校验。

常见校验维度：

```text
数量校验：老表总数 = 新分表总数之和
金额校验：老表金额汇总 = 新分表金额汇总
状态校验：待支付、已支付、已取消、退款中等状态数量一致
抽样校验：随机抽订单逐字段比对
热点校验：当天订单、最近一小时订单、大商户订单、退款订单重点校验
```

订单/支付类数据一定要校验金额和状态，不能只校验 count。

---

### 7. 第六步：灰度切读

不要一次性把所有读流量切到新表。

可以先做双读对比：

```text
主读老表
旁路读新表
比较结果
只返回老表结果
不影响用户
```

确认一致后再灰度：

```text
1% → 5% → 10% → 50% → 100%
```

或者按业务灰度：

```text
内部后台先读新表
测试商户先读新表
小流量业务先读新表
核心支付查询最后切
```

---

### 8. 第七步：切写

读稳定后，再逐步切写。

常见阶段：

```text
老表主写 + 新表影子写
老表主读 + 新表校验读
新表主读 + 老表兜底读
新表主写 + 老表备份写
只写新表
```

不要刚切读成功就马上停止老表写入，要保留一段时间观察。

---

### 9. 第八步：回滚方案

迁移前必须设计回滚。

如果读新表发现问题：

```text
读流量切回老表
继续双写
修复新表数据
重新校验
再灰度
```

如果写新表发现问题：

```text
恢复老表主写
关闭新表写
根据失败日志或 binlog 补齐新表数据
```

老表不能切完马上删除，必须保留一段观察期。

---

### 10. 最容易出问题的地方

| 问题 | 解决方式 |
|---|---|
| 老表写成功，新表写失败 | 失败日志、本地消息表、补偿任务、告警 |
| 全量迁移旧数据覆盖新状态 | `update_time` / `version` 条件更新，或 insert ignore + 增量修正 |
| 非分片键查询没改造 | 索引表、映射表、ES、查询服务改造 |
| 全局唯一约束丢失 | 全局 ID、唯一索引表、业务号生成规则保证唯一 |
| 全局分页排序复杂 | ES、ClickHouse、宽表，不让交易库做复杂检索 |
| 切换后无法回滚 | 老表保留、双写保留、灰度切读、可快速切回 |

---

### 11. 面试标准回答

如果面试官问：

> 一个线上大订单表，现在要按 hash 取模分表，你怎么做？

可以这样回答：

**答：**

我不会直接停机迁移，因为订单表是核心表，数据量大，停机时间不可控，而且回滚风险高。

我会采用不停机平滑迁移的方式。

第一步，先设计新的分表结构和路由规则，比如按 `order_id` hash 到 64 张表，确保字段、索引、字符集、约束都和老表一致，同时评估原来的唯一索引在分表后是否还需要全局唯一约束。

第二步，上线双写。老表仍然作为主数据源，新表作为影子表。新增和更新订单时同时写老表和对应的新分表。如果新表写失败，记录失败日志或本地消息，后续补偿，不能影响老链路。

第三步，做历史数据全量迁移。按主键范围小批量扫描老表，根据 `order_id` 路由写入新表，控制速率，避开高峰，避免大事务和主从延迟。

第四步，处理迁移期间增量数据。可以依赖业务双写，也可以用 Canal/Debezium 订阅 binlog 做增量同步。迁移写入时要用 `update_time` 或 `version` 做条件更新，避免旧数据覆盖新状态。

第五步，做数据校验，包括总数量、金额汇总、状态分布、随机抽样和重点业务数据校验。订单这种场景金额和状态一定要校验。

第六步，灰度切读。先双读对比，主读老表、旁路读新表，只做校验不影响用户。确认一致后，再按商户、用户或流量比例逐步切到新表。

第七步，读稳定后再逐步切写，从老表主写新表影子写，过渡到新表主写老表备份写，最后只写新表。

整个过程中要有回滚方案。如果新表读有问题，读流量立即切回老表；如果新表写有问题，关闭新表写，继续老表主写。老表要保留一段时间，不能切完马上删。

所以核心不是简单取模，而是双写、全量迁移、增量同步、数据校验、灰度切流和可回滚。

## 十三、面试高频题

### Q1：你怎么理解 MySQL 分库分表？

**答：**

分库分表本质是为了解决单库单表的容量和性能瓶颈。分表主要解决单表数据量太大导致索引膨胀、查询变慢、DDL 和归档困难的问题；分库主要解决单个 MySQL 实例 CPU、IO、连接数、存储容量的瓶颈。

拆分方式分为垂直拆分和水平拆分。垂直拆分是按业务边界拆库，比如订单库、支付库、对账库；水平拆分是把同一类数据按分片键拆到多个库表，比如按 `payment_id`、`user_id` 或 `merchant_id` hash 分片。

---

### Q2：分片键怎么选？

**答：**

分片键要根据核心访问路径决定。原则是高频查询能带上分片键，数据分布要均匀，业务上稳定，并且尽量让一个业务事务落在一个分片内。

支付系统里，如果主链路主要按支付单号点查，可以按 `payment_id` 分片；如果商户交易查询和对账是高频场景，可以考虑 `merchant_id`，但要注意大商户热点。非分片键查询可以通过映射表、冗余索引表、ES 或 ClickHouse 解决。

---

### Q3：分库分表后怎么查非分片键？

**答：**

常见有三种方式。

第一，建立映射表，比如 `merchant_order_no → payment_id → shard_no`，先查路由再查主表。

第二，建立冗余索引表，把高频查询维度单独冗余出来。

第三，如果是复杂检索、运营后台、多条件分页排序，就同步到 ES、ClickHouse 或数仓，避免交易主库承担复杂查询。

---

### Q4：分库分表后怎么处理跨库事务？

**答：**

设计上要尽量避免跨库事务，让同一个业务事务只落到一个分片内。比如支付单、支付子单、退款单尽量使用同一个分片键。

如果确实跨服务、跨库，不会轻易用 2PC 去包住所有服务，因为性能和可用性都不好。支付系统更常用的是本地事务保证本服务状态正确，跨服务通过可靠消息最终一致，配合幂等、重试、补偿和对账兜底。

---

### Q5：分库分表有什么缺点？

**答：**

分库分表会带来很多复杂度，包括跨分片查询困难、跨库 Join 困难、分布式事务问题、全局唯一 ID、分页排序困难、扩容迁移复杂、运维和排查成本上升。

所以分库分表不是数据库优化的第一选择，而是在单库单表真的遇到容量和吞吐瓶颈后，才考虑的水平扩展方案。

---

## 十三、一句话记忆

```text
分表解决单表大。
分库解决单库压力大。
分片键决定系统上限。
非分片键查询靠索引表/搜索系统。
跨分片事务尽量避免，靠最终一致兜底。
```

支付系统里的表达：

```text
主链路按核心查询路径选择分片键；
一次支付相关数据尽量落在同一分片；
复杂查询走索引表、ES、ClickHouse；
跨服务一致性靠本地事务、可靠消息、幂等、补偿和对账。
```
