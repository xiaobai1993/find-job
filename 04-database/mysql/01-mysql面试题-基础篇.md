## 一、索引相关

### 1. 什么是索引？MySQL 支持哪些索引类型？

**答：**
索引是帮助 MySQL 高效获取数据的数据结构，本质是通过缩小扫描范围来加速查询。

MySQL 常见索引类型：

| 索引类型 | 说明 |
|---------|------|
| **B+Tree 索引** | InnoDB 默认索引，多路平衡查找树，叶子节点双向链表，支持范围查询 |
| **Hash 索引** | Memory 引擎默认，等值查询极快，但不支持范围查询和排序 |
| **全文索引** | MyISAM/InnoDB(5.6+) 支持，用于文本搜索 |
| **R-Tree 索引** | 空间索引，用于地理数据 |

> **支付场景关联**：支付单表的 `out_order_no`(业务单号)、`user_id`(用户ID)、`created_at`(创建时间) 都是高频查询字段，必须建索引。

---

### 2. 聚簇索引和非聚簇索引的区别？

**答：**

| 维度 | 聚簇索引 (Clustered) | 非聚簇索引 (Secondary) |
|------|---------------------|----------------------|
| **叶子节点存储** | 完整的行数据 | 主键值 + 索引列值 |
| **数量** | 一个表只能有一个 | 可以有多个 |
| **查询效率** | 一次查询就能拿到行数据 | 需要回表(再查聚簇索引) |
| **物理存储** | 数据按索引顺序物理排序 | 逻辑顺序，物理不连续 |
| **谁创建的** | InnoDB 自动用主键创建，无主键选唯一键，再不行就隐式 row_id | 用户手动创建 |

> **支付场景关联**：查支付单用 `id = xxx` 走聚簇索引最快；用 `out_order_no = xxx` 查需要先走唯一二级索引，再回表拿完整数据。

---

### 3. 什么是回表？什么是覆盖索引？

**答：**
- **回表**：二级索引查到主键值后，再去聚簇索引查完整行数据的过程，多一次 IO
- **覆盖索引**：查询的列正好都在二级索引里，不需要回表。用 `Explain` 看 `Extra` 里有 `Using index` 就是覆盖索引

**支付场景例子：**
```sql
-- 支付子单表有 account_type 索引
-- 这个查询只查 payment_slip_id，索引里有，覆盖索引，不需要回表
SELECT payment_slip_id FROM payment_sub_slip WHERE account_type = 'WECHAT';

-- 这个要查 amount，索引里没有，需要回表
SELECT amount FROM payment_sub_slip WHERE account_type = 'WECHAT';
```

---

### 4. 什么是最左前缀原则？

**答：**
联合索引的查询要从最左边的列开始匹配，不能跳过中间的列。

**例子：** 联合索引 `(a, b, c)`

| 查询条件 | 是否走索引 |
|---------|----------|
| `a = 1` | ✅ 用 a |
| `a = 1 AND b = 2` | ✅ 用 a,b |
| `a = 1 AND b = 2 AND c = 3` | ✅ 全用 |
| `b = 2 AND c = 3` | ❌ 不用，跳过了 a |
| `a = 1 AND c = 3` | ✅ 只用 a，b 跳过了，c 用不上 |
| `a > 1 AND b = 2` | ✅ 只用 a，范围查询后的列用不上 |

> **支付场景关联**：支付单经常按 `(user_id, created_at)` 查用户某段时间的支付记录，建联合索引要把等值查询的 `user_id` 放前面，范围查询的 `created_at` 放后面。

---

### 5. 索引失效的场景有哪些？

**答：** 面试必背，至少说 6 个：

1. **在索引列上做计算、函数、类型转换**：`WHERE DATE(created_at) = '2024-01-01'` 失效
2. **like 左模糊**：`WHERE out_order_no LIKE '%abc'` 失效，`'abc%'` 可以
3. **索引列上用 != 或 NOT IN**：大概率失效，优化器可能选全表扫
4. **OR 连接的条件有非索引列**：`WHERE a = 1 OR b = 2`，b 没索引就全失效
5. **字符串不加引号隐式转换**：`WHERE phone = 13800138000` 数字和字符串比，隐式转换失效
6. **联合索引不满足最左前缀**：跳过了前面的列
7. **MySQL 估计全表扫比走索引快**：数据量太少，或者查的数据占比太高

## 二、事务相关

### 6. 事务的 ACID 是什么？

**答：**

| 特性 | 英文 | 说明 | 实现靠什么 |
|-----|------|------|----------|
| **原子性** | Atomicity | 事务里的操作要么全成功，要么全失败 | undo log（回滚日志） |
| **一致性** | Consistency | 事务前后数据的完整性约束不被破坏 | 靠其他三个特性 + 业务代码保证 |
| **隔离性** | Isolation | 多个事务之间互相不干扰 | MVCC + 锁 |
| **持久性** | Durability | 事务提交后数据就永久存在，宕机不丢 | redo log（重做日志） |

> **支付场景关联**：支付扣款是最典型的事务场景：扣余额 + 记子单 + 更状态，这三步必须原子性，要么都成功，要么都回滚。

---

### 7. 并发事务会带来什么问题？四大隔离级别？

**答：**

**并发问题：**
1. **脏读**：A 事务读到了 B 事务还没提交的修改
2. **不可重复读**：A 事务里同一行数据读两次结果不一样（中间被 B 提交改了）
3. **幻读**：A 事务里同一个范围查询两次，行数不一样（中间 B 插入了新行提交了）

**四大隔离级别：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 数据库默认 |
|---------|-----|----------|-----|----------|
| **读未提交 Read Uncommitted** | ✅ 会 | ✅ 会 | ✅ 会 | - |
| **读已提交 Read Committed** | ❌ 不会 | ✅ 会 | ✅ 会 | Oracle、SQL Server |
| **可重复读 Repeatable Read** | ❌ 不会 | ❌ 不会 | ❌ 基本不会(InnoDB MVCC+间隙锁) | MySQL 默认 |
| **串行化 Serializable** | ❌ 不会 | ❌ 不会 | ❌ 不会 | - |

> **面试加分项**：MySQL 默认的 RR 隔离级别其实已经解决了幻读问题，因为有 Next-Key Lock（行锁 + 间隙锁）。

## 三、锁相关

### 8. MySQL 行锁和表锁的区别？

**答：**

| 维度 | 表锁 | 行锁 |
|-----|------|------|
| **粒度** | 锁住整个表 | 锁住具体行 |
| **开销** | 小，加锁快 | 大，加锁慢 |
| **冲突** | 冲突概率高，并发低 | 冲突概率低，并发高 |
| **死锁** | 不会 | 会 |
| **引擎** | MyISAM 默认 | InnoDB 支持 |

> **支付场景关联**：更新支付单状态一定要用行锁，不能锁整张表，不然支付并发上不去。
> ```sql
> -- 正确：行锁，只锁这一行
> UPDATE payment_slip SET status = 6 WHERE id = 12345;
> ```

---

### 9. 什么是死锁？怎么避免？

**答：**
两个事务互相持有对方需要的锁，都不释放，永久等待。

**产生死锁的四个必要条件：**
1. 互斥条件：锁不能共享
2. 持有并等待：拿着锁等别的锁
3. 不可剥夺：锁不能被强行抢
4. 循环等待：A 等 B，B 等 A

**避免方法：**
1. **统一加锁顺序**：所有事务都按相同顺序锁行（比如都按 id 从小到大锁）
2. **缩小事务范围**：事务里不要放 RPC 调用、不要做耗时操作
3. **合理设置索引**：没索引会升级为表锁，更容易死锁
4. **用乐观锁代替悲观锁**：版本号机制

> **支付场景关联**：同时支付多个订单时，一定要按支付单 ID 从小到大排序再更新，不然两个互相等就会死锁。

## 四、日志相关

### 10. undo log、redo log、binlog 分别是什么？有什么区别？

**答：** 这三个日志是面试必考！

| 维度 | undo log | redo log | binlog |
|-----|----------|----------|--------|
| **是谁的** | InnoDB 引擎层 | InnoDB 引擎层 | Server 层，所有引擎都有 |
| **作用** | 事务回滚、MVCC 版本链 | 崩溃恢复，保证事务持久性 | 主从复制、数据归档、恢复 |
| **内容** | 逻辑日志，记录怎么改回去的 | 物理日志，记录页改了什么 | 逻辑日志，记录 SQL 或行变更 |
| **什么时候写** | 事务执行中就写 | 事务提交前刷盘 | 事务提交时写 |
| **循环写？** | 是，用完可以 purge 清理 | 是，固定大小循环写 | 否，追加写，按天滚动 |
| **是否 crash-safe** | - | ✅ 是，宕机恢复用 | ❌ 不是 |

> **支付场景关联**：MySQL 突然宕机了，已经提交的事务会不会丢？不会，因为 redo log 已经刷盘了，重启时会把 redo log 里的变更重放。正在进行的事务怎么办？用 undo log 回滚。

---

### 11. 什么是两阶段提交？为什么需要？

**答：**
因为 redo log 是引擎层的，binlog 是 Server 层的，两个独立的日志，要保证两份日志逻辑一致，所以用两阶段提交：

1. **prepare 阶段**：redo log 写盘，标记为 prepare 状态
2. **commit 阶段**：binlog 写盘，然后把 redo log 标记为 commit

**为什么需要？**
- 如果不用两阶段，假设先写 redo log 成功，写 binlog 失败，主从同步的时候从库就少了这个事务，主从不一致
- 反过来先写 binlog 成功，redo log 失败，主库丢了，从库有，也不一致

> **面试加分项**：可以结合支付说，就像支付时先冻结资金（prepare），确认渠道扣款成功了再正式扣款（commit），逻辑是一样的。

## 五、基础架构

### 12. 一条 SQL 查询语句的执行流程？

**答：**

```
客户端 → 连接器（认证、权限）
        → 查询缓存（8.0 已删）
        → 分析器（词法、语法解析）
        → 优化器（选索引、选执行计划）
        → 执行器（调用引擎接口）
        → InnoDB 存储引擎（查内存缓冲池、查磁盘）
        → 返回结果
```

---

### 13. 一条 UPDATE 语句的执行流程？

**答：**（一定要结合三个日志说）

```
1. 执行器找引擎拿行数据，内存 Buffer Pool 有就直接返回，没有就从磁盘读进去
2. 把旧值写入 undo log（方便回滚）
3. 修改内存里的行数据
4. 把修改操作写入 redo log buffer
5. 事务提交时：
   a) redo log 刷盘，状态 prepare
   b) 写 binlog 并刷盘
   c) redo log 状态改成 commit
6. 后台 IO 线程不定时把内存里的脏页刷回磁盘（刷脏）
```

## 六、其他基础

### 14. varchar 和 char 的区别？

**答：**

| 维度 | char(n) | varchar(n) |
|-----|---------|-----------|
| **长度** | 固定长度，不足补空格 | 变长，实际长度 + 1/2 字节存长度 |
| **空间** | 浪费空间 | 节省空间 |
| **速度** | 快，不需要计算长度 | 稍慢 |
| **n 代表** | 字符数，不是字节数 | 字符数 |
| **适用场景** | 长度固定的：手机号、MD5、身份证号 | 长度变化的：订单号、用户名 |

> **支付场景关联**：支付单号 `out_order_no` 长度固定的话用 char，否则用 varchar；手机号、身份证号固定长度用 char 更合适。

### 15. 为什么主键建议用自增 ID？而不是 UUID？

**答：**
1. **页分裂问题**：UUID 是乱序的，插入时插入到 B+Tree 中间位置，容易导致页分裂，性能差，空间利用率低
2. **自增 ID 是有序的**：每次都插在最后，顺序写入，性能高，页分裂少
3. **大小**：UUID 占 36 个字节，自增 bigint 才 8 字节，索引更小，同样一页能存更多索引，命中率高
4. **二级索引也占空间**：二级索引叶子节点存主键，主键大的话所有二级索引都变大

> **支付场景关联**：你们支付单用雪花 ID 也是有序递增的，道理一样，比 UUID 好很多。
