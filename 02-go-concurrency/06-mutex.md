# Mutex 互斥锁底层原理与最佳实践

---

## 一、先搞懂：Mutex 到底是什么？

Mutex 是 Go 提供的互斥锁，保证同一时间只有一个 goroutine 能进入临界区。

看起来简单，但 Go 的 Mutex 设计非常精妙，经历了三次重大迭代：
- Go 1.1：只有正常模式，饥饿问题严重
- Go 1.9：引入饥饿模式，解决了公平性问题
- Go 1.18：优化了唤醒机制，减少上下文切换

这是面试考察的重点。

---

## 二、Mutex 数据结构（面试必问）

```go
type Mutex struct {
    state int32  // 锁的状态
    sema  uint32 // 信号量，用来阻塞和唤醒 goroutine
}
```

只有两个字段！非常简洁，但功能非常强大。

---

### state 字段详解（32 位，每一位都有含义）

```
31        3  2  1  0
+---------+--+--+--+
| waiters | starvation | woke | locked |
+---------+--+--+--+
    |       |      |     |
    |       |      |     +---- 1: 锁被持有，0: 锁空闲
    |       |      +---------- 1: 已经唤醒了一个 goroutine，解锁时不要释放信号量
    |       +----------------- 1: 处于饥饿模式，0: 正常模式
    +------------------------- 等待锁的 goroutine 数量（29 位，最多 5 亿多）
```

| 位 | 含义 | 说明 |
|----|------|------|
| 0 (Locked) | 锁标记 | 1 表示锁被持有 |
| 1 (Woken) | 唤醒标记 | 1 表示已经有 goroutine 被唤醒了，正在抢锁 |
| 2 (Starvation) | 饥饿标记 | 1 表示处于饥饿模式 |
| 3~31 | 等待者数量 | 29 位，表示有多少个 goroutine 在等这个锁 |

**面试高频追问：为什么把所有状态都放在一个 int32 里？**
- 可以用一次 CAS 原子操作同时修改多个状态
- 不需要单独的锁来保护 Mutex 自己的状态
- 性能极致，内存占用极小

---

## 三、两大模式：正常模式 vs 饥饿模式（核心考点！）

这是 Go Mutex 最精妙的设计，也是面试 100% 会问的内容。

---

### 1. 正常模式（互斥模式）

**行为：**
- 新来的 goroutine 先自旋几次，如果锁刚好释放了，直接抢到锁，不需要进入休眠
- 自旋没抢到，就通过信号量进入休眠排队
- 锁释放时，唤醒队列头部的一个 goroutine
- 被唤醒的 goroutine 和新来的正在自旋的 goroutine 一起抢锁

**问题：**
新来的 goroutine 正在 CPU 上跑，有天然优势，被唤醒的 goroutine 可能抢不过新来的，导致饥饿！

极端情况：一个 goroutine 刚唤醒，锁又被新来的抢走了，再睡，再醒，再被抢... 永远拿不到锁。

---

### 2. 饥饿模式（公平模式）

为了解决饥饿问题，Go 1.9 引入了饥饿模式。

**触发条件：** 当一个 goroutine 等待锁的时间超过 1ms，就把锁切换到饥饿模式。

**饥饿模式下的行为：**
- 锁释放时，直接把锁交给队列头部的第一个 goroutine，不跟新来的抢
- 新来的 goroutine 不准自旋，直接去队列尾部排队
- 不公平！但保证了等待最久的 goroutine 一定能拿到锁

**退出饥饿模式的条件：**
- 当前 goroutine 是队列里最后一个等待者，拿到锁后退出饥饿模式
- 当前 goroutine 等待时间小于 1ms，退出饥饿模式

---

### 3. 两种模式对比

| 特性 | 正常模式 | 饥饿模式 |
|------|---------|---------|
| 性能 | 高（减少上下文切换） | 低（按顺序排队） |
| 公平性 | 不公平，新来的可能抢赢 | 公平，FIFO，先到先得 |
| 适用场景 | 锁竞争不激烈 | 锁竞争激烈，有 goroutine 等太久 |

**设计哲学：** 大部分时间用正常模式追求高性能，真的出现饥饿了就切换到饥饿模式保证公平性。

**面试高频追问：为什么不一直用饥饿模式？**
- 性能差！正常模式下可以利用自旋，很多时候不需要上下文切换
- 饥饿模式是兜底机制，不是常态，只有真的出现饥饿了才用

---

## 四、自旋机制（面试高频）

加锁的时候不会立刻去休眠排队，而是先自旋几次试试。

---

### 自旋的四个条件（必须同时满足）

1. **次数限制：** 最多自旋 4 次
2. **多核 CPU：** 单核 CPU 自旋没用，其他 goroutine 跑不起来，锁永远不会释放
3. **GOMAXPROCS > 1：** 至少要有两个 P，不然自旋也是白忙
4. **P 本地的运行队列为空：** 当前 P 没其他事干，自旋不白占 CPU

**设计非常保守！** 只有在「自旋真的有可能拿到锁，而且不影响别人」的时候才自旋。

---

### 自旋到底在做什么？

执行 `PAUSE` 指令，告诉 CPU 我现在在等一下，你可以先做别的事，别把流水线冲掉。

每次自旋大概 30ns，4 次就是 120ns，非常短。但如果这期间锁释放了，就省掉了一次上下文切换（~1000ns），非常划算。

## 五、加锁完整流程

```
开始
  ↓
Lock() 被调用
  ↓
┌─────────────────────────────────────────┐
│ 第一步：CAS 抢锁                          │
│  state 从 0 -> 1（locked 位设为 1）       │
│  ✅ 成功：直接返回，拿到锁！              │
│  ❌ 失败：锁被别人拿着，继续往下走         │
└─────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────┐
│ 第二步：可以自旋吗？（四个条件同时满足）   │
│  ✅ 可以：自旋 4 次，每次检查锁有没有释放 │
│     自旋期间锁释放了，直接 CAS 抢走       │
│  ❌ 不行：或者自旋完还没拿到，继续往下走   │
└─────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────┐
│ 第三步：计算新 state，准备休眠排队        │
│  - 等待者计数 +1                        │
│  - 如果自己等了超过 1ms，设饥饿位        │
│  - 设 Woken 位，告诉解锁的我正在抢        │
└─────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────┐
│ 第四步：CAS 更新 state                    │
│  ✅ 成功：调用 runtime_SemacquireMutex  阻塞
│  ❌ 失败：期间 state 被别人改了，回到第二步重新判断 │
└─────────────────────────────────────────┘
  ↓
被唤醒，从 Semacquire 返回
  ↓
┌─────────────────────────────────────────┐
│ 第五步：是不是在饥饿模式？                │
│  ✅ 是：直接把锁给我，新的别来抢          │
│  ❌ 不是：再跟新来的 CAS 抢一次          │
└─────────────────────────────────────────┘
  ↓
拿到锁，返回
```

## 六、解锁完整流程

解锁比加锁简单：

```
开始
  ↓
Unlock() 被调用
  ↓
┌─────────────────────────────────────────┐
│ 第一步：Locked 位 -1                     │
│  ✅ 减到 0：锁释放了                     │
│  ❌ 本来就是 0：直接 panic！             │
└─────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────┐
│ 第二步：还有人在等锁吗？或者是不是饥饿模式？│
│  ❌ 没人等，也不饥饿：直接返回           │
│  ✅ 有人在等，或者饥饿模式：继续          │
└─────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────┐
│ 第三步：正常模式 vs 饥饿模式              │
│  正常模式：释放一个信号量，唤醒一个等待者 │
│  饥饿模式：直接把锁交给队列第一个         │
└─────────────────────────────────────────┘
  ↓
返回
```

## 七、常见坑（90% 的 Go 开发者踩过）

---

### 坑 1：Unlock 一个没 Lock 的锁，直接 panic

```go
var mu sync.Mutex
mu.Unlock() // ❌ panic: sync: unlock of unlocked mutex
```

这个是设计如此，故意的。如果你解锁了一个没加的锁，说明你的代码逻辑有问题，应该立刻崩溃，而不是静默失败。

**支付业务特别提醒：** 加锁和解锁一定要在同一个函数里，保证一一对应，不要跨函数传锁，很容易多解锁一次。

---

### 坑 2：Mutex 是值类型，传参拷贝会导致锁失效

```go
// ❌ 错误写法：Mutex 是值传递，拷贝了一份，两个函数用的不是同一个锁！
func bad(mu sync.Mutex) {
    mu.Lock()
    defer mu.Unlock()
    // ...
}

// ✅ 正确写法：传指针
func good(mu *sync.Mutex) {
    mu.Lock()
    defer mu.Unlock()
    // ...
}
```

**面试高频：** struct 里包含 Mutex，这个 struct 也绝对不能值拷贝！

```go
type Server struct {
    mu sync.Mutex
    // ...
}

// ❌ 错误：值拷贝 Server，mu 也跟着拷贝了，变成两个锁！
func process(s Server) { ... }

// ✅ 正确：传指针
func process(s *Server) { ... }
```

一个小技巧：如果你的结构体里有 Mutex，用 `go vet` 可以检查出意外的值拷贝。

---

### 坑 3：死锁

四个必要条件，只要一个不满足就不会死锁：
1. **互斥**：锁只能一个人拿
2. **占有并等待**：拿着锁 A 等锁 B
3. **不可剥夺**：锁只能自己释放，别人不能抢
4. **循环等待**：G1 等 G2 的锁，G2 等 G1 的锁

**最佳实践：** 总是按固定的顺序加锁，比如先锁 A 再锁 B，所有地方都按这个顺序，就不会循环等待。

---

### 坑 4：Lock 之后忘记 Unlock

永远这么写：
```go
mu.Lock()
defer mu.Unlock() // ✅ 加锁之后立刻 defer 解锁
```

不要写在中间，中间如果有 return 或者 panic，就永远不会解锁了，死锁。

---

## 八、最佳实践（支付业务必须遵守）

### 实践 1：锁的粒度越小越好

```go
// ❌ 不好：整个函数都加锁，锁的粒度太大
func process() {
    mu.Lock()
    defer mu.Unlock()

    doDB()      // 100ms
    doNetwork() // 200ms
    doCompute() // 50ms
}

// ✅ 好：只在真正需要保护的临界区加锁
func process() {
    doDB()
    doNetwork()

    mu.Lock()
    doCompute() // 只有这 50ms 需要锁
    mu.Unlock()
}
```

锁的粒度越小，冲突越少，并发越高。

---

### 实践 2：不要在锁里面做 IO、网络调用

IO 太耗时了，持有锁期间做 IO，其他 goroutine 都在等，吞吐量直接掉下来。

---

### 实践 3：优先用 RWMutex 在读多写少的场景

读读不互斥，性能比 Mutex 高很多。支付系统的配置缓存、字典缓存都应该用 RWMutex。

---

### 实践 4：永远不要把锁暴露给外部

锁是你的实现细节，不要对外暴露。不要让调用者帮你加锁解锁，很容易错。

## 九、面试高频问答

| 问题 | 答案 |
|------|------|
| Mutex 两个字段分别是什么？ | state int32 存所有状态，sema uint32 是信号量。 |
| state 每一位的含义？ | 0位locked，1位woken，2位starvation，3~31位是等待者数量。 |
| 为什么把所有状态都放一个 int32？ | 可以用一次 CAS 原子操作同时修改多个状态，不需要额外的锁来保护锁自己。 |
| 正常模式和饥饿模式的区别？ | 正常模式：新来的可以跟被唤醒的一起抢，性能高，但是可能不公平；饥饿模式：按顺序排队，先到先得，保证公平，性能稍低。 |
| 什么时候进入饥饿模式？ | 一个 goroutine 等待锁的时间超过 1ms。 |
| 什么时候退出饥饿模式？ | 1) 当前 goroutine 是最后一个等待者；2) 等待时间小于 1ms。 |
| 自旋的四个条件？ | 1) 最多 4 次；2) 多核 CPU；3) GOMAXPROCS > 1；4) 当前 P 本地队列为空。 |
| 为什么要有自旋？ | 自旋开销很小（30ns），如果刚好锁释放了，省掉一次上下文切换（1000ns），非常划算。 |
| Unlock 一个没 Lock 的锁会怎么样？ | 直接 panic。Go 故意这么设计的，锁的状态不对说明代码有 bug，应该立刻崩溃。 |
| Mutex 可以拷贝吗？ | 绝对不可以。Mutex 是值类型，拷贝之后变成两个独立的锁，完全失效。struct 里包含 Mutex 的话，struct 也必须用指针传递。 |
| 死锁的四个必要条件？ | 互斥、占有并等待、不可剥夺、循环等待。破坏任意一个就不会死锁，最常用的是固定加锁顺序。 |
| Mutex 是公平锁吗？ | 正常模式不公平，饥饿模式公平。大部分时间偏向性能，真的出现饥饿了就保证公平。 |
| 为什么不一直用饥饿模式？ | 性能差，正常模式可以利用自旋，减少上下文切换，大部分场景性能更好。饥饿模式是兜底，不是常态。 |

---

## 十、一句话总结

> Mutex 用一个 int32 存了所有状态，正常模式自旋抢锁追求性能，等太久了就切换到饥饿模式保证公平；记住：绝对不要拷贝锁，加锁之后立刻 defer 解锁，锁的粒度越小越好。
