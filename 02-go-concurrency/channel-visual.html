Go Channel 可视化学习

底层结构 + 读写流程 + 常见坑 + 面试题

hchan 底层结构

type hchan struct {
    qcount   uint    // 当前队列元素个数
    dataqsiz uint    // 环形队列总长度
    buf      Pointer // 环形队列指针
    elemsize uint16  // 每个元素大小
    closed   uint32  // 关闭标志
    elemtype *_type  // 元素类型
    sendx    uint    // 写入位置下标
    recvx    uint    // 读取位置下标
    recvq    waitq   // 等待读的 G 队列
    sendq    waitq   // 等待写的 G 队列
    lock     mutex   // 互斥锁
}

💡 核心三部分

  • 环形队列缓冲区：有缓冲 channel 存数据的地方，无缓冲 channel 没有这部分
  • 等待队列：recvq（读阻塞的 G）和 sendq（写阻塞的 G）
  • 互斥锁：同一时间只允许一个 goroutine 读写 channel

向 channel 写数据流程

1 recvq 不为空？（有 G 在等读）

是 → 直接把数据写给等待的 G，唤醒它，结束

2 缓冲区有空位？

是 → 数据写入 buf，qcount++，sendx++，结束

3 都不满足？

当前 G 加入 sendq，阻塞等待被读 G 唤醒

📝 关键结论

  • 无缓冲 channel（size=0）直接走步骤 1 或 3，跳过缓冲区
  • 写阻塞的 goroutine 会被读的 goroutine 唤醒
  • 向已关闭的 channel 写数据 → 直接 panic

从 channel 读数据流程

1 sendq 不为空 且 无缓冲区？

是 → 直接从等待写的 G 里读数据，唤醒它，结束

2 sendq 不为空 且 缓冲区满了？

是 → 从 buf 队首读，再从 sendq 取一个 G 的数据写到 buf 队尾，唤醒它，结束

3 缓冲区有数据？

是 → 直接从 buf 读，qcount--，recvx++，结束

4 都不满足？

当前 G 加入 recvq，阻塞等待被写 G 唤醒

💡 最容易忽略的细节

步骤 2 是很多资料没讲清楚的

当缓冲区满了，同时还有 G 在等写的时候，读操作会做两件事：

  1. 从 buf 队首读出一个元素
  2. 从 sendq 取出一个等待写的 G，把 G 要写的数据放到 buf 队尾
  3. 唤醒那个等待写的 G

这样缓冲区永远保持满的状态，避免数据丢失。

面试高频追问

Q: 读已关闭的 channel 会怎样？

A: 如果缓冲区还有数据 → 正常读；读完之后 → 返回类型零值，不会阻塞，不会 panic。

常见坑 & 最佳实践

❌ 坑 1：goroutine 泄漏（最常见）

// 错误写法
func leak() {
    ch := make(chan int)  // 无缓冲
    go func() {
        ch <- result  // 没人读就永久阻塞
    }()

    select {
    case v := <-ch:
        return v
    case <-time.After(time.Second):
        return nil  // 超时返回，子 G 卡死
    }
}
// 正确写法
func noLeak() {
    ch := make(chan int, 1)  // 缓冲 1
    go func() {
        ch <- result  // 有空位，写完就退出
    }()

    select {
    case v := <-ch:
        return v
    case <-time.After(time.Second):
        return nil
    }
}

原则：启动 goroutine 写 channel 前，一定要想：如果读端退出了，写端会不会堵死？

❌ 坑 2：close 时机不对

操作 结果
关闭 nil channelpanic
重复关闭同一个 channelpanic
向已关闭的 channel 写数据panic
从已关闭的 channel 读数据正常，返回零值 + false

原则：永远是生产者负责 close channel，消费者只负责感知关闭。不要在消费者那边 close。

❌ 坑 3：time.After 内存泄漏

for {
    select {
    case msg := <-msgCh:
        // 处理消息
    case <-time.After(time.Minute):  // ❌ 每次循环都会创建新定时器！
        // 超时
    }
}

// 定时器不会在 select 退出时立刻停止，直到 1 分钟后才释放
// 高并发场景下会积累大量未过期的定时器，内存暴涨

解决：循环外创建定时器，或者用 context.WithTimeout

❌ 坑 4：range 时忘记 close

go func() {
    for v := range ch {  // 如果 ch 没 close，这里会永远等下去
        fmt.Println(v)
    }
}()

// 写端退出了但没 close(ch) → 读端 goroutine 永久阻塞

面试高频题（点击看答案）

Q1: channel 底层结构是什么？

▼

channel 底层是 hchan 结构体，包含三部分：

  1. 环形队列缓冲区：qcount（当前元素数）、dataqsiz（总容量）、buf（数据指针）、sendx（写位置）、recvx（读位置）
  2. 等待队列：recvq（读阻塞的 G）、sendq（写阻塞的 G）
  3. 其他：互斥锁 lock、元素类型 elemtype、关闭标志 closed

Q2: 有缓冲和无缓冲 channel 区别？

▼
  • 同步 vs 异步：无缓冲是同步通信，写必须等有人读才能返回；有缓冲是异步，缓冲区有空位就能写成功
  • 数据流向：无缓冲是 G 直接到 G 拷贝；有缓冲先走 buf，满了才阻塞
  • 创建方式：make(chan int) vs make(chan int, 10)

Q3: 向 channel 写数据的完整流程？

▼
  1. 先加锁
  2. 如果 recvq 不为空（有 G 在等读）→ 直接把数据写给第一个等待的 G，唤醒它，解锁，结束
  3. 如果缓冲区有空位 → 数据写入 buf，qcount++，sendx++，解锁，结束
  4. 以上都不满足 → 当前 G 加入 sendq，释放锁，阻塞等待

Q4: 关闭 channel 会发生什么？

▼
  • 把 recvq 中所有读阻塞的 G 全部唤醒，每个 G 读出类型零值
  • 把 sendq 中所有写阻塞的 G 全部唤醒 → 这些 G 继续执行写操作时会发现 channel 已关闭，直接 panic
  • 注意：close 不会主动清空缓冲区，里面的数据还能正常读

Q5: 哪些操作会导致 panic？

▼
  1. 关闭值为 nil 的 channel
  2. 重复关闭同一个 channel
  3. 向已经关闭的 channel 写数据

✅ 读已关闭的 channel 不会 panic，会返回零值 + false

Q6: select 多个 case 的执行顺序？

▼

随机！Go 会把所有 ready 的 case 打乱顺序，然后随机选一个执行。

面试常考场景：两个 channel 同时有数据，select 不会按代码顺序选，是随机的。

Q7: 怎么防止 goroutine 泄漏？

▼

最常见的泄漏原因：goroutine 阻塞在 channel 读写上，永远等不到。

  1. 加缓冲区：比如缓冲 1，保证写操作不管有没有人读都能完成
  2. 双向监听取消信号：写端 goroutine 也要监听 context 或者 done channel，超时了自己退出
  3. 生产者负责 close：用 range 读的话，生产完一定要 close，否则 range 永远不退出

Q8: 谁负责 close channel？为什么？

▼

永远是生产者（写端）负责 close。

原因：如果消费者 close 了，生产者后续写数据就会直接 panic。而生产者自己知道什么时候写完，写完 close 通知消费者退出。

反模式：不要让多个生产者去 close，会重复 close 导致 panic。这种情况用 sync.Once 或者 refcount。

Q9: channel 是并发安全的吗？为什么？

▼

是并发安全的。因为 hchan 里面有互斥锁 lock，任何读写操作之前都会先加锁，同一时间只允许一个 goroutine 操作。
