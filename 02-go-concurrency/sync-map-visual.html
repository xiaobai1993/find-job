sync.Map 内部实现动态可视化

Go 1.9 ~ 1.23 双 Map 设计 | 交互式演示

🏗 核心数据结构：read + dirty 双表
📖 read (readOnly) — 前台，无锁原子访问
"user1" → &entry{p:} &Alice 有效
"user2" → &entry{p:} nil nil
"user3" → &entry{p:} expunged expunged
amended: true ← dirty 有 read 没有的 key
📦 dirty (map) — 后台，需要加 Mutex
"user1" → &entry{p:} &Alice 有效
"user4" → &entry{p:} &Dave 新key
misses: 2
关键设计：read["user1"] 和 dirty["user1"] 指向同一个 *entry 指针！
修改已有 key 的 value 只需原子修改 entry.p，不需要加锁。

📝 操作日志
一锁 · 两表 · 三态 · 四提升 · 五操作
记住这 5 个数字，sync.Map 内部实现再也不会忘
1
一锁 — Mutex
只保护 dirty map 的写入。
read map 通过 atomic.Value 无锁访问。
已有 key 更新只 CAS entry.p，不走这把锁。
2
两表 — read + dirty
read：前台快查，原子操作，大部分请求在这解决。
dirty：后台暂存新 key，加锁写入。
两表共享 *entry 指针，改值只需 CAS。
3
三态 — valid / nil / expunged
valid：正常值，可 CAS 更新。
nil：Delete 后软删除，还在 dirty，可 CAS 激活。
expunged：dirty 重建时标记，不在 dirty，必须加锁恢复。
4
四提升 — miss 累积触发
条件：misses >= len(dirty)。
动作：dirty 整体替换为 read，dirty 置 nil，misses 归零。
本质：用户一直在后台找东西，不如把后台搬前台。
5
五操作 — Load/Store/Delete/Range/LoadOrStore
Load：先 read 后 dirty，miss 计数。
Store：read 有就 CAS，没有就加锁写 dirty。
Delete：read 有就 CAS 置 nil，没有就加锁删 dirty。
Range：先提升，再遍历 read。
LoadOrStore：原子读或写。
🧠 一句话记住 Load 流程
read 查 → 没找到？amended? → 加锁 → 查 dirty → miss 满了？提升！
口诀："先查前台再后台，后台找多了就搬前台"
🧠 一句话记住 Store 流程
read 有？ → CAS 更新 (无锁!)
read 没有？ → 加锁 → dirty 有？更新 → dirty 没有？新 key 写 dirty
口诀："老客户无锁改，新客户加锁存后台"
🧠 三态记忆法
🟢

🟡

人不在但工位还在
随时可回来（CAS 激活）
🔴

人走了，工位也撤了
回来要走 HR 流程（加锁）
口诀："在岗无锁找，休假CAS回，离职加锁办"
✅ 适合 sync.Map
• 读多写少（读:写 > 10:1）
• key 集合稳定，很少增删
• 更新已有 key 的 value
• 配置缓存、路由表、连接池
❌ 不适合 sync.Map
• 写多读少
• key 频繁增删
• 需要遍历快照一致性
• 不断写入新 key（dirty 反复重建）
🏪 超市记忆法：把 sync.Map 想象成一家超市

read = 前台货架：顾客（goroutine）自由挑选，无需排队（无锁）。货架上有的商品，直接拿走（CAS）。

dirty = 后台仓库：新货先入仓库，店员（Mutex）才能进出。前台没有的，去仓库找（加锁）。

misses = 投诉次数：顾客在前台找不到东西，每次投诉 +1。投诉太多，店长一怒之下把仓库所有东西搬前台（提升）！

expunged = 下架商品：已被删除的商品标签（nil），在盘点重建仓库时被标记为"永久下架"（expunged），不再出现在仓库清单里。想重新上架？走流程（加锁）。

指针共享 = 价格标签：前台和仓库的同一商品共享同一个价格标签，前台改价，仓库自动同步。这就是 CAS 更新 entry.p 的本质。

dirty 提升为 read!
