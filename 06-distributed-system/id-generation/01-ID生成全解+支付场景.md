## 一、基础概念

### 1. 分布式ID有什么要求？好的分布式ID需要满足哪些特性？

**答：**
分布式ID就是在分布式系统里，全局唯一的ID，比如支付单ID、订单ID、用户ID，都需要全局唯一。

**六大核心要求：**
1. **全局唯一**：任何时候都不会出现重复的ID，最基本的要求
2. **趋势递增**：ID整体是递增的，数据库B+树索引插入的时候不会有页分裂，性能好，这个很重要
3. **高性能**：生成ID要快，最好是纳秒级，不能成为性能瓶颈
4. **高可用**：ID生成服务不能挂，挂了整个系统都创建不了订单支付单了
5. **信息安全**：ID不能被猜出来，不能按顺序爬取数据，比如ID是1,2,3...，别人就能知道你一天有多少订单，顺序爬
6. **可读性**：最好能从ID里看出是什么业务、什么时候生成的，排查问题方便

> 支付场景的ID要求更高，不仅要全局唯一，还要有时间信息，排查问题方便，还要不容易被遍历。

---

### 2. 常见的分布式ID生成方案有哪些？各有什么优缺点？

**答：** 常见的5种方案，各有优缺点：

| 方案 | 唯一性 | 递增性 | 性能 | 可用性 | 安全性 | 适用场景 |
|-----|-------|-------|------|-------|-------|---------|
| **UUID** | 基本唯一 | 完全不递增 | 快 | 极高 | 安全，无法猜测 | 不需要入库的场景，比如traceId，不适合当数据库主键 |
| **数据库自增ID** | 唯一 | 完全递增 | 低 | 低，数据库单点 | 不安全，容易猜 | 小系统，单库单表 |
| **号段模式** | 唯一 | 趋势递增 | 快 | 高，集群部署 | 一般，容易猜 | 大部分业务场景，美团Leaf就是这个 |
| **雪花算法 Snowflake** | 唯一 | 趋势递增 | 极快，本地生成，不需要远程调用 | 高，本地生成，不依赖第三方 | 一般，能反解析出时间和机器ID | ✅ **支付场景最常用！** 我们支付单、订单ID都是用的这个 |
| **Redis 自增INCR** | 唯一 | 完全递增 | 快 | 中，依赖Redis高可用 | 不安全，容易猜 | 短码类ID，比如流水号 |

> 支付场景我们用的是雪花算法，本地生成，不依赖第三方，性能极高，还带时间信息，排查问题非常方便。

## 二、雪花算法（重点，面试100%问）

### 3. 雪花算法原理是什么？64位分别是怎么分的？

**答：**
雪花算法是Twitter开源的分布式ID生成算法，生成的是一个64位的long型整数，分四个部分：

```
0 - 0000000000 0000000000 0000000000 0000000000 0 - 0000000000 - 000000000000
│   │                        timestamp(41位)                 │ 机器ID(10位)  │ 序列号(12位)
│   │                                                          │                │
└─ 最高位符号位，永远是0，保证ID是正数
```

**四部分详解：**
1. **第1位：符号位**，固定是0，因为ID是正数，不用负数
2. **第2-42位：41位时间戳**，毫秒级，41位的时间戳可以用 2^41 / (1000*60*60*24*365) ≈ 69年，足够用了，从服务上线开始算，能用69年
3. **第43-52位：10位机器ID**，最多支持 2^10 = 1024 个机器节点，一般分成5位机房ID + 5位工作机器ID，最多32个机房，每个机房32台机器
4. **第53-64位：12位序列号**，同一毫秒内的计数器，最多支持 2^12 = 4096个ID，也就是同一毫秒同一台机器最多生成4096个ID，完全够用，一般业务都达不到这么高的并发

> 简单算一下，1024台机器，每毫秒每台4096个ID，理论QPS可以到 1024 * 4096 * 1000 = 400多万，完全可以支撑任何业务的并发量，包括支付大促。

### 4. 雪花算法有什么问题？怎么解决？

**答：** 必问！雪花算法最大的问题就是**时钟回拨**

**问题1：时钟回拨**
服务器的时间如果往回调了，就可能生成重复的ID，因为时间戳部分变小了，之前已经用过的时间戳又回来了，就会生成重复的ID，这是雪花算法最大的问题。

**怎么解决时钟回拨？**
1. **简单方案：回拨时间短就等待**，如果回拨时间小于50ms，就等着，等时间追上来了再继续生成ID
2. **回拨时间长就报错**，如果回拨超过了阈值，比如1秒，就抛异常，拒绝服务，防止生成重复ID
3. **优化方案：时间戳取之前最大的时间戳 + 序列号**，回拨了不用等，直接用之前最大的时间戳，序列号继续递增，等时间追上来了再切回真实时间
4. **机器号动态分配**：用ZooKeeper或者配置中心动态分配机器号，启动的时候拿机器号，不用手动配置，也可以避免机器号重复
5. **兜底：校验重复**，生成的ID落库的时候如果唯一索引冲突了，就重试生成，兜底保证不重复

**问题2：机器号重复**
如果两台机器配置了一样的机器ID，就会生成重复的ID
- 解决：机器号不要写死配置，用配置中心或者ZooKeeper动态分配，启动的时候自动拿不重复的机器号，或者用IP哈希生成机器号，只要IP不重复就没问题

**问题3：序列号不够用**
极端高并发下，同一毫秒4096个序列号不够用
- 解决：等到下一毫秒再生成，或者把序列号位数调大，机器ID位数调小一点，根据自己的业务量调整位分配

---

### 5. 雪花算法怎么优化？针对支付场景的优化？

**答：** 我们的支付场景是这么优化的：
1. **调整位分配**：我们机器没有那么多，不需要10位机器ID，就改成5位机器ID（32台机器足够），7位序列号改成17位，同一毫秒最多13万ID，完全够大促用，时间戳还是41位，不影响使用年限
2. **增加业务位**：在机器ID或者序列号里加几位业务类型，比如支付单是1，退款单是2，订单是3，拿到ID就能知道是什么业务的，排查问题非常方便
   > 比如我们拿到一个ID，反解析出来业务位是1，就知道是支付单，不用去各个表查，太方便了
3. **时钟回拨优化**：回拨小于100ms就等待，超过1s就报警，同时用之前最大的时间戳+序列号兜底，绝对不会生成重复ID
4. **机器号自动分配**：启动的时候从注册中心拿机器号，自动分配，不用手动配置，避免机器号重复

## 三、支付场景落地实践

### 6. 你们支付的ID是怎么生成的？用的什么方案？

**答：** 直接说你们的方案，面试官肯定感兴趣

我们支付单、退款单、流水号的ID都是用的优化版雪花算法：
1. **本地生成**，每个服务实例启动的时候自动分配一个5位的机器号，总共支持32个实例，完全够我们用
2. **加了3位业务位**：支付单是1、退款单是2、换单是3，拿到ID直接就能知道是什么业务的，排查问题非常方便，不用去各个表查
3. **时间戳还是41位**，从2020年开始算，能用69年，完全够用
4. **序列号19位？不对，总64位，符号位1+41时间+3业务+5机器+14序列号，序列号14位同一毫秒16384个ID，大促完全够用
5. **时钟回拨处理**：回拨小于50ms就等，超过50ms就用之前最大的时间戳+序列号，超过1s就报警，保证绝对不会生成重复ID
6. **兜底校验**：ID入库的时候有唯一索引，就算极端情况重复了，数据库也会报错，重试生成就行。

**为什么不用号段模式或者数据库自增？**
1. 雪花算法是本地生成，不需要远程调用，性能更高，没有依赖，就算注册中心挂了也能生成ID，高可用更好
2. 带时间和业务信息，排查问题太方便了，出问题的时候根据ID就能知道是什么时间生成的，什么业务的，比纯数字自增ID好用太多
3. 趋势递增，数据库索引性能好，不会有页分裂。

### 7. 怎么从雪花ID里反解析出时间、机器号、业务信息？

**答：** 这个是加分项，说明你真的用过雪花算法，不是只会背原理
很简单，位运算就行了：
```java
// 反解析时间戳
long timestamp = (id >> 22) + startTimeStamp;
Date createTime = new Date(timestamp);

// 反解析业务位
int bizType = (int)((id >> 19) & 0b111);

// 反解析机器号
int workerId = (int)((id >> 14) & 0b11111);

// 反解析序列号
int seq = (int)(id & 0b11111111111111);
```
我们运维做了个小工具，输入ID就能直接解析出创建时间、业务类型、机器号，排查问题的时候巨方便，比如用户反馈支付出问题，给了个支付单号，我们直接解析出来是什么时候创建的，哪台机器生成的，直接去对应机器查日志，不用去数据库查，省了好多时间。

### 8. 用雪花算法踩过什么坑？

**答：** 说两个真实的，面试官一听就知道你真用过

**坑1：机器号重复，生成重复ID**
最开始机器号是写在配置文件里的，部署的时候运维复制配置，两个实例用了同一个机器号，高峰期生成了重复的支付单ID，入库的时候唯一索引报错了，创建支付单失败
- 解决：改成启动的时候自动从Nacos配置中心拿机器号，自动分配，实例下线就释放，再也不会有重复的机器号了

**坑2：服务器时间同步问题，时钟回拨了2秒**
有一次运维同步服务器时间，把一台机器的时间往回调了2秒，导致那台机器生成的ID重复了，报唯一键冲突
- 解决：加了时钟回拨处理，回拨时间短就等待，时间长就用最大时间戳+序列号，同时禁止运维随便手动改服务器时间，用NTP自动同步时间，回拨控制在毫秒级，再也没出过问题。
