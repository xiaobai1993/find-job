# CAP理论从零理解 + 支付场景

> CAP 不要背“三选二”，要理解：分布式系统发生网络分区时，必须在一致性和可用性之间取舍。

---

## 一、CAP到底是什么？

CAP 是分布式系统里的三个特性：

```text
C = Consistency，一致性
A = Availability，可用性
P = Partition Tolerance，分区容错性
```

一句话理解：

> CAP 说的是：在一个分布式系统里，当发生网络分区 P 的时候，系统只能在一致性 C 和可用性 A 之间二选一。

重点不是简单的“三选二”，而是：

```text
发生网络分区时，C 和 A 不能同时完全满足。
```

---

## 二、C：Consistency，一致性

CAP 里的 C 不是 MySQL ACID 里的 C，它更接近：

> 所有节点在同一时刻看到的数据是一致的。

更准确一点：

> 一个写操作成功之后，后续所有读操作都应该读到这个最新值。

比如支付订单状态从：

```text
待支付 → 已支付
```

写到了节点 A。

如果马上读节点 B，也必须读到：

```text
已支付
```

这就是强一致。

---

## 三、A：Availability，可用性

CAP 里的 A 指的是：

> 每个请求都能在有限时间内得到响应，而且不能返回错误。

注意，它不是说系统永远不宕机，而是说：

```text
只要请求打到一个还活着的节点，这个节点就必须给出响应。
```

比如节点 A 和节点 B 网络断开了，请求打到节点 B。

如果 B 说：

```text
我现在不确定数据对不对，所以我拒绝服务。
```

这就是牺牲了可用性 A。

---

## 四、P：Partition Tolerance，分区容错性

P 指的是：

> 分布式系统在节点之间网络断开、消息丢失、延迟严重的情况下，仍然能继续运行。

网络分区不是节点宕机，而是：

```text
节点 A 和节点 B 都活着，但是它们之间网络不通了。
```

正常情况：

```text
Node A  <----网络正常---->  Node B
```

网络分区：

```text
Node A  xxxx 网络断开 xxxx  Node B
```

只要是分布式系统，P 基本无法放弃，因为网络故障一定可能发生。

---

## 五、为什么 CAP 不能三个都要？

关键在于：

```text
分布式系统必须面对网络分区 P。
```

只要系统是多节点部署，就可能遇到：

- 机房之间网络断开
- 跨 AZ 网络抖动
- 节点之间延迟过高
- 防火墙规则错误
- DNS 异常
- 网络包丢失

所以实际工程里不是讨论“要不要 P”，而是：

```text
当 P 发生时，你选择 C 还是选择 A？
```

---

## 六、用支付订单理解 CAP

假设支付系统有两个节点：

```text
北京节点 A
上海节点 B
```

订单 `order_100` 初始状态：

```text
待支付
```

用户在北京节点 A 完成支付：

```text
order_100 = 已支付
```

正常情况下，A 会把状态同步给 B。

但现在网络分区了：

```text
A 和 B 之间网络断了
B 不知道 A 已经把订单改成已支付
```

这时候另一个请求打到 B，查询订单状态。

B 有两个选择。

---

## 七、选择 CP：保证一致性，牺牲可用性

B 可以说：

```text
我现在联系不上 A，不确定自己数据是不是最新的。
为了不返回错误状态，我拒绝服务。
```

这样：

- 好处：不会返回旧数据，不会把已支付订单说成待支付
- 坏处：用户请求失败，可用性下降

这就是 CP：

```text
保证 C
容忍 P
牺牲 A
```

适合：

- 支付扣款
- 账户余额
- 退款
- 分布式锁
- 配置中心强一致场景
- 支付状态终态更新

支付场景里，CP 的原则是：

> 宁可提示“系统繁忙，请稍后重试”，也不能重复扣钱、超额扣钱、错账资损。

---

## 八、选择 AP：保证可用性，牺牲一致性

B 也可以说：

```text
虽然我联系不上 A，但我仍然对外服务。
我本地看到订单还是待支付，那我就返回待支付。
```

这样：

- 好处：用户请求有响应，系统可用
- 坏处：返回了旧数据，短时间不一致

等网络恢复后，再把 A 和 B 的数据同步一致。

这就是 AP：

```text
保证 A
容忍 P
牺牲 C
```

适合：

- 商品评论
- 点赞数
- 消息未读数
- 推荐系统
- 日志系统
- 缓存
- Feed 流
- 支付成功后的异步通知

AP 的核心思想是：

> 短时间不一致可以接受，后续通过异步同步、重试、补偿、对账达到最终一致。

---

## 九、CAP不是简单“三选二”

很多人会说：

> CAP 三选二。

这个说法不够准确。

更准确是：

> 在没有网络分区的时候，系统可以同时满足 C 和 A。只有发生网络分区 P 的时候，才必须在 C 和 A 之间取舍。

所以实际工程里讨论的是：

```text
发生网络分区时，系统选择 CP 还是 AP？
```

---

## 十、常见系统属于 CP 还是 AP？

### 1. ZooKeeper / etcd：偏 CP

ZooKeeper 和 etcd 都依赖多数派协议。

比如 3 个节点：

```text
ZK1
ZK2
ZK3
```

写入必须多数派确认：

```text
至少 2 个节点确认
```

如果网络分区：

```text
ZK1 | ZK2 ZK3
```

只有拥有多数派的一边可以继续服务，少数派会停止服务。

所以它们保证一致性，牺牲部分可用性，是典型 CP。

适合：

- 分布式锁
- Leader 选举
- 配置中心
- 服务注册的强一致场景

---

### 2. Redis 主从 / Redis Cluster：更偏 AP

Redis 主从复制是异步的。

可能出现：

```text
客户端写主节点成功
主节点还没同步给从节点
主节点挂了
从节点提升为新主
刚才写入的数据丢失
```

这说明 Redis 更重视性能和可用性，不是强一致系统，所以更偏 AP。

Redis Cluster 也是类似，主从同步异步，故障切换时可能丢少量数据。

---

### 3. Redis 分布式锁为什么有争议？

因为 Redis 偏 AP，不是强一致系统。

极端情况下可能出现：

```text
客户端 A 在主节点加锁成功
锁还没同步到从节点
主节点挂了
从节点提升为主
客户端 B 又加锁成功
```

结果：

```text
A 和 B 都以为自己拿到了锁
```

所以 Redis 锁适合大多数业务互斥场景，但不能作为资金安全的唯一保障。

支付系统里应该这样设计：

```text
Redis 锁：降低并发冲突
数据库唯一索引：防重复
状态机条件更新：防状态错乱
乐观锁/事务：最终兜底
对账系统：最终发现和修正
```

面试时可以说：

> 我们可以用 Redis 锁提高并发控制效率，但真正的资金安全不能只靠 Redis 锁，数据库约束和状态机条件更新才是最终兜底。

---

### 4. MySQL 主从：异步复制时偏 AP

普通 MySQL 主从如果是异步复制，也不能保证强一致。

可能出现：

```text
主库写成功
还没同步到从库
主库挂了
从库提升
刚才的数据丢失
```

所以普通异步主从更偏 AP。

如果使用强同步复制，或者基于 Raft/Paxos 的数据库，才会更偏 CP。

---

## 十一、支付系统里怎么应用 CAP？

支付系统不是所有地方都选 CP，也不是所有地方都选 AP，而是按业务分层。

---

### 1. 核心资金链路偏 CP

包括：

- 扣余额
- 退款
- 支付状态终态更新
- 账户流水
- 幂等记录

原则：

> 宁可失败重试，也不能错账资损。

例如支付状态更新：

```sql
UPDATE payment_slip
SET status = 'SUCCESS'
WHERE id = ? AND status = 'PROCESSING';
```

只有状态符合预期才更新，这就是用数据库条件更新保证一致性。

---

### 2. 通知链路偏 AP

包括：

- 支付成功通知订单
- 通知 BI
- 通知财务
- 发消息给下游系统

这些可以最终一致。

如果订单系统暂时没收到支付成功通知，可以通过：

- MQ 重试
- 定时补偿
- 用户查询时主动查支付状态
- T+1 对账兜底

最终把订单状态修正过来。

---

### 3. 缓存链路偏 AP

包括：

- 商户配置缓存
- 支付渠道配置缓存
- 用户展示状态

短时间不一致可以接受，最终刷新即可。

但核心支付状态不能只依赖缓存。

---

### 4. 对账系统是最终兜底

对账本质上就是接受分布式系统里的短时间不一致，然后通过 T+1 对账把最终结果校正回来。

比如：

```text
支付系统成功，订单系统没更新
第三方渠道账单成功，内部流水缺失
内部支付单成功，账户子流水缺失
```

对账系统会发现差异，然后进入自动补偿或人工处理流程。

所以支付系统的整体思路是：

```text
核心资金操作偏 CP
外围通知和异步链路偏 AP
最终通过可靠消息、重试补偿和对账系统实现最终一致
```

---

## 十二、BASE 和 CAP 有什么关系？

BASE 是 AP 系统的一种工程思想。

BASE 是：

```text
BA = Basically Available，基本可用
S = Soft state，软状态
E = Eventually consistent，最终一致
```

意思是：

> 不追求每一刻都强一致，而是允许短时间不一致，最终达到一致。

比如支付成功后通知订单：

```text
支付系统已经成功
订单系统暂时还是待支付
```

这是软状态。

之后通过 MQ 重试或查询补偿：

```text
订单最终变成已支付
```

这是最终一致。

## 十三、面试标准回答

### Q：你怎么理解 CAP？

**答：**

CAP 指的是分布式系统里的三个特性：Consistency 一致性、Availability 可用性、Partition Tolerance 分区容错性。

C 表示写成功之后，后续所有读都能读到最新数据；A 表示每个请求都能在有限时间内得到非错误响应；P 表示系统在网络分区、节点之间通信失败时仍然能继续运行。

CAP 不是简单的三选二，更准确地说，因为分布式系统必须面对网络分区，所以当 P 发生时，系统只能在 C 和 A 之间取舍。

如果选择 CP，就是宁可部分节点不可用，也要保证数据一致，比如 ZooKeeper、etcd，适合分布式锁、配置中心、账户扣款这类强一致场景。

如果选择 AP，就是宁可短时间数据不一致，也要保证服务可用，比如缓存、消息通知、点赞数、Feed 流这些场景，后面通过异步同步达到最终一致。

在支付系统里，核心资金链路，比如扣款、退款、支付状态终态更新，一般偏 CP，宁可失败重试也不能错账；但支付成功通知订单、BI、财务这些外围链路偏 AP，通过 MQ 重试、补偿任务、对账系统保证最终一致。

## 十四、一句话记忆

```text
CAP 不是告诉你随便选两个。
而是告诉你：网络分区一定会发生，发生时你要在一致性和可用性之间做取舍。
```

支付系统里的选择：

```text
钱相关：偏 CP
通知展示：偏 AP
最终靠对账兜底
```
