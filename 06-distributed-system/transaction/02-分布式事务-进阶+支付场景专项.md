# 分布式事务 - 进阶篇 & 支付场景专项

> 重点：可靠消息最终一致性、本地消息表、Saga，以及支付业务实际落地实践

---

## 一、可靠消息最终一致性（支付场景最常用！）

### 1. 可靠消息最终一致性方案原理是什么？

**答：** 这是支付业务90%的分布式事务场景用的方案，一定要讲透

**核心思想：**
只要上游服务的事务提交成功了，下游服务最终一定能消费成功，达到最终一致，不用实时同步，不用强一致。

**执行流程：**
```
1. 上游服务执行本地事务，同时发消息给MQ
2. MQ 保证消息一定投递成功，不丢
3. 下游服务消费消息，执行本地事务，失败就重试，直到成功
4. 超过重试次数进死信，告警人工处理
5. 最终对账兜底，保证100%一致
```

**优点：**
1. 性能极高，没有同步阻塞，和正常发消息没区别
2. 侵入性低，不用写额外的接口，和普通MQ消费一样
3. 可用性高，不会有锁资源的问题
4. 适合大部分异步场景，支付场景绝大多数都是异步的

**缺点：**
1. 不保证实时一致，是最终一致，可能会有几秒到几分钟的延迟
2. 只适合上下游都是异步的场景，同步等待结果的场景不适用

> 支付场景几乎所有的跨服务通知场景都是用这个方案：支付成功通知订单、通知对账、通知风控、通知用户，全部用可靠消息最终一致性，性能好又简单。

---

### 2. 本地消息表方案是什么？和可靠消息有什么区别？

**答：** 本地消息表是可靠消息的增强版，解决「本地事务提交了，消息没发出去」的问题，是支付核心消息的兜底方案。

**执行流程：**
```
1. 上游服务在同一个本地事务里，执行业务逻辑 + 往本地消息表插一条消息记录，状态是待发送
2. 事务提交成功
3. 后台定时任务定时扫描本地消息表里待发送的消息，发送到MQ
4. 发送成功了就把消息状态改成已发送，失败就重试
5. 下游消费消息，处理成功了就ACK，失败就重试
6. 后台定时任务扫描超过一定时间还没消费成功的，告警人工处理
```

**解决了什么问题？**
解决了「本地事务提交成功了，但是发MQ的时候网络断了，消息没发出去」的问题，只要本地事务提交了，消息存在数据库里，定时任务一定会重试发出去，最终一定能发到MQ，保证100%不丢消息。

> 支付场景的核心消息，比如支付成功、退款成功这些，我们都是用本地消息表兜底的，就算MQ全挂了，消息也存在本地数据库里，恢复了还能补发，绝对不会丢消息。

---

### 3. 最大努力通知方案是什么？和可靠消息有什么区别？

**答：**
最大努力通知就是可靠消息的简化版，适合非核心、允许丢的场景：
1. 上游发消息，最多重试几次，下游收不到就算了，不兜底
2. 下游可以主动调用上游接口查询结果，自己补
3. 没有本地消息表兜底，没有对账兜底

**适用场景：** 短信通知、站内信、非核心的统计类通知，丢了也没关系的场景。

**可靠消息 vs 最大努力通知 区别：**
| 方案 | 可靠性 | 兜底 | 适用场景 |
|-----|-------|------|---------|
| 可靠消息 + 本地消息表 | 100%不丢，最终一定成功 | 定时重试 + 死信告警 + 对账兜底 | 核心业务、资金相关 |
| 最大努力通知 | 尽力送，可能丢 | 没有兜底，最多重试几次 | 非核心、丢了也无所谓的 |

## 二、Saga 模式

### 4. Saga 模式是什么？和 TCC 有什么区别？

**答：**
Saga 是长事务解决方案，把一个大的分布式事务拆成多个本地小事务，每个小事务都有对应的补偿回滚接口，如果某个步骤失败了，就按逆序调用之前所有已经成功的步骤的补偿接口，把所有操作都回滚回去。

**两种实现方式：**
1. **编排式**：有个协调者，统一调度各个服务，成功就往下走，失败就调用补偿
2. ** choreography 编排式**：各个服务自己触发下一个步骤，通过事件驱动，没有中心协调者

**和TCC的区别：**
| 维度 | TCC | Saga |
|-----|-----|------|
| 阶段 | Try-Confirm-Cancel 三个阶段，Try预留资源 | 每个步骤直接提交，失败了补偿回滚 |
| 隔离性 | 有隔离，Try阶段冻结了资源，其他事务不能用 | 没有隔离，操作直接提交，补偿的时候可能已经被其他事务改了 |
| 侵入性 | 侵入性极高，每个接口要写三个方法 | 侵入性中等，每个操作写一个正常接口一个补偿接口 |
| 适用场景 | 短流程、资金类、强隔离要求 | 长流程、多步骤、跨公司跨系统的流程 |
| 回滚难度 | 简单，冻结的资源释放就行 | 复杂，操作已经提交了，可能要做逆向操作，比如钱已经打给用户了，要追回来 |

> 支付场景里跨多个系统的长流程，比如用户提现，要先检查余额、扣余额、调用银行打款、记账，这种长流程就适合用Saga模式，比TCC简单。

## 三、支付场景落地实践（重点！面试就说这个）

### 5. 你们支付服务的分布式事务是怎么做的？

**答：** 直接说你们的实际方案，这道题面试官100%会问

我们没有用复杂的Seata之类的框架，就是用最稳妥的「可靠消息最终一致性 + 本地消息表 + 对账兜底」的方案，简单可靠，出问题好排查：

**核心流程以支付成功为例：**
1. **本地事务**：支付服务扣款成功，更新支付单状态，在同一个事务里往本地消息表插一条支付成功消息，状态待发送，提交事务
2. **消息发送**：后台定时任务每秒扫一次本地消息表，把待发送的消息发到Pulsar MQ，发送成功就把消息状态改成已发送，失败就重试
3. **下游消费**：订单、对账、风控、通知这些下游服务各自消费消息，处理成功就ACK，处理失败就自动重试，超过3次进死信，告警人工处理
4. **兜底对账**：每天凌晨跑全量对账任务，核对支付服务和各个下游系统的状态，有不一致的自动补单或者人工介入，保证最终100%一致

**为什么不用TCC或者Seata？**
1. 太复杂了，侵入性太高，每个服务都要改接口，开发量大，出问题难排查
2. 我们大部分场景都是异步通知，不需要同步等待结果，可靠消息完全够用
3. 简单的方案最稳定，出问题好排查，支付系统要的就是稳定，不要为了用框架而用框架

**只有极少数场景用TCC**：比如换单场景，旧单退款 + 新单支付，这两个操作必须要么都成功要么都失败，我们就用TCC模式，Try阶段冻结旧单的退款和新单的支付，Confirm就都提交，Cancel就都释放。

### 6. 分布式事务场景踩过什么坑？

**答：** 说2-3个真实的坑，显得你有经验

**坑1：没有本地消息表，MQ挂了导致消息丢了**
最开始我们没用本地消息表，直接事务提交了就发MQ，有一次MQ集群故障，发消息失败，本地事务已经提交了，但是消息没发出去，下游没收到，导致订单还是待支付状态，用户付了钱但是订单没更新，最后对账才发现
- 解决：加本地消息表，所有核心消息都先存数据库，定时任务重试发送，就算MQ挂了也不会丢，恢复了还能补发

**坑2：下游消费失败，无限重试，导致死循环**
有一次下游订单服务的代码出了bug，处理支付成功消息一直报错，MQ就无限重试，打满了日志，也占了消费线程
- 解决：加最大重试次数，超过3次就进死信队列，告警人工处理，不要无限重试

**坑3：TCC的悬挂问题**
最开始写换单的TCC的时候没考虑悬挂问题，Cancel执行完了，Try才因为网络延迟到了，执行成功了，旧单的退款冻结了，没人释放，导致用户余额一直冻结用不了
- 解决：执行Try的时候先检查有没有执行过Cancel，如果已经Cancel了就不执行Try了，直接返回失败，解决了悬挂问题

---

### 7. 分布式事务怎么保证最终一定一致？

**答：** 多层兜底，永远不要只靠一个方案：
1. **第一层：本地消息表 + MQ可靠投递**，保证消息一定发出去，一定能投递到下游
2. **第二层：消费重试 + 死信告警**，消费失败自动重试，超过次数告警人工处理
3. **第三层：定时对账兜底**，每天全量核对一遍，不一致的自动补，就算前面所有层都挂了，对账也一定能发现，补回来
> 支付系统里，对账是最终的兜底，只要对账做的好，就算中间环节出再多问题，最终也不会出资金问题。

## 面试答题技巧
分布式事务这块，你就重点突出两点：
1. **你们没有用花里胡哨的Seata之类的框架，就是用最简单最稳妥的可靠消息+本地消息表+对账兜底**，面试官就喜欢这种，因为生产环境就是越简单越稳定，复杂的框架出问题根本排查不了
2. **踩过的坑**，比如本地消息表之前丢过消息，TCC踩过悬挂问题，这些一说出来，面试官就知道你是真的在生产环境做过分布式事务，不是只会背概念。
