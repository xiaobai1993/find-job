# 分布式事务专题 PDF 复习版 + 支付场景

> 这份笔记是对《分布式事务专题-v1.1.pdf》的整理。重点不是背概念，而是把几种方案放到真实业务里理解：什么场景需要强一致，什么场景只要最终一致，什么场景根本不适合上复杂分布式事务框架。

---

## 一、这份 PDF 的核心脉络

PDF 的整体思路可以概括为：

```text
本地事务
  ↓
分布式系统拆服务后，本地事务不够用了
  ↓
CAP / BASE 说明为什么很多场景选择最终一致
  ↓
常见分布式事务方案：2PC、TCC、可靠消息最终一致、最大努力通知
  ↓
通过转账、注册、开户、满标审核等案例分析方案选择
```

一句话总结：

> 分布式事务不是为了追求“所有场景都强一致”，而是在一致性、性能、可用性、开发复杂度之间做权衡。

---

## 二、为什么会有分布式事务问题？

单体系统里，一个业务操作只访问一个数据库，可以直接依赖数据库本地事务：

```sql
begin;
update account set balance = balance - 100 where user_id = 1;
insert into account_log(...);
commit;
```

这时数据库能保证 ACID。

但服务拆分后，一个业务动作可能跨多个服务、多个数据库：

```text
订单服务：创建订单
支付服务：扣余额
积分服务：加积分
库存服务：扣库存
```

每个服务只能保证自己的本地事务，无法天然保证“所有服务一起成功或一起失败”。典型问题是：

```text
支付扣款成功了
订单状态更新失败了
积分发放失败了
```

这就产生了分布式事务问题。

---

## 三、先记住一个原则：能不用分布式事务就不用

PDF 最后总结里有一个很重要的观点：

> 条件允许时，优先选择本地事务单数据源，因为它最简单、最稳定、性能最好。

工程里应该先问：

1. 能不能把强一致的数据放到同一个服务、同一个数据库事务里？
2. 能不能通过业务拆分，把同步强一致改成异步最终一致？
3. 这个场景真的需要分布式事务吗？还是重试、幂等、对账就够了？

支付系统里也是一样：

```text
核心资金状态：尽量本地事务 + 条件更新 + 幂等
跨服务通知：可靠消息最终一致
外围通知：最大努力通知
最终兜底：对账系统
```

## 四、2PC：强一致但性能差

### 1. 2PC 是什么？

2PC 是 Two Phase Commit，两阶段提交。

它有三个角色：

| 角色 | 作用 |
|---|---|
| 事务管理器 TM | 全局协调者，决定提交还是回滚 |
| 资源管理器 RM | 数据库、消息系统等实际资源 |
| 应用程序 AP | 发起业务请求 |

两个阶段：

```text
阶段一：Prepare
协调者问所有参与者：能不能提交？
参与者执行本地事务但不提交，锁住资源，返回 Yes/No。

阶段二：Commit/Rollback
如果所有人 Yes，协调者通知全部 Commit。
只要有一个 No，协调者通知全部 Rollback。
```

### 2. 2PC 的优点

```text
一致性强，业务侵入小，理论模型简单。
```

### 3. 2PC 的缺点

| 缺点 | 解释 |
|---|---|
| 同步阻塞 | Prepare 后资源一直锁着，要等协调者最终决定 |
| 性能低 | 网络交互多，锁持有时间长，吞吐量低 |
| 协调者单点 | TM 出问题，参与者可能长期等待 |
| 数据不一致风险 | Commit 阶段部分节点收到提交，部分节点没收到，仍可能不一致 |
| 不适合长事务 | 执行时间越长，资源锁定越久 |

PDF 里的总结非常关键：

> 2PC 最大诟病是阻塞协议。RM 执行分支事务后要等待 TM 决定，此时资源会被锁定，所以很难用于高并发和长流程业务。

### 4. 支付场景怎么回答？

面试可以这样说：

> 2PC 理论上能提供强一致，但在支付这种高并发场景不太适合。因为它会长时间锁资源，吞吐量低，而且协调者异常时会阻塞。我们更倾向于把核心资金更新控制在本地事务内，跨服务部分用可靠消息最终一致和对账兜底，而不是把所有服务放进一个 2PC 全局事务里。

## 五、TCC：业务层面的两阶段提交

### 1. TCC 是什么？

TCC 是：

```text
Try
Confirm
Cancel
```

它不是数据库层面的 XA，而是业务代码层面的事务控制。

| 阶段 | 做什么 | 支付例子 |
|---|---|---|
| Try | 资源检查和预留 | 冻结用户余额、冻结库存 |
| Confirm | 真正提交 | 扣减冻结余额、确认支付成功 |
| Cancel | 取消回滚 | 释放冻结余额、释放库存 |

### 2. TCC 和 2PC 的区别

| 对比项 | 2PC | TCC |
|---|---|---|
| 实现层 | 数据库/资源管理器层 | 业务代码层 |
| 锁粒度 | 数据库资源锁 | 业务资源预留 |
| 性能 | 较低 | 较高 |
| 侵入性 | 较低 | 很高 |
| 复杂度 | 协议复杂 | 业务开发复杂 |
| 适合场景 | 小规模强一致事务 | 核心资金、库存、账户类业务 |

PDF 里的观点是：

> TCC 处理过程放在应用层，能够让应用自己定义数据操作粒度，降低锁冲突，提高吞吐量，但需要每个分支事务都实现 try、confirm、cancel。

### 3. TCC 的三个经典坑

#### 1）幂等问题

Confirm 或 Cancel 可能重复调用，必须保证重复执行不会重复扣款、重复解冻。

解决：

```text
全局事务 ID + 分支事务状态表 + 唯一索引
```

#### 2）空回滚

Try 还没执行成功，Cancel 先到了。

解决：

```text
Cancel 先查 Try 是否成功执行过。
如果没有 Try 记录，写一条 Cancel/空回滚记录，然后返回成功。
```

#### 3）悬挂问题

Cancel 先执行了，之后 Try 请求又因为网络延迟到达。如果 Try 再成功，就没人 Confirm/Cancel，资源会挂住。

解决：

```text
Try 执行前先查是否已经有 Cancel 记录。
如果已经 Cancel，Try 必须拒绝执行。
```

### 4. 支付场景怎么回答？

> TCC 适合资金类强隔离场景，比如跨账户转账、余额冻结、保证金冻结。它的好处是业务层可以自己控制资源预留，不像 2PC 那样长时间锁数据库；缺点是侵入性很强，每个参与方都要实现 Try、Confirm、Cancel，还必须处理幂等、空回滚、悬挂。所以我们不会在所有支付流程里滥用 TCC，只会在真正需要资源预留和强业务隔离的核心场景使用。

## 六、可靠消息最终一致：最常用的异步方案

PDF 里重点讲了“可靠消息最终一致性”，这是互联网业务里最常用的一类方案。

### 1. 解决什么问题？

它解决的是：

```text
上游本地事务成功后，下游最终一定能收到消息并完成处理。
```

例如用户注册后加积分：

```text
用户服务新增用户
积分服务增加积分
```

这两个操作不一定要在同一秒完成，只要最终一致即可。

### 2. 本地消息表方案

核心流程：

```text
1. 用户服务本地事务里：新增用户 + 插入积分消息日志
2. 本地事务提交
3. 定时任务扫描未发送消息
4. 发送消息到 MQ
5. 发送成功后删除消息或标记已发送
6. 积分服务消费消息并增加积分
7. 消费端 ACK 成功，失败则 MQ 重投
```

关键点：

| 点 | 说明 |
|---|---|
| 本地事务绑定消息 | 业务数据和消息日志在同一个本地事务里提交 |
| 定时扫描 | 解决“事务提交了但消息没发出去”的问题 |
| MQ ACK | 解决“消费者处理失败”的问题 |
| 消费端幂等 | 解决消息重复投递导致重复加积分、重复更新的问题 |

### 3. 消费端为什么一定要幂等？

因为 MQ 只能尽量保证消息不丢，但不能保证消息只被消费一次。

可能出现：

```text
消费者处理成功了
还没来得及 ACK 就宕机
MQ 认为没消费成功，又投递一次
```

所以消费端必须做幂等，例如：

```sql
CREATE TABLE de_duplication (
  tx_no varchar(64) PRIMARY KEY,
  create_time datetime
);
```

消费时：

```text
先查 tx_no 是否处理过
没处理过：执行业务 + 插入去重记录
处理过：直接返回成功
```

### 4. 本地消息表的优缺点

| 维度 | 说明 |
|---|---|
| 优点 | 简单、可靠、容易排查，业务可控 |
| 缺点 | 需要维护消息表和扫描任务，有一定延迟 |
| 适合 | 支付成功通知订单、发积分、通知财务、通知风控 |
| 不适合 | 必须同步返回最终结果的强一致场景 |

## 七、RocketMQ 事务消息方案

PDF 里也讲了 RocketMQ 事务消息，它可以理解为“把本地消息表的一部分能力放到了 MQ 里”。

### 1. RocketMQ 事务消息流程

```text
1. Producer 先发送 Half Message 到 MQ Server
2. MQ Server 标记消息为 Prepared，消费者暂时不可见
3. MQ Server 返回发送成功
4. Producer 执行本地事务
5. 本地事务成功：Producer 发送 Commit，消息变为可消费
6. 本地事务失败：Producer 发送 Rollback，消息被删除
7. Producer 挂了或超时：MQ Server 回查本地事务状态
```

### 2. Half Message 是什么？

Half Message 就是半消息：

```text
消息已经到了 MQ，但还不能被消费者看到。
```

只有 Producer 本地事务提交成功后，发送 Commit，消费者才能消费。

### 3. 事务回查是什么？

如果 Producer 执行本地事务后挂了，MQ Server 不知道应该 Commit 还是 Rollback，就会回调 Producer 的检查接口：

```java
RocketMQLocalTransactionState checkLocalTransaction(Message msg)
```

Producer 根据本地事务状态返回：

```text
COMMIT   ：提交消息
ROLLBACK ：回滚消息
UNKNOWN  ：暂时不知道，后续继续回查
```

### 4. RocketMQ 事务消息和本地消息表对比

| 对比项 | 本地消息表 | RocketMQ 事务消息 |
|---|---|---|
| 原子性实现 | 业务数据 + 消息表在本地事务里提交 | Half Message + 本地事务 + Commit/Rollback |
| 消息补偿 | 定时任务扫描消息表 | MQ Server 事务回查 |
| 业务侵入 | 要建消息表、扫描任务 | 要实现事务监听器和回查逻辑 |
| 可排查性 | 很直观，查数据库即可 | 要结合 MQ 状态和本地事务状态查 |
| 适合 | 公司自研可控、强审计场景 | RocketMQ 体系内、希望减少消息表的场景 |

### 5. 支付场景怎么说？

> RocketMQ 事务消息解决的是 Producer 端“消息发送”和“本地事务提交”的一致性问题。它通过 Half Message、Commit/Rollback 和事务回查来保证：本地事务成功，消息最终可投递；本地事务失败，消息不会被消费。但它不能替代消费者幂等，消费端仍然要防重复处理。

## 八、最大努力通知：一致性要求最低

### 1. 什么是最大努力通知？

最大努力通知是：

```text
发送方尽最大努力把业务处理结果通知给接收方。
如果通知失败，会按规则重试。
接收方也可以主动查询发送方结果。
```

PDF 里的充值例子：

```text
账户系统调用充值系统
充值系统完成支付
充值系统通知账户系统充值结果
如果通知失败，按策略重复通知
账户系统也可以主动查充值结果
```

### 2. 最大努力通知的关键机制

| 机制 | 作用 |
|---|---|
| 重复通知 | 失败后按 1min、5min、10min、30min、1h、2h 等间隔重试 |
| 消息校对接口 | 接收方主动查询发送方业务结果 |
| ACK 机制 | 接收方处理成功后返回确认 |
| 时间窗口 | 超过最大通知时间后停止通知，转人工或查询补偿 |

### 3. 和可靠消息最终一致有什么区别？

| 对比项 | 可靠消息最终一致 | 最大努力通知 |
|---|---|---|
| 关注点 | 消息从发送方到接收方必须最终一致 | 尽量把结果通知给接收方 |
| 可靠性责任 | 主要在发送方和 MQ | 主要在接收方主动查询和通知重试 |
| 一致性要求 | 较高 | 较低 |
| 典型场景 | 注册发积分、支付成功通知内部系统 | 银行通知、第三方支付结果通知 |

PDF 里说得很清楚：

> 最大努力通知无法保证消息从发出到接收的一致性，只提供消息接收的可靠性机制。接收方如果没有收到通知，可以主动查询业务处理结果。

### 4. 支付场景怎么说？

> 支付渠道回调其实很像最大努力通知。比如微信、支付宝通知我们支付结果，它们会按规则多次回调；我们如果没收到，也可以主动查询渠道订单状态。所以我们接收回调时一定要做验签、幂等、状态机条件更新，同时还要有主动查询和对账兜底。

## 九、四种方案对比

| 方案 | 一致性 | 吞吐量 | 实现复杂度 | 典型场景 |
|---|---|---|---|---|
| 2PC | 强一致 | 低 | 易/中 | 低并发、短事务、少量资源 |
| TCC | 最终一致/业务强一致 | 中 | 难 | 资金冻结、库存冻结、跨账户转账 |
| 可靠消息最终一致 | 最终一致 | 高 | 中 | 注册发积分、支付成功通知、异步记账 |
| 最大努力通知 | 最终一致，可靠性较弱 | 高 | 易 | 银行通知、支付渠道回调、外部系统通知 |

记忆方式：

```text
2PC：强一致，但慢，锁资源。
TCC：业务强控制，但开发复杂。
可靠消息：最常用，适合内部异步最终一致。
最大努力通知：适合外部通知，靠重试 + 查询兜底。
```

## 十、PDF 里的综合案例怎么理解？

### 1. 用户注册 + 统一账号

业务：

```text
用户中心注册用户
统一账号服务创建登录账号
```

一致性要求较高，因为用户信息和账号信息不一致会导致登录、认证、授权问题。

PDF 分析：

| 方案 | 是否适合 | 原因 |
|---|---|---|
| 可靠消息 | 不太适合 | 只保证消息发出后最终执行，不适合需要失败回滚的注册主链路 |
| 最大努力通知 | 不适合 | 一致性要求太低 |
| 2PC | 可用 | 用户中心和账号服务可作为全局事务参与者 |
| TCC | 可用 | Try 创建不可用用户/账号，Confirm 改为可用，Cancel 删除 |

面试表达：

> 注册主链路如果强依赖账号创建成功，可以用 2PC 或 TCC；但真实互联网系统也常通过业务设计降低一致性要求，比如先注册用户，再异步创建账号，失败后让用户重试或后台补偿。

### 2. 银行存管开户

业务：

```text
P2P 用户中心提交开户资料
跳转银行存管系统开户
银行异步通知开户结果
用户中心更新开户状态
```

PDF 分析：

| 方案 | 是否适合 | 原因 |
|---|---|---|
| 2PC | 不适合 | 银行是外部系统，不可能接入你的全局事务 |
| TCC | 不适合 | 不能要求银行实现你的 Try/Confirm/Cancel |
| 可靠消息 | 不适合或受限 | 外部银行不一定监听你的 MQ |
| 最大努力通知 | 适合 | 银行通知结果，平台可主动查询开户结果 |

面试表达：

> 外部银行、微信、支付宝这类系统不能被我们纳入本地事务或 TCC，所以通常采用最大努力通知：外部系统回调结果，我们做幂等处理；如果没收到回调，就主动查单；最后对账兜底。

### 3. 满标审核生成还款计划

业务：

```text
交易中心审核标的满标
修改标的状态为还款中
通知还款服务生成还款计划
```

PDF 分析：

| 方案 | 是否适合 | 原因 |
|---|---|---|
| 2PC | 不适合 | 生成还款计划耗时长，长事务会锁资源 |
| TCC | 不适合 | 一致性要求没高到必须 TCC |
| 可靠消息 | 适合 | 交易中心改状态后发消息，还款服务异步生成计划 |
| 最大努力通知 | 也可 | 接收方可以查询校对 |

面试表达：

> 对于生成还款计划这类耗时较长、可以异步完成的业务，不应该阻塞主流程。更适合用可靠消息最终一致，主服务先把状态推进到下一步，再由下游异步消费生成计划，失败则重试和告警。

## 十一、结合美餐支付怎么落地

### 1. 支付成功通知订单

适合方案：

```text
可靠消息最终一致 + 本地消息表 + MQ 重试 + 对账兜底
```

流程：

```text
1. Payment 本地事务更新支付单为 SUCCESS
2. 同一个事务写支付成功消息记录
3. 后台任务或消息组件投递到 MQ
4. 订单系统消费消息，把订单改成已支付
5. 消费失败自动重试，超过阈值进 DLQ 告警
6. T+1 对账发现订单未更新时补偿
```

关键点：

```text
支付成功状态不能丢
订单系统消费必须幂等
Payment 侧提供查单接口给下游主动校对
对账系统最终兜底
```

### 2. 支付渠道回调

适合方案：

```text
最大努力通知 + 主动查单 + 状态机条件更新 + 对账
```

因为微信、支付宝、银行都是外部系统，我们不能要求它们参与我们的事务。

处理原则：

```text
验签
幂等
查内部支付单
状态机条件更新
重复回调直接返回成功
异常时主动查渠道订单
T+1 渠道账单对账
```

### 3. 退款

退款比支付更敏感，因为涉及资金回退。

适合组合：

```text
本地事务控制退款单状态
渠道退款结果用最大努力通知/主动查询
退款成功通知订单和财务用可靠消息最终一致
对账兜底
```

### 4. 账户余额扣减

如果余额账户就在 Payment 内部：

```text
优先用本地事务 + 条件更新 + 流水唯一索引
```

如果跨多个账户服务：

```text
核心冻结/扣减可以考虑 TCC
普通通知链路不要用 TCC，使用可靠消息最终一致
```

## 十二、面试高频题

### Q1：分布式事务有哪些方案？

**答：**

常见有 2PC、TCC、可靠消息最终一致、本地消息表、RocketMQ 事务消息、最大努力通知、Saga 等。

2PC 偏强一致，但性能差、锁资源，不适合高并发长事务；TCC 是业务层的 Try/Confirm/Cancel，适合资金冻结、库存冻结这类核心场景，但侵入性强；可靠消息最终一致适合内部异步通知，比如支付成功通知订单；最大努力通知适合外部系统结果通知，比如微信支付宝回调、银行通知；Saga 适合长流程、多步骤、有补偿动作的业务。

---

### Q2：你们支付系统为什么不用 2PC？

**答：**

2PC 会在 Prepare 阶段锁住资源，所有参与者要等协调者最终决定，吞吐量低，而且协调者异常会导致参与者阻塞。支付系统高并发、链路长，如果把订单、支付、账户、财务都放进一个 2PC 全局事务，性能和可用性都会很差。

我们更倾向于核心资金状态用本地事务保证，跨服务通知用可靠消息最终一致，异常通过重试、死信告警和对账兜底解决。

---

### Q3：可靠消息最终一致怎么保证消息不丢？

**答：**

核心是把业务操作和消息记录放到同一个本地事务里。

例如支付成功时，Payment 在一个事务里更新支付单状态，并插入一条待发送消息。事务提交后，即使 MQ 短暂不可用，消息记录也还在数据库里，后台任务可以继续扫描重发。下游消费失败由 MQ 重试，超过阈值进死信队列并告警。消费端必须做幂等，最后通过对账系统兜底。

---

### Q4：RocketMQ 事务消息解决了什么问题？

**答：**

它解决 Producer 端本地事务和消息发送的一致性问题。

Producer 先发 Half Message 到 MQ，这个消息消费者不可见；然后执行本地事务。本地事务成功就 Commit 消息，消费者才能看到；本地事务失败就 Rollback 消息。如果 Producer 挂了，MQ 会回查本地事务状态，再决定提交还是回滚消息。

但它只解决生产端一致性，消费端仍然要幂等。

---

### Q5：最大努力通知和可靠消息最终一致有什么区别？

**答：**

可靠消息最终一致更强调“消息从发送方到接收方最终一定可靠送达”，通常用于内部系统之间，比如支付成功通知订单。

最大努力通知更强调“发送方尽力通知业务结果，接收方也可以主动查询”，可靠性要求更低，通常用于外部系统通知，比如银行、微信、支付宝回调。外部系统不会接入我们的 MQ 或事务，所以我们只能通过回调重试、主动查单、对账来保证最终结果正确。

---

### Q6：消费 MQ 为什么要做幂等？

**答：**

因为消息可能重复投递。比如消费者业务处理成功了，但是 ACK 前宕机，MQ 会认为消费失败并重新投递。如果消费端不幂等，就可能重复加积分、重复更新订单、重复入账。

所以消费端一般用业务唯一号、消息 ID 或交易单号做幂等，数据库加唯一索引，处理过的消息直接返回成功。

---

### Q7：如果支付成功消息发出去了，订单系统一直消费失败怎么办？

**答：**

先靠 MQ 自动重试；超过重试次数进入死信队列并触发告警；同时 Payment 提供查单接口，订单系统可以主动查询支付状态；最后 T+1 对账会发现支付成功但订单未更新的差异，进入自动补偿或人工处理。

所以最终链路是：

```text
MQ 重试 → DLQ 告警 → 主动查单补偿 → 对账兜底
```

---

## 十三、一句话记忆

```text
2PC：强一致，但慢，锁资源，支付高并发少用。
TCC：业务层两阶段，适合资金冻结，但开发复杂。
可靠消息：内部异步最终一致，支付通知最常用。
RocketMQ事务消息：Half Message + 本地事务 + 回查。
最大努力通知：外部系统结果通知，靠重试、查单、对账兜底。
```

支付系统的最佳表达：

```text
核心资金状态尽量收敛到本地事务；
跨服务链路用可靠消息最终一致；
外部渠道结果用最大努力通知 + 主动查单；
最终全部通过对账系统兜底。
```
