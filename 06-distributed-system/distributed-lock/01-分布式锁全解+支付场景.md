# 分布式锁全解 + 支付场景应用

> 覆盖 Redis、ZooKeeper、数据库 三种实现方式对比，踩坑经验，支付场景最佳实践

---

## 一、基础概念

### 1. 为什么需要分布式锁？和本地锁有什么区别？

**答：**
本地锁（synchronized、Lock）在单进程多线程的场景下有用，但是分布式系统多实例部署的时候，本地锁只能锁当前进程的线程，锁不住其他实例的，这时候就需要分布式锁，能锁住所有实例的所有线程，保证同一时间只有一个线程在执行某个操作。

**支付场景最典型的例子：**
用户支付，部署了10个支付服务实例，同一个用户同时发两个支付请求，打到两个不同的实例，本地锁拦不住，就会出现重复支付，这时候就需要分布式锁，同一个用户同一时间只能有一个支付请求在处理。

---

### 2. 分布式锁的四大特性是什么？

**答：** 好的分布式锁必须满足这四个：
1. **互斥性**：同一时间只有一个线程能拿到锁
2. **防死锁**：拿到锁的线程挂了，锁最后也能释放，不会一直死锁
3. **解铃还须系铃人**：只有加锁的人才能解锁，不能把别人的锁给释放了
4. **高可用**：只要大部分节点活着，就能正常加锁解锁，不影响业务

## 二、三大分布式锁实现方式对比（必问！）

### 3. Redis、ZooKeeper、数据库 三种实现分布式锁的区别？各有什么优缺点？

**答：** 这个是面试必考题，一定要能说清楚各自的优缺点和适用场景

| 维度 | Redis 分布式锁 | ZooKeeper 分布式锁 | 数据库分布式锁 |
|-----|---------------|-------------------|--------------|
| **实现原理** | SET NX EX + 唯一值 + Lua解锁 + 看门狗续期 | 临时有序节点 + watch 监听 | 唯一索引插入 / FOR UPDATE行锁 |
| **互斥性** | 可以满足 | 可以满足 | 可以满足 |
| **死锁** | 过期时间+看门狗续期，不会死锁 | 会话断开临时节点自动删，不会死锁 | 事务提交或者回滚自动释放，不会死锁 |
| **高可用** | 主从集群，但是主从切换可能丢锁 | 集群过半可用就没问题，可用性高 | 数据库高可用依赖数据库本身 |
| **性能** | 极高，单节点几万QPS | 中等，几千QPS | 低，最多几百QPS |
| **阻塞等待** | 默认不支持，要自己写自旋等待 | 支持，watch监听节点变化，释放了自动通知，不用自旋 | 不支持，自己自旋或者数据库锁等待 |
| **可重入** | Redisson支持，用Hash结构存加锁次数 | 支持，同一个会话多次加锁计数 | 不支持，要自己实现 |
| **自动续期** | Redisson看门狗自动续期 | 不用续期，会话在节点就在 | 不用续期，事务在锁就在 |
| **可靠性** | 一般，主从切换可能丢锁，红锁可以提升可靠性，但是成本高 | 极高，CAP里选CP，不会丢锁 | 高，但是数据库挂了就全挂 |
| **适用场景** | 高并发、性能要求高、允许极小概率丢锁的场景，大部分业务场景 | 对可靠性要求极高，并发不是特别高的场景，比如分布式任务调度 | 简单场景、低并发、没有Redis/ZK的时候临时用 |

> **支付场景我们用什么？**
> 我们主要用 Redisson 的 Redis 分布式锁，因为性能高，支付场景并发高，而且我们有数据库层的唯一索引+状态机兜底，就算极小概率锁失效了，数据库层也能拦住，不会出资金问题，完全够用。
> 核心的资金类场景，比如余额扣款，除了Redis锁，还有数据库行锁双重保证，绝对不会有问题。

## 三、Redis 分布式锁深度题

### 4. 手写一个正确的 Redis 分布式锁？错误的写法有哪些？

**答：**

**正确的加锁写法（原子操作）：**
```redis
SET lock_key unique_value NX EX 30
```
- NX：只有key不存在才会成功，保证互斥
- EX 30：30秒自动过期，防止死锁
- unique_value：每个客户端生成的唯一值，解锁的时候要判断是不是自己加的锁

**正确的解锁写法（Lua脚本保证原子性）：**
```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```
- 先get判断是不是自己的锁，再删，两个操作原子执行，不然中间锁过期了别人加上了，你就把别人的锁删了

**常见的错误写法（一定要说出来，加分！）：**
1. **加锁和设过期时间分开写**：先SETNX成功了，还没设EX进程挂了，锁就永远不会过期，死锁
   ```java
   // 错误写法！不是原子操作
   redis.setnx(key, value);
   redis.expire(key, 30); // 这步之前挂了就死锁
   ```
2. **解锁的时候不判断是不是自己的锁**：直接del，别人加的锁也给删了
3. **解锁的时候先get再del，不是原子操作**：get判断是自己的，这时候锁刚好过期了，别人加上了，你再del就把别人的删了
   ```java
   // 错误写法！不是原子操作
   if (value.equals(redis.get(key))) {
       redis.del(key); // 中间锁过期了别人加上了，就删错了
   }
   ```
4. **过期时间设太短，业务没执行完锁就释放了**：导致并发问题

---

### 5. 锁过期了业务还没执行完怎么办？看门狗原理？

**答：**
这个是Redis分布式锁最常见的问题，设置了30秒过期，但是业务执行了40秒，锁自动释放了，别的线程就拿到锁了，就有并发问题。

**怎么解决？**
**看门狗（Watch Dog）自动续期**：Redisson就是这么实现的：
1. 加锁成功之后，后台启动一个定时任务，每隔10秒（过期时间的1/3）检查一下，如果还持有锁，就把过期时间重新设成30秒，自动续期
2. 只要业务还在执行，锁就不会过期，业务执行完释放锁了，定时任务就停掉
3. 就算客户端挂了，定时任务也挂了，锁到了30秒也会自动过期，不会死锁

> 所以生产环境不要自己手写分布式锁，直接用 Redisson 就好了，这些坑都帮你踩过了，可重入、看门狗续期、原子解锁都给你实现好了，直接用就行。

### 6. 什么是红锁 RedLock？有必要用吗？

**答：**
红锁是Redis作者提出来解决Redis主从切换丢锁的问题：
- 原理：向N个独立的Redis节点（一般是5个）都加锁，超过半数（N/2+1）加锁成功，才算加锁成功
- 这样就算有1-2个节点挂了，还有其他节点有锁，不会丢锁，可靠性更高

**有必要用吗？**
**99%的场景都没必要用！**
1. 性能差很多，要加5个节点的锁，性能下降很多
2. 运维成本高，要维护5个独立的Redis节点，不能是主从集群
3. 支付场景根本不需要，因为我们有数据库层的兜底，就算锁失效了，数据库唯一索引+状态机也能拦住，不会出问题，完全没必要为了那极小的概率牺牲性能增加复杂度
> 大部分人说红锁都是背概念，生产真用的极少，面试的时候说清楚你的业务场景不需要用，为什么不需要，比背红锁原理更加分。

## 四、支付场景最佳实践（重点！）

### 7. 支付场景哪些地方用了分布式锁？怎么用的？

**答：** 直接说你们的实际用法，面试官一听就知道你真用过

我们支付服务主要在这几个场景用分布式锁：

1. **防重复支付**：同一个用户同一个订单发起支付，按out_order_no加锁，防止重复创建支付单
   ```java
   RLock lock = redisson.getLock("pay:lock:order:" + outOrderNo);
   lock.lock(10, TimeUnit.SECONDS);
   try {
       // 创建支付单逻辑
   } finally {
       lock.unlock();
   }
   ```

2. **餐点库存扣减**：同一个餐别同一个用户扣库存，按餐别ID+用户ID加锁，防止超卖
3. **换单操作**：旧单退款+新单支付，按旧支付单ID加锁，防止旧单同时被其他操作修改
4. **回调处理**：同一个支付单的回调按out_order_no加锁，防止并发回调导致状态错乱

**为什么不用ZooKeeper？**
- 支付场景并发太高了，ZK性能扛不住，Redis能扛几万QPS，ZK只有几千，性能差一个数量级
- 我们有数据库层兜底，就算Redis锁极小概率失效了，也不会出问题，完全够用

---

### 8. 分布式锁失效了怎么办？会不会出资金问题？

**答：** 这个问题考察你有没有兜底思维，面试官很喜欢问

分布式锁只是第一层防护，不是正确性的保证，我们有多层兜底，就算锁完全失效了也不会出问题：
1. **第二层：数据库唯一索引**：out_order_no唯一索引，重复创建支付单数据库直接报错，插不进去
2. **第三层：状态机判断**：更新支付单状态的时候带上原状态条件，比如 `UPDATE payment_slip SET status = 6 WHERE id = 123 AND status = 3`，就算锁失效了，并发更新也只有一个能成功，不会重复更新
3. **第四层：每日对账**：每天核对所有支付单状态，有不一致的自动补单，兜底

> 核心思想：分布式锁是用来优化性能，减少并发冲突的，不是用来保证正确性的，正确性最终靠数据库和对账来保证，永远不要把所有希望都放在分布式锁上。
> 你这么一说，面试官就知道你有生产经验，不是纸上谈兵。

---

### 9. 用分布式锁踩过什么坑？

**答：** 说几个真实的，加分项

**坑1：最开始自己手写分布式锁，没有看门狗，过期时间设的10秒，支付渠道调用超时，业务执行了15秒，锁自动释放了，另一个请求进来，导致重复扣款**
- 解决：改用Redisson，自带看门狗自动续期，再也没出现过锁过期的问题

**坑2：加锁粒度太大，锁了整个支付入口，所有请求都串行，性能上不去**
- 解决：缩小锁粒度，按out_order_no加锁，不同订单的请求互不影响，并发直接上去了

**坑3：加了锁没在finally里释放，异常了锁没释放，等到过期才能释放，导致一段时间内同一个订单不能支付**
- 解决：统一封装锁工具类，自动在finally释放，不用业务代码自己释放，避免忘记
