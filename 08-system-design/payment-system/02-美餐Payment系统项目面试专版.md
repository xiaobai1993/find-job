## 一、项目介绍（面试开场白就说这个）

我之前在美餐做支付中台系统，这个系统是整个公司的支付核心，负责所有业务线的收单、退款、对账全流程，支持堂食、食堂、外卖配送、团餐、门店全场景。

**项目规模：**
- 每日处理几百万笔支付交易，支持10+种支付账户（补贴、企业余额、个人余额、餐点、微信、支付宝、银联、钱包等）
- 支持3大支付产品：内部支付、快捷支付、Web端收银台，覆盖4种业务类型
- 全年支付成功率99.98%，上线两年多没有出过一次资损问题。

**我在项目中负责的工作：**
1. 整体架构设计，领域建模、状态机、渠道适配层这些核心基础设施开发
2. 多账户混合支付模块开发，自动支付、手动支付、先享后付核心流程
3. 全额退款、部分退款、改单退款的核心逻辑开发，菜品维度校验机制设计
4. 性能优化，把支付接口的P99响应时间从800ms优化到200ms，支持大促4.5倍峰值流量。

## 二、整体架构 & 核心流程

### 1. 整体架构是怎么设计的？

**答：** 经典的四层DDD架构，Go语言开发，微服务部署：

```
应用层 → 领域服务层 → 核心服务层 → 基础设施层
```

1. **应用层**：对接不同的支付产品入口，内部支付、快捷支付、Web收银台分别有独立的Transaction入口，做参数校验和协议转换
2. **领域服务层**：核心业务逻辑，包含支付、退款、改单、自动支付、消费者、餐点处理等领域服务，所有业务逻辑都在这一层
3. **核心服务层**：通用的核心能力，支付单核心、退款核心、支付渠道抽象、状态机FSM，上层业务都调用这一层
4. **基础设施层**：持久化、RPC客户端、MQ、缓存、分布式锁、ID生成器，和具体技术解耦

**核心设计亮点：**
- **渠道适配器模式**：所有支付渠道都实现统一的IPayChannel接口，新增渠道只要加一个适配器，核心逻辑不用改，一周就能接入新渠道
- **主子单设计**：一笔支付单对应多个子支付单，每个子单对应一个账户，支持多账户混合支付，精细化管理每个渠道的支付状态
- **状态机驱动**：所有支付单、退款单的状态流转都用FSM状态机管理，不会出现状态倒流，逻辑非常清晰
- **支付快照**：支付的时候打快照，记录当时的账户优先级、补贴比例，退款的时候按快照原路退回，不会因为规则变更导致退款错误

---

### 2. 核心数据模型是什么？为什么要设计主子单？

**答：** 五大核心实体，这个是支付系统的骨架：
1. **支付主单 PaymentSlip**：聚合根，记录总金额、商户、用户、业务订单号、整体状态
2. **支付子单 PaymentSubSlip**：每个账户对应一个子单，记录每个渠道的支付金额、状态、第三方交易号
3. **退款单 RefundSlip**：逆向聚合根，记录退款总金额、是否全额退款、状态
4. **退款子单 RefundSubSlip**：每个账户对应一个退款子单，分别退款
5. **支付快照 PaymentSnapshot**：记录支付时的账户优先级、补贴百分比，退款时用

> **为什么要主子单设计？** 这个是我们系统最核心的设计，因为美餐的支付场景非常特殊，一笔订单可能同时用了企业补贴+个人余额+微信支付，三种渠道混合支付，每个渠道的回调时机、失败重试、退款逻辑都不一样，拆成子单就能精细化管理每个渠道的状态，部分成功、部分失败都能准确处理，而且退款的时候可以按账户原路退回。

---

### 3. 完整的支付流程是怎么样的？

**答：** 分三步，和普通支付不一样的地方是我们有自动支付环节：

**第一步：创建支付单（同步）**
1. 参数校验、幂等检查，业务订单号重复的直接返回
2. 生成雪花ID，初始化支付单状态为PendingProcessing
3. 计算账户金额分配，补贴、余额、餐点分别分配金额，创建对应的子支付单
4. 事务写入支付单和子单，发送支付超时延迟消息和异步支付任务

**第二步：自动支付 AutoPay（异步，核心环节）**
1. 并行查询所有可支付账户的可用余额，补贴、个人余额、餐点同时查
2. 总余额足够的话，并发调用各个渠道的扣款接口，goroutine并发执行
3. 全部成功就更新支付单状态为Succeeded，全部失败就进入待手动支付
4. 部分成功的话标记为PartialSucceeded，失败的渠道让用户手动补付
5. 发送支付成功MQ消息，通知下游订单、对账系统

**第三步：手动支付 ManualPay（用户触发）**
1. 用户在收银台选微信/支付宝，调用对应渠道获取支付参数
2. 返回JSAPI/H5参数给前端，用户完成支付
3. 第三方渠道异步回调，验签后更新对应子单状态
4. 所有子单都成功了，更新主单状态，发通知

---

### 4. 先享后付业务怎么做的？

**答：** 这个是我们特色业务，用户先吃饭，后付款，对接微信支付分：
1. 用户下单后，先创建后付单，跳转到微信支付分进行授权签约
2. 用户签约成功后，状态变为Signed，消费完结的时候才发起扣款
3. 完结的时候自动调用微信支付分扣款，扣款成功就直接完成
4. 扣款失败就唤起用户收银台手动支付，保证钱能收回来
5. 零元订单直接完结，不用走支付流程

---

### 5. 退款流程怎么设计的？全额退款和部分退款有什么区别？

**答：** 退款比支付更复杂，因为要处理的边界情况特别多，我们分全额退款和部分退款两种，逻辑差别非常大：

| 对比项 | 全额退款 | 部分退款 |
|--------|---------|---------|
| 金额计算 | 系统自动算可退金额 | 调用方传退款金额，校验不能超过可退金额 |
| Pending支付单处理 | 全部加锁，二次刷新状态，改成已关闭 | 不处理，只针对已成功的单 |
| 后付订单处理 | 取消微信支付分授权订单 | 不处理 |
| 子单构建策略 | 每个子单全额退 | 按支付快照的账户优先级+百分比分配退款金额 |
| 菜品校验 | 不需要 | 外卖业务必须传菜品，校验退款菜品数量不能超买的数量 |
| 后续退款 | 退完就关闭，不能再退 | 可以多次退，直到可退金额为0 |

**全额退款核心流程：**
1. 先对所有Pending状态的支付单加分布式锁，二次刷新状态，防止用户刚好支付成功
2. 把所有Pending支付单改成FullRefundClosed，子单改成Failed，回滚已扣的余额
3. 取消后付订单的授权
4. 给每个已成功的子支付单创建退款子单，按原路退回
5. 补贴、余额同步退款，微信支付宝异步退款，回调更新状态

**部分退款核心难点：退款金额怎么分配到各个账户？**
- 用支付时打的快照，里面存了每个账户的支付比例和优先级
- 高优先级的账户先退款，比如先退微信，再退个人余额，最后退补贴
- 百分比账户按比例分摊退款金额，保证和支付的时候对应，不会出现退错账户的情况

## 三、难点 & 优化点（重点讲，面试核心加分项）

### 1. 多账户混合支付有什么难点？你怎么解决的？

**答：** 这个是美餐支付最核心的难点，一笔支付涉及多个账户，每个账户扣款成功失败情况都不一样，处理不好就会资损：

**第一个问题：并发扣款的一致性怎么保证？**
- 最开始是串行扣，一个个扣，速度特别慢，P99要800多ms
- 我改成了goroutine并发扣，每个账户的扣款单独开goroutine，用channel收集结果，速度直接降了一半
- 但是要处理部分成功的情况：只要有一个账户扣失败，就要把已经扣成功的全部逆序回滚，不能多扣用户的钱
- 每个账户的操作都做幂等，回滚也做幂等，重复执行也没问题

**第二个问题：账户余额不够怎么优雅降级？**
- 自动支付前先并行查所有账户的余额，总余额不够就直接进入手动支付，不浪费时间去扣
- 扣款的时候如果某个账户余额不足，就标记这个子单失败，剩下的金额自动转成用户用微信付，不用整个支付失败，用户体验好很多

**第三个问题：退款的时候怎么原路退回？**
- 支付的时候打快照，记录每个账户实际付了多少钱，还有优先级和比例
- 退款的时候严格按照快照来分配退款金额，不会因为后来补贴规则变了就退错
- 比如用户付的时候补贴出了10块，余额出了10块，微信出了10块，退15块的时候，先退微信10块，再退余额5块，补贴不退，符合财务规则

---

### 2. 支付接口性能怎么优化的？你做了哪些优化？

**答：** 我做的核心优化，把支付接口P99从800ms优化到200ms，提升了4倍：

**第一：串行改并行**
- 查询账户余额从串行查改成并行查，3个账户一起查，时间从300ms降到100ms
- 多渠道扣款并发执行，不用等一个扣完再扣下一个，又降了200ms

**第二：数据库层面优化**
- 支付单表按时间范围做分区，单表数据量小，查询快
- 所有查询都走覆盖索引，业务订单号建唯一索引，幂等校验不用回表
- 写操作都批量处理，批量插入子单、批量更新状态，比一条条快好几倍
- 读写分离，所有查询都走从库，主库只处理写

**第三：缓存优化**
- 商户配置、用户账户信息、渠道配置这些不经常变的，都做了多级缓存，本地Caffeine+Redis，不用每次查数据库
- 缓存预热，大促前把热点商户的配置都加载到缓存里

**第四：逻辑精简**
- 非核心逻辑全部异步化，发通知、记流水、统计这些都扔到MQ里异步处理，主流程只保留核心的状态更新和扣款
- 大促的时候开启降级开关，把风控校验、非必要的校验都关掉，只保留最核心的逻辑

> 优化完之后，大促峰值4.5倍流量，支付接口P99还是200多ms，非常平稳，用户完全感知不到。

---

### 3. 怎么防止重复支付？怎么保证幂等？

**答：** 四层幂等兜底，绝对不会重复扣钱：
1. **前端层**：用户点击支付按钮后置灰，禁止重复点击，加防重token
2. **业务层**：创建支付单的时候，业务订单号建唯一索引，同一个订单号只能创建一个支付单，重复创建直接失败
3. **状态机层**：状态变更都带前置条件，`UPDATE payment_slip SET status = 6 WHERE id = 123 AND status = 3`，只有状态对才更新，不会重复处理
4. **渠道层**：调用第三方渠道的时候，用我们的子单号当渠道的外部订单号，渠道那边做幂等，就算我们重复调用，渠道也不会重复扣款

> 四层幂等，层层防护，上线以来没出现过重复支付的情况。

---

### 4. 并发更新支付单冲突怎么解决？

**答：** 两层保证：
1. **分布式锁**：每个支付单操作前先加Redis分布式锁，key是`payment:slip:id`，看门狗自动续期，保证同一时间只有一个协程在操作这个支付单
2. **乐观锁兜底**：数据库更新的时候带版本号，`UPDATE payment_slip SET ... WHERE id = 123 AND version = 旧版本`，并发冲突了就重试，最多重试3次

> 分布式锁挡掉99%的冲突，剩下的1%乐观锁兜底，完全不会出现并发更新错乱的问题。

## 四、踩过的坑（必讲，非常加分）

### 1. 最开始退款没打支付快照，补贴规则变更了，退款的时候多退了钱，差点出资损

**坑描述：** 最开始退款的时候是实时算当前的补贴比例，不是按支付时候的比例，后来公司补贴规则改了，用户上个月付的单，这个月退款，按新的补贴规则算，补贴部分多退了几千块，还好财务对账的时候发现了。

**怎么解决的：**
- 加上支付快照机制，支付成功的时候把当时的账户列表、每个账户的支付金额、优先级、补贴百分比都序列化存下来
- 退款的时候严格按照快照来算退款金额，不受当前规则变更的影响
- 加上了退款总金额校验，退款总金额不能超过原支付金额，对不上就告警人工处理，再也没出过这个问题。

---

### 2. 全额退款的时候没处理Pending状态的支付单，用户退款的时候刚好支付成功了，钱扣了订单却关了

**坑描述：** 最开始全额退款只处理已成功的支付单，不处理待支付的，有一次用户发起全额退款，刚好那一秒用户那边又支付成功了，结果支付单成功了，订单却关了，钱付了没有消费记录，用户投诉了。

**怎么解决的：**
- 全额退款的时候，把同一个业务订单所有状态为Pending、Processing的支付单全部找出来，一个个加分布式锁
- 二次刷新支付单的最新状态，确认还在处理中，就更新为FullRefundClosed，子单改成Failed，回滚已经扣的钱
- 关单前必须再调用渠道查一下最新的支付状态，不能相信库里的状态，双重保证，再也没出现过退款的时候支付成功的情况。

---

### 3. 并发退款的时候，多个退款单同时处理，总退款金额超过了支付金额，超退了

**坑描述：** 最开始退款的时候没加锁，用户同时点了两次部分退款，两个请求同时进来，都查了可退金额是100块，都校验通过了，然后两个都退了100块，总共退了200，多退了100。

**怎么解决的：**
- 退款的时候先对支付单加分布式锁，同一时间同一个支付单只能有一笔退款在处理
- 数据库更新的时候带条件，`UPDATE payment_slip SET refunded_amount = refunded_amount + 100 WHERE id = 123 AND refunded_amount + 100 <= paid_amount`，更新不成功就说明超退了，直接失败
- 双重保证，分布式锁+数据库条件更新，不会再出现超退的情况。

## 五、面试官高频问题 & 标准答案

### Q1：支付系统的核心设计原则是什么？
**A：** 三个核心原则，优先级从高到低：
1. **资金安全第一**：钱不能错，宁可支付失败，也不能多扣、少扣、重复扣，一致性是最高优先级，性能和可用性都要让位于一致性
2. **幂等性是生命线**：所有写接口必须做幂等，重复调用结果要一样，网络抖动、重试、重复请求都不能出资损
3. **最终一致性**：跨服务调用不要追求强一致，用可靠消息+对账兜底，保证最终一定一致就可以

### Q2：怎么保证支付和订单的状态一致？回调失败了怎么办？
**A：** 多层兜底，保证最终一致：
1. **支付系统自动重试回调**，间隔递增重试，最多重试24小时，只要订单系统恢复了就能收到
2. **用户查询补偿**，用户查订单状态的时候，如果还是待支付，就主动调用支付系统查状态，查到成功了就更新
3. **每日对账兜底**，每天凌晨订单和支付双向对账，支付成功订单没成功的自动补更新，100%保证最终一致
> 核心思想：支付结果以支付系统为准，只要支付成功了，不管回调成没成功，最终订单一定要改成已支付，绝对不能出现用户付了钱订单还是待支付的情况。

### Q3：支付超时了怎么处理？怎么关单？
**A：** 两层保证：
1. **延迟消息自动关单**，创建支付单的时候发一个30分钟的延迟消息，30分钟后检查支付状态，还是待支付的就自动关单，恢复库存
2. **定时任务兜底**，每分钟扫描超过30分钟还没支付的订单，自动关单，防止消息丢失
> 重点：关单前必须再调用渠道查一遍最新的支付状态，不能直接关，防止用户刚好支付成功了你给关了，就资损了。

### Q4：第三方渠道回调怎么处理？要注意什么？
**A：** 五个步骤，一个都不能少：
1. **验签**：先校验渠道的签名，确认是渠道发过来的，不是伪造的请求，不然就被人攻击了
2. **幂等校验**：已经处理过的回调直接返回成功，不用重复处理
3. **只更新对应子单的状态**，不要直接更主单，一个子单成功不代表整个支付成功
4. **汇总所有子单的状态**，全部成功了才更主单状态，发通知
5. **返回成功响应给渠道**，告诉渠道不用再重试了，不然渠道会一直回调

## 面试答题技巧
