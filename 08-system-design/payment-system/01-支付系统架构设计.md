# 支付系统架构设计

> 面试经典题：如何设计一个高可用高可靠的支付系统，结合美餐支付实际业务来讲

---

## 一、需求分析 & 设计目标

### 1. 设计一个支付系统，核心目标是什么？

**答：** 先讲设计目标，显得有条理，不然后面都是乱的
支付系统是金融级系统，核心目标优先级：
1. **资金绝对安全**：钱不能错，不能多扣少扣重复扣，一致性100%，不能有资损，这是第一优先级
2. **高可用 99.99%**：用户要能付钱，全年停机时间不超过50分钟，核心功能不能挂
3. **高并发高吞吐**：能扛住大促峰值流量，支持水平扩展
4. **高可扩展**：支持快速接入新的支付渠道（微信、支付宝、银联、新的渠道），不用改核心逻辑
5. **可追溯可审计**：所有资金变动都有流水，可查可对账，出了问题能回溯，能找到责任人

---

## 二、整体架构设计

### 2. 支付系统的整体分层架构是什么样的？

**答：** 经典的四层架构，职责清晰，高内聚低耦合：

```
┌───────────────────────────────────────────────────────────┐
│                    接入层 (Gateway)                        │
│  统一接入、鉴权、限流、熔断、参数校验、防重、签名校验          │
└───────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────┐
│                    业务层 (Service)                        │
│  支付产品层：收银台、支付、退款、对账、提现、转账             │
│  核心领域层：支付单、退款单、流水、账户、对账、渠道适配       │
└───────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────┐
│                    基础服务层 (Infra)                      │
│  分布式锁、幂等、MQ、配置中心、监控告警、链路追踪、任务调度   │
└───────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────┐
│                    数据存储层 (Storage)                    │
│  数据库：分库分表、主从复制、读写分离                        │
│  缓存：Redis多级缓存                                       │
│  MQ：Pulsar/Kafka 异步解耦削峰                              │
│  对象存储：凭证、账单文件存储                                │
└───────────────────────────────────────────────────────────┘
```

**核心设计原则：**
1. **核心逻辑和渠道隔离**：所有渠道对接都做成适配器模式，新增渠道只要加一个适配器就行，核心逻辑不用改，符合开闭原则
2. **同步改异步**：所有非核心逻辑都异步处理，核心流程尽量短，响应快，削峰填谷
3. **状态机驱动**：所有单据（支付单、退款单）都用状态机管理状态流转，逻辑清晰，不会乱
4. **多层幂等兜底**：所有写接口都做幂等，最后数据库唯一索引兜底，绝对不重复处理
5. **全链路可追溯**：所有操作都有流水，所有资金变动都有记录，出了问题能查能回溯

---

### 3. 支付系统的核心领域模型有哪些？

**答：** 五大核心实体，搞懂这五个就懂支付的核心了：
1. **支付单 PaymentSlip**：支付的核心聚合根，记录一笔支付的所有信息，金额、用户、商户、状态、渠道、过期时间等
2. **支付子单 SubSlip**：一个支付单可能用多个支付渠道组合支付（比如补贴+余额+微信），每个渠道对应一个子单，分别记录每个渠道的支付情况
3. **退款单 RefundSlip**：逆向的核心实体，记录一笔退款的所有信息，对应原支付单，支持全额和部分退款
4. **流水单 TransactionLog**：所有资金变动的流水，每一笔扣钱加钱都有一条流水，永不删除，对账的核心依据，是资金变动的凭证
5. **账户 Account**：用户、商户、平台的资金账户，余额、冻结余额、累计收支等，所有资金变动都记在账户上

> 核心原则：所有资金变动必须有流水，流水是不可变的，只能新增不能修改删除，作为最终的凭证。

## 三、核心流程设计

### 4. 支付核心流程是怎么样的？

**答：** 分三步，清晰明了：

**第一步：创建支付单（同步）**
1. 网关层校验签名、鉴权、参数校验、幂等校验，重复请求直接返回
2. 校验订单状态、金额、商户信息，校验是否可以支付
3. 生成支付单和子单，写入数据库，状态是「待支付」
4. 返回支付方式列表和支付参数给前端

**第二步：执行支付（异步，核心流程）**
1. 用户选择支付方式，发起扣款请求
2. 按渠道优先级依次扣款：补贴→余额→餐点→微信/支付宝，每个渠道扣成功了就处理下一个，失败了就回滚之前扣的
3. 所有渠道都扣款成功，支付单状态改成「成功」，记录流水
4. 发送支付成功MQ消息，通知下游订单、对账、通知等系统
5. 有任何渠道扣款失败，就逆序回滚所有已经扣成功的渠道，支付单状态改成「失败」

**第三步：渠道回调处理（异步）**
1. 第三方渠道回调过来，先验签，校验合法性
2. 幂等校验，已经处理过的直接返回成功
3. 更新对应子单的状态，处理成功的就更新，失败的就回滚
4. 所有子单都处理完了，更新主单状态，发MQ通知下游
5. 返回成功给第三方渠道，告诉对方不用再重试了

---

### 5. 退款流程是怎么样的？

**答：** 退款是逆向流程，比支付更要小心，退多了钱就没了：
1. 创建退款单，校验原支付单状态，必须是支付成功的才能退款，退款金额不能大于支付金额
2. 按照支付渠道的逆序退款，先退微信/支付宝，再退余额，再退补贴
3. 所有渠道都退款成功了，退款单状态改成「成功」，支付单状态改成「已退款」
4. 发送退款成功MQ，通知下游
5. 任何一个渠道退款失败，就进入待重试状态，定时重试，超过次数进死信人工处理
> 退款要比支付更谨慎，所有操作都要做幂等，宁可退失败也不能退重复。

## 四、高可用 & 一致性设计

### 6. 怎么保证支付系统的数据一致性，不会资损？

**答：** 多层兜底，层层防护，绝对保证资金正确：
1. **状态机+乐观锁保证状态正确**：所有状态变更都带上原状态条件，只有原状态对才可以更新，不会出现状态倒流
   ```sql
   UPDATE payment_slip SET status = 6 WHERE id = 123 AND status = 3;
   ```
2. **所有资金变动都有流水**：每一笔扣钱加钱都必须写流水，流水不可变，只能新增，不能修改删除，作为最终凭证
3. **TCC/可靠消息最终一致性**：跨服务的资金操作，用TCC或者可靠消息，最终一定一致
4. **每日对账兜底**：每天凌晨跑全量对账，支付流水和渠道流水对，账户流水和支付流水对，有不一致的立刻告警，自动补单或者冲正，最终一定一致
5. **操作全留痕**：所有人工操作、接口调用，都有操作日志，出了问题能回溯，能找到原因和责任人

---

### 7. 怎么保证支付系统的高可用？

**答：** 从架构、运维、容灾三层来做：
1. **架构层面**：
   - 全链路集群部署，没有单点，所有服务都多实例，数据库主从+高可用，MQ集群，Redis集群
   - 核心服务资源隔离，和非核心服务分开部署，不会互相影响
   - 同步改异步，削峰填谷，峰值流量MQ扛，不直接打数据库
   - 全链路熔断降级，下游挂了快速失败，不拖垮主服务
2. **运维层面**：
   - 全链路压测，大促前压到5倍峰值，保证容量足够
   - 提前扩容，大促前所有资源扩到3倍冗余
   - 灰度发布，所有变更小流量验证，没问题再全量，出问题秒级回滚
   - 全链路监控告警，出问题5分钟内发现，15分钟内解决
3. **容灾层面**：
   - 多机房部署，单机房挂了流量切到其他机房，业务无感知
   - 数据多副本备份，数据库每日全量备份，实时增量备份，误删了能恢复
   - 灾备演练，每季度做容灾演练，确保机房挂了能快速切走

---

### 8. 怎么快速接入新的支付渠道？架构上怎么设计？

**答：** 适配器模式，把渠道的差异都屏蔽在适配层，核心逻辑不用改：
1. 定义统一的支付渠道接口 `IPayChannel`，定义统一的 `pay、refund、query` 三个核心方法
2. 每个渠道都实现自己的适配器，比如WechatPayChannel、AlipayChannel，把渠道自己的参数、返回值转换成统一的格式
3. 用工厂模式，根据渠道类型获取对应的适配器，核心逻辑不用改，新接入渠道只要加一个适配器类就行，不用动核心代码
> 比如我们接入新的数字人民币渠道，只用写一个DCPayChannel实现类，实现三个接口就行，核心支付逻辑完全不用改，一周就能接入完成，非常方便。

## 五、面试答题技巧

面试的时候让你设计支付系统，就按这个逻辑讲：
1. **先讲设计目标**：资金安全第一，然后高可用、高并发，突出你懂支付系统的核心诉求
2. **再讲整体架构**：四层架构，职责清晰，适配器模式隔离渠道，状态机驱动这些设计原则讲出来
3. **再讲核心流程**：支付和退款的流程，讲清楚每个环节做了什么
4. **最后讲高可用和一致性**：怎么保证钱不错，怎么保证服务不挂，怎么对账兜底
按照这个逻辑讲下来，条理非常清晰，面试官绝对满意，说明你真的懂支付系统的整体设计，不是只知道写CRUD。
