# 幂等性设计全解 + 支付场景落地实践

> 支付面试核心中的核心，100%会问，结合美餐支付业务实际落地经验，讲透所有场景的幂等方案

---

## 一、基础概念

### 1. 什么是幂等性？为什么支付系统幂等这么重要？

**答：**
幂等性就是：同一个请求，调用一次和调用N次，结果都是一样的，不会重复处理，不会产生副作用。

**支付系统为什么幂等是生命线？**
1. 重复支付：用户点击两次支付，或者网络重试，扣了两次钱，就是资损，用户会投诉，赔钱
2. 重复退款：同一个退款请求退了两次，钱就亏了，找不回来
3. 重复回调：微信支付宝异步回调，会重复发好几次，处理两次的话就会重复更新状态，出问题
4. MQ重复消费：消息队列至少一次投递，一定会重复，消费两次的话就会出问题
> 支付系统，任何涉及资金变动的接口，必须100%做幂等，这是底线，没有任何商量的余地。

---

### 2. 什么时候会产生重复请求？哪些场景需要做幂等？

**答：** 所有写接口都要做幂等，读接口天然幂等，不用做。

**常见的重复请求场景：**
1. **用户重复提交**：用户点太快，或者网络卡，连续点击两次提交按钮，发了两次请求
2. **网络重试**：HTTP调用超时了，调用方会自动重试，gRPC、Feign默认都有重试机制
3. **MQ重复消费**：消息队列默认是至少一次投递，一定会有重复消费
4. **第三方回调重复**：微信支付宝的回调，会重试很多次，直到你返回成功
5. **开关切换、服务重启**：定时任务重复跑，或者服务重启的时候任务重复执行
6. **运维人工操作**：运营重复操作，手动执行了两次任务

**支付场景必须做幂等的接口：**
- 创建支付单接口
- 支付扣款接口
- 退款接口
- 第三方回调处理接口
- MQ消费的所有写接口
- 所有资金变动的接口

## 二、常用的幂等方案对比（必问！）

### 3. 常见的幂等方案有哪些？各有什么优缺点？适用什么场景？

**答：** 六大常用方案，各有适用场景，没有银弹：

| 方案 | 实现原理 | 优点 | 缺点 | 适用场景 | 支付场景用不用 |
|-----|---------|------|------|---------|--------------|
| **数据库唯一主键/唯一索引** | 业务唯一键建唯一索引，重复插入直接报错 | 最简单，最可靠，兜底方案，100%不重复 | 只能防插入，防不了更新，插入报错要处理 | ✅ 所有场景的最后兜底，必做 |
| **数据库乐观锁，版本号机制** | UPDATE的时候带版本号条件，`UPDATE xxx SET status = 2, version = version + 1 WHERE id = 1 AND version = 1`，影响行数为0就是重复了 | 简单，性能好，防并发更新 | 只能用在更新场景，每个操作都要先查版本号 | ✅ 支付单状态更新，扣款更新，非常常用 |
| **去重表/流水表** | 单独建一个幂等流水表，每次请求先插流水，插入成功就执行业务，失败就返回已经处理过了 | 通用性强，所有接口都能用，和业务解耦 | 多一次数据库插入，高并发有性能瓶颈 | ✅ 核心接口，回调、MQ消费，常用 |
| **Redis 分布式锁 + 去重** | 请求过来先加锁，key是业务唯一键，加锁成功就执行，加锁失败就返回重复 | 性能好，分布式场景好用 | 有锁失效的风险，要兜底数据库层 | ✅ 接口层面防重复提交，第一层防护 |
| **状态机判断** | 业务有明确的状态流转，比如支付单：新建→支付中→成功→关闭，更新的时候带上原状态条件，只有原状态对才更新，否则就重复了 | 非常符合业务逻辑，性能最好，零额外开销 | 只适用于有明确状态流转的业务 | ✅ 支付单、退款单状态更新，必做 |
| **token 令牌机制** | 进入页面前先申请一个唯一token，存在Redis，提交的时候带上token，提交了就删掉，删成功就执行，失败就重复 | 防前端重复提交非常好用 | 要前后端配合，接口单独申请token | 前端提交按钮防重复提交用 |

> **核心原则：幂等一定要多层兜底，不要只靠某一层，至少两层以上，Redis层防大部分重复，数据库层做最终兜底，100%不重复。**

## 三、支付场景幂等落地实践（重点！面试就说这个）

### 4. 你们支付系统的幂等是怎么做的？举实际的例子？

**答：** 直接说你们的实际方案，这个面试官100%感兴趣

我们支付是**四层幂等兜底**，层层防护，绝对不会出现重复扣款重复处理的问题：

**第一层：前端防重复提交**
- 支付按钮点击之后立刻置灰，10秒内不能再点，防止用户手快点两次，简单挡住80%的重复请求
- 重要接口前端先申请唯一token，提交的时候带上，后端校验token，用过就删

**第二层：接口层分布式锁去重**
- 所有核心接口，进来先拿业务唯一键（比如out_order_no + 接口类型）加Redis分布式锁，加锁失败就直接返回"处理中"，挡住大部分并发重复请求
- 锁的过期时间设成比业务最长执行时间长一点，防止锁过期释放了业务还没执行完

**第三层：业务层状态机判断**
- 所有支付单、退款单的状态更新，全部带上原状态条件，比如：
  ```sql
  UPDATE payment_slip SET status = 6, update_time = now()
  WHERE id = 12345 AND status = 3;
  ```
  - 如果影响行数是0，说明已经被其他请求更新过了，直接返回成功就行，不用重复处理
  - 这个是性能最好的，零额外开销，和业务逻辑结合的非常好，我们所有状态变更都这么做

**第四层：数据库唯一索引兜底**
- 所有业务唯一键都建唯一索引，out_order_no + 业务类型建联合唯一索引，就算上面三层都失效了，数据库这层绝对拦得住，重复插入直接报错，不会插入重复的数据
  - 就算所有防护都失效了，数据库这层一定兜得住，绝对不会出现重复的支付单，不会出现资损

> 四层防护，从前端到接口到业务到数据库，层层拦截，就算前面的都失效了，最后数据库兜底，绝对不会出重复处理的问题。

### 5. 第三方回调的幂等怎么做？微信支付宝重复回调怎么办？

**答：** 这个是支付必问题，就说你们的方案：
三层幂等：
1. **第一层：Redis去重**，回调的唯一流水号（微信的transaction_id或者回调ID）作为key，先setnx，设置成功就处理，设置失败就直接返回成功，不用处理了，key过期时间设24小时，24小时内的重复回调直接拦截
2. **第二层：状态机判断**，处理之前先查支付单状态，如果已经是终态（成功/失败/关闭），直接返回成功，不用处理，大部分重复回调到这一步就挡住了
3. **第三层：数据库唯一索引兜底**，回调流水表建唯一索引，同一个回调流水号只能插一次，插入失败就直接返回成功

> 还有个小细节：所有第三方回调，不管重复多少次，你处理完都要返回成功，不然第三方会一直重试，你只要保证自己幂等就行，返回成功让对方不要再发了。

---

### 6. MQ消费的幂等怎么做？重复消费了怎么办？

**答：** 和回调差不多，三层兜底：
1. **第一层：消息唯一ID去重**，每个消息都有唯一的msgId，先去Redis查有没有处理过，处理过就直接ACK，不用处理
2. **第二层：业务状态机判断**，处理之前查业务状态，已经是终态就直接ACK，不用处理
3. **第三层：数据库唯一索引兜底**，业务唯一键建唯一索引，重复插入直接报错，ACK就行，不会有问题

> MQ的幂等是必须做的，所有消息队列默认都是至少一次投递，一定会有重复消费，永远不要假设消息只会来一次。

---

### 7. 退款接口的幂等怎么做？怎么保证不会重复退款？

**答：** 退款比支付更危险，退多了钱就找不回来了，幂等要做的更严格：
1. 退款单号是唯一的，建唯一索引，同一个退款单号只能插一次
2. 退款处理的时候，带上原支付单的状态条件，只有支付成功的才能退款，已经退款过的就不能再退
3. 同一个支付单，同一时间只能有一个退款在处理，加分布式锁，防止并发退款
4. 退款成功后，把支付单状态改成已退款，所有状态更新都带原状态条件

> 所有资金出的接口，幂等校验要比入的更严格，宁可退失败也不能退重复。

## 四、踩过的坑（必讲，加分项）

### 8. 幂等设计踩过什么坑？

**答：** 说2-3个真实的，非常加分

**坑1：最开始只做了Redis去重，没有数据库唯一索引兜底，有一次Redis集群故障，重启了，锁都没了，刚好有重复的回调过来，导致重复处理了两个退款，多退了几千块钱**
- 教训：幂等永远不能只靠缓存，必须有数据库唯一索引兜底，缓存是用来优化性能的，不是用来保证正确性的，正确性一定要靠数据库兜底
- 解决：所有业务唯一键全部建唯一索引，作为最后一道防线

**坑2：乐观锁的版本号用了自增，重试的时候会版本冲突，业务重试的时候总是失败**
- 最开始更新支付单状态用了version版本号，用户重试支付的时候，因为版本号变了，总是返回更新失败，导致用户以为支付没成功
- 解决：对于只有正向流转的状态机，不用版本号，直接带上原状态条件就行，比如只有支付中才能改成成功，不管版本号是多少，只要原状态对就能更新，避免不必要的冲突
  ```sql
  -- 不用这么写，容易冲突
  UPDATE payment_slip SET status = 6, version = version + 1 WHERE id = 123 AND version = 1;
  -- 改成这样，只要原状态对就可以更新，更符合业务
  UPDATE payment_slip SET status = 6 WHERE id = 123 AND status = 3;
  ```

**坑3：幂等的key漏了业务维度，不同业务的相同单号撞了**
- 最开始幂等key只传了订单号，没有加业务类型，支付单和退款单用了同一个订单号，幂等的时候撞了，退款请求直接被当成重复的拦截了，退款没成功
- 解决：所有幂等key都加上业务类型前缀，比如支付的key是pay:{out_order_no}，退款的是refund:{refund_no}，不会撞。

### 9. 幂等处理失败了怎么返回？返回成功还是失败？

**答：** 这个非常重要，很多人踩坑：
**只要业务最终是成功的，不管是不是重复，都返回成功，不要返回重复请求错误！**
- 比如回调重复了，你处理过了，就直接返回成功，告诉第三方处理成功了，不然他会一直重试，反而出问题
- 用户重复提交支付，已经支付成功了，就直接返回支付成功，不要告诉用户你重复提交了，用户会懵，只要结果是对的就行
- 只有正在处理中的请求，才返回"处理中，请稍后查询"，让用户稍后查结果
> 核心原则：对调用方要友好，幂等是你系统内部的事情，不要暴露给调用方，调用方只要知道成功还是失败就行，不用知道是不是重复的。

## 面试答题技巧
幂等这块是支付面试的重中之重，你就重点突出：
1. **四层幂等兜底的架构**，从前端到接口到业务到数据库，层层防护，最后数据库兜底，这个设计思想面试官非常认可，说明你做的系统非常稳
2. **不同场景的幂等方案选型**，不是所有场景都用同一个方案，状态机适合状态更新，唯一索引适合插入，Redis锁适合接口层防并发，根据场景选
3. **踩过的坑**，比如只靠Redis没做数据库兜底导致资损，这个一说出来，面试官就知道你真的在支付系统踩过坑，不是纸上谈兵，非常加分。
