> 基于美餐对账系统源码分析 + 面试高频追问整理

---

## 一、短款 / 长款

### 定义（不要记反）

| 术语 | 场景 | 含义 |
|------|------|------|
| **短款** | 渠道有，我们没有 | 我们账目"短缺"，用户已付款但我们漏记 |
| **长款** | 我们有，渠道没有 | 我们账目"多余"，我们多记了成功 |

记忆口诀：站在**我方账目**视角——我们的记录比渠道少 = 短款，比渠道多 = 长款。

### 短款才是最紧急的

短款的"慌"不是因为我们亏了钱，而是：
- 用户付了钱，钱确实到了我们的商户号
- 但我们系统以为支付失败，**没有给用户履约**（没发货、没激活订单）
- 用户会投诉，可能重复支付，属于**欠用户的服务**

长款相对可控：我们多记了，可以查清楚再决定是退款还是追款。

## 二、短款 / 长款触发场景

### 短款（渠道成功，我们没记到）

核心原因：支付结果没有成功同步到我们系统。

1. **回调丢失（最常见）**：微信发回调时我们服务器刚好重启/宕机/网络抖动，回调丢了
2. **回调收到但处理失败**：DB 写入抛异常或事务回滚，状态没持久化
3. **主动查单判断错误**：支付超时后主动查单，查单接口超时，我们把"超时"当"失败"处理
4. **幂等误判**：渠道重试回调，我们幂等逻辑有 bug，把成功回调当重复请求忽略

### 长款（我们记了成功，渠道没有）

核心原因：我们系统错误地记录了一笔不存在的成功。

1. **伪造/重放回调**：签名验证有 bug，攻击者伪造的回调被当真的处理了（安全漏洞）
2. **代码逻辑 bug**：错误处理代码写反，把渠道返回的失败当成功写进去了
3. **消息重复消费**：MQ 幂等没做好，同一笔成功写入两次
4. **渠道账单边界问题（最常见的"假长款"）**：23:59:59 的支付被渠道算入下一天账单，当天对账时我们有、渠道账单没有，第二天自然平账

## 三、边界问题处理方案

### 方案一：宽窗口查询

查数据时两头各多取缓冲时间，把跨天边界的数据都拉进来：

```
对 5月18日 的账：
  查询时间范围：5月17日 23:55 ~ 5月19日 00:05
```

**项目实现**（`generate_bill.go`）：
```go
StartTime: period.Add(-5 * time.Minute),
EndTime:   period.Add(time.Hour*24 + 5*time.Minute),
```

### 方案二：过滤跨天数据（isVerboseBill）

差异发现后，检查 tradeTime 是否在严格周期内，在周期外的静默丢弃：

**项目实现**（`diff_bill.go`）：
```go
func isVerboseBill(period time.Time, tradeTime time.Time) bool {
    startTime := period
    endTime := period.Add(time.Hour * 24)
    return tradeTime.Before(startTime) || tradeTime.After(endTime) || tradeTime.Equal(endTime)
}
```

### 宽窗口 vs isVerboseBill 的关系（重点）

两者作用于**不同阶段**，不是重复的：

```
generate_bill：  ±5min 宽查询  →  两边都能拉到边界数据
reconciliation：  按 trade_no 匹配  →  匹配上的直接删除，不再走后续
diff_bill：       isVerboseBill  →  只过滤【未匹配上】的跨天数据
```

关键：**匹配成功的记录不会走到 isVerboseBill**。

典型场景：
```
payment_slip.created_at  = 23:59:58（我们的数据）
tpw_transaction.created_at = 00:00:03 次日（异步写入稍晚）
两者 trade_no 相同

没有 buffer：右边 00:00:03 查不到 → 左边未匹配 → isVerboseBill(23:59:58)=false → 误报差错
有 buffer：  右边 00:00:03 能查到 → 匹配成功 → 两边从 map 删除 → 完全不报错
```

**结论**：buffer 防止误报（帮助记录找到匹配），isVerboseBill 兜底丢弃（处理真正找不到匹配的跨天数据）。

### 方案三：只对终态订单

SQL 查询时只取已完成状态（`status = success`），处理中（pending）的不参与对账，避免状态未稳定就报差错。

### 方案四：悬挂账机制（项目未实现，理论方案）

差错不立即处理，先挂起等待几天，看能不能自动匹配上，超时才真正报差错。项目里差错直接写入 `error_transaction` 表，没有挂起逻辑。

## 四、对账实现方式

### 不是 MySQL JOIN，是应用层内存 hash 匹配

整体分两步：

**第一步：GenerateCSV**
```
DB（各业务表）→ 分页查 500 条 → 写本地 CSV → 上传 S3
```

**第二步：Reconcile**
```
读左边 CSV（我们的数据）
读右边 CSV（下游/渠道的数据）
→ Go map[trade_no]*Bill 内存匹配
→ 匹配上且金额相等 → 两边从 map 删除，计入平账
→ 未匹配 → HandleDiffBill → isVerboseBill 过滤 → 写 error_transaction
```

**为什么不用 MySQL JOIN：**
- 左右两边数据来自**不同数据库实例**，跨库无法 JOIN
- 应用层分页加载更可控，不会打垮数据库
- CSV 缓存到 S3，重跑任务不需要重新查 DB

## 五、微信 / 支付宝账单的处理方式

### 账单不入 MySQL，存 S3

下载的微信/支付宝账单是 CSV 格式，全程只在本地临时文件和 S3 之间流转，不写入 MySQL。

### tpw2wechat 完整流程

```
Step 1: GenerateCSV
  TPW MySQL (wechat_payment_transaction) → CSV → S3（我们的数据）

Step 2: Download
  逐个商户调用微信 API → 每个商户一个 CSV → /tmp/{sp_mch_id}/{sub_mch_id}/ → S3

Step 3: mergeMchBill
  把所有商户 CSV 合并成一个大 CSV（io.Copy 拼接）→ S3

Step 4: Reconcile
  左边：读 TPW CSV（我们的数据）
  右边：读 WeChat 合并 CSV（微信的数据）
  → 内存 hash map 匹配 → 差异写 error_transaction
```

### 微信账单下载时的边界处理

| 情况 | 处理 |
|------|------|
| 账单还在生成中 | Sleep 10 分钟后重试 |
| 账单不存在 / 已过期 | 写一个空文件，不报错，跳过 |
| 超过 36 小时未生成（第二天中午） | 强制写空文件，放弃等待 |
| 小微商户无权下载子账单 | 改用服务商账号重新下载 |

36小时对应**第二天中午12点**，微信说10点出账单，给2小时缓冲后放弃。

## 六、项目里的错账数据结构

`error_transaction` 表关键字段：

```go
Status    // 0=平账 1=单边(一方没有) 2=错账(金额不等)
LeftHas   // 左边是否存在
RightHas  // 右边是否存在
LeftValue // 左边金额
RightValue// 右边金额
TradeTime // 交易时间（用于 isVerboseBill 判断）
```

重复执行时遇到 `Duplicate entry` 直接忽略，保证幂等。
