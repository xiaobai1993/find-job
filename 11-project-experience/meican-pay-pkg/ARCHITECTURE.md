## 支付系统核心保障机制

### 1. 数据一致性保障
```
支付请求
    ↓
┌─────────────────────┐
│ 分布式锁 (redis_lock)│  ← 防止重复提交
│  订单级别的互斥     │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│  数据库事务 (xorm)   │
│  ┌ 扣余额           │
│  └ 写订单记录       │
│  ┌ 写本地消息表     │  ← txmsg
│  └ 事务提交         │
└──────────┬──────────┘
           ↓ afterCommit 回调
┌─────────────────────┐
│  发送 MQ 消息        │  ← 通知下游系统
└─────────────────────┘
           ↓
┌─────────────────────┐
│  Daemon 补偿         │  ← 兜底保证消息必达
└─────────────────────┘
```

### 2. 并发控制机制
| 层级 | 机制 | 作用 |
|------|------|------|
| 接入层 | 限流 (rate limit) | 防止流量突增 |
| 业务层 | 分布式锁 (redis_lock) | 同一订单串行处理 |
| 数据层 | 数据库事务 + 乐观锁 | 数据最终一致 |
| 消息层 | 幂等去重 (mq/uniqueness) | 消息不重复处理 |

### 3. 可观测性保障
- **链路追踪**: xotel + mq 属性传递 trace
- **错误追踪**: xerrors 记录完整调用栈
- **性能监控**: timecost 统计各阶段耗时
- **业务指标**: metrics 统计成功率、错误率

## 关键设计模式

### 1. 本地消息表模式 (Transaction Outbox)
- 消息和业务数据落库在同一个事务
- 事务提交后异步发送
- 后台 Daemon 轮询补偿
- **应用**: 支付成功通知、订单状态变更

### 2. 补偿机制模式
- 任何可能失败的操作都要有补偿
- 事务消息: Daemon 重发
- 支付: 对账系统平账
- 退款: 定时任务重试

### 3. 上下文传递模式
- ctx 贯穿整个调用链
- 事务信息、trace、用户信息都在 ctx 中
- goroutine 中注意剥离事务上下文

## 生产环境踩坑记录

### 坑1: goroutine 中误用事务 DB
```go
// ❌ 错误：事务已提交，DB 连接已归还
xorm.Transaction(ctx, func(ctx context.Context) error {
    db.Create(&order)
    go func() {
        db.Create(&log)  // 这里的 db 可能已失效！
    }()
    return nil
})

// ✅ 正确：用 safe_go.Go 自动剥离
safego.Go(ctx, func(ctx context.Context) {
    xorm.GetRWDB(ctx).Create(&log)  // 使用全局 DB
})
```

### 坑2: 分布式锁没有自动续期
```go
// ❌ 锁 30 秒后过期，业务执行了 1 分钟
lock := redislock.NewMutex("key", 30*time.Second, false, pools)

// ✅ 开启自动续期
lock := redislock.NewMutex("key", 30*time.Second, true, pools)
```

### 坑3: 事务消息 Daemon 频率太低
```go
// ❌ 5 分钟轮询一次，用户等不及
// ✅ 支付场景 10-30 秒轮询 + 实时回调双保险
```

## 面试要点总结

### Q: 如何保证支付和消息的原子性？
**A:** 本地消息表 + 事务回调 + 后台补偿
1. 业务数据和消息在同一个数据库事务写入
2. 事务提交后回调发送到 MQ
3. 后台 Daemon 轮询超时未发送的消息兜底

### Q: 消息重复了怎么办？
**A:** 生产端 + 消费端双重保证
1. 生产端: 每条消息带 uniqueKey，数据库唯一键约束
2. 消费端: 基于 uniqueKey 做幂等校验，去重表

### Q: 分布式锁失效了怎么办？
**A:** 多层防护
1. 锁只是为了提高并发，数据库层面最终兜底
2. 订单表唯一键约束防重复
3. 幂等设计保证重复处理结果一致

### Q: nested transaction 的 savepoint 作用？
**A:** 支持嵌套事务的部分回滚
1. 子事务失败只回滚子事务，不影响外层
2. 子事务成功可以提前做一些操作（如写消息表）
3. 外层回滚时子事务的数据也一起回滚
