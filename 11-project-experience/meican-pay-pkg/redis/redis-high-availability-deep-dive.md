# Redis 高可用方案深度解析 - 面试版

> 🎯 核心考点：TCP 连接本质、端口耗尽原因、五种高可用方案对比、适用场景、美餐项目实践
> 源码位置：`pkg/redis_lock/`

---

## 一、先搞懂最本质的：TCP 连接是什么？

### 🔌 TCP 四元组 - 全局唯一标识

任何一个 TCP 连接，在整个互联网上的唯一标识就是这四个东西：

```
(源IP, 源端口, 目的IP, 目的端口)
```

### 📞 用打电话类比：

| 四元组 | 类比 | 说明 |
|-------|------|------|
| 目的 IP | 对方公司总机号 | 固定，比如 `192.168.1.100` |
| 目的端口 | 对方分机号 | 固定，Redis 永远是 `6379` |
| 源 IP | 你的手机号 | 固定，你的机器 IP |
| 源端口 | 你的手机分机号 | 操作系统随机分配！ |

**你可以用不同的源端口打同一个总机的同一个分机，这就是不同的 TCP 连接。**

---

## 二、新建 Redis 连接到底在干什么？

当你执行：

```go
conn, _ := net.Dial("tcp", "192.168.1.100:6379")
```

操作系统会做这几件事：

1. 目的 IP：`192.168.1.100`（固定）
2. 目的端口：`6379`（固定）
3. 源 IP：你的机器 IP（固定）
4. **源端口：操作系统从 `ip_local_port_range` 里随机选一个空闲的**

### ⚠️ 最关键的点：源端口是有限的！

Linux 默认的端口范围是：`32768 ~ 60999`，一共也就 **28231 个可用端口**。

> 💡 **结论：一台机器最多只能建立约 2.8 万个连接到同一个 Redis 实例！** 源端口用完就没了！

---

## 三、为什么端口会耗尽？TIME_WAIT 的锅！

### ❌ 极其错误的写法：

```go
// 每次操作新建一个连接，用完就关
for i := 0; i < 100000; i++ {
    conn, _ := net.Dial("tcp", "192.168.1.100:6379")
    // 用完就关
    conn.Close()
}
```

**为什么关了还会耗尽？**

因为 TCP 连接有个状态叫 **TIME_WAIT**：
- 谁主动关闭连接，谁就进入 TIME_WAIT
- 这个状态会持续 **2MSL（约 2 分钟）**
- 这段时间这个端口 **不能被复用**！

所以：
- 你 1 秒钟建 1000 个连接
- 2 分钟 = 120 秒，就是 12 万个连接
- 但是可用端口只有 2.8 万个
- 大概 28 秒就全部耗尽了！

**这就是没有连接池会崩的根本原因！**

---

## 四、一个 Redis 实例最多允许多少个连接？

### 理论上限：`maxclients` 参数

Redis 配置里有个参数叫 `maxclients`，默认是 **10000**，也就是最多允许 1 万个连接同时连上来。

### 实际上限：远低于 1 万！

Redis 是 **单线程** 的！太多连接的话，光处理连接的上下文切换就把 CPU 耗光了，根本没精力处理命令。

**生产级最佳实践：**
- 单个 Redis 节点，同时连接数不要超过 **200-500**
- 再多 QPS 不会提升，反而会因为连接太多变慢
- 所以连接池的 `MaxActive` 设 100-200 足够了，设 1 万完全是浪费，反而会把 Redis 压垮

## 五、Redis 高可用方案大全

高可用分两大类，场景完全不一样：

| 分类 | 解决的问题 | 代表方案 |
|-----|-----------|---------|
| **锁的高可用** | 锁服务不能挂，挂了也不能出现两个线程同时拿到锁 | Redlock |
| **数据存储的高可用** | 数据不能丢，节点挂了数据要能恢复，服务不能断 | 主从、哨兵、集群、代理分片 |

---

### 方案 1：主从复制（Master-Slave）- 最基础的

#### 原理：

```
Master (主节点) ← 所有写操作
    |  写操作异步同步
    v
Slave1 (从节点) ← 读
    |
    v
Slave2 (从节点) ← 读
```

- 1 个主节点，N 个从节点
- 写只能写主节点
- 读可以读任意节点（读写分离）
- 主节点会把所有写操作异步同步给所有从节点

#### 优点：
- ✅ 简单，配置 5 分钟搞定
- ✅ 读性能线性提升，从节点越多读越快
- ✅ 数据有备份，主节点挂了从节点还有完整数据

#### 缺点：
- ❌ **没有自动故障转移！** 主节点挂了，必须手动把某个从节点提升成新主，期间服务完全不可用
- ❌ 有数据不一致窗口：主挂了的时候，有些写操作可能还没同步到从节点，会丢数据
- ❌ 写性能还是只有一个主节点，没有提升
- ❌ 单节点容量上限，存不下太多数据

#### 适用场景：
- 非核心业务，允许短时间停机
- 读多写少，主要用来做读写分离
- 可以接受少量数据丢失

---

### 方案 2：哨兵模式（Sentinel）- 生产级最常用

#### 原理：
在主从复制的基础上，加了 **N 个哨兵节点** 做监控：

```
Sentinel1  Sentinel2  Sentinel3  (至少3个，必须是奇数个!)
    |          |          |
    v          v          v
  Master <--> Slave1 <--> Slave2
```

哨兵做的四件事：
1. **监控**：所有哨兵不断 ping 主从节点，看还活没活着
2. **故障检测**：超过半数哨兵认为主节点挂了，就判定主节点真的挂了（防止误判）
3. **自动故障转移**：从从节点里选一个新的主节点，通知所有从节点连新主
4. **通知**：告诉客户端新的主节点地址是什么

#### 优点：
- ✅ **自动故障转移！** 主节点挂了，一般 30 秒内就能自动切到新主，业务几乎无感知
- ✅ 还是主从的所有优点，读写分离、数据备份
- ✅ 成熟稳定，生产环境用得最多的方案

#### 缺点：
- ❌ 部署复杂，要至少 3 个哨兵节点，还要配主从
- ❌ 还是单节点写瓶颈，写性能还是只有一个主
- ❌ 还是单节点容量上限，存不下太多数据
- ❌ 还是有数据不一致窗口，故障转移时可能丢少量数据

#### 适用场景：
- 绝大多数业务场景
- 核心业务，需要高可用，不能接受长时间停机
- 数据量不是特别大（几十 GB 到几百 GB）

---

### 方案 3：Redis Cluster（官方集群）- 大数据量用

#### 原理：
**分片 + 高可用结合**，把数据分散到多个节点上：

```
分片1：MasterA <-> SlaveA
分片2：MasterB <-> SlaveB
分片3：MasterC <-> SlaveC
...
```

- 整个集群有 **16384 个哈希槽（slot）**
- 每个 key 算 CRC16 然后对 16384 取模，落到对应的槽
- 每个主节点负责一部分槽，比如 MasterA 负责 0-5000，MasterB 负责 5001-10000
- 每个主节点有从节点做备份，主挂了自动切从

#### 优点：
- ✅ **解决了容量问题！** 数据分散在多个节点，理论上可以无限扩容
- ✅ **写性能线性提升！** 多个主节点可以同时写
- ✅ 内置高可用，每个分片都是主从，自动故障转移
- ✅ 官方原生支持，不需要第三方组件

#### 缺点：
- ❌ 非常复杂，运维成本高
- ❌ 有很多限制：不能跨节点事务，不能批量操作跨节点的 key
- ❌ 数据倾斜问题：某些 slot 特别热，导致某个节点压力大
- ❌ 客户端要支持集群协议，老的客户端用不了

#### 适用场景：
- 数据量特别大，单节点存不下（几百 GB 以上）
- 写压力特别大，单主节点写性能不够用
- 大厂，有专门的 DBA 运维

---

### 方案 4：代理分片方案（Twemproxy / Codis）- 上古时代的方案

#### 原理：
在客户端和 Redis 中间加一层代理，代理负责分片：

```
客户端
   |
   v
Codis / Twemproxy 代理层
   |
   v
Redis1 Redis2 Redis3 ...
```

- 代理层负责把 key 分到不同的 Redis 节点
- 客户端以为自己连的是单个 Redis，完全透明
- 这是在 Redis 官方还没有 Cluster 的时候大家用的方案

#### 优点：
- ✅ 客户端完全不需要改代码，透明
- ✅ 比 Redis Cluster 出来得早，生态成熟

#### 缺点：
- ❌ 多了一层代理，有性能损耗
- ❌ 代理本身也可能成为瓶颈和单点
- ❌ 维护成本极高，现在基本被 Redis Cluster 取代了

#### 适用场景：
- 老系统，还在用很老版本的 Redis，没法升级到 Cluster
- 基本上新项目不会用了

---

### 方案 5：Redlock - 专门做分布式锁的高可用

#### 原理：
这个我们之前讲过了，**N 个完全独立的 Redis 节点**，没有主从关系：

```
Redis1  Redis2  Redis3  Redis4  Redis5  (完全独立，没有任何关系!)
```

加锁的时候同时给所有节点加，超过半数成功就算加锁成功。

#### 和其他方案的本质区别：

> **Redlock 根本不关心数据，只关心可用性！**

分布式锁是什么？是个临时的东西，最多几十秒就过期了，哪怕某个节点完全挂了，丢了所有锁，过 30 秒也都自动释放了，不会有什么严重后果。

所以 Redlock 的设计哲学是：
- 哪怕 2 个节点挂了，还有 3 个能用，服务不中断就行
- 丢了点锁数据没关系，反正过会儿就过期了
- 不需要主从，不需要持久化，不需要数据一致
- 就是为了锁这个场景专门设计的！

## 六、所有高可用方案对比总表

| 方案 | 核心解决的问题 | 数据一致性 | 自动故障转移 | 写性能 | 容量 | 复杂度 | 适用场景 |
|-----|---------------|-----------|-------------|-------|-----|-------|---------|
| **主从复制** | 读扩展、数据备份 | 最终一致，可能丢 | ❌ 没有 | 单节点 | 单节点 | 极低 | 非核心，读多写少 |
| **哨兵模式** | 高可用，主挂了自动切 | 最终一致，可能丢少量 | ✅ 有 | 单节点 | 单节点 | 中 | 绝大多数生产业务 |
| **Redis Cluster** | 大容量、高写性能 | 最终一致 | ✅ 有 | 线性提升 | 几乎无限 | 高 | 数据量大，写压力大 |
| **代理分片** | 老版本 Redis 分片 | 最终一致 | ❌ 自己实现 | 线性提升 | 几乎无限 | 极高 | 老系统，不推荐 |
| **Redlock** | 分布式锁的高可用 | 不需要一致 | ✅ 本质就是防单点 | 多数派 | 极小（只存锁） | 中 | 分布式锁专用场景 |

## 七、美餐项目里的实际用法

美餐是分开用的，不要混着用！

1. **分布式锁用 Redlock**：5 个独立的 Redis 节点，专门用来做锁，不存其他数据
2. **业务数据存储用哨兵模式**：主从 + 哨兵，自动故障转移，存业务缓存、用户数据这些

> 💡 **千万不要用存业务数据的哨兵集群来做 Redlock！**
>
> 万一业务 Redis 挂了，锁服务也跟着挂了，两个核心服务同时崩，雪崩效应！
> 一定要分开部署，独立集群，各司其职。

## 八、📝 面试标准回答模板

### 面试官问：Redis 高可用方案有哪些？你们用的是哪个？

> "Redis 高可用分两大类，一类是数据存储的高可用，一类是分布式锁的高可用。
>
> 数据存储的高可用主要有四个方案：
>
> 第一个是主从复制，一主多从，读写分离，优点是简单，缺点是没有自动故障转移，主挂了要手动切，适合非核心业务。
>
> 第二个是哨兵模式，在主从的基础上加了至少 3 个哨兵节点做监控和自动故障转移，主挂了 30 秒内就能自动切到新主，业务无感知，这是生产环境用得最多的方案，适合绝大多数业务。
>
> 第三个是 Redis 官方集群，也就是 Redis Cluster，用 16384 个哈希槽把数据分到多个主节点上，解决了单节点容量问题，写性能也能线性提升，适合数据量特别大、写压力特别高的场景，但缺点是比较复杂，有很多限制，运维成本高。
>
> 第四个是代理分片方案比如 Codis 和 Twemproxy，这是官方 Cluster 出来之前的方案，现在基本上被取代了，新项目不会用。
>
> 然后是分布式锁的高可用，用的是 Redlock 算法，这个和数据存储的高可用思路完全不一样，它用 N 个完全独立的 Redis 节点，没有主从关系，加锁超过半数成功就算成功，只要不超过半数节点挂，服务就可用，专门适合分布式锁这种不需要数据持久化、丢了也没关系的场景。
>
> 我们项目里是分开用的：业务数据存储用哨兵模式，稳定可靠；分布式锁用 Redlock，5 个独立节点，防单点故障。"

## 九、一句话总结

> **主从是备份，哨兵是自动切换，集群是分片扩容，Redlock 是防单点。**
>
> 没有最好的方案，只有最适合场景的方案。

## 📝 面试要点复盘

1. ✅ **TCP 四元组** - 源IP、源端口、目的IP、目的端口，四个东西唯一标识一个连接
2. ✅ **一台机器最多连同一个 Redis 多少次？** 约 2.8 万次，因为源端口只有这么多
3. ✅ **TIME_WAIT 是什么？** 主动关闭的一方会保持 2 分钟，端口不能复用，这是端口耗尽的根本原因
4. ✅ **单个 Redis 最佳连接数？** 200-500，再多没用，Redis 是单线程的
5. ✅ **五种高可用方案的原理、优缺点、适用场景** - 必背！
6. ✅ **哨兵为什么至少要 3 个？** 要超过半数才能做故障判定，防止脑裂
7. ✅ **Redis Cluster 有多少个哈希槽？** 16384 个，必背！
8. ✅ **为什么分布式锁要用 Redlock 不用哨兵？** 哨兵故障切换期间可能两个线程同时拿到锁
