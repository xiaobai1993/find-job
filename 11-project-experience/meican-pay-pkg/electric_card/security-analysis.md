# 电子美餐卡完整案例 + 安全边界分析

> 🔥 核心问题：抓包拿到卡号，就能伪造二维码消费吗？

---

## 一、完整流程案例（从头到尾）

### 场景：老王办了一张电子美餐卡

---

#### Step 1：发卡/注册（服务器端）

```go
// 服务器生成一张新卡
cardID := 12345          // 老王的卡号（9位以内）
apiKey := "KJ82XZPQ7A"   // 随机生成，只有服务器和老王的设备知道！
                         // ⚠️ 这个才是真正的核心机密！

// 这个 apiKey 会：
// 1. 写入数据库，和卡号 12345 绑定
// 2. 通过安全信道传给老王的手机/设备
// 3. 设备本地存好，永远不会再传输
```

✅ **关键点：apiKey 从来不会出现在网络传输中！**

---

#### Step 2：设备生成当前卡号（老王的手机）

假设现在是：**2026-05-18 12:30:45**，时间戳 = `1779136245000`

```go
// 设备本地计算，完全不联网！

// 第 1 步：计算时间计数器（30 秒一变）
epoch := 1262275200000  // 2010-01-01 基准时间
timestamp := 1779136245000 - epoch
counter := timestamp / 30000  // = 17230701，每 30 秒 +1

// 第 2 步：生成 6 位 OTP
OTP = otp.Generate(apiKey, counter, 6)
// 假设算出来 = 876543

// 第 3 步：把 OTP 和卡号编码成 15 位 AuthCode
prime := 931353139
AuthCode = OTP * prime + cardID
// = 876543 * 931353139 + 12345
// = 816396736123122

// 第 4 步：生成 3 位 CheckCode
checkKey := fmt.Sprintf("%d%06d", cardID, OTP)  // = "12345876543"
CheckCode = otp.Generate(checkKey, counter, 3)
// 假设算出来 = 789

// 第 5 步：最终卡号
FinalCode = "E" + AuthCode + CheckCode
// = E816396736123122789
```

✅ **最终老王屏幕上显示：E816396736123122789**

---

#### Step 3：服务器验证

老王刷卡，把这个 19 位字符串 + 设备时间戳发给服务器：

```go
code := "E816396736123122789"
deviceTimestamp := 1779136245000

// 第 1 步：解析
code = strings.TrimPrefix(code, "E")  // 去掉 E
AuthCode = 816396736123122
CheckCode = 789

// 第 2 步：解码出 OTP 和卡号
CardNumber = AuthCode % prime  // = 816396736123122 % 931353139 = 12345 ✅
OTP = AuthCode / prime         // = 816396736123122 / 931353139 = 876543 ✅

// 第 3 步：从数据库取出卡号 12345 对应的 apiKey
apiKey := db.GetAPIKey(12345)  // = "KJ82XZPQ7A"

// 第 4 步：服务器用这个 apiKey 算 OTP，看和收到的一样吗
serverOTP := otp.Generate(apiKey, counter, 6)  // = 876543 ✅ 对上了！

// 第 5 步：校验 CheckCode（防止卡号被篡改）
checkKey := fmt.Sprintf("%d%06d", CardNumber, OTP)
serverCheckCode := otp.Generate(checkKey, counter, 3)  // = 789 ✅ 也对上了！

// ✅ 验证通过！老王可以吃饭了
```

## 二、核心安全问题分析：抓包能伪造吗？

### 🎯 你的问题：抓包拿到卡号，能伪造吗？

**答案：能，但只有 3 分钟有效期！**

---

### 攻击场景 1：实时抓包，3 分钟内用掉 ✅ 可以伪造

```
攻击者的操作：
1. 站在老王后面，用摄像头拍到二维码
2. 或者在网络层抓包，截获卡号 E816396736123122789
3. 1 分钟后，攻击者拿着这个卡号去刷自己的卡

✅ 结果：能刷成功！
```

**为什么？**
- 这个卡号在前后 3 分钟内都是有效的
- 只要在这个时间窗口内用，服务器认不出来

---

### 攻击场景 2：抓包后存着，明天用 ❌ 不行

```
攻击者的操作：
1. 今天抓了老王的卡号
2. 第二天拿出来用

❌ 结果：验证失败！
```

**为什么？**
- 30 秒一变，3 分钟后这个卡号就彻底失效了
- 攻击者没有 apiKey，算不出下一个卡号是什么

---

### 攻击场景 3：暴力破解 ❌ 几乎不可能

```
攻击者想猜一个有效的卡号：
- 6 位 OTP + 3 位 CheckCode = 9 位
- 10 亿种可能
- 每 30 秒变一次
- 每秒试 1000 次 = 要试 11 天才能猜中一个
- 等猜中了早就变了
```

---

## 三、这个系统的真实安全边界

| 攻击方式 | 能否成功 | 前提条件 |
|---------|---------|---------|
| **实时抓包 + 立即使用** | ✅ 能 | 必须在 3 分钟窗口期内 |
| **重放攻击（过几天再用）** | ❌ 不能 | 3 分钟后就失效 |
| **暴力破解** | ❌ 几乎不能 | 9 位组合太难猜 |
| **知道卡号，推算 apiKey** | ❌ 不能 | 单向哈希，不可逆 |
| **偷到设备本地的 apiKey** | ✅ 完全能 | 偷到了密钥就等于偷了卡 |

## 四、微信/支付宝是怎么解决这个问题的？

你问得非常对！微信支付宝的付款码也有同样的问题！

### 微信支付宝的防护措施：

| 措施 | 作用 |
|------|------|
| **1 分钟失效** | 比美餐的 3 分钟窗口更小 |
| **一次性** | 用过一次立刻作废，就算被截获也没用 |
| **风控规则** | 异地、异常设备、大额交易需要二次验证 |
| **限额** | 付款码当面付通常单笔限额 1000-5000 |
| **赔付机制** | 被盗刷了保险公司赔 |

## 五、美餐这个系统的改进空间

如果我是架构师，会加这几层防护：

### 🛡️ 改进 1：OTP 一次性使用
```go
// 验证通过后，把这个 counter 标记为已使用
redis.SetEX(fmt.Sprintf("otp_used_%d_%d", cardID, counter), 1, 5*60)

// 下次验证前先检查
if redis.Exists(fmt.Sprintf("otp_used_%d_%d", cardID, counter)) {
    return errors.New("OTP already used")
}
```

✅ **效果：抓包拿到了也没用，因为老王已经用过了！**

---

### 🛡️ 改进 2：风控规则
- 一张卡 5 分钟内最多刷 3 次
- 异地刷卡需要人工审核
- 连续失败 3 次锁定 10 分钟

---

### 🛡️ 改进 3：缩短时间窗口
- 把 3 分钟改成 1 分钟，减少攻击窗口

## 六、面试标准回答模板

### 面试官问：这个动态密码系统有什么安全问题？抓包了能伪造吗？

> "首先要分情况看：
>
> 第一，实时抓包然后在窗口期内使用 —— 是的，这个是可以的。任何 TOTP/HOTP 系统都有这个问题，包括微信支付宝的付款码。本质上是「持有者即合法」的设计，你拿到了当时的令牌就等于你是持有者。
>
> 第二，过了窗口期再用 —— 不行，因为 30 秒一变，3 分钟后这个令牌就失效了，攻击者没有 apiKey 算不出下一个。
>
> 第三，暴力破解 —— 几乎不可能，9 位组合有 10 亿种可能，还在不断变化。
>
> 改进的话，可以加几层：
> 1. OTP 用过一次就标记失效，防止重放
> 2. 加风控规则，限制刷卡频率和地点
> 3. 缩短时间窗口，从 3 分钟改成 1 分钟
>
> 总的来说，这是一个典型的「便利性 vs 安全性」的权衡。线下场景攻击成本比较高，需要物理 proximity，站在别人后面拍二维码，这个风险是可接受的。"

## 七、一句话总结

> **抓包只能偷到「现在能用 3 分钟的临时门票」，偷不到「永久的开门钥匙」**
>
> 就像你偷到了酒店房门的门卡，今天能进，明天房卡一换就没用了，你还是进不去。
