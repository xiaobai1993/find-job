## 一、这是什么？

**电子美餐卡** —— 美餐的离线动态验证码系统，类似 Google Authenticator。

**核心设计思想：**
- 设备和服务器不需要联网，各自独立计算验证码
- 靠时间同步和共享密钥来验证身份
- 类似银行的动态口令卡、Steam 令牌、Google Authenticator

---

## 二、18 位卡号结构解析

```
卡号格式示例：E 123456 789012 345
             ──┬───── ───┬───── ─┬─
               │        │       └── 3 位校验码（CheckCode）
               │        └────────── 卡号（CardNumber）
               └────────────────── 6 位动态密码（OTP）
```

**拆解：**

| 部分 | 长度 | 作用 | 算法 |
|------|------|------|------|
| **OTP** | 6 位 | 动态密码，30 秒一变 | HOTP（RFC 4226） |
| **CardNumber** | 9 位 | 卡号，最大 9 位素数 | `AuthCode % prime` |
| **CheckCode** | 3 位 | 校验码，防止伪造/篡改 | HOTP（卡号 + OTP 作为 key） |

**核心公式：**
```go
AuthCode = OTP * prime + CardNumber  // prime = 931353139（9 位素数）
Code = E + AuthCode(15位) + CheckCode(3位)
```

> 💡 **面试加分：** 用素数做模运算，保证卡号分布均匀，这是密码学常用技巧。

## 三、算法演进历史：V1 → V2

美餐的电子餐卡算法经历过一次重大简化，这是非常典型的工程化权衡案例。

### 📜 V1 原始算法（双素数版本）

```go
// 两个大素数
prime_small = 68718952447   // 11 位素数
prime_big   = 4398050705407 // 13 位素数

code = prime_small * n + id + prime_big * OTP
// n = timestamp % 30，用于本地刷新
```

**V1 设计思路：**
- 两个不同大小的素数做分层编码
- 数学上安全性更高，碰撞概率更低
- 但计算更复杂，跨语言实现容易出问题

---

### 📜 V2 当前算法（单素数简化版）

```go
// 只用一个 9 位大素数
p = 931353139

code = number + OTP * p
```

**为什么从 V1 演进到 V2？**

| 维度 | V1 | V2 |
|-----|----|----|
| 数学安全性 | 更高 | 足够高 |
| 计算复杂度 | 高 | 低 |
| 跨语言实现 | 容易出错 | 简单不易错 |
| 调试排查 | 困难 | 直观 |

> 💡 **面试必问点：为什么要简化？**
>
> "这是典型的安全与工程的权衡。V1 的双素数设计在数学上确实更安全，但对于支付场景来说，单素数的 0.1% 碰撞率已经完全够用了。
>
> 实际生产环境中，**实现正确性比理论安全更重要**。V2 简化后，客户端、POS 机、服务器三端不容易出不一致的 bug，整体系统的可靠性反而更高。
>
> 这也是很多安全系统的设计原则：**够用就好，不要过度设计**。"

## 四、otp 包源码解析 - HOTP 算法（RFC 4226）

这是完全标准的 RFC 4226 HOTP 实现，和 Google Authenticator 算法一模一样！

```go
func Generate(key string, input int64, digits int) uint32 {
    return oneTimePassword([]byte(key), toBytes(input), digits)
}

func oneTimePassword(key []byte, value []byte, digits int) uint32 {
    // 第 1 步：HMAC-SHA1 签名
    hmacSha1 := hmac.New(sha1.New, key)
    hmacSha1.Write(value)
    hash := hmacSha1.Sum(nil)  // 20 字节 SHA1 哈希

    // 第 2 步：动态截断（Dynamic Truncation）- RFC 4226 §5.3
    // 用最后一个字节的低 4 位作为偏移量（0-15）
    offset := hash[len(hash)-1] & 0x0F

    // 第 3 步：从偏移量位置取 4 个字节
    hashParts := hash[offset : offset+4]

    // 第 4 步：去掉最高位，避免符号问题（RFC 要求）
    hashParts[0] = hashParts[0] & 0x7F

    // 第 5 步：转成 32 位整数，取模得到指定位数
    number := toUint32(hashParts)
    return number % uint32(math.Pow(10, float64(digits)))
}
```

**面试点：**
1. **为什么用 SHA1？** —— RFC 4226 标准指定，而且速度快、硬件支持好
2. **为什么要动态截断？** —— 让输出分布更均匀，避免攻击者预测
3. **为什么要 & 0x7F 去掉最高位？** —— 避免有符号整数的正负号问题

## 四、完整验证流程

```
用户刷卡，传来 18 位卡号 + 时间戳
    ↓
Step 1: 去掉前缀 "E"，拆分成 15 位 AuthCode + 3 位 CheckCode
    ↓
Step 2: 解析出 OTP 和 CardNumber
        CardNumber = AuthCode % 931353139
        OTP = AuthCode / 931353139
    ↓
Step 3: 验证 CheckCode（防伪造）
        用「卡号 + OTP」作为 key，生成 3 位 HOTP
        和收到的 CheckCode 对比，**前后 30 分钟内都算有效**
        （最多需要连续计算 240 次 OTP 进行穷举验证）
    ↓
Step 4: 验证 OTP（防重放）
        用卡的 api_key 作为 key，生成 6 位 HOTP
        和收到的 OTP 对比，前后 3 分钟内都算有效
    ↓
✅ 验证通过
```

## 五、设计亮点（面试必背）

### 亮点 1：双重 HOTP 校验，安全性加倍

| 校验层级 | Key | 位数 | 作用 |
|---------|-----|------|------|
| CheckCode | `卡号 + OTP` | 3 位 | 防止卡号被篡改、伪造 |
| OTP | `api_key` | 6 位 | 防止重放攻击、验证时间有效性 |

**为什么两层？**
- 只有 3 位 CheckCode 的话，1000 次就能暴力破解
- 只有 6 位 OTP 的话，攻击者可以随便写卡号蒙
- 两层加起来，相当于 9 位验证码，暴力破解概率是 1/1,000,000,000

---

### 亮点 2：±30 分钟超大时间容错，POS 机离线友好

```go
// 官方实际容错窗口：前后各 30 分钟，最多 240 次 OTP 计算
// 30 分钟 / 30 秒 = 60 个窗口 × 2 方向 = 120 个窗口
// 双向穷举，最多计算 240 次
```

**为什么要这么大的窗口？**
- POS 机很多是长期离线的，系统时间不准
- 用户手机时间也可能不准
- **业务可用性 > 绝对安全**：宁愿多算几次，也不能让用户刷不了卡

> 💡 面试加分：这又是一个典型的工程化权衡案例！
> 理论上窗口越小越安全，但离线场景下，用户体验比那点理论安全重要多了。

**设计思考：**
- 设备的时钟不可能完全准确
- 网络传输也有延迟
- 3 分钟是安全和用户体验的平衡点
- 太长容易被重放攻击，太短用户体验差

---

### 亮点 3：素数模运算，保证卡号均匀分布

```go
prime int64 = 931353139  // 9 位素数
CardNumber = AuthCode % prime
```

**为什么用素数？**
- 素数的模运算分布最均匀，不会出现某些号段特别集中
- 避免攻击者推测出卡号的生成规律
- 密码学的标准做法

## 六、官方内部设计细节

### 6.1 apiKey 的编码格式

```
apiKey = "MZSWEZLBHA4DQLLEGY3TGLJUGBRDMLJYMNRDOLLCHAZGCM3GGM3DANLFGI======"
```

这是 **Base32 编码**，和 Google Authenticator 的密钥格式完全一致！

解码后是标准 UUID：
```
073ce5df-493b-40ea-81c8-65affc4517e4
```

**为什么用 Base32？**
- RFC 4226 标准指定的密钥格式
- 字母都是大写，没有 0/O 1/I 这种容易混淆的字符
- 方便人工输入（比如绑卡时手动输密钥）

### 6.2 官方完整计算示例

美餐内部文档给出了完整的数值计算示例，可以用来验证你的实现：

```
输入：
  number = 930878892
  apiKey = GA3TGY3FGVSGMLJUHEZWELJUGBSWCLJYGFRTQLJWGVQWMZTDGQ2TCN3FGQ======
  timestamp = 1488791421696 (2017年的时间戳)
  时间元年偏移 = 1262275200000 (2010-01-01 00:00:00 北京时间)

计算步骤：
  1. 计算相对时间戳：1488791421696 - 1262275200000 = 224963931123
  2. OTP = HOTP(apiKey, 相对时间戳/30000) = 091621
  3. check_code 输入字符串："930878892" + "091621" = "930878892091621"
  4. check_code = HOTP(check_code 输入字符串, 相同时间戳) 的后 3 位 = 304
  5. 左 15 位 = 930878892 + 091621 * 931353139 = 085332436827211
  6. 最终支付码 = 085332436827211 + 304 = 085332436827211304
```

### 6.3 POS 机离线校验的抗碰撞测试数据

美餐做了 20 万次暴力碰撞测试，结果非常漂亮：

| 测试场景 | 测试数量 | 碰撞率 |
|---------|---------|-------|
| 正确码随机修改 1 位 | 200,000 | 0.1% |
| 正确码随机修改 2 位 | 200,000 | 0.1% |
| 完全随机的 18 位 | 200,000 | 0.1% |

**解读：**
- 3 位校验码的理论碰撞率就是 1/1000 = 0.1%
- 所有场景都完美符合理论值
- 说明这个密码学设计是教科书级别的，没有任何缺陷

## 七、常见攻击方式 & 防护措施

| 攻击方式 | 防护措施 |
|---------|---------|
| **暴力破解** | 9 位组合 = 10 亿种可能，加上 3 分钟窗口，几乎不可能 |
| **重放攻击** | OTP 30 秒一变，用过的验证码服务器要标记失效 |
| **时钟漂移攻击** | 限制最大容错窗口（30 分钟），配合风控异常检测 |
| **钓鱼攻击** | 需要配合业务侧的风控，异常设备报警 |
| **密钥泄露** | 每张卡独立密钥，即使泄露不影响其他卡 |

## 八、和 Google Authenticator（TOTP）的对比

| 特性 | 电子美餐卡（HOTP变种） | Google Authenticator（TOTP） |
|------|----------------------|---------------------------|
| 时间步长 | 30 秒 | 30 秒 |
| 容错窗口 | ±30 分钟，最多 240 次计算 | 通常 ±1 步，3 个窗口 |
| 校验码 | 额外 3 位 CheckCode 校验卡号 | 没有 |
| 时间基准 | 2010-01-01 00:00 UTC（epoch） | Unix epoch（1970-01-01） |
| 密钥 | 每张卡独立 api_key | 每个账号独立密钥 |

## 八、面试标准回答模板

### 面试官问：能说说这个电子美餐卡的设计原理吗？

> "这是一个基于 HOTP（RFC 4226）的离线动态验证码系统，类似 Google Authenticator。
>
> 核心设计有几层：
>
> 第一，18 位卡号本身是三层结构，6 位 OTP 动态密码、9 位卡号、3 位校验码，用一个 9 位素数做模运算把 OTP 和卡号编码成 15 位整数，保证卡号均匀分布。
>
> 第二，双重 HOTP 校验，第一层用卡号加 OTP 做 key 生成 3 位校验码，防止卡号被篡改伪造；第二层用卡的独立密钥生成 6 位 OTP，验证时间有效性。
>
> 第三，时间容错设计，允许前后 30 分钟的时钟误差，最多计算 240 个时间窗口，专门适配 POS 机长期离线时间不准的场景，这是典型的业务可用性优先的工程权衡。
>
> 这个设计的好处是设备完全不需要联网，和服务器各自独立计算，靠时间和共享密钥来验证，非常适合离线刷卡的场景。
>
> 密钥分发的原则是「一次传输，永久离线」：用户绑卡时通过 HTTPS 把 apiKey 下发一次，存在手机安全区，之后日常刷卡绝对不传密钥，只传计算结果。换设备就重新走一遍绑卡流程，旧 key 直接作废，和支付宝微信付款码的机制完全一样。"

## 十、进阶思考题（面试官可能追问）

### Q1：为什么时间基准选 2010 年而不是 Unix epoch？
A：Unix epoch 到现在已经 50 多年了，计数器值比较大，选更近的时间点可以减少碰撞概率，也符合美餐成立的时间线。

### Q2：30 分钟容错会不会太大，导致重放攻击窗口？
A：是个典型的工程权衡。一方面 POS 机很多是离线的，时间不准是常态，太小的窗口用户体验很差；另一方面，业务侧会配合「用过的 OTP 标记失效」机制，同一个 OTP 用过就不能再用了，即使被截获也只能用一次，风险可控。

### Q3：为什么不用 TOTP 标准（RFC 6238）？
A：本质上就是 TOTP，只是美餐自己实现了一层卡号编码和双重校验，更适合业务场景。

### Q4：如果设备时间完全不准怎么办？
A：可以在设备端做时间校准，或者服务器端记录每个设备的时间偏移量，动态调整窗口。

## 十一、核心机制：密钥分发与设备管理

这是整个系统最容易被追问的环节——**密钥怎么到用户设备上的？换设备了怎么办？**

### 🎯 核心原则：一次传输，永久离线

> apiKey 不是"不通过网络"，是**只通过网络一次**！

| 传输类型 | 频率 | 风险 |
|---------|------|------|
| ❌ 每次计算密码都传 | 每次刷卡 | 极高 - 每次都暴露 |
| ✅ 绑卡时只传一次 | 设备生命周期内一次 | 极低 - 只暴露一次窗口 |

---

### 阶段 1：用户注册 / 首次绑卡

```
用户 App                           服务器
  |                                 |
  |------- 用户名密码登录 ---------->|
  |                                 | 验证通过
  |                                 | 生成用户专属 apiKey
  |                                 | 存入数据库（加密存储）
  |<------ 通过 HTTPS 返回 apiKey ---|
  |                                 |
  |  apiKey 存入手机安全存储区域      |
  |  (KeyStore / Secure Enclaves)   |
```

**三大关键点：**
1. **只传这一次**！绑卡成功后，apiKey 永久存在手机里
2. **必须走 HTTPS + 证书双向校验**，防止中间人攻击
3. **apiKey 不能明文存**，必须用系统级安全存储：
   - Android：Android Keystore
   - iOS：Keychain / Secure Enclave
   - 小程序：本地加密存储

---

### 阶段 2：日常刷卡（真·离线模式）

```
用户 App                           服务器
  |                                 |
  |  本地用 apiKey 计算动态密码      |
  |  HOTP(apiKey, timeCounter)      |
  |                                 |
  |------- 展示二维码/数字 --------->|
  |                                 |
  |                                 | 服务器用数据库里的 apiKey 验算
  |                                 | 通过就放行
```

**源码佐证：** 看 `ElectricCardAuthCodeInput` 结构体
```go
type ElectricCardAuthCodeInput struct {
    CardNo    string `json:"cardNo"`    // 卡号
    CheckCode string `json:"checkCode"` // 校验码
    Otp       string `json:"otp"`       // 动态密码
}
```

> 💡 **关键洞察：** apiKey 从来不会出现在日常的网络请求里！
>
> 刷卡时只传卡号、OTP、校验码——都是计算结果，没有密钥。
> 这就是"离线"两个字的真正含义。

---

### 阶段 3：用户换设备了

```
新设备 App                        服务器
  |                                 |
  |------- 用户名密码登录 ---------->|
  |                                 |
  |<------ 返回：已绑定设备 X -------|
  |                                 |
  |------- 申请换设备 ------------->|
  |                                 |
  |<------ 短信/人脸/实名校验 ------|
  |                                 | 验证通过
  |                                 | 🔴 废弃旧设备的 apiKey
  |                                 | 🟢 生成新的 apiKey
  |<------ HTTPS 返回新 apiKey -----|
  |                                 |
  |  新 apiKey 存入新设备安全区      |
```

**换设备 = 重新走一次绑卡流程！**

旧 key 直接作废，就算旧手机丢了也没关系。

---

### 为什么支付宝/微信付款码也是这么做的？

```
用户第一次登录 App
    |
    V
服务器下发设备密钥（deviceSecret）
    |
    V
密钥存在手机安全区
    |
    V
付款码 = HOTP(deviceSecret, timeCounter)
    |
    V
换设备登录 → 下发新的 deviceSecret → 旧的作废
```

和美餐的方案 100% 对齐——这是工业界的标准做法。
