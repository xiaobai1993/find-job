## 三、支付核心流程

### 3.1 创建支付单流程

```
1. 参数校验
   ├─ 校验商户信息
   ├─ 校验业务单号幂等性
   └─ 校验支付金额

2. 构建支付单
   ├─ 生成唯一支付单ID (Snowflake)
   ├─ 计算支付截止时间
   ├─ 初始化支付单状态为 PendingProcessing
   └─ 关联业务信息 (门店、餐别等)

3. 构建子支付单
   ├─ 计算各账户支付金额
   │   ├─ 补贴账户 (按优先级/百分比)
   │   ├─ 企业余额账户
   │   ├─ 个人余额账户
   │   └─ 餐点账户
   └─ 为每个账户创建子支付单

4. 持久化存储
   └─ 事务写入支付单和子支付单

5. 发送异步任务
   ├─ 支付超时检查任务 (延迟消息)
   └─ 异步支付处理任务
```

### 3.2 自动支付流程 (AutoPay)

**触发时机：**
- 创建支付单后立即触发
- 异步任务队列消费时执行

**流程：**
```
1. 获取可支付账户列表
   └─ BatchGetPayableAccounts (并行查询各渠道余额)

2. 账户余额校验
   └─ 总余额 >= 待支付金额 ? 继续 : 进入待手动支付

3. 批量并行支付
   └─ BatchPay (并发调用各支付渠道)

4. 处理支付结果
   ├─ 全部成功 → 更新支付单状态为 Succeeded
   ├─ 部分成功 → 更新为 PartialSucceeded
   └─ 全部失败 → 更新为 PendingManualPay

5. 发送支付完成通知
   └─ 异步通知业务方支付结果
```

### 3.3 手动支付流程 (ManualPay)

**触发时机：**
- 用户在收银台选择微信/支付宝等第三方支付方式

**流程：**
```
1. 获取支付参数
   ├─ 微信: GetWechatPaymentParams
   ├─ 支付宝: GetAlipayPaymentParam
   ├─ 钱包直连: WalletPay
   └─ POS付款码: Micropay (微信/支付宝扫码枪)

2. 返回支付参数给前端
   └─ JSAPI参数 / H5链接 / 小程序参数

3. 前端调用第三方SDK完成支付
   └─ 第三方异步回调支付结果

4. 回调处理
   ├─ 验签
   ├─ 更新子支付单状态
   ├─ 汇总更新主支付单状态
   └─ 发送业务通知
```

### 3.4 后付支付流程 (PayAfter)

**特点：** 用户先消费，后续统一结算

**流程：**
```
1. 创建后付订单
   └─ CreatePayAfterOrder (创建微信支付分等订单)

2. 授权完成
   └─ 用户授权后冻结额度

3. 完成支付
   └─ 后续消费完成后统一扣款结算
```

## 四、退款核心流程

### 4.1 全额退款 vs 部分退款对比

| 维度 | 全额退款 | 部分退款 |
|------|---------|---------|
| 金额来源 | 系统自动计算已支付金额 | 调用方传入退款金额 |
| 处理Pending单 | ✅ 取消所有待处理支付单 | ❌ 不处理 |
| 后付单处理 | ✅ 取消后付订单 | ❌ 不处理 |
| 子单构建策略 | 简单全额分配 | 按优先级/百分比分配 |
| 菜品校验 | 不需要 | 外卖业务必须传菜品 |
| 可重复退款 | ❌ 退款后关闭订单 | ✅ 可多次退款直到金额为0 |
| 退款后状态 | FullRefundClosed | 保持Succeeded |

### 4.2 全额退款详细流程

```
1. 校验参数
   ├─ 检查是否已全额退款
   └─ 计算可退款金额 = 支付成功金额 - 已退款金额

2. 处理Pending状态支付单
   ├─ 加锁防止并发
   ├─ 二次刷新状态
   ├─ 更新Pending主单为 FullRefundClosed
   ├─ 更新Pending子单为 Failed
   └─ 回滚已扣减的账户余额

3. 处理后付订单
   └─ 取消后付授权订单

4. 构建退款单
   ├─ 创建退款单 (FullRefund = true)
   └─ 为每个已成功子支付单创建对应退款子单

5. 发起异步退款
   ├─ 补贴/余额账户: 同步退款
   └─ 微信/支付宝等第三方: 异步退款 + 回调通知

6. 退款完成处理
   ├─ 所有子单成功 → 退款单状态 Succeeded
   └─ 发送退款成功通知给业务方
```

### 4.3 部分退款详细流程

```
1. 校验参数
   ├─ 校验可退款金额充足
   └─ 外卖业务必须传菜品信息

2. 菜品校验 (仅外卖)
   ├─ 查询已支付菜品
   ├─ 减去已退款菜品
   └─ 校验本次退款菜品数量 <= 可退数量

3. 构建退款单
   ├─ 创建退款单 (FullRefund = false)
   └─ 按账户优先级分配退款金额

4. 退款金额分配策略
   ├─ 按支付快照中的账户优先级排序
   ├─ 高优先级账户先退款
   └─ 百分比账户按比例退款

5. 发起退款 (同全额退款)
```

### 4.4 菜品校验机制

**设计目的：**
- 防止超退：退款菜品数量不能超过实际购买数量
- 精确核算：按菜品维度核算补贴成本
- 渠道对接：钱包渠道退款需要菜品明细

**校验逻辑：**
```
可退菜品数量 = 支付时菜品数量 - 已退款菜品数量 - 改单取消菜品数量

本次退款菜品数量 <= 可退菜品数量 ? 通过 : 失败
```

**注意：** 当前该校验仅打印警告日志，未真正阻断退款流程。

## 五、改单流程 (ChangeSlip)

### 5.1 改单业务场景

用户下单后需要修改订单内容（加菜、减菜），涉及金额变动需要补款或退款。

### 5.2 改单流程

```
1. 计算金额差
   ├─ 新订单金额 > 原订单 → 需要补款
   └─ 新订单金额 < 原订单 → 需要退款

2. 补款流程
   └─ 创建新的支付单，走正常支付流程

3. 退款流程
   └─ 调用部分退款接口，退还差额

4. 记录改单流水
   └─ 保存改单前后的菜品、金额信息
```

## 九、关键技术点

**使用场景：**
- 支付单并发处理保护
- 退款操作互斥
- 改单操作原子性

**多层幂等校验：**
1. 业务单号唯一索引
2. 支付单状态前置校验
3. 数据库乐观锁更新

### 9.3 并发控制

- 批量支付使用 goroutine 并发调用
- safego 包保护 goroutine 不崩溃
- channel 收集并发结果

### 9.4 缓存策略

- 支付单信息缓存
- 用户错误消息缓存

## 十二、关键设计决策

### 12.1 主子单设计

**Q：为什么一个支付单需要多个子支付单？**

**A：**
- 一笔订单可能使用多种支付方式 (企业补贴+个人余额+微信)
- 不同支付渠道有不同的异步回调机制
- 部分成功、部分失败的精细化状态管理
- 按账户维度对账和退款

### 12.2 全额退款处理Pending单

**Q：为什么全额退款要特殊处理Pending状态的支付单？**

**A：**
- 用户可能发起多次支付尝试，产生多个支付单
- 全额退款意味着整个订单取消，需要关闭所有待处理的支付尝试
- 防止用户在退款过程中其他支付单支付成功

### 12.3 菜品维度退款

**Q：为什么退款需要按菜品维度校验？**

**A：**
- 外卖/团餐业务按菜品计算补贴
- 部分退款通常是退某几道菜
- 财务需要按菜品维度核算成本
- 第三方钱包渠道退款需要菜品明细
