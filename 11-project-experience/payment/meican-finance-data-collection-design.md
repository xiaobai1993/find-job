## 📋 项目背景与核心问题

### 面试官问：简单介绍一下财务系统是做什么的？为什么需要做数据采集？

> **标准答案：**
>
> "美餐财务系统的核心是解决「收付款结算」问题。
>
> **举个例子：**
> 一笔6月29日的外卖订单，用户支付了44元（餐补40 + 微信4），包含两个商家的菜品。后续7月2日营运人员做了事故退菜，退了8元。
>
> **结算的时候要解决三个核心问题：**
> 1. **美餐向商户付多少钱？** 宏状元17元、童话夏尔19元（6月），然后宏状元-8元（7月）
> 2. **美餐向客户收多少钱？** 企业客户A 40元（6月），然后-4元（7月）
> 3. **按哪个时间结算？** 是按订单时间（6月29日）还是交易时间（7月2日）
>
> **结算的基础是「以交易为粒度采集商品和交易明细**。每一笔支付、每一笔退款都要完整记录，这样财务才能对账、做账、报税。
>
> 这个项目我是核心设计者和主要开发者，从0到1设计并完成了整个数据采集系统的设计与实现。"

## 🔴 数据采集的五大核心挑战

### 面试官问：做财务数据采集遇到了哪些技术挑战？

> **标准答案：**
>
> "我们遇到了5大核心挑战，每一个都很棘手：

---

### **挑战一：数据采集是「推」还是「拉」？

**问题：**
- 新支付（收银台）是"推"模式：支付系统会推送支付领域事件，有完整的事件结构
- 老外卖、老到店、食堂没有事件缺失：上游系统太老了，改造风险大，而且能不改就不改

**为什么不推的三个核心原因：**
1. **尽量不影响上游系统——像play这种核心交易系统，能不改就不改
2. **数据维度不匹配——财务既需要订单明细又需要支付明细，单一上游提供不了
3. **粒度不匹配**——财务需要以「交易」为粒度，但上游订单系统是以「订单」为粒度
   - 一个订单可能对应多笔交易（支付+多次退款）

**最终方案：推 + 拉结合，能推的推，不能推的就拉。**

---

### **挑战二：多业务线 + 多支付版本 = 大量异构数据

**异构矩阵：**

| | 老支付(libra) | 新支付v1 | 新支付v2(收银台) |
|---|---|---|---|
| 老外卖(play) | ✅ | ✅ | ✅ |
| 新外卖(order20) | | | ✅ |
| 老到店 | ✅ | ✅ | |
| 新到店 | ✅ | | ✅ |
| 食堂 | ✅ | ✅ | ✅ |

**问题：** 不同的订单系统、不同的支付版本，都是独立的系统，都有自己的库表设计！
光需要拉取数据的表就有20多张！

老外卖要拉的表：
`fan.corporderuser`、`fan.corporderitem`、`fan.accidentrefunddish`、`fan.dishrevision`、`libra.main_transaction`、`libra.subsidy_transaction`、`fan.usertransaction`...

食堂要拉的表：
`order_system.user_order`、`order_system.user_transaction`、`order_system.restaurant_order`、`order_system.order_product`...

**这还只是老支付！还有新支付v1的表！**

---

### **挑战三：采集后订单发生变更如何感知？

**问题：** 订单不是一次性的，采集完还会变！
- 外卖预点单：用餐时间之前可以取消
- 用餐时间之后：营运人员可能操作事故退菜、加减菜、补单
- 老到店：下单支付完成后可以全额退款
- 食堂：可以按金额退款、按菜品退款

**最极端的场景：**
6月29日对一笔1月15日的订单做了部分退款，财务系统怎么能知道呢？

**模式：**
- 一次支付 + 多次支付/退款
- 一次支付 + 一次退款
- 一次支付 + 多次退款

---

### **挑战四：上游系统设计有缺陷或者有bug如何处理？

**这是最头疼的问题，我们遇到的真实bug：
1. 订单金额与交易金额不一致
2. 订单金额与菜品总价不一致
3. 外卖手工记账订单没有交易数据
4. 外卖订单事故退菜金额超出原订单金额
5. 老支付存在非原路退款：支付用餐补A，退款退给了餐补B
6. play存在非原路退款：专项账户支付退款给了美餐通用余额
7. 食堂订单未退款，但对应老支付已经全额退款

**灵魂拷问：上游的bug，财务系统怎么办？**

---

### **挑战五：数据量越来越大，如何保证性能？

每天几十万笔订单，每笔订单要查十几个表，还要做数据转换、校验、保存。
**既要保证不影响上游系统（查从库！），还要保证当天的数据当天出。"

## 🟠 核心架构设计

### 面试官问：整个数据采集系统是怎么设计的？

> **标准答案：**
>
> "我们的设计思路是「分层解耦、统一模型、流水线处理」。

---

### **设计一：以订单为「抓手」的统一采集模型

**核心思想：所有业务线均以订单作为入口，先查订单，再「顺藤摸瓜」查菜品和交易数据。

**老外卖 + 老支付链路：

```
fan.corporderuser
     ↓
fan.corporderitem → libra.main_transaction
     ↓                    ↓
fan.accidentrefunddish  libra.subsidy_transaction
                          ↓
                    fan.user_transaction
                          ↓
        fan.special_account_user_transaction
        fan.special_account_user_refund_transaction
```

**食堂 + 老支付链路：**

```
order_system.user_order
     ↓
order_system.user_transaction → libra.main_transaction
     ↓                                ↓
order_system.restaurant_order    libra.subsidy_transaction
     ↓
order_system.order_product
```

**为什么这么设计？**
- 所有业务线都有target_time字段：外卖是用餐时间，到店/食堂是下单时间
- 每天凌晨采集target_time是前一天的所有订单
- **对外卖特别友好：6月26日预点6月29日的订单，6月30日采集，如果6月28日取消了，6月30日就不用采了

---

### **设计二：生产者 + 消费者模式

```
     订单系统从库
          ↓
     Producer（批量扫描前一天订单id）
          ↓
        Pulsar MQ
          ↓
     多个 Consumer（并发采集）
          ↓
     支付系统从库
          ↓
     财务系统库
```

**为什么用MQ？
1. **削峰填谷：几十万订单不会一下子压过来，上游从库也扛不住
2. **容错：某个订单采集失败了，不影响其他订单，还可以重试
3. **并发：多个consumer水平扩展，提高采集速度

---

### **设计三：全量快照 + 增量交易双层存储

**第一层：订单快照（全量）

每次采集到的订单数据「全量」存储为一个订单快照：
- `order_snapshot` 订单快照表
- `order_snapshot_product_detail` 订单快照商品详情表

| 采集时间6月29日 | 采集时间7月2日 |
|---|---|
| 芝麻酱糖饼 1份 17元 | 芝麻酱糖饼 1份 17元 |
| 三丝大春卷 1份 8元 | （三丝大春卷没了） |

**为什么存全量快照？**
方便对比！两次快照一对比，就知道哪个菜品没变，哪个变了！

---

**第二层：交易（增量）

每次采集到的交易数据「增量」存储为一笔交易：
- `transaction` 交易表
- `transaction_product_detail` 交易商品详情表
- `transaction_account_detail` 交易账户详情表

**核心实现：
通过比较当前订单快照与上一次快照的差异获取交易商品详情！

```
快照1（6月29日）：总计44元（餐补40 + 微信4）
快照2（7月2日）：总计36元（餐补36 + 微信4）
     ↓ 对比差异
生成一笔交易：餐补 -4元
```

**这个设计太妙了！**
不用关心中间发生了什么，只要对比两次快照，差异就是交易！
上游怎么变的不重要，结果才重要！

---

### **设计四：基于Go Channel的流水线处理

```
    待采集订单ids
        ↓ （generate）
    订单id（检查是否已采集，未采集放入流水线
        ↓ （extract）
    原始订单和交易数据 + 数据校验
        ↓ （transform）
    财务系统数据或异常数据
        ↓ （save）
    保存到数据库
```

**四个步骤：**
1. **generate**：检查订单id是否已采集，未采集则放入流水线
2. **extract**：从上游系统从库查询原始订单和交易数据并校验
3. **transform**：将原始数据转化为财务中间层数据
4. **save**：将财务中间层数据保存到数据库

**重要原则：整个流水线只有发生数据库或网络异常时才会中断，数据异常只记录，不报错！

**为什么这个原则很重要？**
不能因为一笔订单数据有问题，整个采集任务就挂了！
财务数据容不得半点马虎，但是也不能因为个别数据有问题，影响整体。

## 🟡 订单变更感知设计

### 面试官问：采集完的订单又变了怎么办？半年前的订单退款了怎么发现？

> **标准答案：**
>
> "我们做了两套机制，双保险！

---

### **方案一：外卖 + 到店基于DMS的变更监控

```
    订单系统库
        ↓
       DMS（数据库变更数据变更数据
        ↓
      Kafka
        ↓
   Consumer
        ↓
   财务系统库 → 订单变更表
```

**流程：**
1. 将订单相关表的改动通过DMS获取后发送到Kafka
2. 财务系统接收到Kafka消息后将变化的订单id记录到订单变更表中
3. 每天凌晨对前一天检测到变更的订单进行追加采集

**DMS的问题：** 不太稳定，能不用尽量不用

---

### **方案二：食堂基于自身交易表的反向感知

**核心洞察：** 食堂订单采集后的变动一定是退款！
有退款，`user_transaction`表就会插入数据！

**流程：**
1. 每天凌晨在开启订单采集之前
2. 查询user_transaction表中前一天创建的所有退款交易
3. 如果退款交易对应的订单财务系统已经采集过
4. → 说明该笔订单发生了变动，需要重新采集！

**效果：** 不用DMS，不用依赖上游，自己就能发现变更！

## 🟢 异常数据处理哲学

### 面试官问：上游系统有bug怎么办？让他们不修bug怎么办？

> **标准答案：**
>
> "这是财务系统最考验智慧的地方。我们的处理哲学是：**能让上游修的就让上游修，修不了或者不好修的，财务系统做兼容！

**处理流程：**

```
发现异常数据
    ↓
上游系统排查异常原因
    ↓
有bug吗？ ──否──→ 财务系统做兼容
    ↓是
好修吗？ ──否──→ 财务系统做兼容
    ↓是
上游系统修复bug
```

**我们的五大兼容策略：**

| 异常场景 | 兼容方案 |
|---|---|
| 手工记账无交易数据 | 通过订单构造交易 |
| 订单金额与交易金额不一致 | 以订单金额为准 |
| 订单金额与菜品总价不一致 | 以菜品总价为准 |
| 支付存在非原路退款 | 记录退款时调整为原支付渠道 |
| 订单未退款但支付全额退款 | 仅采集支付交易 |

**这就是财务系统的「担当」：
上游的锅，财务来背。
但是！

## 🔵 数据自检体系

### 面试官问：怎么保证采集到的数据是对的？

> **标准答案：**
>
> "我们做了三层自检策略，数据对不对自己说了算！

**三种自检模式：
1. **LastNDay**：检查过去N天的数据，比如定期检查过去10天
2. **CurrentMonth**：检查当月所有数据
3. **Increment**：增量检查，只检查前一天新采集的数据

**四项核心校验维度：**
1. 订单当前的金额与财务系统最新的订单快照金额一致
2. 订单当前的金额与中间层历史交易的总金额一致
3. 订单当前的菜品与中间层最新的订单快照菜品一致
4. 订单当前的菜品与中间层历史交易商品的聚合结果一致

**这四个校验维度，就是财务数据的四道护城河

## 🎯 面试总结：财务系统设计的哲学思考

### 面试官问：做这个项目最大的收获是什么？

> **答：**
>
> "我总结了三条：
>
> **第一：财务系统的本质是「翻译官」
> 把上游乱七八糟的业务数据，翻译成财务能懂的会计语言。
> 这个翻译过程，既要准确、要一致、要可追溯。
>
> **第二：对上游系统不完美，甚至有bug很正常
> 做下游系统，不能要求上游改，上游说「这个bug影响太大了」。
> 好的下游系统，能在不完美的世界里，把事情做成。
>
> **第三：数据一致性不是100%
> 财务数据不是追求100%准确，但是要100%可追溯。
> 哪笔钱去哪了，清清楚楚，明明白白，这才是财务系统的终极目标。
>
> 这个项目上线后，财务结账效率提升了300%，以前要花3天变成1天，
> 而且数据准确率从80%多到99.9%，
> 财务同事再也不用熬夜加班核对Excel对账了。"
