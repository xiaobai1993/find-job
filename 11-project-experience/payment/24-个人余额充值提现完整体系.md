## 二、线上充值流程（非现金）

### 2.1 首次创建充值单

```go
// OnlineRecharge.Recharge()
流程：
1. 调用 PB.ListRechargeMethods() 获取可用支付方式
   - 校验金额在上下限内
   - 校验币种匹配
   - 校验活动规则一致

2. 生成充值单ID，状态 = Pay
3. 创建充值单入库 + 事务内发送5分钟超时检查任务
4. 幂等处理：
   - 如果唯一索引冲突，查询已存在的单
   - 已成功 → 返回 RECHARGE_SLIP_SUCCEEDED
   - 已超时关闭 → 返回 RECHARGE_SLIP_TIMEOUT_CLOSED

5. 根据支付方式类型调用TPW获取支付参数：
   - 微信 → GetWechatPaymentParams()
   - 支付宝 → GetAlipayPaymentParams()
   - 钱包 → WalletPay() 或 GetWalletH5PaymentParam()
   - 农行 → GetABCPaymentParams()
   - 通联微信 → GetAllinpayWechatPaymentParam()
   - 通联支付宝 → GetAllinpayAlipayPaymentParam()

6. 返回充值单ID + 支付参数字节数组
```

### 2.2 更换支付方式

```go
// OnlineRecharge.ChangePayMethod()
流程：
1. 查询充值单
2. 状态校验：
   - 已成功 → 返回 RECHARGE_SLIP_SUCCEEDED
   - 已超时关闭 → 返回 RECHARGE_SLIP_TIMEOUT_CLOSED
3. 调用 PB.ListRechargeMethods() 校验新支付方式可用
4. 重新调用TPW获取新支付方式的参数
5. 返回同一个充值单ID + 新支付参数
```

**设计亮点**：不创建新单，复用原有RechargeSlipId，用户体验更好，同时保证订单唯一性。

### 2.3 TPW回调处理

```go
// OnlineRecharge.HandleRechargeCallback()
流程：
1. 加分布式锁：LockRechargeSlip(TransactionId)
2. 查询充值单：
   - POS场景：自旋最多6次，每次500ms等单创建完
   - 其他场景：直接查询，不存在就走异常流程
3. 状态机处理：
   - 状态=Pay：
     - TPW回调失败 → 状态=PayFailed，完成
     - TPW回调成功 → 状态=Recharge，记录TpwAccountId/TpwPayScene/TpwExternalTradeNo/AccountType/AccountSubType
   - 状态=Recharge 且 OutTransactionId相同 → 重复回调，直接返回
   - 其他状态 → 抛错，走异常处理
4. 调用 PB.Recharge() 增加个人余额
5. 状态=Success，记录ActivityAmount
6. 发送充值成功事件
7. 异常分支：回调无效但微信显示支付成功 → 发送TPW退款回滚任务
```

### 2.4 超时关闭

```go
// OnlineRecharge.RechargeTimeoutCheck()
流程：
1. 加锁查单
2. 如果已完成 或 已在Recharge状态 → 直接返回
3. 状态设为 TimeoutClosed，设置CompletedAt
```

## 三、线下充值流程（现金/对公转账）

### 3.1 发起充值

```go
// OfflineRecharge.Recharge()
流程：
1. 生成充值单ID，状态 = Recharge（跳过Pay状态，不用用户付钱）
2. DB建单 + 事务内发送 RechargeTask 异步消息
3. 返回充值单ID
```

### 3.2 异步处理充值

```go
// OfflineRecharge.DoRecharge()
流程：
1. 查询充值单
2. 幂等检查：已完成 或 不是现金充值 → 直接返回
3. 调用 PB.Recharge() 加个人余额
   - PaymentMethodType = CASH（现金）
   - RechargeScene = CASH
4. 状态 = Success，设置CompletedAt
5. 发送充值成功事件
```

**特点**：不用用户支付，后台审核通过后直接加余额。适用于线下现金、对公转账、活动赠送等场景。

## 四、余额退款（提现）流程

### 4.1 核心数据结构

```
BalanceRefundSlip（退款单/父单）
  ├── Id: 退款单ID
  ├── UserId: 用户ID
  ├── PersonalBalanceId: 余额账户ID
  ├── Amount: 总退款金额
  ├── RefundedAmount: 已退款金额
  ├── Status: Processing/Success/Failed
  ├── IsCash: 是否现金退款
  ├── Type: 普通/超期线下/其他
  ├── CompletedAt: 完成时间
  └── SubSlips: []BalanceRefundSubSlip （一对多子单）
       ├── Id: 子单ID
       ├── SlipId: 父单ID
       ├── RechargeSlipId: 关联的充值单ID
       ├── PersonalBalanceTxId: 关联的PB余额交易ID
       ├── Amount: 子单退款金额
       ├── Status: Pending/Succeeded/Failed
       ├── TpwAccountId/TpwPayScene/AccountType/...
       ├── TpwExternalTradeNo: 微信/支付宝退款流水号
       └── CompletedAt: 子单完成时间
```

### 4.2 线上退款（原路退回微信/支付宝）

```go
// OnlineRecharge.BalanceRefund()
流程：
1. 调用 PB.CanWithdraw() 校验是否可提现
   - 余额足够？
   - 账户状态正常？
2. 状态 = Processing
3. DB建退款单 + 事务内发送 BalanceRefundTask
4. 返回退款单ID
```

```go
// OnlineRecharge.DoBalanceRefund()
异步处理流程：
1. 查询退款单（带子单）
2. 已完成 → 直接返回
3. 无子单（首次处理）：
   - 调用 PB.Withdraw() 扣个人余额
     - PB按充值时间倒序返回多条退款明细（先充后退）
   - 批量创建子单，状态=Pending
4. 遍历所有子单，逐个调用 TPW.Refund() 发起微信/支付宝退款：
   - 成功 → 继续下一个
   - 失败（不可重试）→ 发告警，等TPW最终通知
5. 异步等待TPW退款回调
```

### 4.3 线下退款（直接打款）

```go
// OfflineRecharge.BalanceRefund()
流程：
1. 调用 PB.CanWithdraw() 校验
2. 状态 = Processing
3. DB建退款单 + 事务内发送 BalanceRefundTask
4. 返回退款单ID
```

```go
// OfflineRecharge.DoBalanceRefund()
异步处理流程：
1. 查询退款单（带子单）
2. 已完成 → 直接返回
3. 无子单（首次处理）：
   - 调用 PB.Withdraw() 扣余额，拿回退款明细
   - 创建子单，isSucceed = true（直接成功，不用走TPW）
4. 累加 RefundedAmount
5. 状态 = Success，完成
6. 发送退款完成事件
```

### 4.4 超期线下退款（超过微信/支付宝退款期限）

```go
// OnlineRecharge.DoBalanceRefund()
特殊分支：
if Type == ExpiredRefund {
   1. 调用 PB.WithdrawExpiredRefund() 扣余额
   2. 创建子单时 isSucceed = true
   3. 累加 RefundedAmount
   4. 状态 = Success，完成
}
```

**业务背景**：微信/支付宝的支付订单超过1年（或其他期限）就不能发起退款了，这种情况走线下打款处理。

### 4.5 TPW退款回调处理

```go
// OnlineRecharge.HandleBalanceRefundCallback()
流程：
1. 用 TransactionId（子单ID）查子单
2. 加父单级别的自旋锁：LockBalanceRefundSlip(SlipId)
   - 关键：用父单ID锁，不是子单ID锁，防止多个子单并发修改父单
3. 重新查父单（带子单列表）
4. 找到对应子单，若已完成 → 直接返回（幂等）
5. TPW回调失败：
   - 子单状态 = Failed
   - 发送失败通知给PB
6. TPW回调成功：
   - 子单状态 = Succeeded
   - 记录TpwExternalTradeNo（微信退款流水号）
   - 原子累加父单 RefundedAmount
   - 发送成功通知给PB
7. 检查所有子单是否都完成：
   - 是 → 父单状态 = Success 或 Failed（看是否有成功退款）
   - 发送最终完成事件
```

**锁设计亮点**：用父单ID锁，不用子单ID锁，因为多个子单同时回调会并发修改父单的RefundedAmount，父单锁保证串行化。

## 五、RechargeCore 公共能力抽离

```go
type RechargeCore struct {
    PersonalBalanceEvent  event.PersonalBalanceEvent
    PersonalBalance       rpcclient.IPersonalBalance
    BalanceRefundSlipRepo repo.BalanceRefundSlipRepo
    Lock                  lock.Locker
    RechargeRepo          repo.RechargeRepo
    MQProducer            mq.Producer
    IDGenerator           snowflakeid.IDGenerator
}

公共方法：
├── GetRechargeByID()
├── ShowBalanceRefundInfo()
├── finishBalanceRefundSlip()        // 完成父单
├── finishFailedSubSlip()            // 完成失败子单
├── finishSucceededSubSlip()         // 完成成功子单
├── createBalanceRefundSubSlips()    // 创建子单（从PB退款明细）
└── transformPersonalBalanceCode()   // PB错误码转Payment错误码
```

**设计模式**：组合复用（Composition Reuse），线上线下充值都内嵌`*RechargeCore`，共享公共逻辑。

## 七、幂等性保障汇总

| 操作 | 幂等保障方式 | 级别 |
|-----|-----------|------|
| 创建充值单 | DB唯一索引 + 冲突后查库返回 | 强一致 |
| TPW支付回调 | 状态判断 + 分布式锁 | 强一致 |
| TPW退款回调 | 子单状态判断 + 父单级锁 | 强一致 |
| 异步充值任务 | 先查状态，已完成直接返回 | 最终一致 |
| 异步退款任务 | 先查状态，已完成直接返回 | 最终一致 |
| 超时检查 | 先查状态，终态直接返回 | 最终一致 |
| 换支付方式 | 同一个充值单ID，不创建新单 | 强一致 |

## 八、异常处理矩阵

| 异常场景 | 处理方式 | 用户体验 |
|---------|---------|---------|
| TPW获取支付参数失败 | 直接返回错误，充值单留在Pay状态等超时 | 显示"支付方式暂时不可用" |
| TPW回调验签失败 | 直接返回非200，让微信重试 | 用户无感知 |
| 回调比创建单快(POS) | 自旋6次等单创建完，还没就退款 | 收银员稍等几秒即可 |
| 多支付了（单不存在但微信显示成功） | 自动发送TPW退款回滚任务 | 自动退款到用户账户 |
| TPW退款调用失败 | 发告警，等待TPW最终状态通知 | 显示"退款处理中"，人工兜底 |
| PB加余额失败 | 回调返回非200，TPW重试，直到PB成功 | 用户无感知，最终到账 |
| PB扣余额失败 | 异步消息重试，直到成功或人工介入 | 显示"提现处理中" |

## 九、关键设计亮点总结

### 1. 统一入口 + 策略分支
```go
CreateRecharge()
    └── IsCash ?
        ├── true  → OfflineRecharge.Recharge()
        └── false → OnlineRecharge.Recharge()
                      └── 单已存在 ? → ChangePayMethod()
```

### 2. 组合复用公共能力
线上线下都内嵌`*RechargeCore`，避免代码重复。

### 3. 父子单退款模型
- 一个提现请求拆成多个子单（对应多笔充值记录）
- 每个子单独立走TPW退款
- 父单汇总状态和金额

### 4. 分级锁设计
- Payment充值单：`recharge_slip_{id}` 锁
- TPW交易：`transaction_key_{id}` 锁
- 退款父单：`balance_refund_slip_{id}` 锁

不同粒度的锁保证不同场景的并发安全。

### 5. 全链路异步驱动
- 超时检查 → 延迟消息
- 线下充值 → 异步任务
- 提现处理 → 异步任务
- 回调通知 → MQ消息
- 事件通知 → MQ消息

### 6. 倒序退款策略
PB按充值时间倒序返回退款明细（先充后退），符合业务逻辑：先充的钱在账户里待的时间最长，优先退这部分。
