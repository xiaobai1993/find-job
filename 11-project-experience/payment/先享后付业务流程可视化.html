PAYMENT SYSTEM · TECHNICAL OVERVIEW

先享后付 业务流程

基于微信支付分（信用付）的先享后付完整业务流程 · 数据状态 · 服务接口

场景：美餐智能零食柜 — 张三扫码开门 → 拿零食 → 关门 → 自动扣款
01 · 核心数据模型
💡
关键理解：整个流程分为两个独立域。签约域（pay_after 系列）负责「授权阶段」，扫码时就创建，此时不知道金额；支付域（payment 系列）负责「结算阶段」，关门确认商品后才创建。两域通过 pay_after_slip.payment_slip_id 关联。
签约域 · 主单

pay_after_slip

后付主单。描述「这个用户为这个订单开通了先享后付」这件事。扫码时创建，与业务订单号一一对应。

  • out_order_no业务方订单号
  • user_id / mch_id用户 / 商户
  • risk_fund_amount风险保障金（授权上限）
  • deadline签约后超时时间（+7天）
  • payment_slip_id关联支付单（关门后填入）
  • status0~7 见状态说明
签约域 · 子单

pay_after_sub_slip

后付执行子单。描述「用哪个具体支付账户（微信支付分）来执行签约和扣款」。支持多渠道扩展。

  • slip_id关联 pay_after_slip.id
  • account_type / sub_type支付渠道（微信/支付宝）
  • tpw_pay_scene扣款场景
  • tpw_external_trade_no微信侧交易号（签约后写入）
  • status0~4 见状态说明
支付域 · 主单

payment_slip

支付主单。描述「这笔消费要收多少钱，收了多少了」。关门确认金额后才创建，与后付主单通过外部订单号关联。

  • out_order_no同后付单的订单号
  • amount应收总金额（分）
  • paid_amount已收金额（累加）
  • option_bits标志位（含先享后付标记）
  • statusSuccess / FullPayFailed 等
支付域 · 子单

payment_sub_slip

支付执行子单。每一次实际扣款动作对应一条记录。自动扣款一条，手动补付时再追加一条。

  • slip_id关联 payment_slip.id
  • amount本次扣款金额
  • effective_amount实际到账（成功后填入）
  • option=IsPayAfter标记为先享后付扣款
  • tpw_external_trade_no微信流水号（成功后填入）
  • statusPending → Succeeded / Failed
TABLE RELATIONSHIPS
pay_after_slip (1) ──────── (N) pay_after_sub_slip [slip_id 关联]
pay_after_slip (1) ──────── (1) payment_slip [payment_slip_id 关联，关门后建立]
payment_slip (1) ──────── (N) payment_sub_slip [slip_id 关联，每次扣款一条]

04 · 服务接口速查
CreatePayAfterSlip()
创建后付主单和子单，返回 payAfterSlipId
调用时机：扫码开门时，业务系统主动调用
触发结果：创建 pay_after_slip(UnSign) + sub_slip(UnSign)
PayAfterSign()
向微信支付分申请签约链接，让前端跳转用户授权
调用时机：CreatePayAfterSlip 后立即调用
触发结果：返回微信签约 URL / 小程序跳转参数
QueryPayAfterSlip()
查询后付单当前状态，供前端轮询判断签约结果
调用时机：前端等待签约结果时轮询
触发结果：返回 pay_after_slip 状态信息
CompletePayAfterSlip()
完结后付单 —— 真正创建 payment_slip，发起自动扣款
调用时机：设备识别用户拿走商品后（关门）
触发结果：建 payment_slip + sub_slip，后付单→Completing，MQ 通知微信扣款
Consumer.PayAfterCallback()
MQ 消费者，处理微信支付分签约成功回调
触发来源：微信签约回调 → TPW → MQ
触发结果：后付单→Signed，设置7天超时，通知业务方开门
Consumer.TpwPaymentCallback()
MQ 消费者，处理微信扣款结果（成功/失败）
触发来源：微信扣款回调 → TPW → MQ
触发结果：成功→所有单据终态 Payed/Success；失败→触发手动支付报警
CreateManualPay()
自动扣款失败后，唤起用户手动收银台支付
调用时机：TpwPaymentCallback 收到扣款失败通知后
触发结果：追加一条 payment_sub_slip，弹出微信收银台
PayAfterTimeoutCompleteTask()
MQ 延迟消费者，处理签约后7天未完结的超时关闭
触发来源：签约时投递的延迟MQ，7天后触发
触发结果：后付单→TimeoutClosed，子单→Canceled，通知微信撤销授权
CancelPayAfterSlip()
主动取消后付单（订单取消/退款场景）
调用时机：业务方取消订单，或发起退款时
触发结果：后付单→FullRefundClosed，MQ 通知微信撤销授权
05 · 异常场景处理
⏱
签约后超时未完结
触发：签约时投递的延迟 MQ 到期（7天后触发 PayAfterTimeoutCompleteTask）
  1. 检查后付单状态是否仍为 Signed（若已完结则跳过）
  2. Redis 加锁防并发
  3. pay_after_slip.status → TimeoutClosed(6)
  4. pay_after_sub_slip.status → Canceled(4)
  5. 发 MQ 通知微信支付分撤销授权
💸
自动扣款失败
触发：微信扣款后回调失败（注意：微信侧实际上会持续重试，失败回调罕见）
  1. payment_sub_slip.status → Failed
  2. 发送报警 MQ（sendPayAfterAlert）
  3. 调用 CreateManualPay() 唤起用户手动支付
  4. 用户手动支付成功后走正常回调路径
  5. payment_slip 成功后，后付单随之 → Payed
🚫
退款 / 取消订单
触发：业务方调用 CancelPayAfterSlip 或发起退款
  1. 查询处于 Signed/Completing 状态的子单
  2. pay_after_slip.status → FullRefundClosed(7)
  3. pay_after_sub_slip.status → Canceled(4)
  4. 发 MQ (PayAfterSlipCancel) 通知微信撤销授权
  5. 若支付单存在，同步处理退款流程

关键业务规则
·签约后立即设置 deadline = +7天，超时自动关闭
·payment_slip 在 CompletePayAfterSlip 时才创建，扫码时不创建
·Redis 分布式锁 + double-check 保证签约回调幂等
·超时前先查微信侧状态，已扣款则不取消（防资损）
·扣款成功时取消同单所有其他 Pending 子单（防重复扣）

微信支付分扣款行为
⚠ 关键认知
微信支付分不会主动推送扣款失败通知，失败时会在后台静默重试，handleAsyncPayCallbackFiled 几乎不会被触发。
1
微信发起扣款后，若余额不足或扣款中，状态变为 Completing
2
微信在后台周期性重试扣款（通常 3 天内），业务侧通过 queryPayAfterOrder 主动轮询结果
3
扣款最终失败才落入 handleAsyncPayCallbackFiled，触发手动支付流程

ManualAutoPay（帮点）机制
·帮点 = 用户绑定的美餐钱包余额，CanAutoPay=true
·余额充足时，系统无感知自动从钱包扣款，用户无需手动操作
·帮点失败后会重发 AutoPayTask MQ，回退到微信扣款流程
·防重复扣：成功时调用 UpdateManualPayPendingSubSlipFailed 取消其余待支付子单
QueryManualPayResult 轮询
·用户端收到推送后拉起收银台，支付完成后需查询结果
·调用 QueryManualPayResult 查询手动支付单状态
·支付成功后 pay_after_slip.status → Payed，流程结束
·长连接推送确保用户端实时感知，无需依赖端侧主动轮询
08
取消订单时机
pay_after_slip 状态 可取消? 取消行为 / 注意事项 典型触发场景
0 · New ✓ 直接关闭后付单，无需调用微信 极少见，刚创建立即取消
1 · UnSign ✓ 直接取消，用户未签约微信无预授权需撤销 用户扫码后放弃开门，或业务侧超时
2 · Signed ✓ 调用微信取消授权（签约撤销），关闭子单 签约后门没开成功，硬件故障取消
3 · Paying ✓ 先调 RollBackPendingPaymentSlip 回滚支付单，再取消 识别商品出错（0元），运营介入取消
4 · Completing △ 有条件
先查微信侧 QueryPayAfterOrder
若已扣款成功 → 禁止取消，防资损
若未扣款 → 允许取消，回滚支付单
 扣款中用户投诉，运营紧急干预
5 · Payed ✗ 已完成支付，不可取消；需走退款流程 —
6 · TimeoutClosed ✗ 已超时关闭，终态，不可操作 —
7 · FullRefundClosed ✗ 全额退款关闭，终态，不可操作 —
⚠ Completing 状态竞态保护
// CancelPayAfterSlip 内部逻辑
if slip.IsPaying() || slip.IsCompleting() {
  // 先查微信侧实际状态
  result = QueryPayAfterOrder()
  if result.IsPaid {
    return ErrAlreadyPaid
  }
  RollBackPendingPaymentSlip()
}
取消发起时微信可能已悄悄扣款成功，若不查询直接取消会造成钱扣了但订单取消的资损问题。
实际取消触发场景
用户主动 扫码后反悔，关门前手动取消订单
硬件故障 门锁异常、柜机断网，系统自动取消未完成订单
识别异常 商品识别出错（金额为 0），业务侧判断后取消
运营介入 运营后台强制取消异常订单
超时系统 7 天签约截止，PayAfterTimeoutTask 自动触发关闭
退款诉求 已支付但用户申请退款，走 CreateRefundSlip 流程
