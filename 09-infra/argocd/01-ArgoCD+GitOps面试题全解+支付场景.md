# ArgoCD + GitOps面试题全解 + 支付场景落地实践

> GitOps核心工具，云原生部署主流方案，面试常考点，结合支付系统K8s部署来讲

---

## 一、基础概念

### 1. 什么是GitOps？和传统的CI/CD有什么区别？

**答：**
GitOps是一种基于Git的运维方式，核心思想是：**Git是唯一的真值来源（Single Source of Truth）**，所有要部署到集群的配置都存在Git仓库里，所有部署变更都通过Git MR/PR来做，审批通过之后，自动同步到K8s集群里，不用人直接操作集群。

和传统CI/CD的区别：

| 对比项 | 传统CI/CD | GitOps |
|--------|----------|--------|
| 真值来源 | CI/CD系统里的配置、流水线参数 | Git仓库，所有配置都在Git里，Git是唯一来源 |
| 部署方式 | CI/CD系统拿着kubeconfig去集群里apply，推送式部署 | 集群里的Agent自动拉取Git里的配置，拉取式部署，集群不用对外暴露权限 |
| 权限模型 | CI/CD系统要有集群的写入权限，权限很大，泄露了很危险 | 只有ArgoCD Agent有集群写入权限，CI/CD只有Git的提交权限，不需要集群权限 |
| 一致性校验 | 不知道集群里实际部署的和配置是不是一致，可能有人手动改了 | 自动对比Git配置和集群实际状态，不一致就告警或者自动同步，保证一致性 |
| 回滚方式 | 重新跑一遍旧的流水线发布 | 直接Git revert一下，自动同步回去，秒级回滚，和回滚代码一样简单 |
| 可追溯性 | 变更记录在CI/CD系统里，容易丢 | 所有变更都在Git的commit历史里，天然可追溯，谁改的、改了什么、什么时候改的，一清二楚 |

**支付场景：** 我们美餐的K8s部署全部用GitOps + ArgoCD，所有部署配置都存在Git仓库里，改部署只需要提MR，审批通过合并后自动同步到集群，非常安全，不会出现有人偷偷改生产配置的情况。

### 2. 什么是ArgoCD？它的工作原理是什么？

**答：**
ArgoCD是现在最流行的GitOps工具，专门为K8s设计的，运行在K8s集群里，自动把Git仓库里的部署配置同步到集群里。

**工作原理：**
1. ArgoCD持续监控Git仓库里的部署配置（K8s YAML、Helm Chart、Kustomize这些）
2. 同时监控集群里的实际资源状态
3. 自动对比Git里的期望状态和集群里的实际状态，如果不一致，就显示OutOfSync
4. 可以设置自动同步，发现不一致就自动把集群里的资源改成Git里的配置，也可以手动点同步
5. 同步完成后会通知你成功还是失败

> 简单说：ArgoCD就是个自动同步的机器人，保证集群里部署的永远和Git里写的一模一样，有人手动改了集群里的配置，ArgoCD会自动给改回去。

---

### 3. ArgoCD的核心组件有哪些？

**答：**
ArgoCD的核心组件不多，主要有这几个：
1. **API Server**：提供REST API，给UI和CLI调用，做鉴权、用户管理
2. **Repository Server**：缓存Git仓库，拉取Git代码，渲染Helm/Kustomize配置，生成最终的K8s YAML
3. **Application Controller**：核心控制器，负责对比Git里的期望状态和集群里的实际状态，执行同步操作，管理Application的生命周期
4. **Dex Server**：集成SSO登录，对接企业的账号系统，比如LDAP、OIDC、企业微信这些
5. **Redis**：缓存，存临时数据，提升性能

---

### 4. ArgoCD的Application是什么？

**答：**
Application是ArgoCD里的核心概念，代表一个要部署的应用，每个Application对应一个Git仓库的路径，和一个集群的命名空间，告诉ArgoCD："你要把这个Git路径下的配置，部署到这个集群的这个命名空间里"。

一个Application的主要配置：
- **Source**：Git仓库地址、分支、路径，或者Helm仓库地址、Chart名、版本
- **Destination**：目标集群地址、目标命名空间
- **Sync Policy**：同步策略，要不要自动同步、要不要自动自愈、要不要自动删资源

例子：支付服务的Application配置：
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-service
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://gitlab.example.com/infra/k8s-deploy.git
    targetRevision: main
    path: prod/payment-service
  destination:
    server: https://kubernetes.default.svc
    namespace: payment
  syncPolicy:
    automated:
      prune: true      # 自动删除Git里已经去掉的资源
      selfHeal: true   # 自动自愈，有人手动改了集群配置就自动改回去
    syncOptions:
      - CreateNamespace=true
```

## 二、进阶特性

### 5. ArgoCD的同步策略有哪些？

**答：**
主要分手动同步和自动同步两种：
1. **手动同步**：默认模式，Git改了之后，需要手动点一下同步按钮，或者用CLI执行argocd sync，才会同步到集群，适合要求严格控制发布时机的场景
2. **自动同步（Automated）**：ArgoCD自动检测Git变更，发现不一致就自动同步，不需要人工操作，又分两个选项：
   - **Prune**：自动删除Git里已经不存在的资源，比如你把Deployment删了，ArgoCD会自动把集群里的Deployment也删了，默认是不开的，防止误删
   - **SelfHeal**：自动自愈，有人手动改了集群里的资源，和Git里不一致了，ArgoCD会自动改回去，恢复到Git里的状态，这个非常有用，防止有人偷偷改配置

**支付场景使用：**
- 非核心的测试环境开自动同步+自愈，代码合并了自动部署，不用人管
- 生产环境用手动同步，MR合并了之后，负责人确认了，手动点同步，更安全，不会自动乱改
- 核心支付服务开了SelfHeal，禁止手动改生产配置，改了也会被ArgoCD自动改回去，保证环境一致性。

### 6. ArgoCD怎么做多环境管理？开发、测试、生产怎么隔离？

**答：**
常用的有三种方案：
1. **单仓库多分支**：一个Git仓库，不同环境对应不同的分支，dev分支对应开发环境，main对应生产，改的时候先合dev，测试没问题再cherry-pick到main分支，适合小团队
2. **单仓库多目录**：一个Git仓库，不同环境对应不同的目录，envs/dev、envs/test、envs/prod，每个目录下是对应环境的配置，公共的基础配置抽出来用Kustomize overlay覆盖，适合中大型团队，配置更清晰
3. **多仓库**：每个环境单独的Git仓库，权限分开，生产仓库只有少数人有权限合代码，最安全，适合对安全要求非常高的场景

**我们支付团队用的是单仓库多目录 + Kustomize的方案：**
- 基础配置写在base目录里，所有环境共用
- 每个环境单独的overlay目录，比如dev、test、prod，每个目录下只写自己环境的差异配置，dev副本数2，生产副本数10个，dev用测试数据库地址，生产用生产地址，Kustomize最后把base和overlay合并成最终的配置
- 生产目录的MR必须有运维和开发负责人审批才能合并，权限控制严格
- 每个环境对应单独的ArgoCD Application，互不影响

### 7. ArgoCD和Helm、Kustomize是什么关系？支持哪些配置格式？

**答：**
ArgoCD本身不关心你用什么写K8s配置，它支持所有主流的配置格式：
1. **原生YAML**：直接写K8s YAML，最简单，适合简单的应用
2. **Kustomize**：K8s原生的配置管理工具，不用模板，用overlay覆盖差异，非常适合多环境管理，ArgoCD原生支持
3. **Helm Chart**：Helm是K8s的包管理工具，用模板渲染配置，ArgoCD原生支持，可以直接对接Helm仓库，指定Chart版本部署
4. **Jsonnet、Ksonnet**这些也支持

关系就是：ArgoCD负责拉取配置、对比状态、同步部署，Helm和Kustomize负责生成最终的YAML配置，是互补的关系，不是竞争关系。

**我们用的是Kustomize，因为不用写模板，简单直接，多环境overlay非常方便，团队学习成本低，比Helm更适合我们的场景。**

---

### 8. 什么是App of Apps模式？什么时候用？

**答：**
App of Apps是ArgoCD的一种部署模式，原理是：创建一个根Application，这个根Application负责创建其他所有的Application，相当于把所有应用的Application也用Git来管理，不用一个个手动创建。

适合的场景：
- 集群里有几十个上百个应用，一个个创建ArgoCD Application太麻烦
- 新集群搭建的时候，一键把所有应用都部署好，不用一个个装

优点：
- 所有应用的列表也存在Git里，版本管理，可追溯
- 新环境一键部署，非常方便，搭个新集群半小时就能把所有服务都部署起来
- 新增应用只要在Git里加个Application配置，ArgoCD自动就创建好了，不用手动去ArgoCD里操作

**支付场景：** 我们所有的应用都用App of Apps模式，整个集群的所有应用列表都存在Git里，搭新的预发集群，只要创建一个根Application，半小时所有服务就都部署完了，以前手动搭要几天，效率提升非常明显。

## 三、支付场景实战

### 9. 支付系统用ArgoCD部署，有哪些安全注意事项？

**答：** 支付系统对部署安全要求非常高，用ArgoCD要特别注意这几点：
1. **权限控制严格**：
   - Git仓库的生产目录权限严格控制，只有负责人有权合并MR，普通开发只能提不能合
   - ArgoCD的UI开SSO登录，对接企业账号，权限最小化，普通开发只有查看权限，没有同步和修改权限，只有负责人有操作权限
   - 生产环境的同步操作必须要有审批，不能谁都能点同步
2. **禁止手动变更**：
   - 开SelfHeal自动自愈，有人手动改了集群里的配置，ArgoCD自动改回去，从根本上杜绝手动改配置的情况
   - 生产集群的K8s API Server权限严格管控，除了ArgoCD和运维，其他人都没有写入权限，想改只能走Git MR
3. **变更可追溯**：
   - 所有部署变更都对应Git的一个commit，谁提的、谁审批的、什么时候合并的、改了什么，都一清二楚，出了问题立刻能查到
   - ArgoCD的操作日志和Git的commit对应，变更链路完整可审计
4. **发布安全**：
   - 生产环境不要开自动同步，合并代码后要手动确认才同步，防止误合并代码直接发到生产
   - 灰度发布和回滚都通过Git来做，回滚就是git revert，非常简单，出问题秒级回滚
5. **配置加密**：
   - Git里不要存明文的Secret、密码、密钥这些敏感信息，要用Sealed Secrets或者SOPS加密，加密后再提交到Git，只有集群里能解密，就算Git泄露了也拿不到明文密码

### 10. ArgoCD怎么实现灰度发布和金丝雀发布？

**答：**
ArgoCD本身只负责部署，灰度发布可以结合Argo Rollouts来做，Argo Rollouts是ArgoCD官方的渐进式发布控制器，支持金丝雀发布、蓝绿发布、灰度发布，功能非常强大。

实现流程：
1. 用Argo Rollouts的Rollout资源代替原生的Deployment
2. 配置发布策略，比如先放10%流量到新版本，跑30分钟，没问题再放30%，再50%，最后100%
3. 新版本有问题的话，自动回滚到旧版本
4. 整个发布过程都通过Git来控制，改镜像版本提交到Git，ArgoCD自动同步，Argo Rollouts自动按策略发布
5. 发布过程可以对接Prometheus监控，自动检测新版本的错误率、延迟，超过阈值自动停止发布、回滚

**支付场景使用：** 核心支付服务的大版本发布都用Argo Rollouts做金丝雀发布，先放5%流量跑半小时，监控支付成功率、延迟都没问题，再逐步放大流量，非常稳，出问题影响范围很小，只有少量用户受影响。

### 11. ArgoCD和传统的CI/CD流水线怎么配合？

**答：** 完美配合，是互补的关系，不是替代关系：
- **CI/CD负责CI部分**：代码提交后，GitLab CI跑编译、测试、构建镜像、推送到镜像仓库，然后自动更新Git部署仓库里的镜像版本号，提交一个commit
- **ArgoCD负责CD部分**：检测到Git部署仓库里的镜像版本变了，自动或者手动同步到K8s集群，部署新版本

完整流程：
```
开发提交代码 → GitLab CI跑测试、构建镜像 → 推送镜像到ECR → CI自动更新部署仓库的镜像版本 → 合并到main分支 → ArgoCD检测到变更 → 同步到K8s集群部署 → 发布完成
```
> 这么配合的好处是，CI/CD系统不需要有K8s集群的权限，只需要Git部署仓库的提交权限，权限小很多，更安全，之前CI/CD泄露了kubeconfig非常危险，现在完全不用担心了。

## 四、常见面试题

### Q1：用了ArgoCD之后，还需要Jenkins/GitLab CI吗？
**A：** 当然需要，两者是分工配合的：
- CI/CD负责代码构建、测试、打镜像这些CI的工作，ArgoCD做不了这个
- ArgoCD负责把构建好的镜像部署到集群里，做CD的工作
CI管代码到镜像，ArgoCD管镜像到集群，完美配合。

### Q2：ArgoCD的缺点是什么？有什么坑？
**A：**
1. 学习成本比传统的直接apply高一点，团队要适应GitOps的工作流，要改掉手动改配置的习惯
2. 配置太灵活，用的不好容易搞的很乱，多环境管理要提前规划好目录结构
3. 大量应用的话，同步的时候可能会有点慢，要调参数优化
4. 自动同步加Prune要非常小心，不小心删了Git里的配置，集群里的资源就被自动删了，生产环境一定要谨慎开Prune

### Q3：GitOps为什么比传统的推送式部署更安全？
**A：**
1. **权限收敛**：传统部署CI/CD要有所有集群的写入权限，非常危险，CI/CD系统被攻破了所有集群都完了；GitOps只有集群里的ArgoCD有写入权限，CI/CD只有Git权限，攻击面小很多
2. **变更必须留痕**：所有变更都必须走Git commit，不可能偷偷改集群配置，改了也会被自动改回去，所有变更都有Git历史，可审计
3. **环境一致性**：自动对比集群实际状态和Git配置，不一致立刻告警或者自愈，不会出现配置漂移，环境不会越来越乱
4. **回滚简单安全**：回滚就是Git revert，和回滚代码一样简单，所有人都会，不用改集群配置

## 面试答题技巧

ArgoCD和GitOps是现在云原生的热点，面试问的越来越多，你就重点突出：
1. **你懂GitOps的核心思想**，Git是唯一真值来源，拉取式部署，对比传统CI/CD的优势说清楚
2. **你懂ArgoCD的核心概念**，Application、同步策略、多环境管理、App of Apps这些说清楚
3. **你有实际生产经验**，支付系统怎么用ArgoCD、安全怎么控制、怎么和CI/CD配合、怎么做灰度发布，这些实际经验说出来，面试官就知道你真的在生产环境用过GitOps，不是只听过名词。
