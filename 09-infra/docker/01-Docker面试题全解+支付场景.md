# Docker面试题全解 + 支付场景落地实践

> 基础运维知识，面试高频考点，结合支付系统实际使用场景来讲

---

## 一、基础概念

### 1. Docker和虚拟机有什么区别？为什么Docker轻量？

**答：** 本质区别是虚拟化的层级不一样：
1. **虚拟机**是硬件级虚拟化，每个虚拟机有自己完整的Guest OS内核，占用资源大，启动要几分钟，镜像几个G
2. **Docker是操作系统级虚拟化**，共享宿主机的内核，没有自己的内核，也不用模拟硬件，只是进程级别的隔离，所以特别轻，启动只要几秒，镜像只有几十M

| 对比项 | Docker容器 | 虚拟机 |
|--------|-----------|--------|
| 内核 | 共享宿主机内核 | 独立Guest OS内核 |
| 体积 | 几十M~几百M | 几个G~几十G |
| 启动时间 | 秒级 | 分钟级 |
| 性能损耗 | 几乎没有，接近原生 | 损耗10%~30% |
| 隔离性 | 进程级隔离，安全性一般 | 完全隔离，安全性高 |

**支付场景使用：** 我们的支付服务都打Docker镜像部署，一个服务镜像才200多M，发布的时候秒级启动，弹性扩容非常快，大促的时候一分钟就能扩几百个实例。

---

### 2. 镜像、容器、仓库分别是什么？

**答：** 类比面向对象很好理解：
- **镜像Image**：就是类，是只读的模板，包含运行环境和代码，比如Go运行时+支付服务二进制
- **容器Container**：就是类的实例，是镜像运行起来的进程，有自己的可写层，同一个镜像可以启动无数个容器
- **仓库Registry**：就是存放镜像的地方，比如Docker Hub、私有Harbor、AWS ECR，我们用的是AWS ECR存支付服务的镜像

---

### 3. Docker的核心组件有哪些？

**答：** 三大核心组件：
1. **Namespace**：做资源隔离，让容器里的进程看不到宿主机和其他容器的资源，包括PID（进程）、NET（网络）、MNT（文件系统）、UTS（主机名）、IPC（进程间通信）、USER（用户）这6个Namespace
2. **Cgroups**：做资源限制，限制一个容器最多能用多少CPU、内存、IO，防止某个容器把宿主机资源占满了
3. **UnionFS**：联合文件系统，把多层文件系统合并成一层，镜像分层就是靠这个，相同的层可以复用，不用重复存

> 重点：Docker = Namespace + Cgroups + UnionFS，这三个是Docker的底层基石，面试问到原理就说这三个。

---

### 4. 镜像分层是什么？为什么要分层？

**答：** 镜像是一层层堆叠起来的，每一层都是只读的，只有最上面的容器层是可写的：
- 比如基础层是alpine，然后加Go运行时层，然后加依赖层，最后加代码层
- 好处1：**复用层**，多个镜像可以共享相同的基础层，节省存储空间，拉镜像的时候已经有的层不用再拉
- 好处2：**构建快**，改了代码只有最上层变，其他层都不用重新构建，构建速度快很多
- 好处3：**一致性**，开发测试生产用的是同一个镜像，不会出现"我本地能跑"的问题

**支付场景最佳实践：** 我们的支付服务镜像用多阶段构建，构建阶段用golang镜像编译二进制，运行阶段用alpine镜像，最终镜像只有200M，比直接用golang镜像小了1个G，拉取和启动都快很多。

## 二、进阶原理

### 5. Docker容器的网络模式有哪些？

**答：** 五种常用的：
1. **bridge（默认）**：每个容器都连到docker0网桥上，分配内网IP，容器之间可以通过内网IP互通，对外需要端口映射，适合单机部署
2. **host**：共享宿主机的网络命名空间，容器直接用宿主机的IP和端口，性能最高，没有网络损耗，但是端口不能冲突，适合高性能的场景
3. **none**：没有网络，容器只有lo网卡，完全隔离，安全性要求高的场景用
4. **container**：和另一个容器共享网络命名空间，两个容器可以用127.0.0.1互相访问，比如sidecar模式就是用这个
5. **overlay**：跨主机的容器网络，多个宿主机上的容器可以在同一个内网，Docker Swarm和K8s用的就是这个

**支付场景使用：** 我们生产环境K8s用的是Calico的overlay网络，支付服务之间内网互通，延迟很低；压测的时候会用host模式，把网络损耗降到最低，压出来的QPS更准确。

---

### 6. Docker容器的数据怎么持久化？

**答：** 三种方式：
1. **Volume（推荐）**：Docker管理的宿主机目录，/var/lib/docker/volumes下，容器销毁数据还在，支持共享，生命周期独立于容器
2. **Bind Mount**：直接把宿主机的目录挂载进容器，灵活，但是要自己管理路径和权限
3. **tmpfs Mount**：挂载到宿主机内存里，速度快，容器销毁数据就没了，适合存敏感的临时数据，比如支付的密钥文件，用完就没了

**支付场景最佳实践：** 我们的支付服务日志用Bind Mount挂载到宿主机，然后Filebeat收集，容器挂了日志不会丢；配置和密钥用tmpfs挂载到内存里，不会写到磁盘，防止密钥泄露。

---

### 7. 怎么优化Docker镜像的大小？

**答：** 五个常用手段：
1. **多阶段构建**：编译和运行分开，构建镜像用带编译器的大镜像，运行镜像用alpine这类小的基础镜像，只把编译好的二进制拷进去，不用带编译工具链
2. **选用更小的基础镜像**：用alpine代替ubuntu，alpine才5M，ubuntu要几十M
3. **减少层数**：多个RUN命令合并成一个，用&&连接，用完就删缓存，比如`apt-get install && rm -rf /var/lib/apt/lists/*`
4. **清理不需要的文件**：编译后的临时文件、依赖缓存、文档、debug信息都删掉
5. **层缓存**：把变化少的层放在前面，变化多的代码层放在最后面，充分利用构建缓存，加快构建速度

> 优化前我们的支付服务镜像1.2G，优化完只有200M，缩小了6倍，拉镜像的时间从几十秒降到几秒，发布速度快很多。

### 8. 容器OOM了怎么排查？怎么防止？

**答：**
**排查步骤：**
1. 先看`dmesg`，有没有OOM killer的日志，确认是系统主动杀的容器
2. `docker inspect 容器ID`，看MemoryLimit设置的是多少
3. 看应用的内存使用监控，是内存泄漏还是确实峰值超过了限制

**防止手段：**
1. 启动容器的时候设置合理的内存限制，`--memory`和`--memory-swap`，不要让容器无限制用内存，把宿主机搞挂
2. Java这类有堆内存的应用，要设置JVM堆大小小于容器的内存限制，不然JVM默认用宿主机内存，很容易OOM
3. 应用层面做好内存泄漏排查，定期压测看内存趋势

**支付场景踩坑经验：** 最开始我们的Go支付服务没设置内存限制，有一次内存泄漏把宿主机的内存占满了，上面十几个支付服务都挂了，后面所有容器都强制设了CPU和内存限制，就算单个服务出问题也不会影响其他的。

## 三、Dockerfile最佳实践

### 9. 写Dockerfile有哪些注意事项？

**答：** 高频面试题，说这几点就行：
1. **基础镜像要选官方的、小的、安全的**，优先用alpine，不要用乱七八糟的第三方镜像，可能有后门
2. **不要用latest标签**，latest是滚动的，每次构建可能不一样，环境不一致，要用固定版本号的镜像
3. **变化少的层放前面**，FROM、RUN安装依赖、COPY go.mod这些放前面，COPY代码放最后面，最大化利用缓存
4. **不要在镜像里放敏感信息**，密钥、密码、环境变量不要写在Dockerfile里，要运行的时候注入，不然镜像里能搜出来
5. **不要用root用户运行容器**，创建普通用户，用普通用户启动，就算容器被攻破了也拿不到宿主机root权限
6. **每个容器只跑一个进程**，不要一个容器里又跑Nginx又跑应用又跑日志，不符合容器化的思想，出问题不好排查
7. **设置健康检查HEALTHCHECK**，告诉Docker怎么判断容器是不是正常运行，比如curl一下健康检查接口，异常了自动重启

**支付服务的Dockerfile示例（多阶段构建）：**
```dockerfile
# 构建阶段
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o payment-service cmd/main.go

# 运行阶段
FROM alpine:3.19
RUN apk --no-cache add ca-certificates tzdata
RUN adduser -D appuser
USER appuser
WORKDIR /app
COPY --from=builder /app/payment-service .
HEALTHCHECK --interval=10s --timeout=5s --retries=3 \
  CMD wget -qO- http://localhost:8080/health || exit 1
EXPOSE 8080
CMD ["./payment-service"]
```
> 这个就是我们支付服务线上在用的Dockerfile，非常规范，镜像200M不到，安全，有健康检查。

## 四、支付场景实战问题

### 10. 支付系统容器化部署要注意什么？

**答：** 支付系统是资金系统，容器化要特别注意这几点：
1. **时间同步**：容器的时间必须和宿主机和全局时间同步，对账的时候差一秒都可能出问题，要挂载宿主机的/etc/localtime，或者用NTP同步
2. **网络稳定性**：支付服务依赖很多下游RPC，网络要稳定，不要用默认的bridge模式，生产环境用K8s的CNI网络，开启TCP保活
3. **数据不丢失**：日志、对账文件这些要持久化挂载，不要存在容器的可写层里，容器删了数据就没了
4. **敏感信息安全**：密钥、证书不要打包到镜像里，要用Secret或者环境变量注入，用完就删，不要写到日志里
5. **资源隔离**：核心支付服务和非核心服务要部署在不同的节点池，不要混部，防止非核心服务把资源占满了影响支付
6. **优雅关闭**：容器要支持优雅关闭，收到SIGTERM信号的时候先停止接收新请求，把正在处理的支付请求处理完再退出，不能强杀，不然正在支付的请求就断了，容易资损

---

### 11. 大促的时候怎么快速扩容支付服务？

**答：** 容器化的优势就是弹性扩容快，我们这么做：
1. **镜像预拉取**：大促前把最新的支付镜像提前拉到所有节点上，扩容的时候不用再拉镜像，启动时间从十几秒降到1秒
2. **水平扩容**：基于CPU、内存、QPS的指标自动扩缩容，QPS超过阈值就自动加实例，峰值过了自动缩容
3. **预热**：新启动的实例先预热，把缓存、数据库连接都建好了再切流量进去，不会出现启动瞬间请求超时的情况
4. **容量保底**：大促前提前扩到3倍保底容量，自动扩容作为兜底，不会等到峰值来了才扩

---

### 12. 容器里的支付服务怎么排查问题？

**答：** 常用排查手段：
1. `docker logs 容器ID`：看服务日志，先看报错
2. `docker exec -it 容器ID sh`：进容器里看进程、配置、网络
3. `docker stats`：看容器的CPU、内存、网络IO使用情况，是不是资源打满了
4. `docker inspect 容器ID`：看容器的详细配置，IP、挂载、环境变量、限制对不对
5. 进入容器用tcpdump抓包，看RPC调用的返回对不对，是不是网络问题

> 重点：容器不要装太多调试工具，保持镜像精简，排查问题的时候可以用sidecar或者nsenter进入容器的命名空间调试，不用把工具打进镜像。
