# gRPC + Protobuf 全解 + 支付场景应用

> 覆盖 gRPC 核心概念、四种调用模式、和HTTP的区别、Protobuf 优势、性能优化、支付场景最佳实践

---

## 一、基础概念

### 1. 什么是 gRPC？和 HTTP/REST 有什么区别？为什么微服务之间调用选 gRPC？

**答：** 必考题，一定要说清楚选型理由
gRPC 是 Google 开源的高性能 RPC 框架，基于 HTTP/2 协议，用 Protobuf 做序列化，支持多语言，专门用于微服务之间的内部调用。

**和 RESTful HTTP 的核心区别：**

| 维度 | gRPC | RESTful HTTP 1.1 |
|-----|------|-----------------|
| **协议** | HTTP/2，支持多路复用、头部压缩、服务端推送 | HTTP/1.1，没有多路复用，头部冗余 |
| **序列化** | Protobuf 二进制序列化，体积小，速度快 | JSON 文本序列化，体积大，速度慢 |
| **性能** | 极高，比 HTTP JSON 快 5~10 倍 | 一般，序列化反序列化开销大 |
| **接口定义** | .proto 文件定义，强类型，自动生成多语言代码 | 接口文档靠人写，没有强类型约束，容易出错 |
| **调用模式** | 支持4种：一元、服务端流、客户端流、双向流 | 只有一元模式，请求-响应 |
| **适用场景** | 微服务内部调用，对性能要求高的场景 | 对外暴露接口，前端、第三方调用 |

> **我们支付为什么选 gRPC 不选HTTP？**
> 1. 性能高，支付服务调用链很长，每个调用快几毫秒，整体性能提升非常明显
> 2. 强类型，.proto 文件定义接口，自动生成代码，不会出现字段名写错、类型不对的问题，联调成本低很多
> 3. 支持流式调用，比如对账大文件传输、批量支付结果推送，用流模式非常方便
> 4. 内置的拦截器、负载均衡、重试、熔断这些功能都有，不用自己造轮子

---

### 2. Protobuf 是什么？为什么比 JSON 快？体积小？

**答：**
Protobuf 是 Protocol Buffers 的简称，是 Google 开源的二进制序列化协议，和语言无关、平台无关。

**为什么比 JSON 快很多，体积小很多？**
1. **二进制格式**，不是文本，体积本身就小很多，没有JSON的引号、括号、字段名这些冗余
2. **不需要传字段名**，每个字段有唯一的编号，序列化的时候只传编号和值，不用传字段名字符串，节省了大量空间
3. **强类型**，序列化反序列化的时候不需要类型判断，直接按类型解析，速度比JSON快很多
4. **没有多余的空格和换行**，JSON为了人可读有很多空格换行，Protobuf完全没有

> 举个例子：一个支付单对象，JSON序列化要500字节，Protobuf只要100字节不到，序列化速度快5倍以上，网络传输也快很多，微服务调用量大的时候差别非常明显。

### 3. gRPC 的四种调用模式是什么？分别适用什么场景？

**答：** 这是gRPC核心特性，必背

| 调用模式 | 说明 | 适用场景 | 支付场景例子 |
|---------|------|---------|------------|
| **一元调用 (Unary)** | 最常用的，客户端发一个请求，服务端返回一个响应，和普通HTTP调用一样 | 大部分普通的RPC调用，普通接口 | 查询支付单、创建支付单，大部分接口都是这个 |
| **服务端流式 (Server Streaming)** | 客户端发一个请求，服务端返回多个响应，流的形式持续发 | 服务端要返回大量数据，或者持续推送 | 批量导出账单，服务端持续返回一条条账单数据，不用一次性返回全量 |
| **客户端流式 (Client Streaming)** | 客户端发多个请求，服务端最后返回一个响应 | 客户端要传大量数据给服务端 | 批量上传支付流水，客户端一条条发，服务端全部收完了返回处理结果 |
| **双向流式 (Bidirectional Streaming)** | 客户端和服务端都可以双向同时发消息，全双工 | 需要双向交互的实时场景 | 实时支付状态推送，客户端发请求，服务端持续返回状态变更 |

> 我们支付用的最多的还是一元调用，对账的大文件导出用服务端流式，非常方便，不用分页，不用把所有数据都读到内存里，流式处理就行。

## 二、进阶知识点

### 4. gRPC 为什么性能高？底层原理？

**答：** 主要归功于 HTTP/2 + Protobuf
1. **HTTP/2 多路复用**：同一个TCP连接可以同时处理多个请求，不用像HTTP1.1那样一个请求占一个连接，要排队，也不用建很多TCP连接，减少了握手和开销
2. **HTTP/2 头部压缩 HPACK**：HTTP请求的Header有很多重复的，比如Cookie、User-Agent这些，HTTP/2用HPACK算法压缩头部，减少传输体积
3. **Protobuf 高效序列化**：二进制，体积小，序列化反序列化极快
4. **基于Netty的高性能网络框架**，IO多路复用，异步非阻塞，网络处理性能高
5. **零拷贝**，很多地方用了零拷贝技术，减少内存拷贝开销

---

### 5. gRPC 拦截器 Interceptor 是干什么用的？你们一般用来做什么？

**答：**
拦截器可以在RPC调用前后做统一的切面处理，不用在每个业务代码里写，和Spring的AOP差不多。
我们支付主要用在这几个地方：
1. **统一鉴权**：调用的时候在拦截器里加token，服务端拦截器校验权限，不用每个接口都写校验
2. **日志埋点**：所有RPC调用的参数、返回值、耗时、错误码都统一打日志，不用每个接口都写
3. **链路追踪**：拦截器里自动传递traceId，把调用链串起来，排查问题方便
4. **限流熔断**：客户端拦截器里做限流、熔断、重试，不用业务代码处理
5. **参数校验**：统一做参数校验，不用每个接口都写校验逻辑

> 非常好用，所有的公共逻辑都可以放在拦截器里，业务代码非常干净，只关心业务逻辑就行。

---

### 6. gRPC 怎么做重试、超时、熔断？

**答：**
gRPC 原生就支持这些功能，配置就行，不用自己写：
1. **超时**：调用的时候可以设置deadline，超过时间自动超时返回，防止调用卡住，所有调用都必须设置超时时间，不能无限等
2. **重试**：配置重试策略，比如5xx错误、超时都可以自动重试，配置重试次数、重试间隔、重试的错误码
3. **熔断**：可以配合Sentinel或者gRPC自带的熔断插件，失败率高了自动熔断，快速失败
4. **负载均衡**：客户端内置负载均衡，支持轮询、加权轮询、一致性哈希等策略，不用自己做

## 三、支付场景最佳实践 & 踩坑经验

### 7. 你们支付服务之间的gRPC调用有哪些最佳实践？

**答：** 直接说你们的实际规范，面试官一听就知道你真的大规模用过
1. **所有调用必须设置超时时间**，绝对不能用默认的无限超时，防止下游挂了把上游也拖死，核心接口1秒，非核心的3秒
2. **错误码标准化**，所有接口返回统一的错误码，不用HTTP状态码，业务错误都返回200，错误码在返回体里，方便重试判断
3. **重试要配置幂等**，只有幂等的接口才配置重试，非幂等的比如扣款接口不能随便重试，不然容易重复扣款
4. **Protobuf字段不要随便改**，字段编号一旦定了就不能改，不要删字段，不要改字段类型，不然会导致序列化失败，兼容性出问题
5. **大对象不要用gRPC传**，超过1M的不要直接传，传地址，用对象存储或者数据库存，不然会把连接占满，影响其他调用
6. **拦截器做统一的日志和链路追踪**，所有调用都打日志，传traceId，排查问题的时候全链路都能串起来
7. **核心接口做降级兜底**，调用下游失败了，有兜底逻辑，不要直接报错，比如查询用户信息失败了，用缓存的兜底数据，不要影响支付主流程

---

### 8. 用gRPC踩过什么坑？

**答：** 说几个真实的，非常加分

**坑1：没设置超时，下游服务卡死了，上游所有线程都卡住了，整个服务雪崩了**
最开始很多开发图省事，不设置超时，有一次订单服务数据库死锁，所有调用订单的请求都卡死了，上游支付服务的线程全部占满，整个支付服务都挂了
- 解决：强制所有gRPC调用必须设置超时，代码规范里加了检查，不设置超时的代码编译都过不了

**坑2：Protobuf改了字段编号，导致老版本调用新版本序列化失败，解析出来全是空的**
有个开发改proto文件，把字段1和字段2的编号换了，老版本服务调用新版本，字段都对不上，解析出来全是空的，支付状态全错了
- 解决：制定proto规范，字段编号一旦定了绝对不能改，不用的字段标记为deprecated，不能删，不能改编号，CR的时候必须检查proto变更

**坑3：大文件批量导出用了普通的一元调用，返回了100M的数据，把内存占满了，服务OOM了**
最开始对账导出接口，一次性把所有数据查出来返回，导出几十万条账单的时候，返回体100多M，内存直接爆了，服务OOM
- 解决：改成服务端流式调用，查一条发一条，不用把所有数据都加载到内存里，内存占用从几百M降到几M，非常稳定

**坑4：默认的重试策略没有限制错误码，扣款接口调用超时自动重试了，导致重复扣款**
最开始配置了全局重试，所有超时都重试，扣款接口不是完全幂等的，重试了两次，扣了两次钱
- 解决：重试只配置在幂等的查询类接口上，写操作、扣款类接口默认不重试，要重试的单独配置，并且必须保证幂等

### 9. gRPC 怎么做服务端和客户端的性能优化？

**答：**
**服务端：**
1. 合理设置Worker线程池大小，不要太大也不要太小，根据CPU核数设，一般是CPU核数*2
2. 大消息的话调大消息大小限制，默认是4M，不够的话可以调大，但是不要太大
3. 开启keepalive，自动检测死连接，及时释放
4. 业务处理不要阻塞IO线程，复杂业务丢到业务线程池里处理，不要占Netty的IO线程

**客户端：**
1. 连接池复用，不要每次调用都建新连接，同一个服务复用连接
2. 开启压缩，传输数据量大的话开启gzip压缩，减少传输时间
3. 合理配置重试和超时，不要重试太多次，不要超时设太长
4. 负载均衡策略选合适的，比如同机房优先、加权轮询，不要都用轮询
