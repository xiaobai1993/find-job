面试高频陷阱题

「阻塞是被强制暂停吗？」→ 不是！阻塞是进程主动发起的等待行为（调用 read/sleep 等）。
「运行→阻塞 vs 运行→就绪 有什么区别？」→ 前者是主动等IO，后者是时间片用完被调度器踢下去。

为什么需要线程？为什么需要协程？

进程 隔离性最好，崩了不影响别人，但"太重"——fork 要复制页表，切换要刷 TLB。
线程 在进程内部，共享地址空间，切换不用换页表，所以更轻。但线程A崩了整个进程都崩。
协程 把调度搬到用户态，切换只保存几个寄存器，完全不陷入内核，所以最轻。Go 的 goroutine 初始栈只有 2KB，动态扩容，百万级并发不是梦。

为什么 TLB 刷新这么贵？

TLB（Translation Lookaside Buffer）是 CPU 芯片里的地址翻译缓存。
进程A和进程B的虚拟地址是独立的，切换进程必须清空 TLB。
清空后，新进程的每次内存访问都要慢慢查页表（~100ns），直到 TLB 重新"热起来"。
一次 TLB miss = 走一趟内存 = ~100ns，而 TLB hit = ~1ns。差距100倍！

⚠️ 循环等待 → 死锁！

四个必要条件

条件含义破坏方法
互斥 资源只能被一个进程占用 把资源设计为可共享（如只读文件）——但大多数互斥无法破坏
持有并等待 拿着已有资源，还在等新资源 一次性申请所有资源；Go里可以一个事务加所有锁
不可抢占 已获得的资源不能被强制拿走 设置超时自动释放（Go的 context.WithTimeout）
循环等待 A等B，B等C，C等A…… 对资源编号，按序申请（最实用！）
Go 实战防死锁

1. 多个 Mutex 要按固定顺序加锁（如按 ID 从小到大）
2. 用 context.WithTimeout 给锁等待设超时
3. Channel 死锁：双方都阻塞在收/发 → 加 buffer 或 select + default

⑥ Go GMP 调度模型

用户态的调度器——让百万 goroutine 跑在少数几个 OS 线程上

M（Machine） = OS线程，内核调度，通常 = CPU核心数
P（Processor） = 逻辑处理器，有本地G队列，GOMAXPROCS控制数量
G（Goroutine） = 用户态协程，初始栈2KB，动态扩容

全局 G 队列
网络 I/O 等待 (netpoll)
等待操作...
面试必答：为什么需要 P？

没有P的话，每个M都要去全局队列抢G → 全局锁竞争激烈。
P的本地队列让大部分G调度不需要加锁。Work Stealing让负载自然均衡。
G遇到syscall阻塞 → M与P解绑，P找新M继续跑其他G → M不会白白浪费在等IO上。
