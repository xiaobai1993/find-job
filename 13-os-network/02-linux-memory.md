来源：操作系统教材 + 面试高频题整理

## 一、虚拟内存

面试开场：「什么是虚拟内存？为什么需要它？」

**核心思想**：每个进程认为自己独占连续的内存空间，实际物理内存可能分散且不足。

| 维度 | 32 位系统 | 64 位系统 |
|------|-----------|-----------|
| 虚拟地址空间 | 4GB（2^32） | 128TB（实际用 48 位地址，2^48） |
| 用户空间 | 0~3GB | 0~128TB |
| 内核空间 | 3~4GB | 128TB~顶部 |

**虚拟内存的好处**：
1. **隔离**：每个进程独立地址空间，A 崩不影响 B
2. **安全**：内核空间用户不能访问，页表有权限位（R/W/X）
3. **按需分配**：malloc 只是分配虚拟地址，访问时才触发缺页中断实际分配物理页
4. **超越物理内存**：通过 swap 把不活跃的页换到磁盘

**面试追问**：「malloc 返回了地址但物理内存还没分配，那访问时会发生什么？」

> 触发缺页中断（Page Fault）→ 内核检查该虚拟地址是否合法→合法则从物理内存分配一页→修改页表映射→重新执行那条指令。

## 二、分页机制

### 页与页框

| 概念 | 含义 | 大小 |
|------|------|------|
| 页（Page） | 虚拟地址空间的划分单位 | 通常 4KB |
| 页框（Page Frame） | 物理内存的划分单位 | 与页相同大小 |
| 页表（Page Table） | 虚拟页号→物理页框号的映射表 | 每个进程一份 |

### 地址翻译过程

虚拟地址 = `虚拟页号(VPN) + 页内偏移(offset)`

```
虚拟地址 → [页表] → 物理页框号 + offset → 物理地址
```

**两级页表（x86-32）**：

> 为什么需要多级页表？如果一级页表，4GB 空间 / 4KB 页 = 1M 个页表项，每项 4 字节 = 4MB。每个进程都要一张完整页表？内存浪费太大。二级页表让未使用的虚拟地址范围不需要分配二级页表，大幅节省内存。

**x86-64 使用四级页表**：PGD → PUD → PMD → PTE → 物理页

### TLB（Translation Lookaside Buffer）

**面试必问**：「TLB 是什么？为什么对性能影响巨大？」

> TLB 是页表的缓存，在 MMU（内存管理单元）内部。每次地址翻译先查 TLB，命中直接得到物理地址（~1ns），未命中则要查页表（~100ns，可能还要多次内存访问）。

**TLB flush 的代价**：进程切换时 TLB 全刷→新进程的地址翻译全部要慢查页表→这就是进程切换比线程切换慢的核心原因。

**大页（Huge Pages）**：标准页 4KB，大页 2MB 或 1GB。好处：减少页表项数量→减少 TLB miss→提升性能。典型应用：数据库（MySQL、PostgreSQL）、Redis 都推荐开启大页。

## 三、页面置换算法

当物理内存不足时，需要把某些页换出到磁盘（swap），换哪些页出去？

| 算法 | 原理 | 评价 |
|------|------|------|
| OPT（最优置换） | 置换未来最长时间不被访问的页 | 理论最优但无法实现（无法预知未来） |
| FIFO | 置换最早进入内存的页 | 简单但有 Belady 异常（更多帧→更多缺页！） |
| LRU | 罙换最近最少使用的页 | 实际最接近 OPT，但实现成本高（需要维护时间戳链表） |
| Clock（近似 LRU） | 给每页一个访问位，时钟指针扫描，访问位=0 则换出 | 实际操作系统常用，近似 LRU 效果 |

**面试答法**：Linux 实际用的是 **Clock 算法的变种**（多级时钟），不是严格 LRU。因为严格 LRU 每次访问都要更新链表位置，开销太大。

## 四、内存布局

一个进程的虚拟地址空间典型布局（从低到高）：

```
低地址 → 高地址
┌──────────────┐
|  代码段 (text)   |  可执行指令，只读
|  数据段 (data)   |  已初始化全局/静态变量
|  BSS 段          |  未初始化全局/静态变量，零填充
|  堆 (heap)       |  向高地址增长，malloc/new 分配
|  ...              |  空洞
|  共享库映射区     |  libc 等动态库
|  ...              |  空洞
|  栈 (stack)      |  向低地址增长，局部变量、函数调用
|  内核空间         |  用户不可访问
└──────────────┐
```

**面试追问**：「堆和栈的增长方向为什么相反？」

> 堆向高地址增长（malloc），栈向低地址增长（push），中间留空洞→可以按需扩展，不会互相侵占。栈大小有上限（Linux 默认 8MB，`ulimit -s` 查看），堆理论上可以很大（受虚拟地址空间和物理内存限制）。

**Go 的栈不是固定 8MB**：goroutine 初始栈只有 2KB，按需动态增长（分段栈→连续栈），这是 Go 能开百万 goroutine 的关键原因之一。

## 五、内存分配策略

### 内核层面

Linux 物理内存管理使用 **伙伴系统（Buddy System）**：

- 把物理内存按页框分组，每组大小是 2^n 页（1, 2, 4, 8, ... 1024 页）
- 分配时找最小能满足的组，拆分到合适大小
- 释放时合并相邻同大小的空闲组

**面试追问**：「伙伴系统的缺点？」

> 内部碎片：只能分配 2^n 页大小的块，如果只需要 3 页，分配 4 页浪费 1 页。所以内核还有 **slab 分配器**在伙伴系统之上，把大块切成小对象缓存，减少内部碎片。

### Go runtime 层面（TCMalloc 思想）

Go 的内存分配器借鉴 TCMalloc，核心思想：**多级缓存减少锁竞争**

```
mheap（全局堆） → mcentral（中间缓存，按 size class） → mcache（每个 P 的本地缓存）
```

- mcache 是每个 P 专属的，分配小对象不加锁
- mcache 不够→从 mcentral 批量拿一批
- mcentral 不够→从 mheap 大块分配
- size class：Go 把对象按大小分成 67 级（1~32KB），每级单独缓存

## 六、Swap 与 OOM

**Swap**：把不活跃的物理页写到磁盘，腾出物理内存。访问这些页时再从磁盘读回来（缺页中断）。

**面试考点**：

- Swap 带来延迟：磁盘 I/O 比内存慢 10 万倍（内存 ~100ns，磁盘 ~10ms）
- Kubernetes 默认关闭 Swap（`--swapoff`），因为容器内存保障基于物理内存
- Go runtime 在有 Swap 时会把自己不常用的栈页换出去，但 GC 扫描时会全部换回来→造成 **swap storm**

**OOM Killer**：物理内存+Swap 都耗尽时，内核选择一个进程杀掉释放内存。

- 选择策略：选 `oom_score` 最高的进程（占内存多+优先级低）
- 可以通过 `/proc/<pid>/oom_score_adj` 调整（-1000 到 1000）
- 面试追问：「为什么数据库进程经常被 OOM Killer 选中？」→ 因为它占内存最多

## 七、mmap

**面试常问**：「mmap 是什么？为什么比 read/write 快？」

mmap 把文件映射到进程的虚拟地址空间，访问文件就像访问内存一样。

**对比传统 read/write**：

| 方式 | 数据路径 | 拷贝次数 |
|------|----------|----------|
| read | 磁盘→内核缓冲→用户缓冲 | 2 次拷贝 |
| mmap | 研盘→页缓存→直接访问虚拟地址 | 1 次拷贝（甚至 0 次，如果页缓存已有） |

**mmap 的好处**：
- 减少拷贝（用户态不需要额外缓冲区）
- 大文件不需要一次性读入，按需缺页加载
- 多进程映射同一文件→共享页缓存，天然共享内存

**mmap 的缺点**：
- 映射开销（页表修改），小文件不如 read
- 写时不稳定（异常可能导致数据丢失，需要 msync）
- 难以处理文件大小变化

**实际应用**：Kafka 用 mmap 做消息索引、SQLite 用 mmap 访问数据库文件、共享内存 IPC 本质就是 mmap。

## 八、面试高频追问

### Q1：虚拟内存和物理内存的关系？

> 虚拟内存是逻辑上的连续地址空间，物理内存是实际硬件。页表做翻译：虚拟页号→物理页框号。多个进程的虚拟页可以映射到同一物理页（共享库）。虚拟地址空间可以远大于物理内存（靠 swap 和按需分配）。

### Q2：为什么栈有大小限制而堆没有？

> 栈是连续的，需要预分配空间防止溢出，8MB 是历史默认值。堆是链式分配的，理论上可以一直增长直到虚拟地址空间或物理内存耗尽。Go 的 goroutine 栈动态增长所以不需要预分配 8MB。

### Q3：缺页中断和普通中断有什么区别？

> 普通中断是异步的（随时可能来），缺页中断是同步的（由具体指令触发）。缺页中断处理完后要**重新执行触发中断的那条指令**，而不是像普通中断那样继续下一条。
