面试关键区分

前4种模型（阻塞/非阻塞/多路复用/信号驱动）：数据拷贝阶段都是同步的，都需要进程自己调 recvfrom 把数据从内核拷到用户态。
只有异步I/O：连数据拷贝也由内核完成，完成后才通知你。
Linux的AIO实现不完善，实际生产主要用 epoll（多路复用）。

模型等待阶段数据拷贝典型系统调用实际使用

② select / poll / epoll 对比

从 C10K 问题理解为什么需要 epoll。点击按钮模拟连接到达

C10K 问题：一台服务器同时服务 10000 个客户端连接。
select/poll 每次调用都要把所有fd从用户态拷到内核态，内核扫描一遍，再把结果拷回来 — O(n)。
10000个连接，大部分时候只有几十个活跃，却要扫10000次，极度浪费。

Go runtime 的 net poller

Go 把 epoll 封装在 runtime 里对用户透明：
goroutine 读网络数据 → fd没数据 → 注册到 epoll，goroutine 挂起（gopark）
→ epoll_wait 返回就绪 → 把 goroutine 放回 P 的本地队列 → 被调度继续执行
这就是为什么 Go 的网络 I/O 不阻塞 OS 线程，一个M可以服务无数个 goroutine。

③ ET（边缘触发）vs LT（水平触发）

epoll 的两种工作模式，理解错了就会漏读数据。点击按钮模拟数据到达和读取

LT（Level Triggered，水平触发）：缓冲区有数据就一直通知你，像水位报警器，水位高就一直响。
ET（Edge Triggered，边缘触发）：只在数据从无到有的那一刻通知一次，之后不再通知，像上升沿触发。

ET 模式的大坑 ⚠️

ET 模式只通知一次，所以必须循环读直到 EAGAIN（返回-1且errno=EAGAIN），否则剩余数据永远不会被通知！

因此ET模式必须配合非阻塞 fd，不然循环read时如果没数据会卡在那里。

LT（默认）ET
通知时机缓冲区有数据就持续通知仅在数据到来时通知一次
编程难度简单安全需循环读+非阻塞fd
效率相对多一些通知调用通知次数少，效率更高
谁在用Redis（简单安全，单线程不怕）Nginx（追求极致性能）

谁在用零拷贝？

📬
Kafka
消费消息用 sendfile，磁盘数据直接到网卡，不过用户态
🌐
Nginx
静态文件服务用 sendfile，sendfile on 开启
🗺️
mmap
Kafka索引文件、SQLite、共享内存IPC都用mmap映射
🔌
splice
两个fd间零拷贝传输，数据在内核管道缓冲区流动
面试一句话

零拷贝不是"完全不拷贝"，是减少CPU参与的拷贝。DMA拷贝（硬件直接传）是免不了的。
sendfile让数据不过用户态，省掉2次CPU拷贝，还减少了2次内核/用户态上下文切换。
