# TCP/UDP — 后端面试核心考点

来源：计算机网络教材 + 面试高频题整理

---

## 一、TCP vs UDP

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠传输（确认、重传、排序） | 尽力交付，不保证 |
| 顺序 | 保证有序 | 不保证 |
| 流量控制 | 滑动窗口 | 无 |
| 拥塞控制 | 慢启动、拥塞避免、快重传、快恢复 | 无 |
| 速度 | 相对慢（维护状态开销） | 快（无状态、无重传） |
| 头部大小 | 20 字节起 | 8 字节 |
| 通信方式 | 一对一 | 一对一、一对多、多对多 |

**面试答法**：不要只背区别，要说场景——

> TCP 适合需要可靠性的场景（HTTP、数据库连接、RPC），UDP 适合实时性和吞吐量优先的场景（DNS 查询、视频流、游戏、Kafka 早期的跨数据中心复制）。QUIC（HTTP/3 底层）在 UDP 上实现了可靠性，是两者优点的结合。

## 二、TCP 三次握手

```
Client                          Server
  |--- SYN, seq=x ------------>|     （第一次：客户端发起连接）
  |<-- SYN+ACK, seq=y, ack=x+1-|     （第二次：服务端确认并发起连接）
  |--- ACK, ack=y+1 ---------->|     （第三次：客户端确认）
```

### 为什么是三次？两次不行吗？

**核心原因**：防止历史重复连接初始化。

> 假设只有两次握手：客户端发了一个 SYN（因为网络延迟，旧请求），服务端收到就建连接分配资源→但客户端其实不要这个连接了→服务端白等，资源浪费。三次握手让客户端有机会确认「我确实要连」才真正建立连接。

**另一个角度**：三次握手是双方都确认了「对方能收能发」的最小次数。

| 握手次数 | 客户端确认 | 服务端确认 |
|----------|-----------|-----------|
| 一次 | 无 | 无 |
| 两次 | 服务端能收 | 无（不确定客户端能不能收） |
| 三次 | 服务端能收能发 | 客户端能收能发 |

### 三次握手过程中各阶段的状态

| 阶段 | 客户端状态 | 服务端状态 |
|------|-----------|-----------|
| 初始 | CLOSED | LISTEN |
| 第一次握手后 | SYN_SENT | LISTEN |
| 第二次握手后 | SYN_SENT | SYN_RCVD |
| 第三次握手后 | ESTABLISHED | ESTABLISHED |

**面试追问**：「服务端 SYN_RCVD 状态过多是怎么回事？」

> 典型的 SYN Flood 攻击——攻击者发大量 SYN 但不完成第三次握手，服务端为每个 SYN_RCVD 分配资源耗尽。防御：SYN Cookie（不分配资源，把信息编码在 seq 里）、限制半连接数。

## 三、TCP 四次挥手

```
Client                          Server
  |--- FIN, seq=u ------------>|     （第一次：客户端请求关闭）
  |<-- ACK, ack=u+1 -----------|     （第二次：服务端确认）
  |                             |     （服务端可能还有数据要发...）
  |<-- FIN, seq=w, ack=u+1 ----|     （第三次：服务端也请求关闭）
  |--- ACK, ack=w+1 ---------->|     （第四次：客户端确认）
  |  [TIME_WAIT 2MSL]          |
```

### 为什么是四次？三次不行吗？

> 因为 TCP 是全双工的。客户端 FIN 只表示「我不发了」，服务端 ACK 后可能还有数据要发。等服务端也发完了再 FIN，所以是四次。如果服务端没有数据要发，第二次和第三次可以合并成 FIN+ACK，看起来像三次——但不能保证每次都这样。

### 为什么客户端要 TIME_WAIT 等 2MSL？

| 原因 | 说明 |
|------|------|
| 确保最后一个 ACK 能到达 | 如果 ACK 丢了，服务端会重发 FIN，客户端在 TIME_WAIT 内还能重发 ACK |
| 让旧连接的报文消亡 | 防止新连接收到旧连接的延迟报文，2MSL 确保旧报文已被网络丢弃 |

**MSL**（Maximum Segment Lifetime）：报文最大生存时间，通常 30 秒~2 分钟。

### TIME_WAIT 过多的危害与解决

**危害**：占用端口号（一个 IP:Port 只能一个 TIME_WAIT），连接数多了端口耗尽。

**解决方案**：

| 方案 | 说明 | 评价 |
|------|------|------|
| `SO_REUSEADDR` | 允许重用 TIME_WAIT 状态的端口 | 客户端可用，服务端不需要（服务端监听端口不受影响） |
| `tcp_tw_reuse` | 允许复用 TIME_WAIT 连接（仅客户端主动连出时） | 比 REUSEADDR 更安全，会检查时间戳 |
| 长连接 | 减少连接建立和关闭次数 | 最根本的解决方式 |
| `tcp_max_tw_buckets` | 限制 TIME_WAIT 数量 | 超过直接 RST，暴力但有上限 |

**面试加分**：Go 的 `net` 包默认设置了 `SO_REUSEADDR`，所以 Go HTTP 客户端 TIME_WAIT 问题不严重。

## 四、TCP 可靠性保障机制

### 1. 序列号与确认

- 每个 TCP 段有序列号（seq），按字节编号
- 确认号（ack）= 期望收到的下一个字节号
- 累积确认：ack=x 表示 x 之前的所有数据都已收到

### 2. 超时重传

- 发送方启动定时器，超时未收到 ACK→重传
- RTO（Retransmission Timeout）动态计算，基于 RTT 估计
- 经典算法：Jacobson/Karels 算法

### 3. 滑动窗口（流量控制）

- 接收方通过窗口大小（Window）告诉发送方「我还能接收多少字节」
- 窗口大小=0 时发送方暂停发送（零窗口探测机制防止死锁）
- 目的：防止发送方发太快，接收方缓冲区溢出

### 4. 拥塞控制

**面试重点**，四个阶段：

```
慢启动 → 拥塞避免 → 快重传 → 快恢复
```

| 阶段 | 机制 | 拥塞窗口变化 |
|------|------|-------------|
| 慢启动 | 初始 cwnd=1（或 10，Linux 3.0+） | 每个 RTT 翻倍（指数增长） |
| 拥塞避免 | cwnd 达到 ssthresh | 每个 RTT +1（线性增长） |
| 快重传 | 收到 3 个重复 ACK | 立即重传丢失段，不等超时 |
| 快恢复 | 快重传后不回慢启动 | cwnd = ssthresh / 2，继续拥塞避免 |

**面试追问**：「为什么要有慢启动？直接全速发不行吗？」

> 网络容量未知，一开始就全速发可能瞬间拥塞丢包。慢启动从小窗口开始指数增长，快速探测到合适的发送速率，比线性增长快得多，又不会一开始就打爆网络。

## 五、TCP 粘包/拆包

**面试常问**：「TCP 为什么会粘包？怎么解决？」

**根本原因**：TCP 是字节流协议，没有消息边界。应用层两次 write 的数据可能被合并成一次 read 读出（粘包），也可能一次 write 被拆成多次 read 读出（拆包）。

**UDP 不会粘包**：UDP 是消息协议，每个数据报有明确边界，一次 recv 就是一个完整消息。

**解决方案**：

| 方案 | 说明 | 例子 |
|------|------|------|
| 固定长度 | 每条消息固定 N 字节，不够补齐 | 简单但浪费带宽 |
| 分隔符 | 每条消息末尾加特殊分隔符 | HTTP 的 `\r\n\r\n`，Redis 的 `\r\n` |
| 长度前缀 | 消息头用固定字节表示消息体长度 | 最常用，gRPC 用 5 字节头（1 压缩标志 + 4 长度） |
| TLV 格式 | Type-Length-Value | Protobuf 编码方式 |

**Go 代码示例（长度前缀）**：

```go
// 编码：4 字节大端长度 + 消息体
func Encode(msg []byte) []byte {
    buf := make([]byte, 4+len(msg))
    binary.BigEndian.PutUint32(buf[:4], uint32(len(msg)))
    copy(buf[4:], msg)
    return buf
}

// 解码：先读 4 字节长度，再读对应长度的消息体
func Decode(r io.Reader) ([]byte, error) {
    head := make([]byte, 4)
    if _, err := io.ReadFull(r, head); err != nil {
        return nil, err
    }
    length := binary.BigEndian.Uint32(head)
    body := make([]byte, length)
    if _, err := io.ReadFull(r, body); err != nil {
        return nil, err
    }
    return body, nil
}
```

## 六、TCP 状态机

完整的状态转换（面试不一定画全，但要知道关键路径）：

```
CLOSED → SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED

CLOSED → LISTEN → SYN_RCVD → ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```

**面试重点状态**：

| 状态 | 含义 | 大量出现说明 |
|------|------|-------------|
| SYN_RCVD | 收到 SYN，等第三次握手 | SYN Flood 攻击 |
| CLOSE_WAIT | 收到对方 FIN，自己还没关 | **程序 bug**——没调 close() |
| TIME_WAIT | 主动关闭方等 2MSL | 短连接过多 |
| FIN_WAIT_2 | 发了 FIN，等对方 FIN | 对方没关（可能是 CLOSE_WAIT 堆积） |

**面试追问**：「CLOSE_WAIT 大量堆积什么原因？」

> 自己的代码收到对方 FIN 后没有调用 close()——通常是因为连接管理 bug：没检测到对端关闭、没有超时关闭机制、goroutine 泄漏等。这不是系统参数能调的，必须修代码。

## 七、常见面试追问

### Q1：TCP 能同时双方主动关闭吗？

> 可以，叫「同时关闭」。双方同时发 FIN→都进入 FIN_WAIT_1→收到对方 FIN→都进入 CLOSING→都发 ACK→都进入 TIME_WAIT→都等 2MSL→CLOSED。实际很少见。

### Q2：如果第三次握手丢了怎么办？

> 服务端收不到 ACK→超时重发 SYN+ACK→客户端收到后再发 ACK。如果重发多次仍失败→服务端放弃，从 SYN_RCVD 回 CLOSED。

### Q3：RST 是什么？什么时候发？

> RST（Reset）强制重置连接，不经过四次挥手。场景：连接不存在时收到报文、进程崩溃、SYN Flood 防御、SO_LINGER 设为 0 时 close()。
