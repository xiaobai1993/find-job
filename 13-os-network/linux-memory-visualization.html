🔒 内核空间

操作系统内核住在这里。用户程序不能直接访问，一访问就会触发"段错误"（Segmentation Fault）崩溃。

系统调用（read/write/open）就是用户程序请求内核帮忙做事的方式。

面试口诀

内核空间 = 操作系统的地盘，用户程序只能通过"系统调用"这扇门进入，不能直接闯入。

② 虚拟内存 — 每个进程都"以为"自己有全部内存

虚拟地址 → 页表翻译 → 物理地址（或磁盘）

想象一下：你开了 5 个 App，每个都感觉自己有 128GB 内存。但物理内存只有 16GB。
这就是虚拟内存的魔法 — 每个进程看到的都是"假地址"，内核偷偷翻译成真实位置。

👆 点击左边的虚拟页，看翻译过程

面试三句话

1. 隔离：进程A崩了不影响进程B，因为他们的虚拟地址空间是独立的。
2. 按需分配：malloc只是给了个虚拟地址，实际物理内存访问时才分配（触发缺页中断）。
3. 超越物理限制：不常用的数据可以换到磁盘（Swap），虚拟空间可以大于物理内存。

③ 缺页中断 — 内存的"懒加载"机制

malloc 只是口头承诺，真正访问时才"实际到账"

你在超市买了件商品，收银台说"到货通知你"（malloc返回地址）。
你回家打开门取货时发现没到 → 打电话让超市赶紧送过来（缺页中断）→ 到了之后你再去取（重新执行指令）。

1

程序执行访问内存的指令

CPU执行 MOV 指令，要读/写某个虚拟地址

2

MMU 查页表，发现"不在物理内存"

页表里这一页标记为"不存在"，触发缺页中断

3

CPU 进入内核，交给缺页中断处理程序

内核检查：这个虚拟地址合法吗？

4

找一块空闲物理内存，建立映射

修改页表，把虚拟页指向这块物理内存

5

重新执行那条指令 ✅

这次页表里有了，正常访问，程序继续跑

和普通中断的区别

普通中断（如键盘）：异步来的，处理完后执行下一条指令。
缺页中断：由当前指令触发，处理完后重新执行同一条指令。

④ TLB — 地址翻译的"小抄"

每次访问内存都查页表太慢，TLB 是硬件里的缓存

每次读写内存都需要"查页表"把虚拟地址翻译成物理地址。
但页表在内存里，查一次要访问内存，那读写内存就要访问内存两次——太慢了！
TLB 就是 CPU 芯片里内置的"小本本"，记住最近用过的翻译结果。

TLB 命中（Hit）
✅ 缓存里找到
~1ns
和寄存器一样快
TLB 未命中（Miss）
❌ 去查页表
~100ns
慢100倍（还要走内存）

进程切换为什么慢？

进程A切换到进程B时，TLB 里存的全是进程A的翻译结果。
换了进程这些全都失效了，要全部清空（flush）。

新进程一开始所有内存访问都要慢慢查页表，直到 TLB 重新"暖"起来。

线程切换同进程共享页表，TLB 不需要全刷 → 快
进程切换不同进程，TLB 全部清空 → 慢

大页（Huge Page）

标准页 4KB，TLB 条数有限（通常 64~1024 条）。
如果换成 2MB 大页，同样的 TLB 条数能覆盖更多内存 → TLB miss 减少 → 性能提升。

MySQL PostgreSQL Redis 都建议开启大页
面试口诀

TLB = 页表的 CPU 缓存。命中1纳秒，未命中100纳秒。进程切换清空TLB是进程比线程慢的核心原因之一。

⑤ Swap 内存置换 & OOM 杀进程

物理内存不够用时发生什么

把内存想象成你的书桌，磁盘是书架。书桌放不下了，就把不常看的书放回书架（Swap Out）。
需要再看时再从书架取出来（Swap In，触发缺页中断）。
书架比桌面慢10万倍，所以 Swap 太多会让系统非常卡。

系统内存状态（模拟）
已用 40%
Cache 20%
空闲 40%
Swap 使用
Swap 0%
空闲 100%
系统内存充足，一切正常。
☠️ OOM Killer 触发！
[kernel] Out of memory: Kill process 1234 (mysql)
[kernel] oom_score = 823, vm_rss = 8.2GB
[kernel] Killed process 1234 (mysql) total-vm:10GB, anon-rss:8GB
内核会选 oom_score 最高 的进程杀掉（占内存最多+优先级低）。
数据库进程最容易中招，因为它们占内存最多。
可以通过 /proc/<pid>/oom_score_adj 调整，设为 -1000 让内核不杀这个进程。
Kubernetes 为什么禁用 Swap？

K8s 给容器承诺了固定内存配额（limits/requests）。
如果允许 Swap，容器以为自己有 1GB，实际上 800MB 在磁盘上——性能完全不可预测。
所以 K8s 部署节点必须 swapoff -a，保证内存行为可控。

⑥ mmap — 把文件"变成"内存

少一次拷贝，大文件性能提升显著

传统 read() 是：先把文件读进内核缓冲区，再从内核缓冲区复制到你的程序缓冲区 — 数据走了两遍。
mmap 是：直接把文件页和你的虚拟内存空间"接通"，访问内存就等于访问文件 — 数据只走一遍。

📖 传统 read() 方式

💾
磁盘读取数据
⬇️
DMA 拷贝到内核缓冲区拷贝 ①
⬇️
内核把数据 copy 到用户缓冲区拷贝 ②
✅
程序才能用
总计：2次拷贝，2次上下文切换（用户态↔内核态）

🗺️ mmap 方式

💾
磁盘读取数据
⬇️
DMA 拷贝到页缓存拷贝 ①
🔗
页缓存直接映射到进程虚拟地址 零拷贝 ✓
✅
程序访问内存就等于访问文件
总计：1次拷贝（若页缓存命中则 0 次），共享内存无需拷贝

哪些地方在用 mmap？

📬
Kafka
消息索引文件用 mmap，读取时不需要 read() 系统调用
🗄️
SQLite
数据库文件用 mmap 访问，WAL 模式下尤其高效
🔴
Redis RDB
加载 RDB 快照时用 mmap，超大快照秒级加载
🤝
共享内存 IPC
进程间通信本质就是 mmap 同一块内存，零拷贝传数据
mmap 的缺点（别只说好的）

1. 小文件反而慢：建立映射本身有开销，小文件不如直接 read。
2. 写入不稳定：程序崩溃可能导致数据没落盘，需要手动调用 msync。
3. 文件大小变化麻烦：映射建立后文件扩容需要重新映射。
