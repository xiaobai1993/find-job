# 全网通信+HTTP/HTTPS 全套知识点总结
结合咱们全程对话，按学习顺序梳理，分模块提炼核心要点、考点与实战结论，方便复盘记忆。

## 一、IO 模型 & 磁盘/网络 IO 基础
### 1. 核心组件区分
- **epoll**：Linux 多路复用模型，专注**网络IO（Socket）**，实现同步非阻塞，支撑高并发连接，Redis/Nginx 主流依赖。
- **AIO**：异步磁盘IO，用于文件读写、数据库刷盘、持久化场景，解决磁盘IO阻塞。
- **PageCache**：操作系统通用磁盘缓存，内核自主管理，调度不可控、有丢数据风险。
- **BufferPool/应用自建内存**：MySQL、Redis 自研缓存，主动绕开 PageCache（搭配 `O_DIRECT` 直接IO），精准管控内存与刷盘，保障数据可靠。

### 2. 核心结论
1. 数据库/中间件不用系统页缓存，是为了**掌控数据安全与读写时机**。
2. 网络IO靠 epoll，磁盘IO常搭配 AIO + 直接IO，二者分工明确。

## 二、TCP 协议核心（面试重中之重）
### 1. 连接管理：三次握手 & 四次挥手
#### 三次握手（建连）
- 流程：`SYN` → `SYN+ACK` → `ACK`
- 目的：双方确认收发能力正常、同步**ISN（初始序列号）**。
- 为什么不用两次握手：规避**网络延迟的失效报文**长期占用服务端资源（协议原生漏洞）。
- 延伸：客户端故意不回ACK → **SYN洪水攻击**，属于恶意攻击，三次握手无法防御。

#### 四次挥手（断连）
- 原因：TCP 是**全双工**，读写通道独立，一方关闭发送通道后，另一方可能仍有数据传输。
- 关键状态：
    1. **CLOSE_WAIT**（被动关闭方）：收到对方FIN并回复ACK后进入；大量堆积 = 代码未关闭Socket，连接泄漏。
    2. **TIME_WAIT**（主动关闭方）：发出最后一个ACK后进入，必须等待 **2MSL**。
        - 2MSL 两大作用：保证最后ACK送达对方；清空网络残留旧报文，避免干扰新连接。

### 2. 序列号 ISN
- 定义：TCP 字节流的**起始编号**，用于按序、去重、丢包重传。
- 设计要求：随机伪随机生成，防止延迟报文污染新连接。
- 延伸：**SYN Cookie** 复用ISN字段存储加密校验信息，服务端不存储半连接状态，抵御SYN洪水攻击。

### 3. 流量控制 & 拥塞控制
- **流量控制**（点对点）：靠 `rwnd` 接收窗口，接收方限制发送方速率，避免缓冲区溢出。
- **拥塞控制**（全网链路）：靠 `cwnd` 拥塞窗口，发送方自适应网络，避免链路拥堵。
    - 四阶段：慢启动（指数增长）→ 拥塞避免（线性增长）→ 快重传 → 快恢复。
    - 超时重传：判定严重拥塞，重置拥塞窗口，重回慢启动。
- 发送上限：`min(rwnd, cwnd)`，双重约束。

### 4. 其他 TCP 要点
1. **零窗口**：接收缓冲区满（rwnd=0），发送方暂停发送，定时发窗口探测包。
2. 计时器：重传计时器、保活心跳计时器、窗口探测计时器、2MSL计时器。
3. **MSS/MTU**：以太网MTU=1500字节，MSS=1460字节，TCP协商MSS减少网络分片。
4. **粘包/拆包**：TCP是字节流，无数据包边界，框架/成熟协议已封装处理；自研TCP协议需手动分包（固定长度、长度头、分隔符）。

### 5. TCP vs UDP
| 特性 | TCP | UDP |
| ---- | ---- | ---- |
| 连接 | 面向连接（握手挥手） | 无连接，直接发包 |
| 可靠性 | 可靠（重传、有序、去重） | 不可靠（丢包、乱序、重复） |
| 传输形式 | 字节流 → 存在粘包拆包 | 数据报 → 无粘包拆包 |
| 适用场景 | 文件、数据库、接口（要求可靠） | 音视频、直播、游戏、DNS（追求低延迟） |

- 拓展：可靠UDP = 在UDP之上复刻TCP可靠机制（序号、ACK、重传），代表：QUIC。

## 三、HTTP 协议全版本演进
### 1. 基础认知
- 应用层协议，默认基于TCP；明文传输，默认端口80。
- 核心特性：**无状态**，靠 `Cookie+Session`、`Token(JWT)` 实现会话保持。
- 报文结构：请求/响应均由**行 + 头部 + 体**组成；熟记常用请求方法、状态码。
- 缓存机制：强缓存（Expires/Cache-Control）→ 协商缓存（Last-Modified/ETag）。

### 2. 三大版本迭代与差异
#### HTTP/1.0
- 默认**短连接**，一次请求一次TCP断开，频繁握手挥手，性能差。

#### HTTP/1.1（主流现存）
1. **Keep-Alive**：默认长连接，复用TCP连接，减少连接开销，空闲超时自动断连。
2. **管线化**：长连接下客户端可连续发请求，无需逐个等响应；但响应必须按序返回，存在**应用层队头阻塞**。
3. 遗留问题：单TCP流串行、头部冗余、并发依赖多TCP连接。

#### HTTP/2
- 底层仍基于TCP，二进制帧传输；核心优化：
    1. 多路复用：单TCP连接划分多个独立Stream，解决**应用层队头阻塞**。
    2. HPACK头部压缩，大幅减少带宽损耗。
    3. 单连接承载并发，减少端口/连接资源消耗。
- 未解决：**TCP层队头阻塞**（单包丢包，整条TCP流阻塞所有Stream）。
- 现状：普及率95%+，内网、微服务、第三方接口广泛使用（微信支付V3支持）。

#### HTTP/3
- 底层舍弃TCP，改用 **UDP + QUIC协议**。
- 优势：彻底消除两层队头阻塞；内置TLS加密、0-RTT重连、连接迁移，弱网表现优异。
- 背景：由Google先落地（QUIC），后经IETF标准化，不是私有协议。

### 3. 关键补充
1. **队头阻塞总结**
    - HTTP/1.1：应用层+TCP层双重阻塞；
    - HTTP/2：仅TCP层阻塞；
    - HTTP/3：完全解决。
2. 协议升级规则：靠TLS握手**ALPN协商**，向下兼容；
    - 调用第三方接口（如微信支付）：服务端已支持新版本，**仅升级客户端即可，无需两端同步割接**；业务代码无需改动，仅调整网络配置。
    - 自研服务：优先升级服务端，再分批升级客户端，平滑过渡。

## 四、HTTPS 安全协议
### 1. 诞生目的
解决HTTP明文三大风险：窃听、数据篡改、身份伪装；`HTTPS = HTTP + SSL/TLS`，默认端口443。

### 2. 两种加密方式
- **对称加密**：加解密同密钥，速度快，用于大批量数据传输。
- **非对称加密**：公钥加密、私钥解密，速度慢，用于安全交换对称密钥。

### 3. 整体流程
1. 结合**数字证书（CA颁发）** 校验服务端身份，防中间人冒充；
2. 非对称加密协商出**会话对称密钥**；
3. 后续所有HTTP数据，用对称加密传输，兼顾安全与性能。

### 4. 版本优化
- TLS1.2：经典握手（2-RTT）；
- TLS1.3：握手简化为1-RTT/0-RTT，更快、安全性更强，HTTP/3默认集成。
