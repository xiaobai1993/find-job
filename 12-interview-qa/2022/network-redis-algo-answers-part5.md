## Q52：一个 URL 输入到浏览器，哪些环节可能发生缓存

**从近到远，逐层检查：**

```
1. 浏览器内部缓存
   │
   ├── Service Worker Cache（PWA 缓存）
   ├── Memory Cache（内存缓存，当前标签页）
   ├── Disk Cache（磁盘缓存，HTTP 缓存）
   │     ├── 强缓存：Cache-Control / Expires
   │     │   ├── max-age=3600（3600 秒内直接用缓存）
   │     │   └── 未过期 → 200 from cache（不发请求）
   │     │
   │     └── 协商缓存：Last-Modified / ETag
   │           ├── 发请求带 If-Modified-Since / If-None-Match
   │           └── 304 Not Modified（用缓存）或 200（新内容）
   │
   ├── Push Cache（HTTP/2 Server Push 缓存，会话级）
   │
2. 操作系统缓存
   │
   ├── DNS 缓存（hosts 文件 → OS DNS 缓存）
   │
3. 网络层缓存
   │
   ├── 路由器 DNS 缓存
   ├── ISP DNS 缓存
   ├── CDN 缓存（静态资源）
   │     └── CDN 节点缓存 → 回源缓存
   │
4. 服务端缓存
   │
   ├── Nginx / 反向代理缓存
   ├── 应用层缓存（Redis / Memcached）
   ├── 数据库查询缓存（MySQL 8.0 已移除）
   └── OPcache（PHP 字节码缓存）
   │
5. DNS 解析过程
   │
   ├── 浏览器 DNS 缓存
   ├── OS DNS 缓存
   ├── 路由器 DNS 缓存
   ├── ISP DNS 缓存
   └── 递归查询：根域名 → 顶级域名 → 权威域名
```

## Q53：http 和 tcp 的区别

| | TCP | HTTP |
|---|---|---|
| **层级** | 传输层（第 4 层） | 应用层（第 7 层） |
| **作用** | 提供可靠字节流传输 | 定义请求/响应格式 |
| **连接** | 三次握手建立连接 | 基于 TCP（HTTP/1.1 keep-alive 复用连接） |
| **状态** | 有状态（连接状态） | 无状态（每次请求独立） |
| **可靠性** | 确认重传、流量控制、拥塞控制 | 依赖 TCP |

## Q54：不同版本的 HTTP 特性

| 版本 | 年份 | 关键特性 |
|------|------|---------|
| **HTTP/1.0** | 1996 | 短连接，每次请求新建 TCP |
| **HTTP/1.1** | 1997 | 长连接(keep-alive)、管道化、分块传输、Host 头 |
| **HTTP/2** | 2015 | 多路复用、头部压缩(HPACK)、服务器推送、二进制帧 |
| **HTTP/3** | 2022 | **QUIC（基于 UDP）**、0-RTT 连接、无队头阻塞、连接迁移 |

**HTTP/3 的 QUIC 解决了什么：**
- TCP 队头阻塞：一个包丢失阻塞所有流 → QUIC 每个流独立
- 连接建立慢：TCP 3 次握手 + TLS 1-2 RTT → QUIC 0-1 RTT
- 连接迁移：IP 变化 TCP 连接断开 → QUIC 用 Connection ID 标识

## Q55：poll / epoll / select 的区别

| | select | poll | epoll |
|---|---|---|---|
| **最大连接数** | 1024（FD_SETSIZE） | 无限制 | 无限制 |
| **数据结构** | bitmap | 链表（pollfd 数组） | 红黑树 + 就绪链表 |
| **效率** | O(n) 遍历所有 fd | O(n) 遍历所有 fd | O(1) 只返回就绪 fd |
| **内存拷贝** | 每次调用都拷贝 | 每次调用都拷贝 | 只拷贝就绪 fd（mmap 共享） |
| **触发方式** | 水平触发 | 水平触发 | 水平触发(LT) + 边缘触发(ET) |

**为什么 epoll 快：**
1. 不需要遍历所有 fd，只返回就绪的
2. 内核和用户空间共享内存，减少拷贝
3. 红黑树管理 fd，增删改 O(log n)

**边缘触发(ET) vs 水平触发(LT)：**
- LT：fd 有数据就持续通知，直到读完
- ET：fd 从无数据变有数据时只通知一次，必须一次性读完

## Q56：nginx 的原理

**Nginx 采用多进程 + epoll 事件驱动架构：**

```
Master 进程
  │
  ├── 管理 Worker 进程（启动/停止/ reload）
  ├── 读取配置
  │
  ├── Worker 1 ──── epoll_wait() ────→ 处理连接
  ├── Worker 2 ──── epoll_wait() ────→ 处理连接
  └── Worker N ──── epoll_wait() ────→ 处理连接
```

**核心设计：**
- **多进程**：每个 Worker 独立进程，不共享内存，一个挂了不影响其他
- **epoll**：I/O 多路复用，单线程处理大量并发连接
- **异步非阻塞**：所有 I/O 操作都是异步的，不阻塞 Worker
- **连接池**：keep-alive 复用连接
- **零拷贝**：sendfile() 直接在内核态传输文件，不经过用户态

**请求处理流程：**

```
请求 → Worker epoll_wait 接收
  → HTTP 请求解析
  → location 匹配
  → 静态文件？→ sendfile 直接返回
  → 反向代理？→ upstream 转发 → 接收响应 → 返回客户端
```

## Q57：redis 的 zset 是怎么实现的

**ZSET 底层有两种编码：**

| 元素数量 | 元素大小 | 编码 | 数据结构 |
|---------|---------|------|---------|
| ≤ 128 且每个元素 ≤ 64 字节 | - | **ziplist/listpack** | 压缩列表（省内存） |
| 其他 | - | **skiplist + hashtable** | 跳表 + 哈希表 |

### 跳表（Skiplist）

```
Level 4:  1 ───────────────────────────────────────── 50
Level 3:  1 ──────────────── 20 ───────────────────── 50
Level 2:  1 ────── 10 ────── 20 ────── 30 ────────── 50
Level 1:  1 ── 5 ── 10 ── 15 ── 20 ── 25 ── 30 ── 40 ── 50
```

- 平均 O(log n) 查找，最坏 O(n)
- 实现比平衡树简单
- 范围查询高效（从找到的节点向后遍历）
- 每个节点随机层数，概率 1/4 晋升

### 为什么用跳表不用 B+ Tree / 红黑树

| | 跳表 | B+ Tree | 红黑树 |
|---|---|---|---|
| **实现复杂度** | 简单 | 复杂 | 复杂 |
| **范围查询** | 链表遍历 O(k) | 叶子链表 O(k) | 中序遍历 O(k) |
| **内存开销** | 指针多 | 碎片少 | 指针少 |
| **并发友好** | CAS 容易 | 页锁复杂 | 旋转难并发 |

**Redis 选跳表的原因：** 实现简单 + 范围查询高效 + 内存可接受。

## Q58：redis 的集群方案

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **主从复制** | 一主多从，读写分离 | 简单，读高可用 | 写单点，手动故障转移 |
| **Sentinel 哨兵** | 哨兵监控 + 自动故障转移 | 自动主从切换 | 写单点，单机容量限制 |
| **Redis Cluster** | 数据分片（16384 槽），每个节点负责部分槽 | 水平扩展，自动分片/转移 | 限制：多 key 事务需同槽、迁移复杂 |
| **Codis** | 代理层分片，Pre-sharding | 客户端透明，运维方便 | 代理层性能瓶颈，已停止维护 |

**Redis Cluster vs Codis：**

| | Redis Cluster | Codis |
|---|---|---|
| **架构** | 去中心化，P2P | 中心化，代理层 |
| **客户端** | 需要支持 Cluster 协议 | 透明，像单机 Redis |
| **迁移** | 内置，自动 | Dashboard 手动触发 |
| **运维** | 复杂（需理解槽） | 简单（Dashboard） |
| **维护** | 官方维护 | 已停止维护（2020） |

**推荐：** 新项目用 Redis Cluster。

## Q59：redis 的跳跃表和 mysql 的 B+ Tree 异同

| | Redis 跳表 | MySQL B+ Tree |
|---|---|---|
| **应用** | 内存数据库 | 磁盘数据库 |
| **查找** | O(log n) | O(log n)（IO 次数 = 树高） |
| **范围查询** | 链表遍历 | 叶子链表遍历 |
| **存储** | 内存，指针开销可接受 | 磁盘，页对齐减少 IO |
| **插入/删除** | O(log n)，概率平衡 | O(log n)，可能触发分裂/合并 |
| **并发** | CAS 友好 | 页锁/表锁，复杂 |

**为什么 Redis 用跳表、MySQL 用 B+ Tree：**
- Redis 在内存，随机访问快，跳表指针开销可接受
- MySQL 在磁盘，B+ Tree 一个页存更多 key，减少 IO 次数
- 跳表实现简单，B+ Tree 为磁盘优化

## Q60：redis 的分布式锁有什么缺陷

### 基本实现

```go
SET lock:order:123 unique_value NX PX 30000
```

### 缺陷 1：锁过期释放，任务还没完成

```
客户端 A 获取锁（30s）→ 任务执行 40s → 锁过期 → 客户端 B 获取锁
→ A 和 B 同时持有锁！
```

**解决：** 看门狗（Watchdog）自动续期

```go
// Redisson 的看门狗机制
// 每 10 秒（lockWatchdogTimeout/3）检查锁是否还被持有
// 如果持有，自动续期 30 秒
```

### 缺陷 2：Redis 主从切换导致锁丢失

```
客户端 A 在主库获取锁 → 主库宕机 → 从库升为主库（锁数据还没同步）
→ 客户端 B 在新主库获取锁 → A 和 B 同时持有锁！
```

**解决：** RedLock 算法（多数派）

```
向 5 个独立 Redis 实例获取锁
超过半数（3 个）成功 → 锁获取成功
失败 → 向所有实例释放锁
```

### 缺陷 3：不可重入

**解决：** 用 Hash 记录锁持有者和重入次数

```
HSET lock:order:123 thread_id 1   // 首次
HINCRBY lock:order:123 thread_id 1 // 重入
HINCRBY lock:order:123 thread_id -1 // 释放
```

## Q61：一致性哈希算法

**普通哈希的问题：** 节点增减时，几乎所有 key 都要重新映射。

```
hash(key) % N → 节点变化后大量 key 迁移
```

**一致性哈希：** 将哈希值空间组织成环（0 ~ 2^32-1），节点和 key 都映射到环上，key 顺时针找最近的节点。

```
         0
        / \
   Node C   Node A
      |       |
   Key2     Key1
      |       |
   Node B ----
```

**虚拟节点：** 解决节点少时数据倾斜问题。

```
Node A → A#1, A#2, ..., A#200  （200 个虚拟节点）
Node B → B#1, B#2, ..., B#200
```

- 虚拟节点越多，分布越均匀
- 通常 100-200 个虚拟节点/实际节点
- 节点增减时只影响相邻虚拟节点的 key

## Q62：服务发现的实现原理

### 核心流程

```
服务注册：
  服务启动 → 向注册中心注册（IP:Port + 元数据）
  服务停止 → 向注册中心注销

服务发现：
  消费者启动 → 订阅注册中心
  消费者调用 → 从本地缓存获取服务列表 → 负载均衡选一个 → 调用

健康检查：
  注册中心定时心跳检测 → 不健康 → 剔除
```

### 常见实现

| 方案 | 一致性 | 特点 |
|------|--------|------|
| **etcd** | 强一致（Raft） | K8s 使用 |
| **Consul** | 强一致（Raft） | 内置健康检查 |
| **ZooKeeper** | 强一致（ZAB） | 重，运维复杂 |
| **Nacos** | CP 或 AP | 支持 CP/AP 切换 |
| **Eureka** | AP | 自我保护机制 |

## Q63：ThinkPHP 框架哪个操作用了观察者模式

**事件系统（Event）。**

ThinkPHP 的事件机制是典型的观察者模式：

```php
// 1. 定义事件
// 2. 注册监听器（观察者）
// 3. 触发事件 → 通知所有监听器

// 触发事件
event('UserRegistered', $user);

// 监听器（观察者）自动执行
class SendWelcomeEmail {
    public function handle($user) {
        // 发送欢迎邮件
    }
}
```

**观察者模式 vs 装饰模式 vs 职责链模式：**

| 模式 | 核心思想 | 典型应用 |
|------|---------|---------|
| **观察者** | 一对多通知，状态变化自动通知 | 事件系统、消息队列 |
| **装饰器** | 动态添加功能，不改变接口 | 中间件、流式 IO |
| **职责链** | 沿链传递，每个节点决定处理或传递 | 过滤器、审批流程 |

**装饰 vs 职责链：**
- 装饰器：每层都处理，层层包装增强
- 职责链：只有一个节点处理，其余传递

## Q64：同步/异步、阻塞/非阻塞

| | 阻塞 | 非阻塞 |
|---|---|---|
| **同步** | 调用后等待结果，当前线程被挂起 | 调用后立即返回，轮询检查结果 |
| **异步** | —（概念上不存在） | 调用后立即返回，结果由回调/事件通知 |

**举例：**

| 场景 | 模型 |
|------|------|
| 普通 read() | 同步阻塞 |
| read() + O_NONBLOCK + 轮询 | 同步非阻塞 |
| epoll + 回调 | 异步非阻塞 |
| io_uring | 真异步（内核完成通知） |

**Go 的网络 I/O：** 同步写法（`conn.Read()`），底层是异步非阻塞（netpoller + epoll），goroutine 挂起时不阻塞线程。

## Q65：链表和数组的区别

| | 数组 | 链表 |
|---|---|---|
| **内存** | 连续 | 分散（指针连接） |
| **访问** | O(1) 随机访问 | O(n) 顺序访问 |
| **插入/删除** | O(n) 需要移动元素 | O(1) 修改指针 |

| **大小** | 固定（或动态扩容拷贝） | 动态增长 |

## Q66：算法题简要思路

### LRU Cache（单链表版）

```
维护一个单链表 + map[key]*Node
Get: map 找到节点 → 删除节点 → 插入头部
Put: 已存在则删旧 → 插入头部 → 超容量则删尾部
```

### 两个栈实现队列

```
栈 A（入队栈）、栈 B（出队栈）
Push: 直接压入 A
Pop: B 为空则把 A 全部倒入 B，然后 B.Pop()
```

### 二分查找

```go
func binarySearch(arr []int, target int) int {
    lo, hi := 0, len(arr)-1
    for lo <= hi {
        mid := lo + (hi-lo)/2
        if arr[mid] == target {
            return mid
        } else if arr[mid] < target {
            lo = mid + 1
        } else {
            hi = mid - 1
        }
    }
    return -1
}
```

### 字符串转 int

```go
func atoi(s string) int {
    result := 0
    for _, c := range s {
        result = result*10 + int(c-'0')
    }
    return result
}
```

### 链表求和（不反转、不用栈）

```
1. 递归到链表末尾
2. 回溯时逐位相加，处理进位
3. 递归返回进位
```

### 回文子串（长度 >= 4）

```
中心扩展法：以每个字符/间隙为中心，向两边扩展
时间 O(n^2)，空间 O(1)
```

### 第 K 小的数

```
最小堆法：建大小为 K 的最大堆，遍历数组
或快速选择法：partition 找第 K 小
```
