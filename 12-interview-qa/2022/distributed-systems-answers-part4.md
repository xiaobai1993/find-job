## Q42：CAP 是什么，MySQL 主从是 CP 还是 AP

### CAP 定理

| 属性 | 含义 |
|------|------|
| **C（Consistency）** | 一致性：所有节点读到相同的数据 |
| **A（Availability）** | 可用性：每个请求都能得到响应（不保证最新） |
| **P（Partition tolerance）** | 分区容错：网络分区时系统仍能工作 |

**核心结论：** 网络分区不可避免，所以 P 必选。在 C 和 A 之间只能二选一。

- **CP 系统**：分区时牺牲可用性，保证一致性（ZooKeeper、etcd、HBase）
- **AP 系统**：分区时牺牲一致性，保证可用性（Eureka、Cassandra、DynamoDB）

### MySQL 主从复制

**MySQL 主从默认是 AP（异步复制）。**

| 复制模式 | 一致性 | 可用性 | 说明 |
|---------|--------|--------|------|
| **异步复制** | ❌ 弱 | ✅ 高 | 主库写入后不等从库，主库宕机可能丢数据 |
| **半同步复制** | ⚠️ 较强 | ⚠️ 中 | 至少一个从库确认收到 binlog 才返回 |
| **全同步复制** | ✅ 强 | ❌ 低 | 所有从库都写入才返回，性能差 |

**实际：** 大部分业务用异步复制（AP），对一致性要求高的用半同步。

## Q43：协程和线程哪种可能发生 CPU 切换，什么场景下会产生

**都会发生 CPU 切换，但机制不同。**

| | 线程 | 协程 |
|---|---|---|
| **切换触发** | OS 内核调度 | Go 运行时调度 |
| **切换场景** | 时间片用完、阻塞 IO、优先级抢占 | 系统调用、channel 阻塞、锁竞争、抢占信号 |
| **切换成本** | 高（进入内核态，切换寄存器/栈/页表） | 低（用户态，只切换寄存器/栈指针） |

**协程切换到线程的场景：**

```
goroutine G1 在 M1 上运行
  │
  ├── G1 发起系统调用（如文件 IO）
  │     ├── 阻塞型系统调用：M1 被 OS 阻塞
  │     │   → P 与 M1 分离，找新 M 继续运行其他 G
  │     │   → 系统调用返回后，G1 重新进入调度
  │     │
  │     └── 非阻塞型（如网络 IO）：通过 netpoller
  │         → G1 挂起，P 继续运行其他 G
  │         → IO 就绪后 G1 被 netpoller 唤醒
  │
  ├── G1 被 sysmon 信号抢占（运行 > 10ms）
  │     → G1 被挂起，P 运行其他 G
  │
  └── G1 在 channel/锁上阻塞
        → G1 状态设为 waiting，P 运行其他 G
```

**关键：** goroutine 的切换是用户态的，不涉及内核态切换（除非系统调用），所以成本极低。

## Q44：TCC 是什么，和 2PC、3PC 的区别

### 2PC（两阶段提交）

```
协调者                    参与者1         参与者2
   │                        │                │
   ├─── Prepare ──────────→│                │
   │                        │                │
   ├─── Prepare ──────────────────────────→│
   │                        │                │
   │←── Yes/No ───────────│                │
   │←── Yes/No ──────────────────────────│
   │                        │                │
   ├─── Commit/Rollback ──→│                │
   ├─── Commit/Rollback ──────────────────→│
```

**问题：** 同步阻塞、单点故障（协调者宕机）、数据不一致（部分提交部分回滚）

### 3PC（三阶段提交）

在 2PC 基础上增加 **CanCommit** 阶段 + 超时机制：

```
1. CanCommit → 询问是否可以提交（不锁资源）
2. PreCommit → 锁资源，准备提交
3. DoCommit  → 真正提交
```

**改善：** 减少了阻塞范围，但仍有网络分区导致的不一致问题。

### TCC（Try-Confirm-Cancel）

**业务层面的分布式事务，每个参与者实现三个方法：**

| 阶段 | 作用 | 示例（转账） |
|------|------|------------|
| **Try** | 预留资源/冻结 | 冻结转出账户 100 元 |
| **Confirm** | 确认操作 | 扣除冻结的 100 元，增加转入账户 100 元 |
| **Cancel** | 取消操作 | 解冻转出账户的 100 元 |

**对比：**

| | 2PC | 3PC | TCC |
|---|---|---|---|
| **层面** | 数据库/资源层 | 数据库/资源层 | **业务层** |
| **锁** | 数据库行锁 | 数据库行锁 | 业务锁（冻结） |
| **性能** | 低（长锁） | 中 | 高（短锁） |
| **侵入性** | 低 | 低 | 高（需实现三个方法） |
| **适用** | 单数据库 | 单数据库 | **跨服务/跨库** |
| **一致性** | 强一致 | 强一致 | 最终一致 |

**TCC 适用场景：** 跨服务转账、跨库订单+库存、支付+账务

## Q45：分布式事务一致性怎么保证

### 方案对比

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|---------|
| **2PC** | 强一致 | 低 | 中 | 单库多表 |
| **TCC** | 最终一致 | 高 | 高 | 跨服务资金操作 |
| **Saga** | 最终一致 | 高 | 中 | 长流程业务编排 |
| **本地消息表** | 最终一致 | 高 | 低 | 简单跨服务 |
| **可靠消息（RocketMQ）** | 最终一致 | 高 | 低 | 异步通知 |
| **最大努力通知** | 弱一致 | 最高 | 最低 | 第三方回调 |

### 订单+库存+预支付单的方案

**当前方案（常见）：** 分布式事务（Seata/自研 TCC）

**更合理的方案：** 本地消息表 + 补偿

```
1. 创建订单（本地事务，同时写入本地消息表）
2. 发送消息到 MQ → 扣减库存
3. 发送消息到 MQ → 创建预支付单
4. 消费者处理失败 → 重试
5. 定时任务扫描消息表 → 补偿未完成的消息
```

**弊端：** 引入分布式事务框架增加复杂度和性能开销，任何一环失败都要回滚。

**改进：** 改用事件驱动 + 最终一致，用本地消息表保证消息不丢，用补偿机制处理异常。

## Q46：ACID 是怎么实现的

| ACID | 实现机制 |
|------|---------|
| **A（原子性）** | undo log：事务失败时回滚所有修改 |
| **C（一致性）** | 由 A+I+D 共同保证，数据库约束（主键/外键/唯一索引） |
| **I（隔离性）** | MVCC + 锁（行锁/间隙锁/表锁） |
| **D（持久性）** | redo log + WAL：提交时 fsync redo log，崩溃后可恢复 |

```
事务提交的完整流程：
1. 修改数据页（buffer pool）
2. 写 undo log（为了回滚）
3. 写 redo log（prepare）
4. 写 binlog
5. 写 redo log（commit）
6. 返回客户端成功
7. 数据页由后台线程异步刷盘
```

## Q47：设计一个分布式限流器

### 常见算法

| 算法 | 特点 | 问题 |
|------|------|------|
| **固定窗口** | 简单，固定时间窗口计数 | 窗口边界突发 2 倍流量 |
| **滑动窗口** | 窾位窗口滑动，更平滑 | 实现稍复杂 |
| **漏桶** | 固定速率流出，平滑 | 无法应对突发流量 |
| **令牌桶** | 固定速率放令牌，允许突发 | 最常用 |

### 分布式令牌桶方案

```
                    Redis
                  ┌──────────┐
                  │ 令牌桶    │
  ──── 请求 ────→ │ Lua 脚本  │ ──── 通过/拒绝 ────→
                  │ 原子操作  │
                  └──────────┘

Lua 脚本逻辑（原子执行）：
1. 计算当前令牌数 = min(capacity, last_tokens + (now - last_refill) * rate)
2. 如果令牌数 >= 1 → 消耗 1 个令牌 → 返回通过
3. 如果令牌数 < 1 → 返回拒绝
4. 更新 last_refill 和 last_tokens
```

**Go 实现（单机）：**

```go
type RateLimiter struct {
    rate       float64   // 每秒放令牌数
    capacity   float64   // 桶容量
    tokens     float64   // 当前令牌数
    lastRefill time.Time // 上次填充时间
    mu         sync.Mutex
}

func (r *RateLimiter) Allow() bool {
    r.mu.Lock()
    defer r.mu.Unlock()

    now := time.Now()
    // 补充令牌
    r.tokens += now.Sub(r.lastRefill).Seconds() * r.rate
    if r.tokens > r.capacity {
        r.tokens = r.capacity
    }
    r.lastRefill = now

    if r.tokens >= 1 {
        r.tokens--
        return true
    }
    return false
}
```

## Q48：系统稳定性 — 服务降级、熔断、超时控制

### 熔断（Circuit Breaker）

```
     请求成功率高
  ┌──────────────┐
  │   Closed     │ ← 正常状态，请求通过
  │  (关闭/正常)  │
  └──────┬───────┘
         │ 错误率超阈值
         ↓
  ┌──────────────┐
  │    Open      │ ← 熔断状态，请求直接拒绝
  │  (打开/熔断)  │
  └──────┬───────┘
         │ 超时后放少量请求
         ↓
  ┌──────────────┐
  │  Half-Open   │ ← 半开状态，放少量请求试探
  │  (半开/试探)  │    成功 → 回到 Closed
  └──────────────┘    失败 → 回到 Open
```

### 降级（Degradation）

| 降级策略 | 示例 |
|---------|------|
| **返回默认值** | 推荐服务挂了，返回热门商品列表 |
| **返回缓存** | 库存服务挂了，返回上次缓存数据 |
| **关闭非核心功能** | 促销活动挂了，只展示基础价格 |
| **限流** | 排队机制，超出容量直接拒绝 |

### 超时控制

| 层级 | 超时设置 |
|------|---------|
| **HTTP Client** | `client.Timeout = 5s` |
| **RPC** | `context.WithTimeout(ctx, 3s)` |
| **数据库** | `max_execution_time` / `context` |
| **全链路** | 网关层设置总超时（如 10s） |

**原则：** 上游超时 > 下游超时，留出重试时间。

## Q49：10万 QPS 实时统计 top5 数据

### 方案：分片计数 + 堆

```
1. 分片计数
   ┌─── shard1 ───┐  ┌─── shard2 ───┐  ┌─── shardN ───┐
   │  key1: 1000  │  │  key1: 800   │  │  key1: 600   │
   │  key2: 900   │  │  key2: 700   │  │  key3: 500   │
   └──────────────┘  └──────────────┘  └──────────────┘

2. 汇总（定时，如每秒）
   合并所有分片 → {key1: 2400, key2: 1600, key3: 500, ...}

3. Top5（最小堆）
   用大小为 5 的最小堆，遍历合并后的数据
   O(N log 5) ≈ O(N)
```

**实现细节：**
- 用 `atomic.Int64` 或 `sync.Map` 分片计数，无锁写入
- 定时（每 1-5 秒）合并 + 计算 Top5
- 如果需要精确实时，用滑动窗口（如 1 分钟窗口，每秒一个桶）

## Q50：超时控制的手段有哪些

| 方式 | 适用场景 | 特点 |
|------|---------|------|
| `context.WithTimeout` | 几乎所有场景 | 推荐，可传播取消信号 |
| `context.WithDeadline` | 需要绝对时间点 | 设置截止时间 |
| `time.After` + `select` | 简单场景 | 无法取消底层操作 |
| HTTP Client `Timeout` | HTTP 请求 | 最简单 |
| `time.Sleep` + goroutine | 不推荐 | 无法精确控制 |
| `net.DialTimeout` | 网络连接 | 连接阶段超时 |
| `sql.DB.SetMaxOpenConns` | 数据库 | 间接限制等待时间 |

## Q51：如果不让用延迟消息队列实现订单 15 分钟未支付关单

### 方案 1：定时任务扫描

```sql
-- 每 5 分钟扫描
DELETE FROM orders
WHERE status = 'unpaid'
  AND created_at < NOW() - INTERVAL 15 MINUTE;
```

**问题：** 数据量大时慢，锁表，不够精确。

### 方案 2：时间轮（TimeWheel）

```go
// 15 分钟 = 900 秒，900 个槽
// 订单放入对应槽，时间轮转到时触发关单
type TimeWheel struct {
    slots    []map[string]*Order  // 900 个槽
    current  int                  // 当前槽位
    interval time.Duration        // 每槽 1 秒
}
```

**问题：** 内存占用大，重启丢失。

### 方案 3：Redis ZSET（推荐）

```go
// 下单时
zadd order:delay <now+15min> <orderID>

// 消费者轮询
while true:
    items = zrangebyscore order:delay 0 <now> LIMIT 0 100
    for each item:
        closeOrder(item)  // 关单
        zrem order:delay item
    sleep 1s
```

**优点：** 简单、持久化、精确、高性能。

### 方案 4：数据库 + Redis 组合

```
1. 下单时写入 Redis ZSET（延迟触发）
2. 消费者关单
3. 兜底：定时任务扫描数据库（防 Redis 丢失）
```
