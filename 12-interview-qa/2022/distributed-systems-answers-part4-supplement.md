# 补充笔记 — Q43 深度补充：阻塞 vs 非阻塞，同步 vs 异步

> 对应 `distributed-systems-answers-part4.md` 的 Q43

---

## 核心区别：谁被挂住了

**阻塞型系统调用** — OS 线程（M）被挂住。

```
G1 → syscall(read file)
         ↓
    OS 把 M1 挂起，M1 什么都干不了，只能等内核把数据准备好
```

**非阻塞型系统调用** — M 不被挂住，只有 G 被挂住。

```
G1 → syscall(read socket, O_NONBLOCK)
         ↓
    内核说"没数据，你先走，数据好了我通知你"
    G1 被挂起，但 M1 可以立刻去跑别的 G
```

## GMP 视角下的完整流程

### 场景 1：阻塞型（文件 IO）

```
P  ──→ M1(G1) ──→ 发起 read() 系统调用
                          │
                    OS 把 M1 挂起（M1 废了）
                          │
P 发现 M1 没了，立刻脱钩
P  ──→ M2(G2)   ← 找一个新的 M 继续跑
                          │
                    内核 IO 完成，M1 醒来
                    G1 重新排队等 P
```

**代价：** 可能需要创建新的 OS 线程（M），开销大。

### 场景 2：非阻塞型（网络 IO）

```
P  ──→ M1(G1) ──→ 发起 read() 系统调用
                          │
                    内核返回 EAGAIN（"没数据"）
                    G1 注册到 netpoller（epoll/kqueue）
                    G1 状态变为 waiting，M1 没有被挂起
                          │
P 还在 M1 上，继续跑 G2、G3...
                          │
                    网卡数据到了，内核通知 epoll
                    netpoller 把 G1 放回运行队列
M1 后续某个时刻拿到 G1 继续执行
```

**优势：** M1 全程没有被阻塞，一个线程可以服务大量网络连接。

## 同步/异步 vs 阻塞/非阻塞

| 概念 | 层面 | 含义 |
|------|------|------|
| **阻塞/非阻塞** | 内核机制 | 系统调用是否立刻返回 |
| **同步/异步** | 编程模型 | 你写代码时要不要处理回调/通知 |

Go 的核心设计目标：**对程序员屏蔽底层差异，统一呈现为同步写法。**

```go
// 两种 IO 写法一模一样，程序员无感知
data, _ := os.ReadFile("a.txt")   // 底层：阻塞型 syscall，M 被挂起
conn.Read(buf)                     // 底层：非阻塞型 syscall + netpoller，G 被挂起
```

Go runtime 在底层做了转换：

| 你写的代码 | 底层实现 |
|-----------|---------|
| `conn.Read()` "阻塞"等待 | G 挂起 → epoll 监听 → 数据到了唤醒 G |
| `os.ReadFile()` "阻塞"等待 | M 被 OS 挂起 → P 脱钩找新 M |

两者对程序员都是同步写法，不需要回调，不需要 async/await。

---

## 为什么文件 IO 不能用 netpoller 优化？

Linux 的 `epoll` **不支持普通磁盘文件**（内核认为文件始终 ready，没有真正的事件驱动）。

只有 socket、pipe、eventfd 等才支持 epoll。

所以 Go 对文件 IO 没有办法，只能让 M 真的挂起，靠 P 脱钩 + 新 M 来补偿。

> macOS/Windows 也有类似限制，这是 OS 层面的约束，不是 Go 的设计问题。

---

## 对比总结

| | 谁被挂住 | M 是否可用 | 需要新建 M | 典型场景 |
|--|---------|-----------|-----------|---------|
| **阻塞型** | M（OS 线程） | 不可用 | 可能需要 | 文件 IO、某些 syscall |
| **非阻塞型** | G（goroutine） | 可用 | 不需要 | 网络 IO（TCP/UDP） |

**一句话：** Go 不管底层是哪种机制，对你都呈现为同步代码，让你像写串行程序一样写并发。
