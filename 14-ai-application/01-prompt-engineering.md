# Prompt Engineering

## 1. Prompt 设计原则

### 清晰性（Clarity）

Prompt 应该指令明确，避免歧义。LLM 没有上下文推断能力，模糊的指令会产生不可预期的输出。

**反面示例：**
```
帮我处理一下这个数据
```

**正面示例：**
```
将以下 JSON 数据中的 price 字段从分转换为元，保留两位小数，
输出格式保持 JSON 不变：
{data}
```

### 具体性（Specificity）

越具体的指令，输出越可控。包含：输出格式、长度限制、语气风格、边界条件。

```
用 3-5 个要点总结以下文章，每个要点不超过 20 字，
语气客观中立，不要加入个人观点：
{article}
```

### 角色设定（Role Assignment）

给 LLM 设定角色，可以约束输出视角和专业度。

```
你是一位资深的支付系统架构师，有 10 年以上分布式系统经验。
请分析以下支付流程的潜在风险点：
{payment_flow}
```

> **面试要点**：角色设定本质上是在激活 LLM 参数空间中特定领域的知识分布，让输出更聚焦。

## 2. 基础模式

### Zero-shot

不提供示例，直接给出指令。依赖模型预训练知识。

```
将以下文本翻译为英文：
{text}
```

**适用场景**：简单任务、模型已有足够能力的场景。

### Few-shot

提供若干示例，让模型学习输入输出的模式。

```
判断以下交易是否异常：

交易：用户 A 转账 100 元给用户 B → 正常
交易：用户 C 在 1 分钟内向 5 个不同账户各转 5000 元 → 异常
交易：用户 D 每月 15 日向同一账户转 3000 元 → 正常
交易：用户 E 在凌晨 3 点向陌生账户转 50000 元 →
```

**适用场景**：
- 任务规则难以用自然语言精确描述
- 输出格式需要严格遵循特定模式
- 分类任务中类别边界模糊

**Few-shot 示例数量选择**：

| 示例数 | 效果 | 成本 |
|--------|------|------|
| 0 | 依赖指令质量 | 最低 |
| 1-2 | 简单模式学习 | 低 |
| 3-5 | 复杂模式学习 | 中等 |
| 5+ | 边际收益递减 | 高 |

### Chain-of-Thought (CoT)

让模型"展示思考过程"，逐步推理，显著提升逻辑推理和数学计算能力。

**方式一：直接要求**
```
请一步步思考以下问题：
一个商品原价 200 元，先打 8 折，再满 100 减 20，最终价格是多少？
```

**方式二：Few-shot + CoT**
```
Q: 商店有 23 个苹果，卖了 15 个，又进货 8 个，还有多少？
A: 初始有 23 个苹果。卖出 15 个后剩下 23-15=8 个。又进货 8 个，8+8=16 个。答案是 16。

Q: 商品原价 200 元，先打 8 折，再满 100 减 20，最终价格？
A:
```

> **面试要点**：CoT 的核心价值在于让模型的推理过程显式化，减少"跳步"导致的错误。在支付金额计算、风控规则推理等场景中特别有效。

### Tree-of-Thought (ToT)

CoT 的扩展，在推理过程中探索多条路径，通过评估选择最优路径。

```
在每一步推理时，生成 3 个可能的思考方向，
评估每个方向的可行性（1-5分），
选择得分最高的方向继续推理：

问题：设计一个支付系统的幂等方案
```

**适用场景**：复杂决策、创意生成、方案设计。

**四种基础模式对比**：

| 模式 | 推理方式 | Token 消耗 | 准确性 | 适用场景 |
|------|---------|-----------|--------|---------|
| Zero-shot | 直接输出 | 低 | 一般 | 简单任务 |
| Few-shot | 模式匹配 | 中 | 较好 | 格式化任务 |
| CoT | 线性推理 | 高 | 好 | 逻辑推理 |
| ToT | 树状探索 | 很高 | 最好 | 复杂决策 |

## 3. 进阶模式

### Self-Consistency

多次采样 CoT 推理路径，取多数结果作为最终答案。

```
# 步骤 1：生成多个推理路径（temperature > 0）
# 路径 A：... → 答案是 X
# 路径 B：... → 答案是 X
# 路径 C：... → 答案是 Y

# 步骤 2：多数投票
# X 出现 2 次，Y 出现 1 次 → 最终答案 X
```

**实现要点**：
- 需要 `temperature > 0`（通常 0.5-0.7）
- 采样次数通常 5-10 次
- 适合有明确正确答案的任务

### ReAct Prompting

将推理（Reasoning）和行动（Acting）交织执行，是 Agent 的核心 Prompt 模式。

```
问题：查询用户 U123 最近一笔交易的当前状态

思考 1：我需要先查询用户 U123 的交易记录
行动 1：调用 get_user_transactions(user_id="U123")

观察 1：最近一笔交易 TX456，状态为 PENDING，创建于 2024-01-15

思考 2：PENDING 状态可能是处理中，我需要查询交易详情确认
行动 2：调用 get_transaction_detail(tx_id="TX456")

观察 2：交易 TX456 银行返回码为 PROCESSING，预计 T+1 到账

思考 3：我已经获取了足够的信息来回答问题
回答：用户 U123 最近一笔交易 TX456 当前状态为处理中（PROCESSING），
银行正在处理，预计 T+1 工作日到账。
```

### Directional Stimulus Prompting

用"提示词"引导模型关注特定方面，而非直接给出完整指令。

```
请总结以下客户投诉内容。关注：退款金额和投诉原因。

投诉内容：我 1 月 10 号买了 299 的会员，结果发现跟宣传的完全不一样，
说好有专属客服，根本没人理我。要求全额退款！
```

> **面试要点**：Directional Stimulus 的核心思想是"引导而非命令"，在内容审核、情感分析等需要关注特定维度的任务中效果好。

## 4. 结构化输出

### JSON Mode

让模型输出合法 JSON。

**OpenAI**：
```json
{
  "response_format": { "type": "json_object" }
}
```

**Claude**：
```
请在 <json> 标签内输出 JSON 格式的结果。
```

### Function Calling / Tool Use

通过定义函数 schema，让模型输出结构化的函数调用。

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "query_payment_status",
        "description": "查询支付订单状态",
        "parameters": {
          "type": "object",
          "properties": {
            "order_id": {
              "type": "string",
              "description": "订单号"
            }
          },
          "required": ["order_id"]
        }
      }
    }
  ]
}
```

模型输出：
```json
{
  "tool_calls": [
    {
      "function": {
        "name": "query_payment_status",
        "arguments": "{\"order_id\": \"ORD123456\"}"
      }
    }
  ]
}
```

### Structured Output API

OpenAI 2024 年推出的功能，支持 JSON Schema 约束输出，保证 100% 符合 schema。

```json
{
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "payment_result",
      "schema": {
        "type": "object",
        "properties": {
          "status": { "enum": ["success", "failed", "pending"] },
          "amount": { "type": "number" },
          "error_code": { "type": ["string", "null"] }
        },
        "required": ["status", "amount"]
      }
    }
  }
}
```

**三种方式对比**：

| 方式 | 格式保证 | 灵活性 | 实现复杂度 |
|------|---------|--------|-----------|
| JSON Mode | 输出是合法 JSON | 高（schema 自由） | 低 |
| Function Calling | 函数参数结构化 | 中（函数定义约束） | 中 |
| Structured Output | 严格符合 Schema | 低（Schema 约束） | 中 |

> **面试要点**：生产环境中优先使用 Structured Output 或 Function Calling，它们提供了更强的格式保证，减少输出解析的异常处理。

## 5. Prompt 优化

### 迭代优化流程

```
1. 编写初始 Prompt
2. 准备测试集（覆盖边界 case）
3. 运行评估
4. 分析失败 case
5. 针对性修改 Prompt
6. 重复 3-5 直到满足准确率目标
```

**关键原则**：
- 每次只改一个变量，避免同时修改多处
- 维护测试集，防止回归
- 记录每次修改和效果变化

### A/B 测试

对同一任务使用不同 Prompt 版本，统计对比效果。

```
版本 A（角色设定）：
你是支付风控专家，判断以下交易是否有风险...

版本 B（规则列表）：
根据以下规则判断交易风险：
1. 金额超过 50000 元 → 高风险
2. 凌晨交易 → 中风险
...

对比指标：
- 准确率
- 召回率
- 平均响应 Token 数
- 延迟
```

### 自动 Prompt 优化（DSPy）

DSPy 是一个声明式框架，将 Prompt 视为可优化的程序。

```
核心概念：
- Signature：定义输入输出（如 "question -> answer"）
- Module：组合 Signature 和推理策略（如 ChainOfThought）
- Optimizer：根据训练数据自动优化 Prompt（如 BootstrapFewShot）
- Metric：评估指标

工作流程：
1. 定义任务 Signature
2. 选择 Module（CoT、ReAct 等）
3. 准备少量标注数据
4. 选择 Optimizer 和 Metric
5. 自动编译（compile）生成优化后的 Prompt
6. 在测试集上评估
```

> **面试要点**：DSPy 的核心创新是把 Prompt 工程从"手工艺"变成"工程化"，用优化器自动搜索最优 Prompt，适合需要大量 Prompt 调优的场景。

## 6. Prompt 缓存与成本优化

### Anthropic Prompt Caching

Claude API 支持缓存长 Prompt 的前缀，避免重复计算。

```
使用方式：在 messages 前添加 cache_control 标记

{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "以下是支付系统完整的 API 文档...（很长的系统 Prompt）",
      "cache_control": { "type": "ephemeral" }
    },
    {
      "type": "text",
      "text": "用户问题：{query}"
    }
  ]
}
```

**缓存规则**：
- 缓存最小 Token 数：1024（Claude 3.5 Sonnet）
- 缓存有效期：5 分钟（最后一次使用后）
- 缓存命中时输入成本降低 90%
- 写入缓存时输入成本增加 25%

### OpenAI Cached Response

OpenAI 自动缓存相同 Prompt 前缀，用户无需手动配置。

**规则**：
- 自动检测，无需代码修改
- 缓存命中时输入成本降低 50%
- 适用于 Prompt 前缀完全相同的请求

### 成本优化策略

| 策略 | 节省幅度 | 实现难度 |
|------|---------|---------|
| 系统 Prompt 缓存 | 50%-90% | 低 |
| 减少 Few-shot 示例数 | 20%-50% | 低 |
| 用小模型处理简单请求 | 60%-80% | 中 |
| 压缩上下文（摘要/裁剪） | 30%-60% | 中 |
| 批处理 API（Batch API） | 50% | 低 |
| Prompt 精简（去除冗余） | 10%-30% | 低 |

## 7. 面试高频题

### Q1: Few-shot 和 Zero-shot 分别适用什么场景？

**Zero-shot** 适用于简单、通用的任务（翻译、摘要、简单分类），模型已有足够能力。**Few-shot** 适用于输出格式要求严格、任务规则复杂或分类边界模糊的场景，通过示例明确预期。

### Q2: Chain-of-Thought 为什么能提升推理能力？

CoT 让模型的推理过程显式化，每一步的中间结果都可以被验证和修正。本质上，它将一个复杂的"跳步推理"分解为多个简单的"单步推理"，降低了每步的认知负荷，减少了错误累积。

### Q3: ReAct 和 CoT 的区别是什么？

CoT 是纯推理（Reasoning Only），模型只思考不执行动作。ReAct 将推理和行动交织，模型可以在推理过程中调用外部工具获取信息，形成"思考-行动-观察"循环。ReAct 是 Agent 的基础 Prompt 模式。

### Q4: 如何选择结构化输出的方式？

简单 JSON 输出用 JSON Mode；需要调用外部工具用 Function Calling；需要严格 Schema 约束用 Structured Output。生产环境推荐 Structured Output，它提供格式保证，减少解析异常。

### Q5: DSPy 解决了什么问题？

传统 Prompt 工程是手动的"试错"过程，不可复现、不可扩展。DSPy 将 Prompt 视为可优化的程序，用优化器自动搜索最优 Prompt，并保证在测试集上的表现，使 Prompt 工程从"手艺"变为"工程"。

### Q6: Prompt Caching 的原理和适用场景？

Prompt Caching 缓存 Attention 计算的中间结果（KV Cache），当相同前缀的 Prompt 再次请求时，直接复用缓存的 KV 计算结果，跳过前缀部分的 Attention 计算。适用于系统 Prompt 很长、对话轮次多的场景（如客服 Agent、知识库问答）。

### Q7: 如何评估 Prompt 的好坏？

核心指标：**准确率**（输出是否正确）、**一致性**（相同输入是否产生相同输出）、**鲁棒性**（边界 case 是否处理正确）、**效率**（Token 消耗和延迟）。建议维护标注测试集，用自动化评估流程量化效果。

### Q8: Self-Consistency 和 CoT 的关系？

Self-Consistency 是 CoT 的增强版。CoT 只生成一条推理路径，Self-Consistency 通过多次采样生成多条推理路径，然后多数投票选答案。它牺牲了效率（多次调用），但显著提升了准确性，尤其在数学推理等有唯一正确答案的任务上。

### Q9: 如何处理 Prompt 注入攻击？

主要防御手段：
1. **输入输出分离**：用特殊标记区分用户输入和系统指令
2. **输入过滤**：检测和转义可能的注入内容
3. **权限最小化**：限制模型可调用的工具和操作
4. **输出校验**：对模型输出做格式和内容验证
5. **多层防御**：结合规则过滤 + 模型检测

### Q10: Few-shot 示例的顺序会影响结果吗？

会。LLM 存在 **Recency Bias**（近因偏差），靠后的示例对输出影响更大。建议把最典型、最想学习的示例放在最后。同时注意示例的多样性，避免类别分布不均导致模型偏向某一类输出。

### Q11: 如何设计一个好的系统 Prompt？

关键要素：
1. **角色定义**：明确模型的身份和能力边界
2. **任务描述**：清晰说明模型需要做什么
3. **约束条件**：格式要求、长度限制、禁止行为
4. **知识注入**：领域知识、业务规则
5. **示例**：典型输入输出的示例（可选）
6. **错误处理**：遇到不确定或无法完成的任务时如何响应

### Q12: Prompt Engineering 的局限性是什么？

1. **无法突破模型能力上限**：Prompt 不能让模型做超出其能力的事
2. **不稳定**：同一 Prompt 在不同模型/版本上效果可能不同
3. **上下文窗口限制**：Prompt 长度受模型上下文窗口约束
4. **成本**：长 Prompt 增加输入 Token 成本
5. **不可替代 Fine-tuning**：需要大量领域知识注入时，Fine-tuning 更合适
