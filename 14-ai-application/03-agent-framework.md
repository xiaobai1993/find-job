# Agent 框架

## 1. Agent 核心概念

### 什么是 Agent

Agent 是一个能够自主感知环境、推理决策、执行行动并从结果中学习的 AI 系统。与普通 Chatbot 的核心区别：

| 维度 | Chatbot | Agent |
|------|---------|-------|
| 交互模式 | 单轮问答 | 多轮自主循环 |
| 工具使用 | 无 | 可调用外部工具 |
| 状态管理 | 无状态 | 有记忆和状态 |
| 目标达成 | 回答问题 | 完成任务 |
| 决策能力 | 被动响应 | 主动规划 |

### Agent 核心循环

```
感知（Perception）→ 推理（Reasoning）→ 行动（Action）→ 记忆（Memory）
        ↑                                              ↓
        ←←←←←←←←← 观察（Observation）←←←←←←←←←←←←←←
```

1. **感知**：接收用户输入、工具返回结果、环境变化
2. **推理**：分析当前状态，决定下一步行动
3. **行动**：调用工具、返回回答、执行操作
4. **记忆**：存储和检索历史信息
5. **观察**：获取行动结果，反馈到下一轮感知

> **面试要点**：Agent 的本质是 LLM 驱动的循环——LLM 作为"大脑"，在每一步决定调用什么工具、如何处理结果、是否继续。关键挑战是让这个循环可靠终止并产出正确结果。

## 2. ReAct 模式

### 核心思想

ReAct（Reasoning + Acting）将推理和行动交织执行，每一步先推理再行动，观察结果后继续推理。

### 执行流程

```
用户：查询订单 ORD123 的状态，如果失败则重新发起支付

Agent 思考：我需要先查询订单状态
Agent 行动：query_order(order_id="ORD123")

观察：订单状态为 FAILED，支付渠道返回 TIMEOUT

Agent 思考：订单支付失败，原因为超时，需要重新发起支付
Agent 行动：retry_payment(order_id="ORD123", channel="alipay")

观察：重新支付成功，新交易号 TX789

Agent 思考：已完成重新支付，可以向用户汇报结果
Agent 回答：订单 ORD123 原支付因超时失败，已通过支付宝重新发起支付，
         新交易号 TX789，支付成功。
```

### ReAct vs 纯推理 / 纯行动

| 模式 | 特点 | 问题 |
|------|------|------|
| 纯推理（CoT） | 只思考不行动 | 无法获取外部信息，可能基于错误前提推理 |
| 纯行动 | 直接行动不思考 | 行动缺乏推理，可能执行错误操作 |
| ReAct | 思考-行动-观察循环 | 平衡推理深度和行动效率 |

### 实现 Prompt 模板

```
你可以使用以下工具：
{tool_descriptions}

对于每个步骤，你需要：
1. Thought：分析当前情况，决定下一步
2. Action：选择一个工具执行（格式：工具名(参数)）
3. Observation：观察工具返回结果

重复以上步骤直到可以给出最终回答。

Question: {user_question}
```

## 3. Tool Use / Function Calling

### 工具定义

工具是 Agent 与外部世界交互的接口。每个工具需要明确定义：

```json
{
  "name": "query_payment_status",
  "description": "查询支付订单的当前状态。支持查询最近 90 天内的订单。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "订单号，格式为 ORD + 8位数字"
      },
      "include_refund": {
        "type": "boolean",
        "description": "是否同时查询退款信息",
        "default": false
      }
    },
    "required": ["order_id"]
  }
}
```

### 调用流程

```
1. LLM 分析用户意图
2. LLM 输出 tool_call（函数名 + 参数）
3. 应用层执行工具，获取结果
4. 将工具结果作为 observation 返回 LLM
5. LLM 继续推理或生成最终回答
```

### 工具设计原则

1. **单一职责**：每个工具做一件事，职责清晰
2. **参数明确**：类型、格式、范围都有描述
3. **幂等性**：相同参数多次调用结果一致（对查询类工具）
4. **错误处理**：工具内部处理异常，返回结构化错误信息
5. **返回值规范**：统一返回格式，包含状态码和描述

### 错误处理策略

```
工具执行成功：
  { "status": "success", "data": {...} }

工具执行失败：
  { "status": "error", "error_code": "TIMEOUT", "message": "支付渠道超时" }

参数校验失败：
  { "status": "invalid", "error_code": "INVALID_ORDER_ID", "message": "订单号格式错误" }
```

## 4. 规划策略

### Plan-and-Execute

先制定完整计划，再逐步执行。

```
任务：为用户处理退款

计划：
1. 查询订单状态，确认是否可退款
2. 检查退款政策（是否超过退款期限）
3. 调用退款接口
4. 通知用户退款结果

执行：
Step 1: query_order("ORD123") → 状态 DELIVERED，可退款 ✓
Step 2: check_refund_policy("ORD123") → 在退款期限内 ✓
Step 3: process_refund("ORD123", amount=299) → 退款成功
Step 4: notify_user("user@email.com", "退款299元已处理") → 通知已发送
```

**优点**：全局视角，可以优化执行顺序
**缺点**：计划可能基于不完整信息，需要动态调整

### Tree of Planning

在规划阶段探索多条路径，评估后选择最优路径。

```
                    退款请求
                   /        \
            退到原支付方式    退到余额
            /        \         |
      全额退款   部分退款   全额退款
        ✓           ✗         ✓
     (最优)     (不符合政策)  (次优)
```

### Reflexion

Agent 执行后自我反思，发现错误则重新规划。

```
1. 执行任务
2. 自我评估：结果是否正确？是否有遗漏？
3. 如果不满意，记录反思内容
4. 基于反思重新规划执行
5. 重复直到满意或达到最大尝试次数
```

### 策略对比

| 策略 | 规划方式 | 适用场景 | 复杂度 |
|------|---------|---------|--------|
| ReAct | 逐步推理行动 | 交互式、信息逐步获取 | 低 |
| Plan-and-Execute | 先规划后执行 | 多步骤确定性任务 | 中 |
| Tree of Planning | 多路径探索 | 复杂决策、方案选择 | 高 |
| Reflexion | 执行+反思+重试 | 需要自我纠正的任务 | 高 |

## 5. 记忆机制

### 记忆类型

| 类型 | 存储位置 | 持续时间 | 容量 | 示例 |
|------|---------|---------|------|------|
| 短期记忆 | 对话上下文 | 单次会话 | 上下文窗口限制 | 当前对话历史 |
| 长期记忆 | 向量数据库 | 跨会话持久 | 无限 | 用户偏好、历史交互 |
| 工作记忆 | 当前任务状态 | 单次任务 | 内存 | 中间计算结果 |

### 短期记忆管理

对话上下文会随轮次增长，需要管理以避免超出上下文窗口。

**策略**：
1. **滑动窗口**：只保留最近 N 轮对话
2. **摘要压缩**：用 LLM 对早期对话做摘要，用摘要替代原文
3. **优先级排序**：根据相关性保留最重要的上下文

### 长期记忆实现

```
用户交互 → 提取关键信息 → Embedding → 存入向量数据库

需要回忆时：
  Query → 检索相关记忆 → 注入上下文
```

**存储内容**：
- 用户偏好（语言、格式、习惯）
- 历史任务摘要
- 学到的规则和知识
- 用户画像信息

### 对话摘要

```
原始对话（10 轮）：
  用户：帮我查订单 ORD123
  Agent：订单状态为已发货...
  用户：物流信息呢？
  Agent：顺丰 SF123456...
  ...

摘要后：
  [摘要] 用户查询了订单 ORD123 的状态和物流信息，订单已通过顺丰发货，
  单号 SF123456，预计明日到达。用户对配送时间表示满意。
```

> **面试要点**：记忆机制是 Agent "持续智能"的关键。短期记忆解决上下文窗口限制，长期记忆解决跨会话知识积累。生产中需要平衡记忆量和检索精度。

## 6. Multi-Agent 架构

### 协作模式

**顺序模式（Sequential）**：
```
Agent A → Agent B → Agent C
需求分析 → 代码编写 → 代码审查
```

**并行模式（Parallel）**：
```
       → Agent B (前端) →
Agent A                    → Agent E (集成)
       → Agent C (后端) →
       → Agent D (测试) →
```

**层级模式（Hierarchical）**：
```
        Supervisor Agent
       /      |       \
  Worker A  Worker B  Worker C
```
Supervisor 负责任务分解和分配，Worker 负责具体执行。

**辩论模式（Debate）**：
```
Agent A ←→ Agent B ←→ Agent C
  提出方案   反驳/改进   补充/验证
```
多个 Agent 对同一问题辩论，促进更全面的思考。

### 通信机制

1. **共享状态**：Agent 读写共享的工作空间（如黑板模式）
2. **消息传递**：Agent 之间直接发送消息
3. **事件驱动**：Agent 发布/订阅事件

### 任务分配策略

- **静态分配**：根据 Agent 角色预先分配任务类型
- **动态分配**：Supervisor 根据任务特征和 Agent 能力动态分配
- **竞标机制**：Agent 自主竞标任务

### Multi-Agent vs 单 Agent

| 维度 | 单 Agent | Multi-Agent |
|------|---------|-------------|
| 复杂度 | 低 | 高 |
| 可靠性 | 单点 | 分布式 |
| 上下文 | 共享完整上下文 | 需要通信同步 |
| 适合任务 | 简单、线性任务 | 复杂、多角色任务 |
| 调试难度 | 低 | 高 |

> **面试要点**：不要过度设计 Multi-Agent。大多数任务单 Agent + 好的工具定义就能解决。只有当任务天然涉及多个不同角色/专业领域时，Multi-Agent 才有优势。

## 7. Agent 框架对比

| 框架 | 架构模式 | 核心特点 | Multi-Agent | 工具集成 | 适用场景 | 语言 |
|------|---------|---------|------------|---------|---------|------|
| LangGraph | 图状态机 | 灵活的状态图定义 | 支持 | 丰富 | 复杂工作流 | Python/JS |
| CrewAI | 角色协作 | 角色定义直观 | 原生支持 | 丰富 | 团队协作场景 | Python |
| AutoGen | 对话驱动 | Agent 间对话通信 | 原生支持 | 丰富 | 研究/原型 | Python |
| OpenAI Agents SDK | 轻量 | OpenAI 生态原生 | 支持 | OpenAI 原生 | OpenAI 用户 | Python |
| Agno | 轻量高性能 | 极简设计 | 支持 | 丰富 | 快速开发 | Python |

### LangGraph

基于图的有状态 Agent 框架，将 Agent 执行流程建模为状态图。

```
核心概念：
- StateGraph：状态图，节点是函数，边是条件跳转
- State：共享状态，在节点间传递
- Node：状态处理函数
- Edge：状态转移条件

特点：
+ 执行流程可视化、可控
+ 支持循环、分支、并行
+ 内置持久化和人工介入
- 学习曲线较陡
```

### CrewAI

以"团队"为单位组织 Agent，每个 Agent 有角色、目标和背景。

```
核心概念：
- Agent：角色 + 目标 + 背景故事 + 工具
- Task：描述 + 预期输出 + 负责Agent
- Crew：Agent + Task + 流程（顺序/层级）

特点：
+ 角色定义直观
+ 快速搭建多 Agent 系统
- 灵活度不如 LangGraph
```

### OpenAI Agents SDK

OpenAI 官方的轻量 Agent 框架。

```
核心概念：
- Agent：指令 + 工具 + handoff
- Handoff：Agent 间任务交接
- Guardrails：输入/输出护栏

特点：
+ OpenAI 生态原生集成
+ 轻量简洁
- 绑定 OpenAI 生态
```

## 8. Agent 可靠性

### 幻觉问题

Agent 可能在推理过程中产生错误信息。

**应对策略**：
1. **基于事实推理**：强制 Agent 只基于工具返回结果回答
2. **自我验证**：让 Agent 验证自己的推理是否合理
3. **多路径验证**：独立推理多次，取一致结果
4. **引用追溯**：要求 Agent 标注信息来源

### 工具调用错误处理

```
1. 参数校验：执行前验证参数格式和范围
2. 超时处理：设置工具执行超时，超时后重试或降级
3. 重试策略：对可重试错误（网络超时、限流）自动重试
4. 降级方案：工具不可用时切换备选方案
5. 错误传播：将工具错误信息返回 LLM，让其决定下一步
```

### 护栏机制（Guardrails）

在输入和输出层面设置安全检查。

```
输入护栏：
- 检测 Prompt 注入
- 过滤敏感信息
- 验证输入合法性

输出护栏：
- 检查输出格式
- 过滤敏感内容
- 事实性校验
- 操作权限校验
```

### 人工介入（Human-in-the-loop）

关键操作前请求人工确认。

```
设计原则：
1. 高风险操作必须人工确认（支付、删除、发布）
2. 低风险操作可自动执行
3. 提供明确的确认/拒绝接口
4. 记录人工干预的原因
```

## 9. 面试高频题

### Q1: Agent 和 Chatbot 的本质区别？

Agent 是目标驱动的自主循环系统，能够使用工具、维护状态、规划执行；Chatbot 是被动响应的问答系统。Agent 的核心特征是"自主决策 + 工具使用 + 状态管理"。

### Q2: ReAct 模式的优缺点？

优点：推理和行动交织，每步都有推理依据，可解释性强。缺点：线性执行可能效率低，每步都调用 LLM 增加延迟和成本，长链路容易累积错误。

### Q3: 如何设计 Agent 的工具？

核心原则：单一职责、参数描述清晰、返回格式规范、幂等性（查询类）、错误处理完善。工具粒度要适中——太粗灵活性差，太细编排复杂。建议从 5-10 个核心工具开始，按需扩展。

### Q4: 什么时候需要 Multi-Agent？

当任务天然涉及多个不同专业领域（如产品+设计+开发），或需要并行处理子任务，或需要多视角验证时。大多数简单任务单 Agent + 好的工具定义就够了，不要过度设计。

### Q5: Agent 的记忆机制怎么设计？

短期记忆：对话上下文管理，用滑动窗口+摘要压缩控制长度。长期记忆：关键信息存向量数据库，需要时检索注入上下文。工作记忆：当前任务的中间状态。关键是平衡记忆量和检索精度——存太多检索不准，存太少信息不足。

### Q6: 如何提高 Agent 的可靠性？

多层防御：输入护栏（过滤注入/敏感信息）→ 工具层（参数校验+超时+重试）→ 输出护栏（格式校验+内容过滤）→ 人工介入（高风险操作确认）+ 可观测性（日志+追踪）。

### Q7: LangGraph 和 CrewAI 怎么选？

需要精细控制执行流程（循环、条件分支、并行）选 LangGraph；需要快速搭建多角色协作系统选 CrewAI。LangGraph 更灵活但复杂，CrewAI 更简单但灵活度有限。

### Q8: Agent 如何避免无限循环？

1. 设置最大迭代次数（如 10 次）
2. 设置总超时时间
3. 检测重复行动（连续 3 次相同工具调用则终止）
4. 设计"退出"工具，让 Agent 主动判断任务无法完成

### Q9: Function Calling 的执行流程？

LLM 输出 tool_call（函数名+参数）→ 应用层解析并执行工具 → 将结果作为 tool_result 返回 → LLM 继续推理。关键是 LLM 不直接执行工具，应用层负责执行和安全校验。

### Q10: Agent 在生产环境的主要挑战？

1. **可靠性**：LLM 输出不确定，需要护栏和重试
2. **延迟**：多轮 LLM 调用 + 工具执行，端到端延迟高
3. **成本**：每步都消耗 Token，长链路成本高
4. **可观测性**：链路长，难以定位问题
5. **安全性**：工具权限控制、Prompt 注入防御
6. **测试**：LLM 输出不确定，难以编写确定性测试
