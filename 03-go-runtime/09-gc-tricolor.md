# Go GC 三色标记与垃圾回收深度解析

---

## 一、GC 演进历史（面试必问！）

Go 的 GC 经历了五次重大迭代，每次都是革命性的性能提升，版本差异是面试高频考点：

| Go 版本 | 时间 | GC 算法 | STW 停顿 | 核心特性 |
|---------|------|---------|----------|---------|
| **Go 1.0** | 2012 | 串行标记清除 | 几百 ms ~ 几秒 | 单线程 GC，所有 G 都停 |
| **Go 1.3** | 2014 | 并行标记清除 | 几十 ~ 几百 ms | 标记并行，清除并行 |
| **Go 1.5** | 2015 | 三色标记 + 插入写屏障 | 10 ~ 50 ms | 并发标记！革命性改进！ |
| **Go 1.8** | 2017 | 三色标记 + 混合写屏障 | 0.5 ~ 2 ms | 删除屏障 + 插入屏障，STW 降低 10 倍！ |
| **Go 1.12** | 2019 | 不变 | 0.1 ~ 1 ms | 栈扫描优化，大页支持 |
| **Go 1.14** | 2020 | 不变 | 几十 ~ 几百 us | 页分配器优化，异步抢占 |
| **Go 1.19** | 2022 | 不变 | 进一步降低 | 内存清理软上限，调优参数 |

**面试高频追问：**
> 问：Go 1.5 到 Go 1.8 STW 从 10ms 降到了 1ms，做了什么？
> 答：从插入写屏障改成了**混合写屏障**，不需要重新扫描栈了，STW 只需要几百微秒！

---

## 二、GC 核心概念

### 1. 什么是垃圾？

**无法从根对象到达的对象就是垃圾。**

**根对象（Root Set）包括：**
1. **栈上的对象**：每个 goroutine 的栈
2. **全局变量**：.data .bss 段的变量
3. **寄存器**：寄存器里的指针
4. **finalizer 队列**：有 finalizer 的对象
5. **span 缓存**：mcache 里的对象

GC 从根对象出发，遍历所有能到达的对象，没遍历到的就是垃圾，回收掉。

---

### 2. 标记清除算法（Mark and Sweep）

最基础的 GC 算法，分两个阶段：

**阶段 1：标记（Mark）**
- 从根对象出发，遍历所有能到达的对象
- 标记为"存活"

**阶段 2：清除（Sweep）**
- 遍历整个堆
- 把没标记的对象回收，放到空闲列表

**问题：**
- 标记和清除都需要 STW，整个程序都停了
- 堆越大，STW 越长，Go 1.4 之前就是这样，几秒的 STW 很常见

---

## 三、三色标记算法详解（Go 1.5+）

为了实现**并发标记**（不 STW 就能标记），Go 1.5 引入了三色标记 + 写屏障。

### 1. 三种颜色的定义

| 颜色 | 含义 |
|------|------|
| **白色** | 初始状态，还没扫描到，GC 结束后白色就是垃圾 |
| **灰色** | 已经扫描到了，但是它引用的对象还没处理完（中间状态） |
| **黑色** | 已经扫描完了，它引用的所有对象都处理了，安全 |

---

### 2. 标记过程

```
初始状态：所有对象都是白色
        A(白)   B(白)   C(白)   D(白)
          ↓
        E(白)   F(白)

第一步：把根对象（A, B）涂成灰色，放到灰色队列
        A(灰)   B(灰)   C(白)   D(白)
          ↓
        E(白)   F(白)

第二步：从灰色队列拿一个 A，涂成黑色，把它引用的 E 涂成灰色
        A(黑)   B(灰)   C(白)   D(白)
          ↓
        E(灰)   F(白)

第三步：从灰色队列拿 B，涂成黑色，把它引用的 F 涂成灰色
        A(黑)   B(黑)   C(白)   D(白)
          ↓
        E(灰)   F(灰)

第四步：E 和 F 没有引用其他对象，涂成黑色
        A(黑)   B(黑)   C(白)   D(白)
          ↓
        E(黑)   F(黑)

第五步：灰色队列为空，标记结束
        白色的 C、D 就是垃圾，回收！
```

---

### 3. 并发标记的问题：三色不变性被破坏

**并发标记的意思是：标记的时候，用户代码（mutator）还在跑！**

用户代码可能修改对象引用，导致下面的情况发生：

```
标记到一半：
        A(黑)   B(灰)
          ↓
        E(白)

用户代码修改了引用：
B 不再引用 E 了，A 开始引用 E
        A(黑) ←──┐
        B(灰)     │
                E(白)
```

**问题来了：**
- A 已经是黑色了，不会再扫描它了
- E 是白色，但是 A 现在引用了 E
- E 实际上是存活的，但 GC 结束会把它当成垃圾回收掉！

**这就是著名的"悬挂指针"问题！**

---

## 四、写屏障（Write Barrier）

为了解决上面的问题，需要**写屏障**。

写屏障就是：**用户代码修改对象引用的时候，会触发一小段 GC 的代码，保证三色不变性不被破坏。**

Go 历史上有三种写屏障：

---

### 1. 插入写屏障（Go 1.5 ~ Go 1.7）

**规则：** 当一个对象 A 引用对象 B 的时候，把 B 涂成灰色。

```go
// 伪代码
func writePointer(slot *uintptr, ptr uintptr) {
    // 把新引用的对象涂成灰色
    shade(ptr)
    // 真正的赋值
    *slot = ptr
}
```

**回到刚才的问题：**
```
A(黑) 要引用 E(白)，触发写屏障
写屏障把 E 涂成灰色！
        A(黑) ←──┐
        B(灰)     │
                E(灰) ← 变成灰色了！
```

**效果：** E 变成灰色了，一定会被扫描到，不会被误回收。

**插入写屏障的问题：栈上的引用怎么办？**
- 栈是高频修改的地方，每个赋值都插写屏障性能太差了
- Go 的做法是：**栈上不开启写屏障！**
- 但是栈上的引用修改可能破坏三色不变性
- **解决办法：GC 标记结束后，STW，把所有 goroutine 的栈重新扫描一遍！**

**这就是 Go 1.5 ~ 1.7 STW 还是有 10~50ms 的原因：重新扫描栈！**

---

### 2. 删除写屏障

另一种思路：删除引用的时候做处理。

**规则：** 当对象 B 不再引用对象 E 的时候，把 E 涂成灰色。

```go
// 伪代码
func deletePointer(oldPtr uintptr) {
    shade(oldPtr) // 被删除的引用涂成灰色
}
```

**也能解决问题，但是有另一个问题：**
- 保守，会多标记很多对象
- 产生很多"浮动垃圾"（本来可以回收的被标记成存活）

---

### 3. 混合写屏障（Go 1.8+，革命性！）

**Go 1.8 把两种写屏障结合起来，发明了混合写屏障！**

**规则（超级重要，面试必问）：**
1. **GC 开始的时候，把当前所有 goroutine 的栈全部扫描一遍，全部涂黑**
2. **之后栈上新建的对象，全部都是黑色**
3. **插入新引用的时候，把新引用的对象涂灰**
4. **删除旧引用的时候，把旧引用的对象涂灰**

**一句话总结：栈变黑，插入涂灰，删除也涂灰！**

---

### 4. 混合写屏障为什么牛逼？

**最大的好处：不需要重新扫描栈了！**

| 特性 | 插入写屏障（Go 1.5~1.7） | 混合写屏障（Go 1.8+） |
|------|--------------------------|-----------------------|
| 重新扫描栈 | ✅ 需要，STW 几十 ms | ❌ 不需要！ |
| 典型 STW | 10 ~ 50 ms | 0.5 ~ 2 ms |
| 性能提升 | 基准 | 10 ~ 50 倍！ |

**这就是 Go 1.8 STW 一下子从几十毫秒降到几百微秒的原因！**

---

## 五、GC 完整流程（Go 1.8+）

一次完整的 GC 分 4 个阶段：

---

### 阶段 1：GC 开始，STW，开启写屏障

```
STW 1：约 10 ~ 100 us

做的事情：
1. 停止所有 goroutine
2. 开启混合写屏障
3. 扫描所有 goroutine 的栈，把栈上所有对象全部涂黑（！）
4. 把根对象（全局变量等）全部涂成灰色，放入灰色队列
```

**这个阶段的 STW 很短，因为只是扫栈，几微秒到几百微秒。**

---

### 阶段 2：并发标记

```
无 STW！和用户代码并行跑！

做的事情：
1. 专门的 GC worker goroutine 从灰色队列拿对象
2. 把对象涂黑，把它引用的对象涂灰
3. 一直循环，直到灰色队列为空
4. 和用户代码并行跑，完全不影响！
```

**这是 Go GC 最牛逼的地方：标记阶段 99% 的时间都是并发的，几乎不 STW！**

---

### 阶段 3：标记结束，STW，收尾

```
STW 2：约 100 ~ 500 us

做的事情：
1. 停止所有 goroutine
2. 关闭写屏障
3. 做一些清理工作
4. 处理剩下的根对象
```

**这就是 Go GC 主要的 STW，一般几百微秒，几乎感知不到！**

---

### 阶段 4：并发清除

```
无 STW！和用户代码并行跑！

做的事情：
1. 遍历整个堆
2. 把白色对象回收，放到 mcache 的空闲列表
3. 后台慢慢清，用户代码完全不感知
```

---

### 总结：两次 STW，都很短！

| STW 阶段 | 作用 | 典型耗时 |
|----------|------|----------|
| 第一次 | 开启写屏障，扫描栈涂黑 | 10 ~ 100 us |
| 第二次 | 关闭写屏障，收尾 | 100 ~ 500 us |

**总 STW：0.1 ~ 0.6 ms！几乎感知不到！**

## 六、GC 触发时机

什么时候会触发一次 GC？三个条件满足任意一个：

| 触发条件 | 说明 |
|----------|------|
| **内存阈值** | 堆内存达到上次 GC 结束时的 2 倍（默认 GOGC=100） |
| **时间阈值** | 超过 2 分钟没 GC 了，强制 GC 一次 |
| **手动触发** | 调用 runtime.GC() |

**例子：**
- 上次 GC 结束时堆大小是 128MB
- 堆涨到 256MB 的时候，自动触发下一次 GC

## 七、GC 调优技巧（支付业务必看！）

### 1. 调整 GOGC 值

```bash
# 默认为 100，表示 100%，涨到 2 倍触发
# 改成 200，表示涨到 3 倍触发，GC 频率降低一半，内存占用升高
export GOGC=200

# 改成 50，表示涨到 1.5 倍触发，GC 频率升高，内存占用降低
export GOGC=50
```

**支付业务最佳实践：**
- 延迟敏感，内存够 → GOGC 调大（200~500），减少 GC 频率
- 内存紧张 → GOGC 调小（50），GC 更频繁，内存占用低

---

### 2. Go 1.19+ 软内存限制 GOMEMLIMIT

Go 1.19 新增的革命性特性！**再也不用担心 OOM 了！**

```bash
# 设置 Go runtime 最多用 1GB 内存
export GOMEMLIMIT=1GiB
```

**工作原理：**
- 超过软限制后，GC 频率会自动升高，尽量把内存控制在限制内
- 不是硬限制，真不够还是会 OOM，但概率大大降低
- 容器环境神器！再也不会因为 GC 不及时导致 OOM 了！

**支付业务必开！容器环境一定要设 GOMEMLIMIT 为 limit 的 90%！**

---

### 3. 减少对象分配

最好的 GC 优化就是：**少分配对象！**

| 优化手段 | 效果 |
|----------|------|
| **sync.Pool 复用对象** | 减少 50%+ 的小对象分配 |
| **预先分配 slice 容量** | 避免 slice 多次扩容 |
| **返回值用值不用指针** | 小对象在栈上分配，不进堆，不需要 GC |
| **map 预分配** | 避免 map 扩容拷贝 |

**支付业务黄金法则：**
> 少分配 = 少 GC = 低延迟 = 高吞吐

---

### 4. 避免大对象分配

- 大于 32KB 的对象直接从 mheap 分配，不经过 P 的本地缓存
- 分配速度慢，还容易造成内存碎片
- 大对象池化复用

## 八、七个生产级 GC 大坑（90% 的人踩过）

### 坑 1：GC 助手 goroutine 占满 CPU

高并发下，GC 标记的时候会启动 GOMAXPROCS 个 GC worker，占满所有 CPU，业务 goroutine 拿不到 CPU，延迟飙升。

**现象：** p99 延迟突然飙升几百 ms，CPU 100%，GC 日志 mark 阶段很长。

**解决：**
- Go 1.19+ 已经优化了 GC 助手的调度
- 调大 GOGC，减少 GC 频率

---

### 坑 2：大量小对象导致 GC 标记时间长

1000 万个小对象，标记就要遍历 1000 万次，mark 阶段很长。

**解决：**
- 对象池化复用
- 用数组/结构体代替 map，减少指针数量
- Go 1.19+ 有 mark 优化

---

### 坑 3：finalizer 导致对象无法回收

```go
// ❌ 给对象加 finalizer，会导致对象至少活过一轮 GC！
runtime.SetFinalizer(obj, func(obj *Obj) {
    // 清理资源
})
```

**问题：**
- 有 finalizer 的对象，第一次 GC 不会回收，只会把 finalizer 丢到一个 goroutine 去跑
- 下一轮 GC 才会真正回收
- 至少多活一个 GC 周期

**解决：**
- 非必要不要用 finalizer
- 用完手动调用清理方法

---

### 坑 4：goroutine 泄漏导致内存泄漏

G 本身占几 KB 栈，G 泄漏了，栈上引用的所有对象都没法回收，内存持续上涨。

**排查：** pprof goroutine profile。

---

### 坑 5：time.Ticker 没 Stop 导致泄漏

```go
// ❌ ticker 没 Stop，永远不会回收！
for range time.Tick(1 * time.Second) {
    // ...
}
```

**每个 time.Ticker 背后都有一个 goroutine 在跑，泄漏了就永远占着！**

**解决：** 用完一定要 Stop！

```go
ticker := time.NewTicker(1 * time.Second)
defer ticker.Stop() // ✅ 一定要 Stop！
for range ticker.C {
    // ...
}
```

---

### 坑 6：GOGC 太大导致 OOM

容器环境把 GOGC 设成 500，GC 频率太低，内存涨到容器 limit 了还没触发 GC，直接 OOM kill。

**解决：**
- Go 1.19+ 用 GOMEMLIMIT！
- 老版本 GOGC 不要设太大

---

### 坑 7：手动调用 runtime.GC()

没事不要手动调 GC！会强制触发 STW，打断正常业务流程。

**只在两种情况用：**
1. 压测基准测试，控制变量
2. 内存很闲的时候手动触发一下，避免高峰期 GC

---

## 九、Go 1.19+ GC 新特性（面试加分项！）

### 1. GOMEMLIMIT 软内存限制

前面讲过了，容器环境神器，避免 OOM。

---

### 2. GC 内存清扫软上限

Go 1.19 之前：GC mark 结束后，一次性把所有垃圾全部清掉，CPU 突然飙高。

Go 1.19+：清扫阶段做 CPU 限流，最多用 50% CPU，避免清扫时打满 CPU 影响业务。

---

### 3. 大页支持（THP）

GC 扫描大页的时候更快，TLB miss 减少，标记速度提升 10~20%。

---

### 4. 页分配器优化

Go 1.14 重写了页分配器，大对象分配速度提升很多。

## 十、GC 问题排查方法

### 1. 看 GC 日志

```bash
# 开启 GC 日志
export GODEBUG=gctrace=1

# 运行程序
./your-app
```

**GC 日志格式：**
```
gc 12 @25.125s 0%: 0.018+1.2+0.083 ms clock, 0.14+2.5/1.0/0+0.66 ms cpu, 4->4->1 MB, 5 MB goal, 8 P
```

**解读：**
- `gc 12`：第 12 次 GC
- `@25.125s`：程序启动 25.125 秒
- `0%`：GC 占总 CPU 的比例
- `0.018+1.2+0.083 ms`：STW1 + 并发标记 + STW2，三个阶段耗时
- `4->4->1 MB`：GC 开始堆大小 -> GC 结束堆大小 -> 存活对象大小
- `5 MB goal`：本次 GC 目标堆大小
- `8 P`：P 的数量

---

### 2. pprof 排查

```go
// 启动 pprof
import _ "net/http/pprof"

go func() {
    http.ListenAndServe(":6060", nil)
}()
```

**常用命令：**
```bash
# 看堆内存，找哪些对象占的多
go tool pprof http://localhost:6060/debug/pprof/heap

# 看 goroutine 泄漏
go tool pprof http://localhost:6060/debug/pprof/goroutine

# 看 GC 标记时间
curl http://localhost:6060/debug/pprof/block?debug=1
```

## 十一、面试高频问答（100% 会问！）

| 问题 | 答案 |
|------|------|
| Go GC 用的什么算法？ | 三色标记 + 混合写屏障 + 并发标记清除。 |
| 三色标记三种颜色的含义？ | 白色：没扫描，最后是垃圾；灰色：扫描了但引用没处理完；黑色：扫描完成。 |
| 插入写屏障 vs 混合写屏障的区别？ | 插入写屏障只在插入时涂灰，结束后需要重新扫描栈，STW 几十 ms；混合写屏障开始就把所有栈涂黑，插入删除都涂灰，不需要重新扫描栈，STW 几百 us。 |
| 混合写屏障的四个规则？ | 1. GC 开始把所有栈涂黑；2. 之后栈上新对象都是黑色；3. 插入引用涂灰；4. 删除引用涂灰。 |
| GC 有几次 STW？分别做什么？ | 两次。第一次：开启写屏障，扫描所有栈涂黑；第二次：关闭写屏障，收尾。 |
| Go 1.8 STW 为什么比 Go 1.7 快 10 倍？ | 混合写屏障不需要重新扫描栈了，STW 从几十 ms 降到几百 us。 |
| GC 触发条件？ | 内存涨到上次 2 倍（GOGC）、2 分钟没 GC、手动触发。 |
| GOGC 是什么？怎么调优？ | GC 触发阈值，默认 100=2 倍触发。延迟敏感调大（200~500）减少 GC 频率，内存紧张调小（50）降低内存。 |
| GOMEMLIMIT 是什么版本加的？作用？ | Go 1.19 新增，软内存限制，超过后自动提高 GC 频率，避免容器 OOM，支付业务必开！ |
| 怎么优化 GC？ | 1. 少分配对象（sync.Pool、预分配）；2. 调大 GOGC；3. Go 1.19+ 开 GOMEMLIMIT；4. 避免 goroutine 泄漏；5. 不用 finalizer。 |
| 什么是浮动垃圾？ | 标记过程中变成垃圾的对象，本轮 GC 不会回收，要等下一轮。正常现象，所有并发 GC 都有。 |
| 什么是 mutator？ | 修改内存的代码，就是用户的业务代码，和 collector（GC 代码）相对。 |
| 为什么不用分代 GC？ | Go 的逃逸分析把大部分小对象都放到栈上了，栈不需要 GC；分代 GC 对 Go 提升不大，反而增加复杂度；Go runtime 团队评估过，收益不如其他优化大。 |

---

## 十二、一句话总结

> Go GC 从 Go 1.0 的几秒 STW 演进到现在的几百微秒，核心是三色标记 + 混合写屏障实现了真正的并发标记；记住两次 STW 的作用、混合写屏障四条规则、GOGC/GOMEMLIMIT 调优参数，GC 面试基本就满分了。
