# Go GC 进化史：从 Mark-And-Sweep 到三色标记与混合写屏障

---

## 一、Go GC 进化时间线

| Go 版本 | GC 实现 | STW 时间 | 核心改进 |
|---------|---------|---------|---------|
| Go 1.0 | 串行 Mark-And-Sweep | 几百毫秒 ~ 几秒 | 能用就行 |
| Go 1.1 ~ 1.4 | 并行 Mark-And-Sweep | 几十 ~ 几百毫秒 | 并行 GC，分离写屏障 |
| Go 1.5 | 三色标记 + 插入写屏障 | 几十毫秒 | 革命性版本，大部分工作并发 |
| Go 1.6 ~ 1.7 | 性能优化 | 几 ~ 几十毫秒 | 更快，延迟更低 |
| Go 1.8 | 混合写屏障 | 亚毫秒级！ | 删除 STW 的 re-scan 阶段 |
| Go 1.9 ~ 1.13 | 持续优化 | 亚毫秒级 | 大对象、分配器优化 |
| Go 1.14 | 基于信号的异步抢占 | 亚毫秒级 | 解决长循环不被抢占的问题 |
| Go 1.19 | 软内存限制 GOMEMLIMIT | 更稳 | 容器环境友好 |

**面试一句话总结：Go GC 进化就是一部 STW 时间不断缩短的历史，从几秒到几毫秒，现在目标是亚毫秒级。**

---

## 二、Go 1.0 ~ 1.4：Mark-And-Sweep 时代

### 原理

最基础的标记清扫算法：

```
1. STW（Stop The World），所有 goroutine 停掉
2. Mark 阶段：从根对象（栈、全局变量、寄存器）开始，遍历所有可达对象，标记
3. Sweep 阶段：遍历所有内存块，没标记的就是垃圾，回收
4. 恢复所有 goroutine
```

**问题：全程 STW！**

整个 GC 过程世界都是停的，堆越大，对象越多，STW 时间越长，几秒钟很常见。

1.4 版本做了并行优化，STW 时间降到几百毫秒，但还是太慢了。

---

## 三、Go 1.5：革命性的三色标记法

Go 1.5 是 Go GC 的分水岭，彻底重写了 GC，引入三色标记，90% 的工作都可以并发做，STW 时间直接降到几十毫秒。

### 1. 三色标记基本原理

把对象分成三种颜色：
- **白色**：还没访问到的，可能是垃圾
- **灰色**：访问到了，但它引用的对象还没扫描完
- **黑色**：扫描完了，它和它所有引用的对象都处理过了

```
算法流程：
1. 所有对象初始都是白色
2. 把根对象（栈、全局变量）涂成灰色，放到灰色队列
3. 从灰色队列拿一个对象，涂成黑色，把它引用的所有白色对象涂成灰色，加队列
4. 重复，直到灰色队列为空
5. 剩下的白色对象就是垃圾，回收
```

---

### 2. 三色标记的核心问题：漏标

如果 GC 和用户代码并发跑，用户代码修改了指针，就会出现漏标，把存活的对象当成垃圾回收了！

**漏标的两个必要条件（Dijkstra）：**
1. 一个黑色对象引用了一个白色对象
2. 所有灰色对象到这个白色对象的路径都断了

两个条件同时满足，这个白色对象就会被当成垃圾回收，程序直接崩溃。

---

### 3. 插入写屏障（Go 1.5 ~ 1.7）

**解决：破坏条件 1，不让黑色对象引用白色对象。**

每次指针赋值的时候加写屏障：
```go
// 伪代码
func writePointer(slot *Object, newObj *Object) {
    if newObj 是白色 {
        把 newObj 涂成灰色，加入灰色队列
    }
    *slot = newObj
}
```

**任何黑色对象要引用一个白色对象，先把白色对象涂成灰色。**

这样条件 1 永远不成立，不会漏标。

**问题：结束的时候需要重新扫描一遍所有栈（re-scan），因为栈上的指针赋值没有加写屏障（性能原因），re-scan 阶段是 STW 的，有十几到几十毫秒。**

---

## 四、Go 1.8：混合写屏障，亚毫秒级 STW！

Go 1.8 引入混合写屏障，彻底干掉了 re-scan 阶段，STW 时间直接降到 1 毫秒以内！

### 1. 混合写屏障原理

同时监控指针的插入和删除：

```go
// 伪代码
func hybridWritePointer(slot *Object, newObj *Object) {
    oldObj := *slot

    // 插入屏障：newObj 是白的就涂灰
    shade(newObj)

    // 删除屏障：oldObj 是白的就涂灰
    shade(oldObj)

    *slot = newObj
}
```

**同时破坏漏标的两个条件：**
- 插入屏障：不让黑对象引用白对象
- 删除屏障：不让灰到白的路径断开

两个屏障一起用，栈上的指针也不需要 re-scan 了，完美！

---

### 2. 为什么叫"混合"？

就是插入写屏障 + 删除写屏障，两个混合一起用。

之前 Go 1.5 只有插入写屏障，现在两个都有了，所以叫混合写屏障。

**效果：STW 时间从几十毫秒降到不到 1 毫秒！**

---

## 五、Go 1.14：异步抢占，解决 GC 最后一块短板

GC 开始前需要把所有 goroutine 都暂停，进入安全点。

Go 1.14 之前是协作式抢占，goroutine 只有在函数调用的时候才检查要不要暂停。

**问题：一个 goroutine 跑长循环不调用函数，就永远不会暂停，GC 等它一个等几秒钟，STW 直接爆炸！**

Go 1.14 引入基于信号的异步抢占：
- sysmon 监控到 goroutine 跑了超过 10ms
- 给它发 SIGURG 信号
- goroutine 收到信号，保存上下文，暂停

**长循环也能被抢占了，GC 不用等了，STW 稳定在亚毫秒级！**

---

## 六、Go 1.19+：软内存限制 GOMEMLIMIT

容器环境的经典问题：
- Go 不知道容器的内存限制
- 拼命用内存，GC 触发阈值到了才开始回收
- 还没回收完呢，OOM Killer 就把进程杀了

Go 1.19 引入 GOMEMLIMIT：
```bash
GOMEMLIMIT=512MiB ./myapp
```

告诉 Go runtime：你最多能用 512MB，超过了就更激进地做 GC，不要等到 OOM。

**容器环境救星！**

## 七、现在的 GC 完整流程

现代 Go 的 GC 分 4 个阶段：

```
┌─────────────────────────────────────────────────────┐
│ 1. Mark Setup (STW，约 100us)                       │
│    开启写屏障，准备 GC                                │
└─────────────────────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 2. Mark (并发，不 STW)                              │
│    三色标记，和用户代码一起跑，混合写屏障保护         │
└─────────────────────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 3. Mark Termination (STW，约 100us)                 │
│    收尾，标记根对象，关闭写屏障                       │
└─────────────────────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 4. Sweep (并发，不 STW)                             │
│    清扫白色对象，回收内存，和用户代码一起跑           │
└─────────────────────────────────────────────────────┘
```

**总 STW 时间：不到 1 毫秒！** 这就是为什么 Go 的 GC 这么强。

## 八、常见误解与坑

### 1. Go 是分代 GC 吗？

**不是！Go 现在还是非分代的。**

很多人以为 Go 是分代的，和 Java 一样有年轻代老年代，其实不是。

为什么不做分代？
- Go 的编译器会做逃逸分析，大部分小对象直接分配在栈上，函数返回就回收了，根本不用 GC
- 真正需要 GC 的对象比例其实不高
- 分代的复杂度很高，收益没那么大
- 未来可能会加，但现在还没有

---

### 2. Go 有 compaction（压缩）吗？

**没有！Go 是标记清扫，不移动对象。**

为什么不做压缩？
- 移动对象要改所有指向它的指针，STW 时间爆炸
- Go 的分配器是 tcmalloc 那套，分级分配，碎片问题不严重
- 大对象直接 span 级回收，不会有碎片问题

---

### 3. GOGC 调参有用吗？

```bash
GOGC=100  # 默认，堆翻一倍触发 GC
GOGC=50   # 更频繁 GC，内存用得少，CPU 高
GOGC=200  # 更少 GC，内存用得多，CPU 低
```

大部分场景默认就好，极端场景可以调。

Go 1.19 之后有了 GOMEMLIMIT，优先用 GOMEMLIMIT，比 GOGC 好用。

## 九、面试高频问答

| 问题 | 答案 |
|------|------|
| Go GC 用的什么算法？ | 并发三色标记清扫，Go 1.8+ 用混合写屏障。 |
| 什么是三色标记法？ | 把对象分成白、灰、黑三色，从根开始遍历，灰的变黑，引用的白的变灰，最后白的就是垃圾。 |
| 漏标的两个必要条件是什么？ | 1. 黑对象引用了白对象；2. 所有灰对象到这个白对象的路径都断了。两个同时满足就会漏标。 |
| 插入写屏障是干什么的？ | 破坏条件 1，黑对象要引用白对象，先把白的涂灰，保证不会漏标。Go 1.5~1.7 用这个。 |
| 混合写屏障比插入写屏障好在哪？ | 同时有插入和删除屏障，不需要结束时 STW re-scan 栈，STW 时间从几十毫秒降到不到 1 毫秒。 |
| Go 1.14 异步抢占解决了什么 GC 问题？ | 长循环不调用函数不会被抢占，GC 等它一个等几秒，STW 爆炸。异步抢占可以打断长循环，稳定 STW。 |
| GOMEMLIMIT 是干什么的？ | Go 1.19 引入，告诉 Go 内存上限，超过了就激进 GC，防止容器环境被 OOM Killer 杀。 |
| Go 是分代 GC 吗？ | 不是，现在还是非分代的。逃逸分析把大部分小对象放栈上了，分代收益没那么大。 |
| Go GC 有压缩吗？ | 没有，是标记清扫，不移动对象。 |
| 现在 Go GC STW 时间大概多少？ | 亚毫秒级，一般不到 1 毫秒。 |
| Go 1.5 之前的 GC 是什么样的？ | 传统的 Mark-And-Sweep，全程 STW，STW 几百毫秒到几秒，很慢。 |
| 混合写屏障有什么开销？ | 每次指针赋值多执行几十条指令，大概 5% 的性能开销，换来巨大的延迟降低，非常值得。 |
| 什么是安全点？ | GC 开始前需要所有 goroutine 都暂停在安全点，这个点所有指针的状态都是已知的。 |

## 十、一句话总结

> Go GC 进化史就是不断缩短 STW 的历史，从 Go 1.0 全程 STW 几秒，到 Go 1.5 三色标记并发几十毫秒，再到 Go 1.8 混合写屏障亚毫秒级，Go 1.14 异步抢占解决长循环问题，现在的 Go GC 是工业界最好的垃圾回收器之一。
