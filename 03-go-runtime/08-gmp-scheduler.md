# GMP 调度模型底层原理深度解析

---

## 一、先搞懂：为什么需要调度器？

### 1. 问题起源：内核线程调度的痛点

早期的 Go（Go 1.0 之前）只有 M 和 G，没有 P：

| 问题 | 说明 |
|------|------|
| **上下文切换开销大** | 每次 goroutine 切换都要进入内核，几百 ns → 几 us |
| **全局锁竞争严重** | 所有 G 都在一个全局队列，每个 M 拿 G 都要抢锁 |
| **内存局部性差** | M1 把 G1 放到队列，M2 拿过来执行，缓存全部失效 |

**结果：** 多核 CPU 下，Go 程序性能甚至不如单线程 C 程序。

---

### 2. GMP 三个角色（面试必背）

Go 1.1 引入了 P（Processor），形成了经典的 GMP 三层模型：

| 角色 | 全称 | 是什么 | 数量 | 核心作用 |
|------|------|--------|------|---------|
| **G** | Goroutine | 用户态线程，Go 语言级别的"线程" | 几十万甚至更多 | 执行单元，存栈、PC、状态 |
| **M** | Machine | 内核线程，真正在 CPU 上跑的实体 | 默认 GOMAXPROCS，可动态调整 | 执行载体，负责把 G 跑起来 |
| **P** | Processor | 处理器，M 和 G 之间的"中介" | GOMAXPROCS，启动时固定 | 调度逻辑，存本地 G 队列，负责调度 |

**形象比喻：**
- G = 要执行的任务（代码）
- M = 工人（CPU）
- P = 任务队列 + 调度规则
- 每个工人（M）必须绑定一个任务队列（P）才能干活

---

## 二、三个核心数据结构详解

### 1. G：Goroutine 结构体

```go
type g struct {
    // 栈信息
    stack       stack   // 栈范围 [lo, hi]
    stackguard0 uintptr // 栈增长哨兵，小于这个值就触发栈扩容

    // 执行上下文
    pc uintptr // 程序计数器，下一条要执行的指令
    sp uintptr // 栈指针
    goid int64 // goroutine ID

    // 状态
    status uint32 // _Gidle, _Grunnable, _Grunning, _Gsyscall, _Gwaiting...

    // 绑定关系
    m *m // 当前绑定的 M，nil 表示没在跑
    p *p // 所属的 P

    // 调度相关
    schedlink guintptr // 链表指针，串在队列里

    // ... 其他几十字段
}
```

**G 的 6 种核心状态：**

| 状态 | 值 | 说明 |
|------|----|------|
| _Gidle | 0 | 刚分配，还没初始化 |
| _Grunnable | 1 | 就绪，在 P 的本地队列或全局队列，等着被执行 |
| _Grunning | 2 | 运行中，正在 M 上跑 |
| _Gsyscall | 3 | 正在执行系统调用 |
| _Gwaiting | 4 | 阻塞中（等 channel、等锁、sleep） |
| _Gdead | 6 | 执行完了，在 P 的空闲 G 列表里等着复用 |

**面试高频：G 的栈多大？**
- 初始 2KB（Go 1.4 之前是 8KB）
- 最大 1GB（64 位系统），250MB（32 位系统）
- 不够了自动扩容，每次扩 2 倍

---

### 2. P：Processor 结构体

```go
type p struct {
    id          int32   // P 的 ID，0 ~ GOMAXPROCS-1
    status      uint32  // P 的状态：_Pidle, _Prunning, _Psyscall, _Pgcstop...

    // 本地 G 队列！这是引入 P 的核心原因！
    runqhead uint32
    runqtail uint32
    runq     [256]guintptr // 环形队列，最多 256 个 G

    // 调度相关
    m           muintptr // 当前绑定的 M
    gFree struct {       // 空闲 G 列表，复用 G，避免频繁分配
        gList
        n int32
    }

    // GC 相关
    gcAssistTime int64

    // ... 其他字段
}
```

**P 的本地队列是核心创新：**
- 每个 P 有自己的 256 个 G 的本地队列
- P 拿自己队列的 G **完全不需要锁！** 无锁！
- 只有本地队列满了（>256）才会放到全局队列
- 性能提升巨大！从全局一把锁变成每个 P 自己的队列

---

### 3. M：Machine 结构体

```go
type m struct {
    g0      *g      // M 自带的 g0，跑调度代码用的，栈特别大（64 位系统 8MB）
    curg    *g      // 当前正在跑的 G
    p       puintptr // 当前绑定的 P

    // 系统调用相关
    parksema uint32 // 休眠用的信号量
    parknote note

    // 线程 ID
    tid uint64

    // ... 其他字段
}
```

**g0 是理解调度的关键：**
- 每个 M 都有一个专属的 g0
- g0 的栈特别大，不参与栈扩容
- 所有调度代码（schedule()、findrunnable()）都是在 g0 栈上跑的
- G 切换本质就是：从 G 的栈切到 g0 栈，调度完再切到新 G 的栈

---

## 三、调度完整流程（面试必背）

### 1. 调度循环

每个 M 都在跑一个死循环，叫调度循环：

```go
// 伪代码，每个 M 都在跑这个
func schedule() {
    for {
        // 1. 找一个可运行的 G
        gp := findrunnable()

        // 2. 切到这个 G 的栈，执行
        execute(gp)

        // 3. G 执行完了，切回 g0 栈，继续调度
        gogo(&gp.sched)
    }
}
```

---

### 2. findrunnable()：找 G 的完整逻辑（核心！）

这是调度器最核心的函数，面试 100% 会问顺序！

```go
// 伪代码，找 G 的优先级顺序
func findrunnable() *g {
    // =====================================
    // 第一优先级：自己 P 的本地队列！
    // =====================================
    // 99% 的情况都在这里找到，无锁，最快
    if gp := runqget(_p_); gp != nil {
        return gp
    }

    // =====================================
    // 第二优先级：全局队列！
    // =====================================
    // 每调度 61 次，必须去全局队列拿一次，防止全局队列饿死
    if sched.runqsize > 0 {
        lock(&sched.lock)
        gp := globrunqget(_p_, 1) // 拿一个
        unlock(&sched.lock)
        if gp != nil {
            return gp
        }
    }

    // =====================================
    // 第三优先级：从其他 P 偷！（工作窃取）
    // =====================================
    // 随机选一个 P，偷它一半的 G 过来
    for i := 0; i < 4; i++ {
        for enum := stealOrder.start(fastrand()); !enum.done(); enum.next() {
            p2 := allp[enum.position()]
            if p2 == _p_ {
                continue
            }
            if gp := runqsteal(_p_, p2, true); gp != nil {
                return gp
            }
        }
    }

    // =====================================
    // 第四优先级：网络轮询器（netpoll）
    // =====================================
    // 有没有 IO 就绪的 G？比如 socket 可读了
    if netpollinited() && atomic.Load(&netpollWaiters) > 0 {
        if gp := netpoll(false); gp != nil { // false = 不阻塞，只是查一下
            return gp
        }
    }

    // =====================================
    // 第五优先级：去全局队列再查一次，这次拿锁
    // =====================================
    lock(&sched.lock)
    if gp := globrunqget(_p_, 0); gp != nil {
        unlock(&sched.lock)
        return gp
    }

    // =====================================
    // 第六优先级：再去 netpoll 查一次，这次阻塞等
    // =====================================
    // 所有地方都找不到 G 了，去 netpoll 阻塞等 IO
    if netpollinited() {
        gp := netpoll(true) // true = 阻塞等，直到有 IO 就绪
        if gp != nil {
            return gp
        }
    }

    // =====================================
    // 还是找不到？M 休眠，等新的 G 来了唤醒
    // =====================================
    stopm()
    goto top
}
```

**超级重要：找 G 的优先级顺序，按顺序背！**

1. ✅ **第一：自己 P 的本地队列**（无锁，最快，99% 命中）
2. ✅ **第二：全局队列**（每 61 次必须来一次，防止饿死，要锁）
3. ✅ **第三：从其他 P 偷**（工作窃取，随机选 P，偷一半）
4. ✅ **第四：netpoll 非阻塞查**（IO 就绪的 G）
5. ✅ **第五：全局队列再查一次**（确保没漏）
6. ✅ **第六：netpoll 阻塞查**（真的没 G 了，等 IO）
7. ✅ **最后：M 休眠 stopm()**

---

### 3. 调度触发时机

什么时候会触发调度，从 G 切回 g0 重新调度？

| 触发场景 | 说明 |
|----------|------|
| **函数调用时栈检查** | 函数入口编译器插了代码，检查栈够不够，不够就触发调度，顺便检查要不要抢占 |
| **go func() {}** | 新建一个 G，放入队列，触发调度 |
| **系统调用返回** | 从系统调用回来，检查 P 被抢了没，被抢了就重新调度 |
| **主动调用 runtime.Gosched()** | 主动让出 CPU，重新调度 |
| **channel 读写阻塞** | 等 channel，G 进入 _Gwaiting，重新调度 |
| **加锁阻塞** | 拿不到锁，G 休眠，重新调度 |
| **time.Sleep()** | 睡觉，G 挂到 timer 上，重新调度 |
| **GC STW** | 所有 G 都停，GC 完了重新调度 |

---

## 四、工作窃取机制（Work Stealing）

P 的本地队列为空时，就去偷其他 P 的 G。

### 1. 窃取规则

1. **随机选 P：** 从 allp 里随机选一个 P，不是遍历
2. **偷一半：** 偷目标 P 本地队列的一半 G 过来
3. **偷不到就换一个 P 继续试：** 最多试几次，都偷不到就去全局队列
4. **还是没有就休眠：** M 停掉，等有新 G 了再唤醒

**为什么偷一半？**
- 负载均衡！两个 P 的队列长度差不多
- 避免一个 P 特别忙，另一个特别闲

**例子：**
- P0 队列有 100 个 G，P1 队列空了
- P1 去偷 P0 的，偷 50 个过来
- P0 剩 50，P1 有 50，均衡了

---

### 2. 为什么是随机选，不是轮询？

**避免伪共享和锁竞争：**
- 如果所有 P 都按顺序偷，大家都去偷 P0，P0 的锁就炸了
- 随机选，锁的概率分布更均匀，性能更好

**这也是一个经典的分布式调度设计思想！**

## 五、抢占式调度（面试超级高频！）

这是 GMP 演进史的核心，也是面试官最爱问的，分三个阶段：

---

### 阶段 1：Go 1.0 ~ Go 1.13 - 协作式抢占（坑巨多！）

**原理：**
- Go 编译器在每个函数入口插一段代码，检查要不要抢占
- 只有函数调用的时候才检查！
- 如果一个 G 跑大循环，不调用任何函数，它就永远占着 P！

```go
// Go 1.13 及之前，这个代码会把整个 P 占住，永远不调度！
func main() {
    go func() {
        for { // 死循环，没有函数调用
            // 永远占着 P！其他 G 永远拿不到！
        }
    }()
    time.Sleep(time.Second)
    println("永远执行不到这里！")
}
```

**问题巨大：**
- 一个 goroutine 卡主整个 P
- 调度延迟极高，极端情况几十秒都调度不了
- 生产环境经常出现整个服务卡住的问题

---

### 阶段 2：Go 1.14 ~ Go 1.20 - 基于信号的异步抢占（革命性！）

**原理：**
- 注册 SIGURG 信号处理函数
- sysmon 监控线程发现某个 G 跑了超过 10ms，就给这个 G 所在的 M 发 SIGURG 信号
- M 收到信号，把当前 G 的 PC 改成 `runtime.asyncPreempt()`
- 执行完信号处理函数返回，就跳到了抢占函数
- 主动让出 P，重新调度

**效果：**
- 任何时候都可以抢占！不需要等函数调用！
- 调度延迟从几十 ms 降到了几十 us！
- Go 1.14 是性能提升最大的一个版本！

**问题：**
- 信号会打断系统调用
- 有些场景寄存器不好保存，极端情况还是有问题

---

### 阶段 3：Go 1.21+ - 基于寄存器的异步抢占（更优雅！）

**原理：**
- 每个 M 都有一个 special 寄存器
- sysmon 要抢占的时候，直接把这个寄存器设成特定值
- 每条 CPU 指令执行前，CPU 会检查这个寄存器
- 到了调度点就自动触发抢占

**优点：**
- 不需要发信号，更快
- 不会打断系统调用
- 更可靠

**面试加分项：** 你知道 Go 1.14 和 Go 1.21 抢占式调度的区别吗？

---

## 六、系统调用的处理

G 进入系统调用时的处理流程：

### 1. 短系统调用（<20us）

```
G 进入系统调用 → P 还绑在 M 上 → 系统调用返回 → 继续跑 G
```

**特点：** P 不释放，回来直接继续跑，开销最小。

---

### 2. 长系统调用（>20us）

```
G 进入系统调用
    ↓
sysmon 发现 M 跑系统调用超过 20us 了
    ↓
把 P 从 M 身上"偷"走，P 和 M 解绑
    ↓
P 绑定到另一个空闲的 M2 上
    ↓
M2 继续跑 P 队列里的其他 G
    ↓
原来的 M 系统调用返回
    ↓
发现 P 被抢走了，自己去拿一个空闲的 P
    ↓
拿不到就把 G 放到全局队列，M 自己休眠
```

**设计非常精巧！**
- 短系统调用：不释放 P，避免上下文切换
- 长系统调用：释放 P，不让 P 闲着，提高 CPU 利用率
- 用 20us 做阈值，平衡两种场景的开销

## 七、七个调度相关的生产级大坑（90% 的人踩过）

### 坑 1：GOMAXPROCS 设置错误（容器环境重灾区！）

```go
// ❌ 错误：Go 默认 GOMAXPROCS = 宿主机 CPU 核数
// 容器限制了 2 核，宿主机 32 核，GOMAXPROCS = 32
// 结果：32 个 M 抢 2 个 CPU 核，上下文切换爆炸！
func main() {
    fmt.Println(runtime.GOMAXPROCS(0)) // 容器里可能打印 32！但你只有 2 核！
}
```

**影响：** 性能下降 5 ~ 10 倍，CPU 使用率上不去，上下文切换巨高。

**修复：**
- Go 1.16+ 已经自动支持 cgroups，容器里自动读 limit
- 老版本用 `uber-go/automaxprocs` 包，import 一下就好
- `import _ "go.uber.org/automaxprocs"`

**支付业务必加！** 不加的话容器环境性能直接砍半！

---

### 坑 2：G 泄漏（goroutine 泄漏）

```go
// ❌ 错误：channel 没人读，goroutine 永远阻塞，G 泄漏！
func bad() {
    ch := make(chan int)
    go func() {
        ch <- 1 // 永远没人读，G 永远卡在这里！
    }()
    // 函数返回了，goroutine 还在等，泄漏！
}
```

**怎么排查：**
- `pprof` 看 goroutine 数量，一直在涨就是泄漏了
- `go tool pprof http://localhost:6060/debug/pprof/goroutine?debug=1`

**经典泄漏场景：**
1. channel 读写没人对端
2. 没有超时的 http 请求
3. 互斥锁死锁
4. 定时器没 Stop

---

### 坑 3：全局 G 队列锁竞争太激烈

```go
// ❌ 错误：一下子创建 10 万个 goroutine，全部放到全局队列
// 所有 P 都去抢全局队列的锁，锁竞争爆炸！
for i := 0; i < 100000; i++ {
    go func() {
        // ...
    }()
}
```

**优化：**
- 用 worker pool，控制并发数
- 不要一下子创建太多 goroutine

---

### 坑 4：G 本地队列满了，全部放全局队列

P 本地队列只有 256 个位置，满了就把一半 G 移到全局队列，另一半自己留着。

**现象：** 高并发下全局队列锁竞争严重，性能下降。

**优化：** 控制单 P 的 goroutine 数量。

---

### 坑 5：sysmon 线程优先级太低

sysmon 是监控线程，负责抢占、netpoll 等，优先级太低的话抢占不及时，调度延迟高。

**现象：** 压测时尾延迟特别高，p99 几百 ms。

---

### 坑 6：工作窃取不平衡

极端情况：一个 P 特别忙，其他 P 都很闲，但是偷不到（比如忙的 P 一直在加 G）。

**Go 1.20+ 做了优化：** 负载均衡算法改进了。

---

### 坑 7：cgo 调用阻塞了整个 M

cgo 调用会创建新的 M，因为 cgo 调用是阻塞的，不能占着 P。

```go
// ❌ 同时 1000 个 cgo 调用，会创建 1000 个内核线程！
// 内核线程太多，上下文切换爆炸！
for i := 0; i < 1000; i++ {
    go C.someCFunction()
}
```

**优化：** cgo 调用也要做并发控制，用 worker pool 限制数量。

## 八、面试高频问答（100% 会问！）

|------|------|
| GMP 三个角色分别是什么？ | G=goroutine 执行单元，M=内核线程执行载体，P=处理器调度队列。 |
| 为什么要引入 P？没有 P 不行吗？ | 没有 P 的时候全局一把锁，竞争太激烈。P 的本地队列无锁，性能提升 10 倍+。 |

| 为什么每 61 次必须去全局队列拿一次？ | 防止全局队列的 G 饿死，永远轮不到执行。 |
| g0 是什么？作用？ | 每个 M 自带的 goroutine，栈特别大（8MB），所有调度代码都在 g0 栈上跑。 |
| 容器环境 GOMAXPROCS 有什么坑？ | Go 1.15 及之前默认读宿主机 CPU 核数，不是容器的 limit，导致 GOMAXPROCS 太大，上下文切换爆炸。Go 1.16+ 修复了，老版本用 automaxprocs 包。 |
| goroutine 泄漏怎么排查？ | pprof 看 goroutine 数量，debug=1 可以看到所有 goroutine 的栈，看哪个函数一直在涨。 |
| G 的状态有哪些？ | _Gidle（空闲）、_Grunnable（就绪）、_Grunning（运行中）、_Gsyscall（系统调用）、_Gwaiting（阻塞）、_Gdead（死亡可复用）。 |

---

## 九、一句话总结

> GMP 是 Go 高性能的核心，P 的本地队列消除了全局锁，工作窃取实现了负载均衡，异步抢占保证了调度延迟；记住找 G 的 7 步优先级、三个阶段抢占式调度、容器 GOMAXPROCS 坑，调度器面试基本就满分了。
