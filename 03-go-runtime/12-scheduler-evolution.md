# Go 调度器进化史：从 GM 到 GMP 再到异步抢占

---

## 一、Go 调度器进化时间线

| Go 版本 | 调度模型 | 核心问题 |
|---------|---------|---------|
| Go 1.0 | GM 模型，全局 M 队列 | 全局锁竞争严重，调度延迟高 |
| Go 1.1 | GMP 模型，引入 P，本地队列，工作窃取 | 调度性能提升 10 倍 |
| Go 1.2 ~ 1.13 | GMP + 协作式抢占 | 长循环不被抢占，调度延迟高 |
| Go 1.14 | GMP + 基于信号的异步抢占 | 解决长循环问题，调度延迟降到几十微秒 |
| Go 1.21+ | GMP + 基于寄存器的异步抢占 | 更优雅的抢占实现 |

**面试一句话总结：Go 调度器进化就是不断减少锁竞争、降低调度延迟的历史，GMP + 异步抢占是目前的最终形态。**

---

## 二、Go 1.0：GM 模型的黑暗时代

### 1. GM 模型结构

```
           全局锁
             ↓
┌───────────────────────────┐
│     全局 G 队列           │  ← 所有 M 都来这里抢 G
└───────────────────────────┘
      ↓     ↓     ↓     ↓
    M1     M2     M3     M4
```

只有 G（goroutine）和 M（内核线程），没有 P。

所有 G 都在一个全局队列里，每个 M 拿 G 都要抢全局锁。

---

### 2. GM 模型的三大致命问题

**问题 1：全局锁竞争严重**
所有 M 抢同一个全局锁，CPU 核心越多，锁竞争越爆炸。16 核机器上 90% 的时间都在抢锁。

**问题 2：M 之间交接 G 开销大**
M1 把 G1 放到全局队列，M2 拿过来执行，缓存全部失效，局部性极差。

**问题 3：每个 M 都自己做系统调用**
M 进入系统调用就阻塞，回来还要抢锁，没有复用。

**结果：多核下性能甚至不如单线程 C 程序！**

---

## 三、Go 1.1：GMP 横空出世，性能提升 10 倍

### 1. 引入 P（Processor）

GMP 三个角色：
- **G**：goroutine，要执行的代码
- **M**：Machine，内核线程，真正跑的载体
- **P**：Processor，逻辑处理器，每个 P 有自己的本地 G 队列

核心创新：**每个 P 有自己的本地 G 队列，拿本地队列的 G 完全不需要锁！**

```
┌─────┐     ┌─────┐     ┌─────┐     ┌─────┐
│ P1  │     │ P2  │     │ P3  │     │ P4  │
├─────┤     ├─────┤     ├─────┤     ├─────┤
│ 本地 │     │ 本地 │     │ 本地 │     │ 本地 │
│ G队列│     │ G队列│     │ G队列│     │ G队列│
└──┬──┘     └──┬──┘     └──┬──┘     └──┬──┘
   │           │           │           │
   M1          M2          M3          M4
```

数量关系：
- P 的数量 = GOMAXPROCS，默认 CPU 核数
- M 的数量略大于 P，因为有些 M 阻塞在系统调用了

---

### 2. GMP 解决了 GM 的所有问题

**解决全局锁竞争：**
- 99% 的情况拿自己 P 本地队列的 G，完全无锁
- 只有本地队列满了（256 个 G）才放全局队列
- 全局队列访问频率降了两个数量级

**解决内存局部性差：**
- G 都在同一个 P 上跑，缓存命中高
- 工作窃取也是偷一整个 P 的一半 G，不是一个一个偷

**解决系统调用阻塞：**
- M 进入系统调用，把 P 交给其他空闲的 M
- P 不闲着，继续跑其他 G
- 系统调用回来的 M 去抢一个空闲的 P，没抢到就把 G 放全局队列，自己去休眠

---

### 3. 工作窃取（Work Stealing）

P 本地队列空了怎么办？去偷其他 P 的！

```
P1 本地队列空了
  ↓
随机选一个 P，比如 P2
  ↓
偷 P2 本地队列的一半 G 过来
  ↓
大家负载就均衡了
```

**为什么偷一半，不是偷一个？**
- 减少偷的次数，提高效率
- 负载均衡效果更好
- 经典的分布式调度设计

---

### 4. GMP 时代还剩一个大问题：协作式抢占

Go 1.1 ~ 1.13 的抢占是协作式的：

编译器在每个函数入口插一段检查代码：
```go
func funcEntry() {
    if runtime.preemptFlag {
        // 让出 CPU
        runtime.schedule()
    }
}
```

只有函数调用的时候才检查要不要抢占！

**致命问题：goroutine 跑长循环不调用任何函数，就永远占着 P，其他 G 永远跑不了！**

```go
// Go 1.13 及之前，这个代码会把整个 P 占住！
func main() {
    go func() {
        for {
            // 死循环，没有函数调用
            // 永远不被抢占！
        }
    }()
    time.Sleep(time.Second)
    println("永远执行不到这里！")
}
```

这个问题困扰了 Go 整整 9 个版本！

---

## 四、Go 1.14：基于信号的异步抢占，革命性突破！

Go 1.14 终于解决了长循环不被抢占的问题，引入基于信号的异步抢占。

### 1. 原理

```
1. sysmon 监控线程发现某个 G 跑了超过 10ms
   ↓
2. 给这个 G 所在的 M 发 SIGURG 信号
   ↓
3. M 收到信号，中断当前正在执行的 G
   ↓
4. 保存 G 的上下文，PC、SP、寄存器
   ↓
5. 把 G 放回队列，重新调度
```

**任何时候都可以抢占！不需要等函数调用！**

---

### 2. 效果

上面的死循环例子在 Go 1.14+ 就正常了：
```go
// Go 1.14+，正常工作！
func main() {
    go func() {
        for {
            // 跑 10ms 就会被抢占！
        }
    }()
    time.Sleep(time.Second)
    println("正常执行到这里！")  // ✅ 能打印了！
}
```

**调度延迟从几十毫秒直接降到几十微秒！**

---

### 3. 基于信号的抢占的小问题

- 发信号会打断系统调用
- 有些极端场景寄存器不好保存
- 不是 100% 的地方都能抢占（比如 runtime 内部的关键区域）

但已经解决了 99% 的场景了。

---

## 五、Go 1.21+：基于寄存器的异步抢占，更优雅的实现

Go 1.21 引入了更优雅的抢占方式：

每个 M 有一个特殊的寄存器：
- sysmon 要抢占的时候，直接设置这个寄存器的值
- 每条 CPU 指令执行前，CPU 会检查这个寄存器
- 到了调度点就自动触发抢占

不需要发信号了，更干净，更可靠，开销更小。

---

## 六、现在的 GMP 调度完整流程

找 G 的优先级顺序（按顺序找，找到就返回）：

1. ✅ **第一优先级**：自己 P 的本地运行队列（无锁，最快）
2. ✅ **第二优先级**：全局运行队列（每 61 次调度必须来一次，防止饿死）
3. ✅ **第三优先级**：从其他 P 偷一半 G 过来（工作窃取）
4. ✅ **第四优先级**：netpoll 看看有没有 IO 就绪的 G（非阻塞查）
5. ✅ **第五优先级**：再去全局队列查一遍，这次拿锁
6. ✅ **第六优先级**：netpoll 阻塞查，等 IO 就绪
7. ✅ **最后**：实在找不到 G 了，M 休眠，等新 G 来了唤醒

## 七、常见误解与最佳实践

### 1. GOMAXPROCS 调大就越快吗？

**不是！**

GOMAXPROCS 是 P 的数量，不是 M 的数量，也不是 goroutine 的数量。

- P 数量 > CPU 核数：上下文切换开销变大，反而慢
- P 数量 = CPU 核数：默认，最优
- P 数量 < CPU 核数：CPU 用不满

**容器环境大坑：**
Go 1.15 及之前，GOMAXPROCS 默认读宿主机的 CPU 核数，不是容器的 limit。
容器限制 2 核，宿主机 32 核，GOMAXPROCS = 32，32 个 P 抢 2 个 CPU，上下文切换爆炸！

**修复：**
- Go 1.16+ 自动读 cgroup limit
- 老版本用 `go.uber.org/automaxprocs`

---

### 2. goroutine 开得越多越快吗？

**不是！**

goroutine 本身开销很小（2KB 初始栈），但调度是有开销的。

几十万 goroutine 没问题，几百万开始就有调度开销了。

**IO 密集型：** 可以开多一点 goroutine，因为大部分时间在等 IO
**CPU 密集型：** goroutine 数量 = CPU 核数就够了，多了反而慢

---

### 3. 怎么看调度器的状态？

```bash
# 看调度器追踪
GODEBUG=schedtrace=1000 ./myapp  # 每 1000ms 打印一次调度器状态
```

会打印：
- G/M/P 数量
- 本地队列/全局队列长度
- 工作窃取次数
- 抢占次数

## 八、面试高频问答

| 问题 | 答案 |
|------|------|
| Go 1.0 调度模型有什么问题？ | GM 模型，全局一把锁，所有 M 抢同一个 G 队列，锁竞争爆炸，内存局部性差，多核性能甚至不如单核。 |
| GMP 比 GM 好在哪？ | 引入 P，每个 P 有自己的本地 G 队列，99% 的调度无锁；工作窃取实现负载均衡；系统调用时 P 和 M 解绑，P 不闲着。性能提升 10 倍。 |
| GMP 三个角色是什么？ | G=goroutine 执行单元，M=内核线程执行载体，P=Processor 逻辑处理器带本地 G 队列。 |
| P 的数量默认是多少？ | 等于 CPU 核数，可以用 GOMAXPROCS 环境变量改。 |
| 找 G 的优先级顺序是什么？ | 1. 自己 P 本地队列；2. 全局队列（每 61 次必须来）；3. 偷其他 P；4. netpoll 非阻塞查；5. 全局队列再查；6. netpoll 阻塞查；7. M 休眠。 |
| 为什么每 61 次必须去全局队列拿一次？ | 防止全局队列的 G 饿死，永远轮不到执行。 |
| 工作窃取是怎么工作的？ | P 本地队列空了，随机选一个其他 P，偷它一半的 G 过来，负载均衡。 |
| 为什么偷一半，不是偷一个？ | 减少偷的次数，提高效率，负载均衡效果更好。 |
| Go 1.14 之前抢占有什么问题？ | 协作式抢占，只有函数调用时才检查，长循环不调用函数会永远占着 P，调度延迟爆炸。 |
| Go 1.14 异步抢占是怎么实现的？ | sysmon 发现 G 跑了超过 10ms，给 M 发 SIGURG 信号，M 收到信号保存上下文，让出 P，重新调度。任何时候都可以抢占，不需要等函数调用。 |
| 容器环境 GOMAXPROCS 有什么坑？ | Go 1.15 及之前默认读宿主机 CPU 核数，不是容器 limit，导致 P 太多，上下文切换爆炸。Go 1.16+ 修复了，老版本用 automaxprocs 包。 |
| 为什么 M 的数量比 P 多？ | 有些 M 阻塞在系统调用上了，这些 M 不占 P，P 给其他 M 用了。 |
| G 最多能有多少个？ | 没有硬性限制，几十万几百万都可以，只要内存够。 |
| sysmon 线程是干什么的？ | 监控线程，负责检测长运行的 G 发起抢占，检测死锁，检测系统调用超时回收 P，触发 netpoll 等。 |

---

## 九、一句话总结

> Go 调度器从 Go 1.0 全局一把锁的 GM 模型，到 Go 1.1 引入 P 的 GMP 模型性能提升 10 倍，再到 Go 1.14 基于信号的异步抢占解决长循环问题，不断降低锁竞争和调度延迟，现在的 GMP 是工业界最好的 M:N 调度器之一。
