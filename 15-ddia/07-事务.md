# Ch7 事务

## 核心思想

事务是数据库将多个读写操作合并为一个逻辑单元的机制，提供**安全性保证（ACID）**，让应用开发者可以假装没有并发和故障问题。

---

## 1. ACID 拆解

### A - 原子性（Atomicity）

> 要么全部成功，要么全部回滚，没有中间状态。

**不是"并发原子性"**（那是指线性一致性），而是"出错时的原子性"：如果中途失败，已执行的操作必须撤销。

**实现**：WAL（Write-Ahead Log）+ 回滚日志（Undo Log）

### C - 一致性（Consistency）

> 事务前后，数据必须满足不变量（invariant）。

**这是应用的职责，不是数据库的**。数据库提供原子性和隔离性来帮助维护一致性，但不保证应用级别的约束。

### I - 隔离性（Isolation）

> 并发事务互不干扰。

这是最复杂、最常考的部分。详见第 2 节。

### D - 持久性（Durability）

> 事务提交后，数据不会丢失。

**实现**：WAL 刷盘（fsync）+ 复制。实际上，没有任何技术能提供 100% 的持久性——磁盘会坏，机房会断电。关键是**足够可靠**。

## 2. 隔离级别（面试核心）

### 并发问题一览

| 问题 | 描述 | 严重程度 |
|------|------|----------|
| 脏读 | 读到其他事务未提交的数据 | 严重 |
| 脏写 | 覆盖其他事务未提交的修改 | 严重 |
| 不可重复读 | 同一事务内两次读同一行，结果不同 | 中等 |
| 幻读 | 同一事务内两次范围查询，行数不同 | 中等 |
| 写倾斜 | 事务提交前提被其他事务修改 | 隐蔽 |
| 丢失更新 | 两个事务同时更新，一个覆盖另一个 | 严重 |

### 四个隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
|----------|------|-----------|------|------|
| 读未提交 | 可能 | 可能 | 可能 | 无锁 |
| 读已提交 | 避免 | 可能 | 可能 | 短锁/快照 |
| 可重复读 | 避免 | 避免 | 可能* | 快照隔离 |
| 可串行化 | 避免 | 避免 | 避免 | 2PL/SSI |

*注：MySQL InnoDB 的"可重复读"通过 Next-Key Lock 在很大程度上避免了幻读，但不是标准定义的可串行化。

### 2.1 读已提交（Read Committed）

**核心保证**：
1. 不脏读 → 只读已提交的数据
2. 不脏写 → 只覆盖已提交的数据

**实现**：
- 不脏写：行级锁（写锁），直到事务结束才释放
- 不脏读：**MVCC 快照**（PostgreSQL）或**读已提交版本**（MySQL）

### 2.2 可重复读 / 快照隔离（Snapshot Isolation）

> 每个事务看到的是事务开始时的数据库快照。

**实现原理**：MVCC（Multi-Version Concurrency Control）

```
事务A开始 → 看到快照S1
  其他事务修改数据 → 创建新版本
事务A读 → 仍然读旧版本
事务A结束
```

**PostgreSQL 的实现**：
- 每行有 `xmin`（创建事务ID）和 `xmax`（删除事务ID）
- 事务只能看到 `xmin` ≤ 当前事务ID 且 `xmax` 为空或 > 当前事务ID 的行

**MySQL InnoDB 的实现**：
- Undo Log 保存旧版本
- 每个事务有 Read View，决定可见性

### 面试重点：快照隔离能解决的问题和不能解决的问题

**能解决**：脏读、不可重复读
**不能解决**：丢失更新、写倾斜、幻读

### 2.3 丢失更新（Lost Update）

两个事务同时读-改-写同一行：

```
事务A: read(count=50) → count=50+1 → write(count=51)
事务B: read(count=50) → count=50+1 → write(count=51)  ← 丢失了事务A的更新！
```

**解决方案**：

| 方案 | 说明 | 适用 |
|------|------|------|
| 原子更新 | `UPDATE SET count=count+1` | 简单场景 |
| 显式锁 | `SELECT ... FOR UPDATE` | 需要先读后写 |
| CAS | `UPDATE WHERE count=50` | 乐观锁 |
| 可串行化 | 最高保证 | 所有场景 |

### 2.4 写倾斜（Write Skew）

> 两个事务各自满足前提条件，但合在一起就不满足了。

经典例子：值班医生至少留一人

```
事务A: 查值班人数=2 → 满足(≥1) → 删除自己
事务B: 查值班人数=2 → 满足(≥1) → 删除自己
结果: 两人都走了！值班人数=0
```

**写倾斜 vs 丢失更新**：
- 丢失更新：两个事务写同一行
- 写倾斜：两个事务写不同行，但有逻辑依赖

**解决方案**：
- `SELECT ... FOR UPDATE`（对查询行加锁）→ 如果查询涉及多行可能不够
- 可串行化隔离 → 唯一完整解决方案
- 数据库约束 → 有时可行（如 `CHECK on_call_count >= 1`）

### 2.5 幻读（Phantom Read）

> 同一事务内两次相同的范围查询，结果集不同（有新行加入）。

```
事务A: SELECT * WHERE status='active' → 3行
事务B: INSERT status='active' → 提交
事务A: SELECT * WHERE status='active' → 4行  ← 幻读！
```

**写倾斜和幻读的关系**：写倾斜是一种特殊的幻读问题——事务的前提查询结果被其他事务改变。

**MySQL 的 Next-Key Lock**：锁住行 + 行间的间隙，防止插入新行 → 大部分幻读场景可避免。

## 3. 可串行化（Serializable）

> 最强隔离级别，效果等价于事务串行执行。

### 3.1 实际串行执行

- 单线程执行所有事务 → 性能受限
- 存储过程（stored procedure）减少网络往返
- Redis 就是单线程模型

**局限**：吞吐量受限于单核，只适合事务很短的场景

### 3.2 两阶段锁（2PL, Two-Phase Locking）

> 几十年来唯一的通用串行化方案。

**规则**：
- 读锁（共享锁）：多个事务可同时持有
- 写锁（排他锁）：独占
- **写锁阻塞读锁** ← 这是和快照隔离的关键区别

```
阶段1（Growing）: 获取锁，不释放
阶段2（Shrinking）: 释放锁，不获取
```

**谓词锁（Predicate Lock）**：锁住满足某个条件的所有行（包括还不存在的行）→ 解决幻读

**索引范围锁（Next-Key Lock）**：谓词锁的近似实现，锁住索引范围

**2PL 的问题**：
- 性能差：锁竞争严重
- 死锁：需要检测和重试
- 延迟不可预测

### 3.3 可串行化快照隔离（SSI, Serializable Snapshot Isolation）

> 2008 年提出，PostgreSQL 9.1+ 的默认串行化实现。

**核心思想**：乐观并发控制——假设没有冲突，检测到冲突时中止事务。

**检测写倾斜的方法**：

1. **检测过时（stale）的读取**：事务读了一行，这行在事务提交前被其他事务修改了
2. **追踪依赖**：如果事务 A 的决策依赖于事务 B 写入前的值 → A 的决策可能基于过时数据

```
事务A读行R → 事务B修改行R并提交 → 事务A提交
                              ↑
                        检测到依赖冲突 → 中止事务A
```

**SSI vs 2PL**：

| 维度 | 2PL | SSI |
|------|-----|-----|
| 策略 | 悲观（加锁） | 乐观（检测+中止） |
| 性能 | 锁竞争严重 | 无锁，冲突少时极快 |
| 延迟 | 不可预测 | 中止时需重试 |
| 适合 | 冲突多 | 冲突少 |


## 5. 支付场景事务设计

### 支付扣款

```sql
BEGIN;
-- 查余额并加锁
SELECT balance FROM accounts WHERE id = 'user_123' FOR UPDATE;
-- 如果 balance >= amount:
UPDATE accounts SET balance = balance - 100 WHERE id = 'user_123';
-- 记录流水
INSERT INTO transactions (...) VALUES (...);
COMMIT;
```

关键点：
- `FOR UPDATE` 防止丢失更新
- 事务尽量短，避免长时间持有锁
- 高并发下考虑乐观锁（`WHERE balance >= 100`）

### 跨账户转账

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 'from' FOR UPDATE;
SELECT balance FROM accounts WHERE id = 'to' FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 'from';
UPDATE accounts SET balance = balance + 100 WHERE id = 'to';
COMMIT;
```

### 写倾斜的支付场景

- 优惠卷系统：检查用户剩余优惠券数 ≥ 1 → 使用一张 → 可能多人同时用完
- 信贷额度：检查剩余额度 ≥ 金额 → 扣减 → 可能超额

## 本章面试速查

| 问题 | 答案要点 |
|------|----------|
| 四个隔离级别？ | 读未提交 < 读已提交 < 可重复读 < 可串行化 |
| 快照隔离原理？ | MVCC，每个事务看开始时的快照 |
| 丢失更新怎么解决？ | 原子更新/FOR UPDATE/CAS/串行化 |
| 写倾斜是什么？ | 事务前提被改，不是同一行但有逻辑依赖 |
| 2PL vs SSI？ | 悲观加锁 vs 乐观检测，冲突多2PL/少SSI |
| MySQL 可重复读能防幻读吗？ | 大部分场景通过 Next-Key Lock 防了，但不是完全可串行化 |
| 支付扣款用什么锁？ | FOR UPDATE 悲观锁 或 CAS 乐观锁 |
