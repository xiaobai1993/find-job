Chapter 06

分区

复制解决可用性和延迟，分区解决扩展性。将大数据集拆分到多个节点，每个节点只负责一部分数据。

01 — Strategies

分区策略

两种基本策略：键范围分区适合范围查询但有热点问题，哈希分区均匀分布但失去范围查询。混合策略取两者之长。

键范围分区

每个分区负责一段连续的键范围
A-M, M-S, S-Z
✓ 高效范围查询（扫一个分区）
✗ 热点问题（按时间写入时最新分区过载）
代表: HBase, BigTable

哈希分区

对键做哈希，取模分配分区
hash(key) % N
✓ 数据均匀分布，无热点
✗ 范围查询需要查所有分区
代表: Cassandra, DynamoDB

混合策略

复合主键：第一个键哈希分区，第二个键范围排序
(user_id, timestamp)
✓ 均匀分布 + 范围查询
✗ 复杂度更高
代表: Cassandra
02 — Core Algorithm

一致性哈希环

节点在哈希环上占多个位置（虚拟节点），key 顺时针找到第一个节点。增减节点只影响相邻区间 → 最小化数据迁移。这是面试高频考点。

点击「查找节点」查看 key 路由过程
添加/移除节点观察数据迁移
03 — Secondary Index

分区与二级索引

二级索引是分区的难点：索引条目可能和主数据不在同一分区。两种方案各有取舍。

本地索引 (Scatter/Gather)
全局索引 (Term-Partitioned)
查询"状态=成功的支付订单"：
1 查询发送到所有分区（扇出 / fan-out）
分区1: [订单A✓, 订单C✓]
分区2: [订单D✓]
分区3: [订单F✓, 订单G✓]
2 每个分区各自搜索本地索引
3 聚合结果 → [订单A, 订单C, 订单D, 订单F, 订单G]
问题：读放大，查询延迟取决于最慢的分区
代表: MongoDB, Cassandra
查询"状态=成功的支付订单"：
1 直接查询全局索引分区
索引分区1: "成功" → [订单A✓, 订单D✓, 订单F✓, 订单G✓]
索引分区2: "失败" → [订单B, 订单E]
2 只需访问一个分区 → 快
问题：写入时需跨分区更新索引 → 影响写入性能和一致性
代表: DynamoDB GSI
04 — Payment Domain

支付场景分区设计

支付系统分区策略

01
按用户 ID 哈希分区 → 同一用户的支付记录在同一个分区，避免跨分区查询用户交易历史。
02
范围查询需求（按时间查交易流水）→ 需要二级索引。本地索引 scatter/gather 对支付可接受（用户维度查）。
03
热点问题：大商户交易量远超普通商户。解决方案：大商户 ID 加随机前缀分散到多个分区，查询时聚合。
04
一致性哈希在支付系统的应用：Redis Cluster 用一致性哈希分配 slot，节点扩缩容时最小化数据迁移。
面试关键
"支付系统按用户 ID 哈希分区 + 二级索引处理范围查询。为什么不用 hash % N？因为加节点时几乎所有数据都要迁移。一致性哈希只移动相邻区间的数据。"
