# Ch2 数据模型与查询语言

## 核心思想

数据模型是最重要的设计决策——它决定了软件的思考方式。每一层都隐藏了下层的复杂性，为上一层提供抽象。

```
应用层 → 数据模型层 → 存储引擎层 → 字节/硬件层
```

---

## 1. 关系模型 vs 文档模型

### 关系模型（SQL）

- Edgar Codd 1970 年提出
- 数据组织为**表（关系）**，行是**元组**
- 查询优化器自动决定执行计划，开发者不需关心存储路径
- 强大的 JOIN 能力，适合多对多关系

### 文档模型（NoSQL）

- 数据组织为**文档**（JSON/BSON），天然自包含
- **Schema-on-read**（读时校验）vs SQL 的 **Schema-on-write**（写时校验）
- 优势：一条记录包含所有信息，无需 JOIN
- 劣势：多对多关系需要反规范化（denormalization），更新时需要更新多份副本

### 核心取舍：数据访问模式决定模型选择

| 场景 | 推荐模型 | 原因 |
|------|----------|------|
| 一对多，读多写少 | 文档模型 | 自包含，无需 JOIN |
| 多对多，频繁更新 | 关系模型 | JOIN 天然支持，无数据冗余 |
| 层次结构（树形） | 文档模型 | 父子天然嵌套 |
| 图结构（社交网络） | 图模型 | 关系和文档都不擅长 |

### 关键洞察

- **关系模型和文档模型的趋同**：PostgreSQL 的 JSONB → 两种模型在同一个数据库中共存
- 文档模型的"无模式"是误导：只是模式从数据库移到了应用代码，**模式仍然存在，只是更隐式**

### 面试重点

- 能解释为什么 MongoDB 适合内容管理，而不适合订单系统
- **文档模型的更新异常**：如果一个字段被冗余存储在多个文档中，更新需要原子地修改所有副本
- MySQL 8.0 的 JSON 列类型提供了一种折中

### 支付场景关联

- 订单数据 → 关系模型（多对多：用户-订单-商品-支付）
- 支付流水 → 可用文档模型（一条流水自包含）
- 实际选择：**关系模型为主**，因为支付系统对事务和一致性要求极高

## 2. 查询语言

### 声明式 vs 命令式

| 维度 | 声明式（SQL） | 命令式（代码） |
|------|---------------|----------------|
| 描述 | **做什么** | **怎么做** |
| 优化 | 查询优化器自动选择最佳路径 | 开发者手动优化 |
| 并行 | 容易并行化 | 难以并行（有顺序依赖） |
| 局限 | 复杂逻辑难表达 | 任意逻辑 |

### 关键例子

```sql
-- 声明式：只说"我要什么"
SELECT * FROM orders WHERE status = 'paid' ORDER BY created_at DESC LIMIT 10;

-- 命令式：还要说"怎么做"
results = []
for order in all_orders:
    if order.status == 'paid':
        results.append(order)
results.sort(key=lambda x: x.created_at, reverse=True)
return results[:10]
```

**声明式的优势**：数据库可以自由选择索引、执行顺序、并行策略，而不改变查询语义。

### MapReduce：声明式与命令式的混合

- MongoDB 早期使用 MapReduce 做聚合
- map 和 reduce 函数是命令式的 JavaScript
- 但框架（分片、并行）是声明式的
- MongoDB 后来用 **Aggregation Pipeline** 替代了 MapReduce → 更声明式

## 3. 图模型

### 何时需要

- **多对多关系**是主要数据模式
- 关系之间的**属性**很重要
- 需要**遍历**关系图（如社交网络、推荐系统、知识图谱）

### 三种声明

| 概念 | 含义 |
|------|------|
| 顶点 Vertex | 实体（人、地点、事件） |
| 边 Edge | 关系（认识、访问、参与） |
| 属性 Property | 顶点和边都可以有属性 |

### 图查询语言

- **Cypher**（Neo4j）：`MATCH (person)-[:ACTED_IN]->(movie) RETURN person.name`
- **SPARQL**（RDF）：语义网标准
- **Gremlin**（Apache TinkerPop）：偏命令式

### 与关系模型的关系

图模型可以用关系模型实现（顶点表 + 边表），但：
- 关系模型的 JOIN 需要预先知道查询模式
- 图查询可以**动态多跳遍历**，关系模型需要多次 JOIN
- 性能差异：图数据库对多跳查询有专门优化（索引邻接）

### 面试重点

- 三种模型的取舍关系，以及**混合方案**（PostgreSQL + JSONB + 递归 CTE）
- 为什么"无模式"不等于没有模式
- 图模型不是银弹，大多数业务用关系模型就够了

## 本章面试速查

| 问题 | 答案要点 |
|------|----------|
| 关系模型 vs 文档模型？ | 多对多用关系，自包含用文档，趋同是趋势 |
| Schema-on-read vs write？ | 读时校验灵活但不安全，写时校验严格但抗变更 |
| 为什么声明式更好？ | 优化器自动选择执行路径，容易并行 |
| 图模型适用场景？ | 多对多为主、需遍历关系（社交/推荐/知识图谱） |
| 文档模型的更新异常？ | 冗余数据分散存储，更新需同步多份 |
