# Ch5 复制

## 核心思想

复制是分布式系统最基本的问题：**在多台机器上保存同一数据的副本**。目的：高可用（一台挂了另一台顶上）、低延迟（就近访问）、读扩展（多副本分担读压力）。

---

## 1. 三种复制拓扑

### 1.1 单主复制（Single-Leader / Primary-Replica）

```
客户端 → [主节点] → 同步复制 → [从节点1]
                    → 异步复制 → [从节点2]
                    → 异步复制 → [从节点3]
```

**写入规则**：所有写请求必须经过主节点，从节点只接受读请求。

| 复制方式 | 特点 | 数据安全 | 可用性 | 延迟 |
|----------|------|----------|--------|------|
| 同步复制 | 主等从确认 | 最高（零丢失） | 低（任一节点挂则不可用） | 高 |
| 半同步 | 1个从同步，其余异步 | 较高 | 中 | 中 |
| 异步复制 | 主不等从 | 低（可能丢数据） | 高 | 低 |

### 面试高频：同步 vs 异步的取舍

- **MySQL 半同步复制**：主等至少一个从确认后返回成功
- **问题**：如果同步从节点挂了 → 降级为异步 → 可能丢数据
- **最佳实践**：半同步 + 自动降级 + 监控复制延迟

### 复制延迟问题（Replication Lag）

异步复制的致命问题：**从节点的数据落后于主节点**。

三种表现形式：

#### 1) 读己之写（Read-after-Write Consistency）

**问题**：用户写入后立即读取，如果读到了还没同步的从节点 → 看不到自己的写入。

**解决方案**：

| 方案 | 说明 |
|------|------|
| 读自己的写 | 读取可能被自己修改过的数据时，从主节点读 |
| 时间窗口 | 写入后 T 秒内从主读 |
| 版本号 | 客户端记住最近写入的时间戳，从节点至少达到该时间戳才读 |

#### 2) 单调读（Monotonic Reads）

**问题**：用户先后读不同从节点，后读的节点延迟更严重 → 看到数据"回退"（时光倒流）。

**解决方案**：同一用户的读请求始终路由到同一从节点（一致性哈希）。

#### 3) 一致前缀读（Consistent Prefix Reads）

**问题**：因果关系的写入被分散到不同从节点，顺序错乱。

- 先写入"A:你好"，再写入"B:再见"
- 从节点可能先看到"B:再见"，再看"A:你好" → 逻辑不通

**解决方案**：确保因果关系的写入路由到同一分区。

### 1.2 多主复制（Multi-Leader）

```
[数据中心1: 主1 ←→ 从1a, 从1b]
      ↕ 双向复制
[数据中心2: 主2 ←→ 从2a, 从2b]
```

**适用场景**：
- 多数据中心（就近写入）
- 跨区域协作（离线编辑）

**核心问题**：**写冲突**

| 冲突解决策略 | 说明 | 优劣 |
|-------------|------|------|
| 避免冲突 | 同一条记录只在一个主节点可写 | 简单但限制大 |
| 最后写入获胜（LWW） | 用时间戳决定 | 时钟不可靠，可能丢数据 |
| 自定义冲突解决 | 应用层合并 | 最灵活，但开发成本高 |
| CRDT | 无冲突复制数据类型 | 数学保证，但适用范围有限 |

### 1.3 无主复制（Leaderless）

- Cassandra / Dynamo 风格
- 任何节点都可接受写入
- 客户端或协调节点将写请求发送到多个副本
- 读取时也向多个副本读，取最新版本

**Quorum 读写**：

```
W + R > N  →  读和写有重叠 → 强一致性
W + R ≤ N  →  可能读到旧数据 → 最终一致性
```

- N = 副本数
- W = 写入确认数
- R = 读取确认数

| 配置 | 效果 |
|------|------|
| W=3, R=1, N=3 | 写慢读快 |
| W=1, R=3, N=3 | 写快读慢 |
| W=2, R=2, N=3 | **常用**，读写平衡 |
| W=1, R=1, N=3 | 最快，但可能不一致 |

**Quorum 的问题**：
- 即使 W+R>N，在某些边缘情况下仍可能读到旧数据（并发写 + 网络分区）
- 不是真正的"强一致性" → Ch9 详述

## 2. 复制日志的实现

| 方法 | 代表 | 特点 |
|------|------|------|
| 基于语句 | MySQL（早期） | 简单但不安全（NOW()、UUID） |
| WAL 传输 | PostgreSQL | 底层但耦合存储引擎 |
| 逻辑日志 | MySQL Binlog（行格式） | 解耦存储引擎，可跨版本 |
| 触发器 | 应用层 | 灵活但慢，有额外开销 |

### 面试重点

- **MySQL Binlog 的三种格式**：statement/row/mixed → 为什么推荐 row format
- PostgreSQL 的 WAL 为什么不能跨大版本复制 → 存储引擎耦合
- 逻辑复制的优势 → 可以做异构数据同步（MySQL → Kafka → ES）

## 3. 复制延迟监控

### 关键指标

| 指标 | MySQL | PostgreSQL |
|------|-------|------------|
| 延迟秒数 | `Seconds_Behind_Master` | `pg_stat_replication.replay_lag` |
| 位点差距 | `Exec_Master_Log_Pos` vs `Read_Master_Log_Pos` | LSN 差距 |

### 支付场景关联

- 支付系统不能容忍复制延迟 → **写后读必须走主库**
- 对账系统需要确保读到最新数据 → 从主库读或等同步复制完成
- 跨数据中心：支付只能在主数据中心处理，灾备中心做热备
