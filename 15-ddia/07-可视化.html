事务

事务将多个读写操作合并为一个逻辑单元，提供 ACID 安全保证，让应用开发者可以假装没有并发和故障问题。

01 — ACID

ACID 拆解

事务的四个保证，每个都有不同的含义和实现方式。面试中 C（一致性）常被误解——它是应用的职责，不是数据库的。

A — 原子性

要么全部成功，要么全部回滚，没有中间状态。不是"并发原子性"，而是"出错时的原子性"。
实现：WAL + Undo Log

C — 一致性

事务前后，数据必须满足不变量。这是应用的职责，不是数据库的。数据库只提供 A 和 I 来帮助维护 C。

I — 隔离性

并发事务互不干扰。这是最复杂、最常考的部分。不同隔离级别解决不同问题。
详见下方隔离级别矩阵

D — 持久性

事务提交后数据不会丢失。实现：WAL 刷盘 + 复制。实际上没有 100% 持久性——关键是足够可靠。

丢失更新 (Lost Update)

两个事务同时读-改-写同一行，后写覆盖先写。
T1
读 count=50
写 count=51
COMMIT
T2
读 count=50
写 count=51
COMMIT
T1 的更新被 T2 覆盖！count 应该是 52 却变成了 51
解决方案
1. 原子更新: UPDATE SET count=count+1
2. 显式锁: SELECT ... FOR UPDATE
3. CAS: UPDATE WHERE count=50
4. 可串行化隔离

写倾斜 (Write Skew)

两个事务各自满足前提条件，但合在一起就不满足了。写不同行，但有逻辑依赖。
场景：支付系统优惠券 — 至少保留1张
T1
查券数=2 ≥1
使用1张
COMMIT
T2
查券数=2 ≥1
使用1张
COMMIT
两人都用了券 → 券数变成 0！违反"至少保留1张"的约束
解决方案
1. SELECT ... FOR UPDATE — 对查询行加锁
2. 可串行化隔离 — 唯一完整解决方案
3. 数据库约束 — CHECK coupon_count >= 1

幻读 (Phantom Read)

同一事务内两次相同的范围查询，结果集不同（有新行加入）。写倾斜和幻读密切相关。
场景：查询 active 状态的订单
T1
SELECT 3行
SELECT 4行!
幻读!
T2
INSERT
COMMIT
T1 第二次查到 4 行 → 多了一行"幻影"
解决方案
1. MySQL Next-Key Lock — 锁住行+间隙，防止插入
2. 可串行化隔离
3. 谓词锁（理论方案）
04 — Serializable

可串行化 2PL vs SSI

最强隔离级别，效果等价于事务串行执行。两种实现方式：悲观（2PL）和乐观（SSI）。

2PL — 两阶段锁（悲观）

🔒 写锁阻塞读锁
🐌 性能差：锁竞争严重
⚠️ 死锁：需要检测和重试
❓ 延迟不可预测
✓ 冲突多时保证正确
阶段1(Growing): 获取锁，不释放
阶段2(Shrinking): 释放锁，不获取

SSI — 可串行化快照隔离（乐观）

🚀 无锁，冲突少时极快
✓ PostgreSQL 9.1+ 默认串行化
🎯 检测过时读取（stale read）
🔄 中止时需重试
❌ 冲突多时频繁中止
核心：假设没有冲突 → 检测冲突 → 中止并重试
05 — Payment Domain

支付场景事务设计

支付扣款 — FOR UPDATE 悲观锁

BEGIN; -- 查余额并加锁（防止丢失更新） SELECT balance FROM accounts WHERE id = 'user_123' FOR UPDATE; -- 如果 balance >= amount: UPDATE accounts SET balance = balance - 100 WHERE id = 'user_123'; -- 记录流水 INSERT INTO transactions (...) VALUES (...); COMMIT;
01
FOR UPDATE 防止丢失更新 — 另一个事务必须等待
02
事务尽量短，避免长时间持有锁 — 高并发下考虑乐观锁（WHERE balance >= 100）

写倾斜的支付场景

01
优惠券系统：检查剩余券数 ≥ 1 → 使用 → 可能多人同时用完 → 写倾斜
02
信贷额度：检查剩余额度 ≥ 金额 → 扣减 → 可能超额 → 写倾斜
面试关键
"支付扣款用 FOR UPDATE 悲观锁或 CAS 乐观锁。写倾斜是快照隔离无法解决的问题——两个事务写不同行但有逻辑依赖，必须用可串行化或 SELECT FOR UPDATE。"
