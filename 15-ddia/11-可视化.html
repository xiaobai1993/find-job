03 — Duality

流表二象性

流和表是同一数据的两种视图。流 = 变更日志，表 = 聚合结果。两者可以互转。

流 → 表
流上的聚合操作 → 物化为表
交易流 → 聚合 → 每日统计表
⇄
表 → 流
表的变更日志（CDC）→ 流
MySQL Binlog → Kafka → 流处理
变更日志(CDC) → [流处理] → 物化视图(表) → 表变更 → 日志 → 循环
04 — Architecture

Lambda vs Kappa 架构

两种流批结合架构。Lambda 用两套代码保证正确性，Kappa 用一套代码简化维护。趋势走向 Kappa。

Lambda 架构

数据→批处理层→批视图
数据→速度层→实时视图
服务层→合并两个视图
✓ 批处理保证正确性
✓ 实时层提供低延迟
✗ 两套代码（批+流）
✗ 合并逻辑复杂

Kappa 架构

数据→流处理层→实时视图
↑ 可重放（Kafka 保留日志）
✓ 一套代码
✓ 维护简单
✗ 依赖 exactly-once
✗ 重放大量数据延迟高
支付场景：对账系统用 Lambda（批处理保证 100% 正确），风控系统用 Kappa（需要低延迟）。趋势：Flink 统一批流 → 逐渐走向 Kappa。
05 — Payment Domain

支付场景幂等消费

支付 Exactly-Once 设计

Kafka 消息 → 消费者 → 查幂等表 → 已处理? → 是 → 跳过(提交offset) → 否 → 处理业务 + 写幂等表 + 提交offset（同一事务）
01
幂等表和业务数据在同一个数据库事务中 → 原子性保证
02
幂等键 = 订单号（唯一标识一笔交易）→ 重复消费自动跳过
03
不依赖消息系统的 exactly-once → 业务层保证最可靠
面试关键
"支付系统必须用业务层幂等消费保证 exactly-once。幂等表 + 业务事务 + 提交 offset 原子化。Kafka 事务可以辅助，但不能完全依赖。"
