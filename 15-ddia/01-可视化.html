01 — Reliability

可靠性：系统在逆境中仍正确工作

故障不是"是否发生"的问题，而是"何时发生"的问题。三类故障各有不同的应对哲学。

三类故障对比
故障类型典型场景发生频率应对哲学
硬件 磁盘坏道、内存 ECC、网卡故障 大规模集群中 每天都有 冗余 + 热切换 + 容错设计
软件 Leap second bug、级联故障、资源泄漏 系统性故障，影响面大 隔离 + 快速恢复 + 混沌工程
人为 配置错误、误操作、部署异常 第一大原因（Google SRE 数据） 防错设计 + 最小权限 + 灰度发布
关键洞察：硬件故障的平均无故障时间（MTTF）看似很高（硬盘约 10~50 年），但当集群有 10,000 块硬盘时，平均每天都有硬盘坏。所以我们需要的是容错系统，而非仅靠冗余。
案例：2012 闰秒 Bug

2012 年 6 月 30 日，Linux 内核的一个 bug 导致闰秒发生时 CPU 利用率飙升至 100%， 影响 Reddit、FourSquare、LinkedIn 等大量互联网服务。这不是某个组件崩溃，而是一个隐蔽的软件缺陷在特定时间被触发。

// 闰秒导致的问题本质： // Linux 内核的 hrtimer (高精度定时器) 在闰秒插入时 // 产生了 time > futex timeout 的条件 // → 所有 futex_wait 立即返回 → CPU 100% 旋转 if (now > timeout) // 闰秒使 now "跳" 过了 timeout return ETIMEDOUT; // 所有等待线程立即唤醒 → CPU 风暴
教训：软件 bug 的特征是"休眠"直到特定条件触发，且同时影响所有实例（因为是同一份代码），这让基于"独立故障"假设的冗余策略失效。

03 — Performance · 百分位数

为什么平均值毫无意义？

如果你的 p50 延迟是 100ms，p99 是 2s——"平均 200ms"掩盖了 1% 用户的糟糕体验。 在支付系统中，这 1% 可能就是交易失败。

排队效应：为什么延迟会指数级增长

当服务器 CPU 利用率从 80% 升到 95%，吞吐量只增加 15%，但排队延迟却翻了 4 倍。 这就是为什么容量规划要留余量。

利用率 60%
队列长度: ~1.5延迟: 1x
利用率 90%
队列长度: ~9延迟: 4x
排队论公式：根据 Little's Law 和 M/D/1 队列模型，平均等待时间 ≈ 服务时间 × 利用率/(1-利用率)。利用率 80% 时延迟翻倍，90% 时翻 4 倍，95% 时翻 10 倍。
04 — Scalability · 有状态扩展

有状态服务的水平扩展难题

无状态服务（Web 服务器）加机器就行。有状态服务（数据库）水平扩展极难—— 数据怎么分？事务怎么做？一致性怎么保？这是 DDIA 后半本的核心主题。

无状态服务 水平扩展容易
每节点负载
50%请求均匀分布
有状态服务（数据库） 水平扩展极难
主节点负载
80%写入全部压在主节点
有状态服务的扩展策略全景
策略原理解决的问题引入的新问题
读写分离 主节点写，从节点读 读压力大时分散读负载 复制延迟 → 读到旧数据；写入仍是单点
分片/分区 按 key 哈希或范围拆分数据到不同节点 写入和存储都可以水平扩展 跨分片事务/JOIN；热点分片；再平衡
缓存层 Redis/Memcached 缓存热数据 减少数据库读取 缓存一致性；缓存穿透/雪崩
多主复制 多个节点都可写入 写入也可以水平扩展 写冲突解决极复杂；一致性保证困难
核心矛盾：有状态服务的水平扩展本质上是要在一致性、可用性、分区容忍之间取舍（CAP 定理，Ch9 详述）。支付系统通常选择一致性 → 放弃了最简单的写入水平扩展。
支付系统怎么扩展？

支付系统是有状态的（账户余额），且对一致性要求极高。实际扩展路径：

Step 1 — 单主 + 读写分离 → 写入仍是单点
Step 2 — 按用户 ID 分片 → 写入水平扩展，但跨分片事务困难
Step 3 — 业务拆分（账户/订单/流水分离）→ 每个服务独立扩展
Step 4 — 异步化 + 对账兜底 → 核心路径同步，非核心异步
05 — Reliability · 级联故障

级联故障：一个节点倒下，全军覆没

生产环境最常见的系统性故障。一个节点变慢 → 上游超时重试 → 压力传导到其他节点 → 雪崩。 点击下方按钮，观察级联故障如何一步步扩散。

级联故障模拟器
无熔断：1 节点故障 → 重试风暴 → 全部过载 → 雪崩
有熔断：1 节点故障 → 熔断器打开 → 快速失败 → 保护其他节点
降级：返回兜底数据而非报错 → 用户无感知
06 — Maintainability

可维护性：消除意外复杂度

好的抽象能隐藏意外复杂度，暴露本质复杂度。数据库是存储的抽象，消息队列是通信的抽象。

本质复杂度 vs 意外复杂度
本质复杂度
问题域本身的复杂度
支付业务规则（双人复核、T+1 结算）
合规要求（反洗钱、KYC）
金融精度（不能浮点运算）
→ 无法消除，只能管理
意外复杂度
实现引入的非必要复杂度
纠缠的依赖（循环 import）

过度设计（不需要的抽象层）
→ 必须消除
