# Ch10 批处理

## 核心思想

批处理是"正确性比延迟重要"的数据处理模式。它用**有限的输入 → 确定性的处理 → 输出**，与在线服务的"请求-响应"模式截然不同。

---

## 1. 三种处理模式对比

| 维度 | 在线服务 | 批处理 | 流处理 |
|------|----------|--------|--------|
| 延迟 | 毫秒~秒 | 分钟~天 | 毫秒~秒 |
| 输入 | 请求 | 有界文件 | 无界流 |
| 输出 | 响应 | 文件/表 | 流/表 |
| 可重试 | 通常不行 | **天然可以** | 需要设计 |
| 代表 | Web API | MapReduce/Spark | Kafka Streams/Flink |

---

## 2. Unix 哲学与 MapReduce

### Unix 管道

```bash
cat access.log | grep "payment" | awk '{print $7}' | sort | uniq -c | sort -rn | head -10
```

特点：**输入不变、输出新文件、可组合**。

### MapReduce

Google 2004 年提出，将 Unix 管道思想应用到大规模集群。

```
Map:    (key, value) → list(key2, value2)     # 提取/过滤
Shuffle: 按 key2 分组                          # 框架自动完成
Reduce: (key2, list[value2]) → result          # 聚合
```

**例子：统计支付渠道交易量**

```
Map:    (line) → (channel, 1)
        "alipay order123 100" → ("alipay", 1)
        "wechat order456 200" → ("wechat", 1)

Shuffle: "alipay" → [1, 1, 1, ...]
         "wechat" → [1, 1, ...]

Reduce: ("alipay", [1,1,1,...]) → ("alipay", 3000)
        ("wechat", [1,1,...]) → ("wechat", 2100)
```

### MapReduce 的局限

| 问题 | 说明 |
|------|------|
| 多轮 MR 链式 | 每轮都要写磁盘 → 极慢 |
| 不适合迭代 | 机器学习需要多次迭代，MR 每次从头读 |
| 延迟高 | 启动开销大，不适合低延迟 |

## 3. Spark：内存批处理

> Apache Spark 用内存迭代替代 MapReduce 的磁盘 I/O。

```
MapReduce: 磁盘 → Map → 磁盘 → Shuffle → 磁盘 → Reduce → 磁盘
Spark:     内存 → Map → 内存 → Shuffle → 内存 → Reduce → 内存
                                                         ↓ (需要时才写磁盘)
```

**RDD（Resilient Distributed Dataset）**：
- 不可变分区的集合
- 血缘（lineage）→ 某分区丢失时按血缘重建
- 可以 cache 在内存中

### Spark vs MapReduce

| 维度 | MapReduce | Spark |
|------|-----------|-------|
| I/O | 每轮写磁盘 | 内存迭代 |
| 速度 | 慢（10x~100x） | 快 |
| 迭代 | 不支持 | 天然支持 |
| 编程模型 | Map/Reduce | 丰富的算子（filter/map/groupBy/join） |

## 4. 批处理中的 Join

> Join 是批处理中最复杂的操作。

### 4.1 排序合并 Join（Sort-Merge Join）

- 两个输入按 join key 排序
- 线性扫描合并 → 高效
- MapReduce 的标准 join 方式

### 4.2 广播哈希 Join（Broadcast Hash Join）

- 小表广播到所有节点，放入内存哈希表
- 大表流式扫描，查哈希表
- **适合一大一小**的场景

### 4.3 分区哈希 Join（Partitioned Hash Join）

- 两个表按 join key 用相同方式分区
- 同一分区的数据在同一节点 → 本地 join
- **适合两个大表**

### 支付场景

- 交易表（大） JOIN 商户表（小）→ 广播哈希 Join
- 交易表（大） JOIN 订单表（大）→ 排序合并 Join

## 5. 批处理的输出

| 输出类型 | 说明 | 例子 |
|----------|------|------|
| 搜索索引 | 构建倒排索引 | Hadoop → Elasticsearch |
| 键值存储 | 批量构建查找表 | Hadoop → HBase |
| 统计报表 | 聚合结果 | Spark → MySQL 报表 |

### 物化视图（Materialized View）

> 预计算的查询结果，存储为表。

- 批处理可以看作"定期重建物化视图"
- 数据仓库的星型模式就是一种物化视图策略
- 问题：重建代价大 → 增量维护更高效（Ch11 流处理的动机）

---

## 6. 批处理设计原则

| 原则 | 说明 |
|------|------|
| 输入不可变 | 不修改输入文件，只生成新输出 |
| 确定性 | 相同输入 → 相同输出（可重跑） |
| 可组合 | 一个作业的输出是另一个的输入 |
| 容错 | 任务失败可重试，不依赖内部状态 |
