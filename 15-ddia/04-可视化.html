Chapter 04

编码与演化

系统不可避免地需要变更。编码格式决定了变更的难易程度——向后兼容（新代码读旧数据）和向前兼容（旧代码读新数据）是演化的关键。

01 — Formats

编码格式对比

不同编码格式在兼容性上差异巨大。文本格式（JSON/XML）人类可读但兼容性差，二进制格式（Protobuf/Avro）通过模式机制实现良好的向前/向后兼容。

02 — Compatibility

Protobuf 兼容性演示

Protobuf 通过字段编号（tag）而非字段名来标识字段。新字段用新编号 → 向前兼容；旧字段编号不变 → 向后兼容。删除的字段编号必须标记为 reserved。

V1 — 初始版本
int64 amount = 1
string currency = 2
V2 — 新增字段
int64 amount = 1
string currency = 2
string reference = 3 ← 新增
int64 fee = 4 ← 已删除
reserved 4;
V3 — 再新增
int64 amount = 1
string currency = 2
string reference = 3
reserved 4;
string channel = 5 ← 新增

03 — Best Compatibility

Avro 读写模式解析

Avro 的核心创新：读模式和写模式可以不同。解码时按读模式解析，忽略写模式中不存在的字段，新增字段用默认值填充。不需要字段编号，更灵活。

06 — Payment Domain

支付场景编码实践

支付系统的编码与演化策略

01
支付协议变更：新增字段必须向前兼容。旧网关仍能处理新格式消息（忽略未知字段），否则滚动升级时服务中断。
02
Protobuf 是支付系统内部通信的首选（gRPC）。字段编号机制天然支持向前/向后兼容，reserved 防止误用已删除字段。
03
Kafka 消息用 Avro + Schema Registry → 确保消费者兼容。Schema Registry 拒绝不兼容的模式变更，强制遵守兼容规则。
04
对外 API（REST/JSON）：新增字段不能破坏旧客户端。JSON 没有强制模式 → 需要约定"忽略未知字段"。
面试关键
"向后兼容是必须的（否则旧数据无法处理），向前兼容在滚动升级时同样关键。Protobuf 用字段编号保证兼容，Avro 用读写模式独立解析。支付系统内部用 gRPC+Protobuf，外部用 REST+JSON+约定。"
