批处理

批处理是"正确性比延迟重要"的数据处理模式。有限的输入 → 确定性的处理 → 输出。与在线服务的"请求-响应"模式截然不同。

02 — Spark vs MR

Spark 内存迭代

Spark 用内存迭代替代 MapReduce 的磁盘 I/O，速度快 10~100 倍。RDD 通过血缘关系实现容错。

MapReduce

每轮写磁盘 → 极慢
不支持迭代
编程模型受限（Map/Reduce）
简单可靠
磁盘 → Map → 磁盘 → Shuffle → 磁盘 → Reduce → 磁盘

Spark

内存迭代 → 快 10~100x
天然支持迭代
丰富算子（filter/map/groupBy/join）
RDD 血缘容错
内存 → Map → 内存 → Shuffle → 内存 → Reduce
03 — Join Strategies

批处理中的 Join 策略

Join 是批处理最复杂的操作。三种策略适合不同数据规模组合。

排序合并 Join

两个输入按 join key 排序，线性扫描合并。
交易表(JOIN)订单表 → 两大表

广播哈希 Join

小表广播到所有节点放入内存哈希表，大表流式扫描。
交易表(JOIN)商户表 → 一大一小

分区哈希 Join

两表按相同方式分区，同一分区数据在同一节点本地 join。
两表预分区 → 两大表
04 — Payment Domain

支付场景批处理

支付系统的批处理应用

01
T+1 对账：每天凌晨批处理对账 → 交易流水 vs 银行清算文件 → 发现差异自动报警。
02
统计报表：渠道交易量、成功率、平均金额 → Spark 聚合 → 写入 MySQL 报表库。
03
风控特征：历史交易批处理计算用户画像 → 写入特征库 → 实时风控读取。
面试关键
"批处理的核心原则：输入不可变、确定性、可重跑。支付对账用 Spark 批处理保证正确性，交易表 JOIN 商户表用广播哈希 Join（商户表小）。"
