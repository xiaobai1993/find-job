# Ch6 分区

## 核心思想

复制解决的是**可用性和延迟**问题，分区解决的是**扩展性问题**。将大数据集拆分到多个节点，每个节点只负责一部分数据。

---

## 1. 分区策略

### 1.1 键范围分区（Key Range Partitioning）

- 每个分区负责一段连续的键范围
- 类似百科全书的卷：A-B, C-D, E-F...
- **优势**：高效范围查询（扫一个分区即可）
- **劣势**：热点问题（按时间写入时，最新分区承担所有写入）

```
分区1: key [A, M)
分区2: key [M, S)
分区3: key [S, Z]
```

### 1.2 哈希分区（Hash Partitioning）

- 对键做哈希，取模分配分区
- **优势**：数据均匀分布，无热点
- **劣势**：范围查询需要查所有分区

```
分区1: hash(key) % 3 == 0
分区2: hash(key) % 3 == 1
分区3: hash(key) % 3 == 2
```

### 1.3 混合策略

- **复合主键**：第一个键做哈希分区，第二个键做范围排序
- Cassandra 的做法：`(user_id, timestamp)` → 同一用户的记录在同一个分区内按时间排序

### 面试高频：如何处理热点

| 策略 | 说明 |
|------|------|
| 哈希分区 | 均匀分布，但失去范围查询 |
| 随机前缀 | 热点 key 加随机前缀分散，但读取需要聚合 |
| 分片再平衡 | 自动拆分热点分区 |

## 2. 分区与二级索引

二级索引是分区的难点：索引的条目可能和主数据不在同一分区。

### 2.1 本地索引（Document-Partitioned Index）

- 每个分区维护自己的二级索引
- 查询时需要**扇出（fan-out）**到所有分区 → 分散/聚集（scatter/gather）
- MongoDB / Cassandra 的做法

```
查询 "红色商品"：
  分区1 搜 → 结果1
  分区2 搜 → 结果2
  分区3 搜 → 结果3
  聚合 → 最终结果
```

**问题**：读放大，查询延迟取决于最慢的分区

### 2.2 全局索引（Term-Partitioned Index）

- 二级索引独立分区，按索引键分区
- 查询只需访问一个分区
- **问题**：写入时需要跨分区更新索引 → 影响写入性能和一致性

```
全局索引分区1: "红色" → [商品1, 商品5, 商品9]
全局索引分区2: "蓝色" → [商品2, 商品7]
```

### 面试重点

- MongoDB 的二级索引查询为什么慢 → scatter/gather
- 全局索引的一致性问题 → 写入主数据 + 更新全局索引不是原子的

## 3. 分区再平衡（Rebalancing）

> 当节点增减时，数据需要重新分配。

### 三种策略

| 策略 | 做法 | 优劣 |
|------|------|------|
| 哈希取模 | `hash(key) % N` | N 变化时几乎所有数据都要移动 → **极差** |
| 固定桶 | 预分配大量虚拟桶，桶远多于节点 | 较好，但桶数上限难预估 |
| 一致性哈希 | 虚拟节点环，节点增减只影响相邻区间 | **最优**，数据迁移最少 |

### 一致性哈希详解

```
          N1
         / \
   k1→  /   \  ←k3
       /     \
     N2-------N3
      \      /
   k2→ \    / ←k4
        \  /
         N4
```

- 每个节点在哈希环上占多个位置（虚拟节点）
- key 顺时针找到第一个节点 → 该节点负责
- 增减节点只影响相邻区间的 key → 最小化数据迁移
- **虚拟节点**：解决数据倾斜问题

### 面试重点

- 为什么不用 `hash(key) % N`？ → 加一个节点几乎所有数据都要迁移
- 一致性哈希的优势 → 最小化数据迁移
- 虚拟节点的作用 → 负载均衡

## 4. 请求路由

客户端怎么知道该连哪个节点？

| 方案 | 说明 |
|------|------|
| 客户端知道 | 硬编码分区映射 → 不灵活 |
| 路由层 | 独立的代理层（如 MySQL Proxy, Redis Cluster 的路由） |
| 节点转发 | 任意节点可接收请求，如果不是自己的则转发 |

**元数据管理**：ZooKeeper / etcd 存储分区 → 节点的映射关系

## 5. 分区 + 复制

分区和复制通常组合使用：

```
         分区1          分区2          分区3
节点A   [主1]          [从2]          [从3]
节点B   [从1]          [主2]          [从3]
节点C   [从1]          [从2]          [主3]
```

- 每个分区有自己的主节点
- 节点 A 可能是分区 1 的主，同时是分区 2 的从
- 故障转移：一个分区的主挂了，该分区的从提升为新主

### 支付场景关联

- 支付系统按用户 ID 哈希分区 → 同一用户的支付记录在同一个分区
- 范围查询需求：按时间查交易流水 → 需要二级索引（本地 or 全局？）
- 热点问题：大商户的交易量远超普通商户 → 需要特殊处理
