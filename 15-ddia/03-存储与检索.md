# Ch3 存储与检索

## 核心思想

数据库最底层做了两件事：**存数据** 和 **取数据**。选择什么样的索引结构，决定了数据库的性能特征和适用场景。

---

## 1. 数据结构基础

### 最简单的数据库

```bash
# 写：追加到文件
echo "key=value" >> db.log

# 读：从头扫描文件找 key → O(n)
grep "^key=" db.log
```

这就是 **append-only log**。写入是 O(1)，但读取是 O(n)。索引就是用额外空间换读取速度。

### 核心权衡

> **索引是以写入速度换读取速度。** 每加一个索引，写入就要多维护一份结构。

---

## 2. 哈希索引

### Bitcask 模型（Riak 默认引擎）

- 内存中维护 `key → (offset, length)` 的哈希表
- 数据文件 append-only
- 读取：查哈希表得到 offset → 磁盘 seek 一次读取

```
内存哈希表：{ "key1": (offset=0, len=8), "key2": (offset=8, len=12) }
磁盘文件：  [key1=value1][key2=value2_long][key1=value1_new]...
```

### 关键设计

| 问题 | 解决方案 |
|------|----------|
| 文件无限增长 | 分段（segment）+ 压缩合并（compaction） |
| 哈希表放不下内存 | 只索引热 key，冷 key 需要额外查找 |
| 崩溃恢复 | 从文件重建哈希表，或快照到磁盘 |
| 并发控制 | 写操作单线程（append-only 天然串行） |

### 局限

- **哈希表必须放内存** → key 很多时不可行
- **范围查询不支持** → 查 key1~key9 需要逐个查
- 适合：key 数量可控、每个 key 更新频繁（如视频播放计数器）

---

## 3. LSM-Tree（SSTable + MemTable）

### 从哈希索引到 SSTable

**问题**：段文件中 key 是无序的 → 压缩合并必须全量扫描

**解决**：SSTable（Sorted String Table）——要求段文件中 key **按序排列**

### SSTable 的优势

1. **合并高效**：有序归并，像归并排序 → O(n)
2. **不需要内存索引全部 key**：稀疏索引 + 跳跃 → 类似 B-Tree 的思想
3. **范围查询**：有序 → 顺序扫描，极快

### LSM-Tree 完整写入流程

```
写入请求
  ↓
1. 写入 WAL（Write-Ahead Log）→ 崩溃恢复用
  ↓
2. 写入内存表（MemTable）→ 有序数据结构（跳表/红黑树）
  ↓
3. MemTable 满了 → 冻结 → 刷盘为 SSTable（Level 0）
  ↓
4. 后台 Compaction：合并多层 SSTable
```

### 读取流程

```
读取请求
  ↓
1. 查 MemTable（内存）
  ↓
2. 查 Level 0 SSTable（最近的，可能有多个重叠）
  ↓
3. 查 Level 1 SSTable
  ↓
4. ... 逐层向下
  ↓
5. 找到或返回不存在
```

### Compaction 策略

| 策略 | 代表 | 特点 |
|------|------|------|
| Size-tiered | Cassandra | 相似大小段合并，写放大低，空间放大高 |
| Leveled | RocksDB/LevelDB | 每层有序不重叠，空间放大低，写放大高 |
| Hybrid | TiKV | 混合策略 |

### 写放大 / 读放大 / 空间放大

| 指标 | 含义 | LSM-Tree 表现 |
|------|------|---------------|
| 写放大 | 一次逻辑写导致的实际磁盘写次数 | 高（Compaction 反复重写） |
| 读放大 | 一次逻辑读导致的实际磁盘读次数 | 中高（需查多层） |
| 空间放大 | 磁盘占用 vs 有效数据量 | 中（旧版本在 Compaction 前仍占空间） |

**Bloom Filter** 是 LSM-Tree 的关键优化：在查磁盘前先查布隆过滤器，如果说不存在则一定不存在，大幅减少无效磁盘 I/O。

### 面试重点

- **LSM-Tree vs B-Tree** 是面试高频题（见下方对比表）
- 为什么 LSM-Tree 写入快？→ 顺序写 + 后台合并
- 为什么 LSM-Tree 读取慢？→ 需要多层查找
- Bloom Filter 的作用和局限（有假阳性，无假阴性）

## 4. B-Tree

### 结构

```
                 [根节点]
               /    |    \
          [内部节点] [内部节点] [内部节点]
         /    |      |    \       |    \
      [叶子] [叶子] [叶子] [叶子] [叶子] [叶子]
       ↓     ↓      ↓      ↓     ↓      ↓
     数据页 数据页  数据页  数据页 数据页  数据页
```

- 每个节点是一**页**（page，通常 4KB~8KB）
- 分支因子（branching factor）：一个节点有多少个子节点，通常几百
- 3~4 层就能存储 TB 级数据

### 写入流程

1. 找到目标叶子页
2. 如果页有空间 → 原地更新
3. 如果页满了 → **分裂**（页分裂），需要重写父节点

**关键区别**：B-Tree 是**原地更新**（overwrite），LSM-Tree 是**追加写入**（append-only）

### 崩溃恢复

- **WAL（Write-Ahead Log）**：修改页之前先写日志 → 崩溃后从 WAL 恢复
- 这和 LSM-Tree 的 WAL 类似，但用途不同：B-Tree 的 WAL 用于恢复未刷盘的脏页

### 优化技术

| 技术 | 说明 |
|------|------|
|Copy-on-Write B-Tree | 不覆写页，写新页 + 更新父指针（LMDB） |
|缩写键 | 内部节点只存键的前缀，增大分支因子 |
|页缓存 | 操作系统的 page cache 缓存热点页 |

## 5. LSM-Tree vs B-Tree 全面对比

| 维度 | LSM-Tree | B-Tree |
|------|----------|--------|
| 写入 | **快**（顺序写） | 慢（随机写 + WAL） |
| 读取 | 慢（多层查找） | **快**（固定 3~4 次 I/O） |
| 写放大 | 高（Compaction） | 中（WAL + 页分裂） |
| 读放大 | 高（多层 + Bloom Filter） | **低**（树深度固定） |
| 空间放大 | 中（旧版本未合并） | **低**（原地更新） |
| 并发 | 简单（append-only 无锁） | 复杂（锁/ latch） |
| 范围查询 | 快（有序扫描） | 快（叶子链表） |
| 适合场景 | 写多读少、时序数据 | 读多写少、事务性工作 |

### 代表产品

- LSM-Tree：RocksDB、LevelDB、Cassandra、HBase、InfluxDB
- B-Tree：MySQL InnoDB、PostgreSQL、Oracle、SQLite

### 面试黄金回答

> "LSM-Tree 写快读慢，B-Tree 读快写慢。选择取决于工作负载。支付系统用 B-Tree（InnoDB）因为读多且需事务保证；时序监控用 LSM-Tree 因为写多。"

## 6. 其他索引结构

### 聚簇索引 vs 非聚簇索引

| 类型 | 说明 | 代表 |
|------|------|------|
| 聚簇索引 | 索引即数据，叶子页存完整行 | MySQL InnoDB 主键索引 |
| 非聚簇索引 | 索引存主键引用，需回表 | MySQL 二级索引 |
| 覆盖索引 | 索引包含查询所需全部字段，无需回表 | 优化技巧 |

### 多维索引

- **R-Tree**：空间索引（地图、几何数据）
- **GiST**：PostgreSQL 的通用搜索树框架

### 全文搜索

- **倒排索引**（Inverted Index）：词 → 文档列表
- Elasticsearch / Lucene 的核心
- 与数据库索引是不同的问题域

---

## 7. 事务 vs 分析（OLTP vs OLAP）

| 维度 | OLTP | OLAP |
|------|------|------|
| 主要读模式 | 键值查找，少量行 | 聚合查询，大量行 |
| 主要写模式 | 随机写入，用户输入 | 批量导入（ETL） |
| 数据量 | GB~TB | TB~PB |
| 代表 | MySQL, PostgreSQL | ClickHouse, Snowflake |
| 存储格式 | 行存 | **列存** |

### 列存的优势

- 聚合查询只读需要的列 → 大幅减少 I/O
- 同一列数据类型相同 → **压缩比极高**（位图编码、游程编码）
- 适合分析场景

### 数据仓库架构

```
业务数据库 → ETL → 数据仓库（列存） → 分析查询
  (OLTP)           (OLAP)
```

**星型模式**：一个事实表（fact table）+ 多个维度表（dimension table）
