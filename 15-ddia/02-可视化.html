02 — 文档模型的坑

反规范化的更新异常

文档模型为了省 JOIN，把冗余数据塞进每条记录。读起来确实爽——一条查完。但改的时候呢？ 点下面按钮，改个用户昵称试试。

更新异常演示：改个昵称有多难？

用户"张三"的昵称被冗余存储在订单、评论、点赞三条文档里。点击修改昵称，观察数据一致性变化。

这就是反规范化的代价：读 1 次 JOIN 省了，写 1 次变成了写 N 次。而且这 N 次写入如果不在一个事务里——中间挂了怎么办？文档模型没有跨文档事务 → 数据不一致。MongoDB 4.0 才支持多文档事务，但性能打折。
关系模型怎么做？
❌ 文档模型：冗余存储
订单文档 { order_id, user_name:"张三", amount } 评论文档 { comment_id, user_name:"张三", content } 点赞文档 { like_id, user_name:"张三", target_id } // 改昵称 → 更新 3 个集合 × N 条文档 // 不在事务里 → 可能改了一半挂了
✅ 关系模型：规范化
users { id, name:"张三" } orders { id, user_id, amount } comments { id, user_id, content } likes { id, user_id, target_id } // 改昵称 → 更新 1 行，搞定 // 查询时 JOIN 拿名字，永远最新
一句话总结：文档模型用"空间换时间"（冗余存储省 JOIN），关系模型用"时间换空间"（JOIN 换一致性）。写入频繁的字段千万别冗余。
03 — "无模式"真相

"Schemaless"是个伪命题

MongoDB 宣传的"无模式"让很多人以为可以随意加字段，不用管数据结构。 骗人的。模式只是从数据库搬到了应用代码里——而且更隐蔽、更难改。

Schema 到底在哪？
-- MySQL: 写的时候就校验，不合规直接报错 CREATE TABLE users ( id BIGINT PRIMARY KEY, name VARCHAR(64) NOT NULL, -- 必填，最长64 email VARCHAR(255) UNIQUE, -- 唯一约束 age INT CHECK (age >= 0), -- 范围约束 created_at TIMESTAMP DEFAULT NOW() ); -- 插入不合规数据？当场打回： INSERT INTO users(id, name, email) VALUES(1, NULL, 'bad'); -- ❌ ERROR: name violates NOT NULL constraint
优点：数据库帮你守规矩，脏数据进不来。缺点：改 schema 要 DDL，大表加列可能锁表（MySQL < 8.0 的坑）。
// MongoDB: 写的时候啥都不管，想存啥存啥 db.users.insertOne({ name: "张三", emial: "zhangsan@qq.com", // 拼错了！email → emial age: "二十岁", // 字符串？也行！ extra_field: "随便加" // 突然冒出个字段？没事！ }); // 不报错，看起来很爽——直到查询的时候： db.users.find({ email: "zhangsan@qq.com" }); // ❌ 查不到！因为存的是 emial // 而且这种 bug 不会在开发时暴露， // 可能上线几周后才发现数据对不上
"无模式"的真相：模式并没有消失，它只是从数据库的 DDL 藏到了应用代码的 struct/class 里。而且更糟的是——数据库不帮你校验，你只能靠 code review 和测试。一旦有老代码写了奇怪格式的数据，那就永远在那了。
维度Schema-on-WriteSchema-on-Read
谁校验数据库DDL 强制应用代码靠自觉
脏数据进不来随便进后患无穷
改字段要 DDL可能锁表随时加老代码可能崩
数据一致性强弱不同文档可能格式不同
团队协作表结构是契约各写各的字段名打架
踩坑时机写入时查询时（晚了）
实战经验：即使选了 MongoDB，也一定要在应用层做 schema 校验（如 JSON Schema / Mongoose Schema）。所谓"灵活"是给快速原型用的，不是给偷懒用的。生产环境的无模式 = 无纪律 = 定时炸弹。
趋势：两者在"合体"

现实是大家都在往对方的地盘靠：

SQL 学 NoSQL
PostgreSQL JSONB → 一个列存 JSON
MySQL 8.0 JSON 列 + 虚拟列索引
→ 关系表里嵌文档，两头沾
真香指数：⭐⭐⭐⭐⭐
NoSQL 学 SQL
MongoDB 4.0 多文档事务
MongoDB 5.0 Window Functions
→ NoSQL 越来越像 SQL
"我们不是 NoSQL，我们是 YesSQL"
面试加分回答："现在主流做法是 PostgreSQL + JSONB——主体用关系模型保一致性，动态字段用 JSONB 灵活存取。既不用 MongoDB 那样放弃事务，也不用纯 SQL 那样 DDL 改表。"
04 — 查询语言

声明式 vs 命令式：说"要什么"比"怎么做"强在哪？

SQL 是声明式的：你只说"我要已付款的最近10单"，数据库自己想怎么做。 代码是命令式的：你得自己写循环、排序、截断。差在哪？看演示。

核心优势：声明式查询把"怎么做"的决策权交给数据库。数据库比你更了解数据分布、索引、统计信息——它能选出最优执行计划。你只管"要什么"就行。
MongoDB 的弯路：MapReduce → Aggregation Pipeline

MongoDB 早期做聚合只能用 MapReduce——让你写 JavaScript 函数来 map 和 reduce。 又慢又难写，后来自己都看不下去了，搞了 Aggregation Pipeline。

❌ MapReduce（命令式）
// 每个 document 调一次 map var map = function() { emit(this.channel, 1); }; // 按 key 聚合 var reduce = function(key, vals) { return vals.reduce(function(a,b){ return a + b; }, 0); }; db.orders.mapReduce(map, reduce, { out: "result" }); // ← JavaScript 执行，不能走索引 // ← 写起来啰嗦，调试痛苦
✅ Aggregation Pipeline（声明式）
db.orders.aggregate([ { $group: { _id: "$channel", count: { $sum: 1 } }}, { $sort: { count: -1 } }, { $limit: 10 } ]); // ← 声明式，优化器可优化 // ← 像不像 SQL 的 GROUP BY + ORDER BY? // ← MongoDB 终于想通了
这说明什么？连 NoSQL 阵营的代表 MongoDB 都在往声明式方向靠。声明式是正道，命令式是迫不得已。面试时如果被问到"NoSQL 和 SQL 的本质区别"，不要只说"没有 JOIN"——查询范式的差异才是核心。
05 — 图模型

什么时候该上图数据库？

别被社交网络的例子忽悠了。大部分业务用关系模型 + 递归 CTE 就够了。 图数据库真正不可替代的场景是：多跳遍历 + 关系本身有属性。

图模型到底值不值？
场景SQL + 递归CTE图数据库推荐
1跳关系（共同好友） 轻松1个 JOIN 轻松1跳遍历 SQL 就够
2跳（朋友的朋友） 2个 JOIN还行 2跳遍历更自然 SQL 可扛
3~N跳（人脉推荐） N个 JOIN爆炸 遍历天然适合 图数据库
最短路径 极难递归SQL 原生支持 图数据库
关系上有属性 关联表勉强 边属性一等公民 看复杂度
面试清醒剂：图数据库不是银弹。大多数互联网公司的"社交关系"用 MySQL + 缓存就够了。上 Neo4j 之前先问自己：你的查询真的需要 3 跳以上遍历吗？如果不需要，引入图数据库是给自己加运维负担。
