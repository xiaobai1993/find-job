Chapter 05

复制

在多台机器上保存同一数据的副本。目的：高可用、低延迟、读扩展。但异步复制的延迟带来了三种一致性问题。

01 — Single Leader

单主复制流程演示

所有写请求必须经过主节点，从节点只接受读请求。同步复制保证零丢失但影响可用性，异步复制高可用但可能丢数据，半同步是折中。

02 — Replication Lag

复制延迟的三种问题

异步复制导致从节点数据落后于主节点。三种表现形式：读己之写、单调读、一致前缀读。点击标签查看每种问题及解决方案。

读己之写 (Read-after-Write)

用户写入后立即读取，如果读到了还没同步的从节点 → 看不到自己的写入。
用户支付 ¥100
→
写入主节点 ✓
→
读从节点2
→
余额未变！
解决方案
1. 读取可能被自己修改的数据时，从主节点读
2. 写入后 T 秒内从主读
3. 客户端记住最近写入的时间戳，从节点至少达到该时间戳才读
支付场景：用户支付后查订单状态，必须走主库 → 否则看不到"已支付"

单调读 (Monotonic Reads)

用户先后读不同从节点，后读的节点延迟更严重 → 看到数据"回退"（时光倒流）。
读从节点1(延迟小)
→
看到余额 ¥0
→
读从节点2(延迟大)
→
余额 ¥100！时光倒流
解决方案
同一用户的读请求始终路由到同一从节点（一致性哈希）

一致前缀读 (Consistent Prefix Reads)

因果关系的写入被分散到不同从节点，顺序错乱。
写入: "支付成功 ¥100"
→
写入: "已发货"
读到: "已发货"
→
还没看到"支付成功"！
解决方案
确保因果关系的写入路由到同一分区（相同分区键）

05 — Payment Domain

支付场景复制策略

支付系统的复制设计

01
支付系统不能容忍复制延迟 → 写后读必须走主库。用户支付后查订单状态，如果走了从库可能看到"未支付"。
02
对账系统需要确保读到最新数据 → 从主库读或等同步复制完成。账务数据不允许读到旧值。
03
跨数据中心：支付只能在主数据中心处理，灾备中心做热备。不允许双活写入 → 避免冲突。
04
MySQL 半同步复制：主等至少一个从确认后返回成功。同步从挂了降级为异步 → 需要监控复制延迟。
面试关键
"支付系统用半同步复制 + 写后读走主库。核心路径不允许读到旧数据。跨数据中心只允许单主写入，灾备中心热备不承接流量。"
