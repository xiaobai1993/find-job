# Ch9 一致性与共识

## 核心思想

一致性模型定义了"在并发和故障下，系统应该呈现什么样的行为"。共识是分布式系统中最根本的问题——让多个节点对某个值达成一致。

---

## 1. 一致性模型谱系

```
最强 ←————————————————————————————→ 最弱
线性一致性    顺序一致性    因果一致性    最终一致性
(强一致)      (强一致)     (弱一致)      (弱一致)
```

### 1.1 线性一致性（Linearizability）

> 也叫强一致性、原子一致性。操作看起来像发生在单一时间点上，且与实时时间一致。

**核心要求**：一旦写操作完成，所有后续读操作必须返回该值或更新的值。

```
时间 →
客户端A:  ---[write x=1]---
客户端B:  --------[read x=?]---
                       ↑ 必须返回 1（如果读到1，之后所有读也必须≥1）
```

**线性一致性的代价**：

| 代价 | 说明 |
|------|------|
| 性能 | 每次读都要和最新副本确认 → 延迟增加 |
| 可用性 | 网络分区时无法保证线性一致 → 必须牺牲可用性（CAP） |
| 不一定需要 | 很多场景不需要线性一致 → 因果一致就够了 |

### 1.2 顺序一致性（Sequential Consistency）

> 所有操作看起来像按某种顺序执行，每个进程的操作保持程序顺序。

与线性一致的区别：**不需要与实时时间一致**。不同进程看到的操作顺序可能不同，只要每个进程自己的操作顺序一致。

```
线性一致：  A:W(x)=1 → B:R(x)=1 → C:R(x)=1  （实时顺序）
顺序一致：  A:W(x)=1 → C:R(x)=1 → B:R(x)=1  （可能不是实时顺序，但每个进程自洽）
```

### 1.3 因果一致性（Causal Consistency）

> 只保证**有因果关系**的操作顺序一致，无因果关系的操作可以乱序。

**因果关系**：
- A 写 x=1，B 读到 x=1 后写 y=2 → B 的写**因果依赖于** A 的写
- A 写 x=1，C 独立写 y=3 → 无因果关系，顺序无关

**比线性一致弱，但比最终一致强**，且在分区时可用。

### 1.4 最终一致性（Eventual Consistency）

> 如果不再写入，所有副本最终会收敛到相同值。

**问题**：
- "最终"是多久？无保证
- 收敛前可能读到旧值
- 最弱但最高可用的模型

### 一致性模型对比

| 模型 | 保证 | 可用性 | 性能 | 复杂度 |
|------|------|--------|------|--------|
| 线性一致 | 实时顺序 | 分区时不可用 | 低 | 高 |
| 顺序一致 | 程序顺序 | 中 | 中 | 中 |
| 因果一致 | 因果顺序 | 分区时可用 | 高 | 中 |
| 最终一致 | 收敛 | 最高 | 最高 | 低 |

## 2. CAP 定理的真正含义

### 经典表述

> 在网络分区（P）发生时，系统必须在一致性（C）和可用性（A）之间二选一。

### 误解澄清

| 误解 | 真相 |
|------|------|
| "三选二" | 实际是：分区时选 C 或 A；**无分区时可以同时有 C 和 A** |
| "C 是强一致" | CAP 的 C 是**线性一致性**，不是 ACID 的一致性 |
| "A 是高可用" | CAP 的 A 是"每个请求都有响应（不保证最新）" |
| "分区很少发生" | **分区是常态**（网络抖动、GC 停顿都是微型分区） |

### 现代理解

```
无分区：C + A 可以同时满足
有分区：必须选择
  → CP 系统：保证线性一致，拒绝请求（如 ZooKeeper, etcd）
  → AP 系统：保证可用，返回旧数据（如 Cassandra, DynamoDB）
```

**支付系统选 CP** → 宁可拒绝也不能返回错误余额。

## 3. 全序与偏序

| 概念 | 说明 | 例子 |
|------|------|------|
| 全序 | 任意两个事件可比较先后 | 线性一致性 |
| 偏序 | 只有部分事件可比较先后 | 因果一致性 |

**关键洞察**：
- 线性一致性提供**全序** → 所有操作有唯一顺序
- 因果一致性只提供**偏序** → 并发操作顺序不确定
- 共识的本质：将**偏序变为全序**

### Lamport 时间戳

> 为事件赋予全序，同时保持因果序。

**规则**：
1. 每个节点维护逻辑时钟 L
2. 发送消息时 L++，附带 L
3. 接收消息时 L = max(L, 消息中的 L) + 1

```
节点A: L=1 → L=2(send) → L=3 → L=4
节点B: L=1 → L=3(recv,L=2) → L=4
```

**性质**：如果 A 因果先于 B，则 L(A) < L(B)
**局限**：L(A) < L(B) 不意味着 A 因果先于 B → 不够判断因果关系

### 版本向量（Version Vector）

- 每个节点维护自己的计数器
- 比较版本向量可以判断因果关系
- **并发**：两个版本向量不可比较 → 需要合并

## 4. 共识算法

> 共识：让多个节点对某个值达成一致。

### 共识问题的定义

1. **终止性（Termination）**：每个正确的节点最终会决定一个值
2. **一致性（Agreement）**：所有节点决定相同的值
3. **有效性（Validity）**：决定的值必须是某个节点提出的

### 4.1 两阶段提交（2PC, Two-Phase Commit）

> 用于分布式事务，不是共识算法（但有相似之处）。

```
协调者              参与者1     参与者2
  |--- PREPARE ---->|           |
  |<--- YES --------|           |
  |--- PREPARE ---------------->|
  |<--- YES -------------------|
  |                              |
  |--- COMMIT ----->|           |
  |--- COMMIT ------------------>|
```

**问题**：
- **阻塞**：协调者崩溃时，参与者必须等待 → 持有锁 → 系统卡住
- 单点故障：协调者是单点
- 性能差：多轮网络往返

### 4.2 Paxos

> 第一个被证明正确的共识算法（Leslie Lamport, 1990）。

**角色**：提议者（Proposer）、接受者（Acceptor）、学习者（Learner）

**两阶段**：
1. **Prepare**：提议者发送提案编号，接受者承诺不再接受更小编号的提案
2. **Accept**：提议者发送提案值，接受者接受（如果没有更大编号的提案）

**问题**：极其难以理解和实现 → 实际使用不多

### 4.3 Raft

> 易于理解的共识算法（Diego Ongaro, 2014）。etcd、Consul、TiKV 使用。

**核心机制**：

| 机制 | 说明 |
|------|------|
| 领导者选举 | 心跳超时 → 候选人 → 请求投票 → 获多数票 → 领导者 |
| 日志复制 | 领导者追加日志 → 复制到多数 → 提交 |
| 安全性 | 选举限制、日志匹配、领导者完整性 |

**选举过程**：

```
Follower ←(心跳超时)→ Candidate ←(获多数票)→ Leader
   ↑                        |
   |----(选举超时/更高任期)--|
```

**关键设计**：
- **随机选举超时**：避免多个节点同时发起选举（分票）
- **任期（Term）**：逻辑时钟，每轮选举任期递增
- **选举限制**：只有日志最完整的候选人才能被选为领导者

**日志复制**：

```
Leader:  [1: x=5][2: y=3][3: z=1]  ← 提交到3
Follower1: [1: x=5][2: y=3][3: z=1]  ← 已复制
Follower2: [1: x=5][2: y=3]          ← 落后1条

当多数节点确认 → Leader 提交 → 通知 Follower
```

### 4.4 ZAB（ZooKeeper Atomic Broadcast）

- ZooKeeper 使用
- 类似 Raft，但侧重于主备切换
- 比 Raft 更早

### 共识算法面试对比

| 维度 | 2PC | Paxos | Raft |
|------|-----|-------|------|
| 类型 | 原子提交 | 共识 | 共识 |
| 领导者 | 协调者 | 无固定 | 固定领导者 |
| 阻塞 | 是（协调者故障） | 否 | 否 |
| 性能 | 低 | 中 | 高 |
| 复杂度 | 低 | 极高 | 中 |
| 适用 | 分布式事务 | 理论研究 | 实际系统 |

## 5. 共识的局限性

| 局限 | 说明 |
|------|------|
| 投票需要多数 | 至少 3 节点才能容忍 1 故障，5 节点容忍 2 |
| 多数需要低延迟网络 | 跨数据中心共识延迟高 |
| 无法处理拜占庭故障 | 需要更复杂的算法（PBFT） |
| 性能瓶颈 | 所有写入经过领导者 → 吞吐受限于领导者 |

### 成员与协调服务

| 系统 | 用途 | 共识算法 |
|------|------|----------|
| ZooKeeper | 协调服务、配置管理 | ZAB |
| etcd | 键值存储、服务发现 | Raft |
| Consul | 服务发现、健康检查 | Raft |

**核心忠告**：不要用 ZooKeeper/etcd 存储大量数据！它们是**协调服务**，不是数据库。数据量应在内存范围内。

## 6. 支付场景应用

### 分布式锁

```go
// etcd 分布式锁
mutex := concurrency.NewMutex(session, "/payment-lock/user-123")
mutex.Lock(ctx)
// 处理支付
mutex.Unlock(ctx)
```

### 领导者选举

- 对账系统：多实例部署，只有领导者执行对账
- 使用 etcd Lease + Election API

### 配置中心

- 支付路由规则、费率配置 → etcd 存储 → Watch 推送更新

| 问题 | 答案要点 |
|------|----------|
| 线性一致性 vs 因果一致性？ | 全序实时 vs 偏序因果，前者更强但更贵 |

| Lamport 时间戳？ | 逻辑时钟，保持因果序，但不能判断因果关系 |
