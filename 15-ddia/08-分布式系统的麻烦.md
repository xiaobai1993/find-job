# Ch8 分布式系统的麻烦

## 核心思想

分布式系统没有银弹。网络不可靠、时钟不可靠、进程可能随时崩溃。**任何设计分布式系统的人，都必须直面这些"不可回避的麻烦"。**

> "在分布式系统中，你无法区分节点崩溃和网络分区。" —— 这就是分布式系统的根本困境。

---

## 1. 故障与部分故障

### 单机 vs 分布式

| 维度 | 单机 | 分布式 |
|------|------|--------|
| 故障模式 | 全有或全无 | **部分故障** |
| 行为 | 可预测 | **不可预测** |
| 原因 | 可定位 | 可能是网络、超时、慢节点 |

**核心洞察**：分布式系统的新问题不是"新的故障类型"，而是**不确定性**——系统可能工作正常，也可能已经出问题了，你不确定。

---

## 2. 不可靠的网络

### 现实：网络可能出什么问题

```
请求发送方 → [网络] → 接收方

可能的情况：
1. 请求丢失
2. 请求排队，延迟极高
3. 接收方崩溃
4. 响应丢失
5. 响应排队，延迟极高
```

**关键问题**：发送方只能知道"没有收到响应"，但**无法知道**是没有发出去、对方没处理、还是响应丢了。

### 超时：唯一可靠的检测手段

> 超时是分布式系统中最基本的故障检测机制。

**超时太短** → 误判（网络抖动被当成故障）→ 不必要的故障转移 → 系统更不稳定
**超时太长** → 真正故障时恢复慢 → 用户体验差

#### 自适应超时（Phi Accrual Detector）

- 不用固定超时值
- 根据历史响应时间分布动态计算
- Cassandra / Akka 的做法
- 计算当前超时概率 φ，超过阈值则判定故障

### 网络分区

> 网络分区（Network Partition）：网络断裂，部分节点之间无法通信。

**脑裂（Split Brain）**：两个节点都认为对方挂了，都自封为主节点。

解决方案：
- **Fencing Token**：主节点持有递增令牌，存储节点只接受最新令牌的写入
- **Quorum**：获得多数票才能成为主 → 最多只有一个主
- **Lease**：租约过期后才能重新选举

## 3. 不可靠的时钟

### 两类时钟

| 类型 | 实现 | 特点 | 适用 |
|------|------|------|------|
| 时钟（Time-of-Day Clock） | NTP 同步 | 可能跳变（闰秒、NTP 校正） | 时间戳、日志 |
| 单调时钟（Monotonic Clock） | 系统启动后的纳秒数 | **只增不减**，不受 NTP 影响 | 测量时间间隔 |

### 时钟的问题

#### 1) 时钟偏移（Clock Skew）

- 不同机器的时钟不可能完全同步
- NTP 同步受网络延迟影响 → 毫秒级偏移是常态
- Google Spanner 的 TrueTime API 声明时钟不确定范围：`[earliest, latest]`

#### 2) 闰秒（Leap Second）

- 2012 年闰秒导致 Linux 内核 bug → Java 进程 CPU 100% → 多个系统故障
- 解决：闰秒时逐步调整（slew）而非跳变

#### 3) 时钟回拨

- NTP 校正可能导致时钟倒退
- 对依赖时间戳的系统是灾难 → MongoDB 用物理时钟做 LWW 可能丢数据

### 依赖时钟的危险操作

| 操作 | 问题 | 安全替代 |
|------|------|----------|
| 用时间戳判断先后 | 时钟偏移 → 可能错判 | 逻辑时钟（Lamport 时间戳） |
| 用时间戳做 LWW | 时钟回拨 → 丢数据 | 版本向量 |
| 用超时做租约 | 时钟跳变 → 租约异常 | 单调时钟 |

## 4. 知识、真相与一致性

### 真相由多数决定

> 在分布式系统中，**不存在"客观真相"**，只有"多数节点认为的真相"。

**例子**：
- 节点 A 认为自己是主节点
- 节点 B 也认为自己是主节点
- **谁是对的？** → 获得多数票的那个

### Quorum 的意义

- 任何决策都需要**多数节点**同意
- 两个多数必然有交集 → 不可能出现两个互相矛盾的多数决策
- 这是 Raft/Paxos 的基础

### 拜占庭故障

| 模型 | 假设 | 适用 |
|------|------|------|
| 崩溃故障 | 节点可能停止，但不会撒谎 | 大多数系统 |
| 拜占庭故障 | 节点可能撒谎（恶意行为） | 区块链、航空航天 |

**重要**：绝大多数分布式系统假设非拜占庭故障。处理拜占庭故障的成本极高（需要 3f+1 节点容忍 f 个故障）。

### 系统模型

| 模型 | 假设 | 分析难度 |
|------|------|----------|
| 同步模型 | 网络延迟、时钟漂移有上界 | 简单但不现实 |
| 半同步模型 | 大部分时候同步，偶尔异步 | **最常用** |
| 异步模型 | 无任何时间假设 | 最安全但最悲观 |

---

## 5. FLP 不可能定理

> 在异步系统模型中，即使只有一个进程可能崩溃，也不存在确定性共识算法能保证在有限时间内达成共识。

**含义**：
- 不存在完美的共识算法（在纯异步模型下）
- 但**实际系统**不是纯异步的 → 超时和随机性可以打破 FLP
- Raft/Paxos 通过**超时+随机退避**来实际地解决共识

---

## 6. 正确使用超时的实践

| 场景 | 建议 |
|------|------|
| 故障检测 | 自适应超时 + 心跳 |
| 选举超时 | 随机化，避免分票（Raft 的做法） |
| RPC 超时 | 根据操作类型设置（读 < 写 < 批处理） |
| 租约超时 | 用单调时钟，不用时钟 |

## 本章面试速查

| 问题 | 答案要点 |
|------|----------|
| 为什么分布式系统没有客观真相？ | 只能通过网络通信获取信息，网络本身不可靠 |
| 时钟 vs 单调时钟？ | 时钟可回拨，单调时钟只增不减 |
| 为什么不能用时间戳做 LWW？ | 时钟偏移导致旧数据覆盖新数据 |
| 什么是脑裂？ | 两节点都认为自己是主，fencing token 解决 |
| FLP 不可能？ | 异步模型下不存在确定性共识，实际用超时打破 |
| 拜占庭 vs 崩溃故障？ | 恶意撒谎 vs 只是崩溃，成本差 3x |
