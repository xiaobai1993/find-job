# Ch12 数据系统的未来

## 核心思想

Kleppmann 在最后一章提出了一系列**观点和展望**，不是确定性的技术结论，而是对数据系统发展趋势的思考。面试中可以作为架构设计的加分项。

---

## 1. 数据库的" unbundling "（拆解）

### 传统数据库：一体化

```
MySQL/PostgreSQL = 存储 + 索引 + 查询 + 事务 + 复制 + 安全
```

### 现代趋势：拆解为专用组件

```
存储: S3 / HDFS
索引: Elasticsearch
流: Kafka
事务: etcd（共识）
分析: ClickHouse / Snowflake
缓存: Redis
```

**驱动因素**：
- 不同工作负载需要不同的优化
- 云原生 → 存储计算分离
- 开源生态 → 自由组合

**挑战**：
- 组件间一致性难以保证
- 运维复杂度增加
- 跨系统事务难以实现

### 面试观点

> "未来不是选一个数据库，而是选一组专用工具，然后用流处理把它们连起来。"

## 2. 围绕事件流设计系统

### 命令 vs 事件

| 概念 | 说明 | 例子 |
|------|------|------|
| 命令（Command） | "请做某事"，可能被拒绝 | "支付 100 元" |
| 事件（Event） | "某事已发生"，不可变 | "已支付 100 元" |

**关键洞察**：
- 命令是**意图**，可能失败
- 事件是**事实**，已经发生
- 事件流 + CQRS + Event Sourcing 是现代数据系统的架构趋势

### CQRS（Command Query Responsibility Segregation）

> 读写模型分离。

```
写入模型（命令端）:
  客户端 → 命令 → 聚合根 → 事件 → 事件存储

读取模型（查询端）:
  事件存储 → 投影（Projector）→ 读模型（物化视图）→ 查询
```

**优势**：
- 写模型关注业务逻辑和不变量
- 读模型可以针对查询优化
- 不同读模型可以有不同的一致性延迟

**劣势**：
- 最终一致性 → 写入后不一定立即可读
- 复杂度高 → 需要维护两套模型
- 事件模式演化 → 需要版本管理

### 支付场景 CQRS

```
写端：支付命令 → 验证 → 扣款 → 产生"支付成功"事件
读端：事件 → 投影 → 订单状态表、账户余额表、对账表

不同读模型可以有不同的更新策略：
- 订单状态：近实时（1秒内）
- 对账数据：准实时（5分钟内）
- 统计报表：T+1
```

## 3. 从"写时正确"到"读时修复"

### 传统思路

> 写入时保证数据正确（约束、触发器、事务）。

**问题**：写入路径变得复杂 → 性能和可用性受限。

### 新思路

> 允许写入不一致数据，读取时检测并修复。

**类似思想**：
- **CRDT**：无需协调即可合并的复制数据类型
- **Reconciliation（对账）**：事后发现并修复不一致
- **Self-healing**：系统自动检测和修复数据

### 支付场景的启示

> 支付系统两者都用：**写时保证**（事务）+ **读时修复**（对账）。
> 核心路径用事务保证正确，对账兜底捕获遗漏的错误。

## 4. 端到端的正确性

### 端到端参数（End-to-End Argument）

> 功能应该在系统的最顶层（端到端）实现，而不是在每一层都实现。

**例子**：TCP 保证传输可靠，但应用层仍需校验数据完整性 → **底层保证不够，端到端才行**。

### 数据库的类比

| 底层保证 | 不够的原因 |
|----------|------------|
| 数据库事务 | 应用可能在事务外有 bug |
| Kafka exactly-once | 应用可能重复消费 |
| 原子提交 | 应用可能误操作 |

**端到端正确性的核心**：

```
应用层幂等 + 业务约束 + 对账兜底
= 真正的正确性
```

### 支付系统的端到端正确性

```
第1层：数据库事务（ACID）
第2层：消息去重（幂等键）
第3层：业务约束（余额不能为负）
第4层：对账（第三方对账 + 内部对账）
第5层：人工审计

→ 层层防护，没有单点依赖
```

## 5. 做正确的事（伦理）

> 数据系统不仅是技术问题，更是伦理问题。

### 关键议题

| 议题 | 说明 |
|------|------|
| 隐私 | 数据收集的最小化原则 |
| 偏见 | 算法可能放大社会偏见 |
| 问责 | 自动化决策需要可解释 |
| 监控 | 数据追踪与个人自由的平衡 |

这部分面试不考，但体现了工程师的社会责任意识。

## 6. 全书核心观点总结

### 六个核心洞察

1. **复制延迟是常态**，不是异常 → 设计时必须考虑
2. **分区是不可避免的** → CAP 不是理论问题而是现实
3. **事务不是银弹** → 隔离级别的选择比"用不用事务"更重要
4. **时钟不可靠** → 不要用物理时钟做正确性保证
5. **流是未来的方向** → 统一批处理和流处理
6. **端到端正确性** → 底层保证不够，应用层必须兜底

### 面试加分观点

> "分布式系统的正确性不是单一技术能保证的，而是**分层防御**：共识算法保证存储层一致，事务保证操作原子，幂等保证消息不重，对账保证业务最终正确。"
