# Ch11 流处理

## 核心思想

流处理是"在事件发生时立即处理"——不像批处理等数据积累再处理。**事件流是数据系统的"活"的部分**，批处理是"快照"。

---

## 1. 事件流

### 事件 vs 请求

| 维度 | 请求/响应 | 事件流 |
|------|-----------|--------|
| 时机 | 客户端主动 | 生产者主动 |
| 耦合 | 紧耦合 | 松耦合 |
| 消费者 | 一个 | 可多个 |
| 保留 | 处理后丢弃 | **可保留** |

### 事件源（Event Sourcing）

> 将所有状态变更记录为不可变事件序列。

- 不存"当前状态"，存"所有事件"
- 当前状态 = 事件回放的结果
- **优势**：完整审计追踪、时间旅行、任意重建
- **劣势**：事件量大、回放成本高

**支付场景天然适合事件源**：每笔交易都是不可变事件，对账就是回放事件。

---

## 2. 消息系统对比

| 系统 | 模型 | 持久化 | 重放 | 顺序 | 适合 |
|------|------|--------|------|------|------|
| RabbitMQ | 队列 | 消费后删除 | 否 | 队列内有序 | 任务队列 |
| Kafka | 日志 | 保留策略 | **是** | 分区内有序 | 事件流 |
| SQS | 队列 | 消费后删除 | 否 | 近似 | AWS 任务队列 |

### Kafka 的核心设计

```
主题（Topic）→ 分区（Partition）→ 有序日志（Append-only Log）

分区0: [offset=0][offset=1][offset=2]...
分区1: [offset=0][offset=1][offset=2]...
```

- **分区**是并行和顺序的单元
- 分区内有序，跨分区无序
- **消费者偏移量（offset）**：记录消费位置 → 可重放
- **日志压缩（Log Compaction）**：保留每个 key 的最新值 → 类似物化视图

## 3. 流处理的核心问题

### 3.1 时间语义

| 概念 | 说明 |
|------|------|
| 事件时间（Event Time） | 事件实际发生的时间 |
| 处理时间（Processing Time） | 事件被处理的时间 |

**问题**：两者可能差距很大（网络延迟、消费积压）

**解决方案**：**水印（Watermark）**
- 标记"早于时间 T 的所有事件都已到达"
- 水印之后的数据 → 迟到数据（late data）
- 处理：丢弃 / 修正 / 侧输出

### 3.2 窗口

| 窗口类型 | 说明 | 例子 |
|----------|------|------|
| 滚动窗口 | 固定大小，不重叠 | 每小时统计 |
| 滑动窗口 | 固定大小，有重叠 | 最近 5 分钟，每 1 分钟 |
| 会话窗口 | 按活动间隔动态划分 | 用户会话（30 分钟无活动结束） |

```
滚动窗口:  |----10:00----|----11:00----|----12:00----|
滑动窗口:  |---5min---|
           |---5min---|
            |---5min---|
会话窗口:  |---session1---|  |---session2---|
```

### 3.3 Exactly-Once 语义（面试高频）

> 流处理最核心的问题：如何保证每条消息恰好处理一次？

#### 三种语义

| 语义 | 含义 | 实现难度 |
|------|------|----------|
| At-most-once | 最多一次，可能丢 | 最简单 |
| At-least-once | 至少一次，可能重复 | 中等 |
| Exactly-once | 恰好一次，不丢不重 | 最难 |

#### Exactly-once 的实现

**1) 幂等生产者（Idempotent Producer）**

- Kafka 0.11+ 支持
- 每条消息有 Producer ID + Sequence Number
- Broker 去重 → 相同 PID+SeqNum 只写入一次

**2) 事务（Transactional）**

- Kafka 事务：原子写入多个分区
- "消费-处理-产出" 原子化

```go
// 伪代码：Kafka 事务
tx := producer.BeginTransaction()
tx.consume(processedOffset)  // 消费位点
tx.produce(topic1, result1)  // 产出结果
tx.produce(topic2, result2)  // 产出结果
tx.commit()                  // 原子提交
```

**3) Flink 的分布式快照（Checkpoint）**

- Chandy-Lamport 算法
- 定期做全局状态快照
- 故障时从最近快照恢复 → 保证 exactly-once

**4) 幂等消费者（业务层）**

- 最可靠的方案：消费端去重
- 用唯一键（如订单号）做幂等判断
- **支付系统必须用这个方案** → 不依赖消息系统的 exactly-once

```
消费消息 → 查是否已处理（幂等键）→ 是则跳过 → 否则处理并记录
```

### 支付场景的 Exactly-Once 设计

```
Kafka 消息 → 消费者 → 查幂等表 → 已处理? → 是 → 跳过(提交offset)
                                    → 否 → 处理业务 + 写幂等表 + 提交offset（同一事务）
```

关键：**幂等表和业务数据在同一个数据库事务中**。

## 4. 流表二象性（Stream-Table Duality）

> 流和表是同一数据的两种视图。

### 流 → 表

- 流上的聚合操作 → 物化为表
- 例：交易流 → 聚合 → 每日统计表

### 表 → 流

- 表的变更日志（CDC）→ 流
- 例：MySQL Binlog → Kafka → 流处理

### 具体实现

```
变更日志（CDC）→ [流处理] → 物化视图（表）
     ↑                           |
     |_______表变更→日志__________|
```

- **Kafka Streams 的 KTable**：从 changelog topic 构建表
- **Flink 的 Dynamic Table**：表和流可以互转
- **Materialize**：实时物化视图数据库

## 5. 流处理 Join

| Join 类型 | 说明 | 挑战 |
|-----------|------|------|
| 流-流 Join | 两个流的事件匹配 | 需要窗口 + 状态 |
| 流-表 Join | 流事件丰富表数据 | 需要表查找（本地缓存） |
| 表-表 Join | 两个物化视图 Join | 维护 Join 结果的更新 |

### 流-流 Join 例子：支付事件 + 风控结果

```
支付流: (order_id=123, amount=100, time=10:01)
风控流: (order_id=123, result=PASS, time=10:02)

→ 在窗口内匹配 order_id → 合并为完整事件
```

## 6. Lambda 架构 vs Kappa 架构

### Lambda 架构

```
数据 → [批处理层] → 批处理视图
    → [速度层] → 实时视图
                    ↓
              [服务层] 合并两个视图 → 查询结果
```

| 优点 | 缺点 |
|------|------|
| 批处理保证正确性 | **两套代码**（批+流） |
| 实时层提供低延迟 | 维护成本高 |
| | 合并逻辑复杂 |

### Kappa 架构

```
数据 → [流处理层] → 实时视图 → 查询结果
        ↑
   可重放（Kafka 保留日志）
```

| 优点 | 缺点 |
|------|------|
| 一套代码 | 流处理正确性依赖 exactly-once |
| 维护简单 | 重放大量数据时延迟高 |
| | 乱序数据处理更复杂 |

### 支付场景选择

- **对账系统**：Lambda → 批处理保证 100% 正确，实时层快速发现问题
- **风控系统**：Kappa → 需要低延迟，流处理直接产出结果
- **趋势**：Flink 统一批流 → 逐渐走向 Kappa

## 本章面试速查

| 问题 | 答案要点 |
|------|----------|
| 事件时间 vs 处理时间？ | 发生时间 vs 处理时间，水印对齐 |
| Exactly-once 怎么实现？ | 幂等生产+事务+幂等消费（业务层最可靠） |
| 流表二象性？ | 流是变更日志，表是聚合结果，可互转 |
| Lambda vs Kappa？ | 两套代码(批+流) vs 一套代码(纯流) |
| Kafka 为什么能重放？ | 持久化日志+偏移量，不像队列消费后删除 |
| 支付 exactly-once 怎么做？ | 幂等表 + 业务事务 + 提交 offset 原子化 |
